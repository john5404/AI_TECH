# A Developer's Guide to Not Getting Replaced by Agents

Simon Maple 的 AI Native Dev，來賓是 Daniel Jones。他在北歐一家顧問公司，字幕聽成 Re-Sync，幫大型企業做 AI native 轉型。片長 61 分 23 秒，英文自動字幕。這份筆記依英文原稿整理，專有名詞保持 English。字幕把 spec-driven 聽成 spectrum，把 AGENTS.md 聽成 agents MD，把 CLAUDE.md 聽成 Claude MD，把 Tessl 聽成 Tesla、Tessell。開頭有一段倫敦活動預告，下文不記。

- 原片：[YouTube](https://www.youtube.com/watch?v=SEAVE9XgBbM)

## 一句話

DORA 2025 的發現是：開發成熟度高的團隊，引進 agentic coding 之後更快；成熟度低的更慢。把系統的一段加快，兩邊會出現瓶頸。Agent 看不見問題，就不能反應，所以測試、小 commit、容器，是讓它感知和讓你敢放手的條件。真實工作不是 one-shot 一個待辦 app。它是一份 model 沒看過的內部程式庫，細節必須對。Context 一多，推理就掉。AGENTS.md 什麼都塞，品質會變差。組織若要鋪開，先找一個已經做得好、對齊、而且產品規格餵得飽的團隊。

## 成熟度不夠時，加速是在火上加油

[2:03](https://www.youtube.com/watch?v=SEAVE9XgBbM&t=123s) 這集問的是 agentic development 裡你不知道自己正在搞砸的坑，以及開發者本人和整個組織要知道的事。Daniel 的公司做三條線：在軟體開發裡用 AI 提高生產力；幫人做會用上 AI 的產品，也許產品裡有 ML，或在建 agents；以及業務裡不是軟體的部分，會計、行銷，怎麼用 agents 或 workflows 變得更有生產力。他跟很多大企業談採用，怎麼在大量團隊裡鋪開。

[3:42](https://www.youtube.com/watch?v=SEAVE9XgBbM&t=222s) 好的工程實務對 agent 開發有益。DORA 2025 的報告：開發成熟度高的團隊引進 agentic coding 後變快，低的變慢。用限制理論看就合理。把系統的一段大幅加快，兩邊會出現瓶頸。不知道那個轉折點在哪：要好到什麼程度才會變好，要糟到什麼程度就是往垃圾桶的火上倒汽油。好可以從很多維度量。測試覆蓋、對 coding standards 什麼叫好有沒有對齊、批次多大、stories 多大、細節夠不夠、到 production 的路徑、lead time。Coding agents 可以一分鐘接一分鐘吐 commit，但東西要三天才進 production。他說對有些企業，三天已經很樂觀。分支尖端會跑很遠，CI 出事時一堆 merge conflicts。這大多是過去十到二十年就被當成好實務的事。現在一切更快，所以那些 pipeline 和工作流要在，才不會只有「把 code 做出來」這一段被加快，其餘仍在拖。

## 看不見，就不能修；commit 便宜，就該扔掉

[6:02](https://www.youtube.com/watch?v=SEAVE9XgBbM&t=362s) 測試重要，但有nuance。若覆蓋不好，agent 怎麼知道自己弄壞了東西。剛接觸 agentic coding 的人常漏掉：agent 得能感知。感知不到問題，就不可能反應。對 coding agents 挫折時要問，它有沒有可能知道得更清楚，有沒有資訊知道自己做錯。它一直弄壞軟體，有沒有從失敗的測試套件得到快回饋。覆蓋低，它可以把一堆東西弄壞，自己完全不知道。那不是 agent 的錯，是你沒給它感知錯誤的能力。Simon 問，是測試跑失敗在通知它，還是它把測試當 context，理解預期行為。Daniel 說兩者都是。若它夠有禮貌、會一直跑測試，失敗的測試該讓它知道做錯了。把測試當文件、當預期的指引，也很重要。他的 nuance 是：unit tests 也許不再是給人的。太低階。若它們幫 agent 找出弄壞的地方，很好，讓它愛寫多少就寫多少。Acceptance tests，由外而內、定義使用者該能對系統做什麼，才是最終的安全欄杆：這是我需要它做的，也是預期行為，不管現在能不能動，這是它該做的功能。這會接到 spec-driven，以及真相在測試還是在 spec。回到過去十年、二十年的好實務，好的 BDD 測試套件本來就該用人讀得懂的層級描述軟體在做什麼。Codebase 裡有這個，agents 會工作得更好。Simon 說開發者更像 intent 機器，描述期望，agent 負責生出實作。我們在乎的測試該驗證我們要的 intent。Unit tests 該是 agent 的事，因為實作是它寫的。不在乎 code、卻在乎那段 code 的 unit tests，會很怪。測試和 intent、以及生成，最好停在同一層。

[9:36](https://www.youtube.com/watch?v=SEAVE9XgBbM&t=576s) 版本控制特別關鍵。早晚 agent 會做你不想要的事，例如把一個 binary commit 進 Git，四五個 commit 之後才發現，想拿掉。不會 interactive rebase 的話，codebase 會變亂，誤導人也誤導 agents。他說學 rebase 時覺得有點繞。Commits 和 branches 很便宜，幾乎沒有overhead。很多小 commit 本來就是他認為的好實務。也許更小、更頻繁更好，因為這樣才能扔掉 agent 做的工作。採用 agentic coding，很多是行為改變，不只是懂工具、學新知識，還要忘掉舊習慣。因為有很多 commit 可以回去，就該樂意扔掉。扔掉再開始，會比 2022 年自己敲鍵盤更快。Agents 不珍貴，它們寫 code，不在乎扔掉。他常叫人想像自己是最糟的軟體經理：把 agent 當一個你很討厭、想打擊士氣的 junior。扔掉它的工作。叫三個同時做同一件事，只用其中一個的成果。這些模式會讓你更有生產力。就算二十年后 AI 霸主翻我們的聊天紀錄，大家都會有麻煩。Simon 開玩笑說要偶爾加一句我尊重你。

[11:55](https://www.youtube.com/watch?v=SEAVE9XgBbM&t=715s) 誰決定 commit，是人在這條路上心理舒不舒服的指標。一開始大家更舒服自己 commit：叫 agent 做一堆，我讀 code、驗證，然後我 commit。對 spec-driven 有信心、有能力之後，心理上更能接受讓 agent commit。每次引人來做一個動作，會慢好幾個數量級。Agent 坐在那裡問要不要 commit，你的注意力在別處，進度就少很多。但要有護欄，不能橫衝，絕對不要 force push。Simon 說自己一開始也手動 commit，快到後來才發現早該 commit。現在讓 agents 覺得有改動就 commit。回去拆 commit、回到某一點很容易，因為它 commit 得很勤。便宜，回頭看也舒服很多。

## YOLO 要關在容器裡，故事要把腦子裡的知識寫出來

[13:56](https://www.youtube.com/watch?v=SEAVE9XgBbM&t=836s) 企業對安全極敏感。容器化、以及人對它的成熟度，造成的摩擦比他預期大。他來自 cloud-native，部署在 Kubernetes、什麼都容器化，以為大家熟悉 Docker 和字幕裡的 Kalima。很多企業開發者不熟，很多企業也沒讓人在開發機上跑容器。沒有的話，人會用 dangerously skip permissions，在自己的機器上原生跑 coding agents。他說一直這樣做的人會下地獄。跑在容器裡才能鬆韁，不必一直說可以、可以跑 ls、可以 cat 那個檔。他對 dev containers 曾經樂觀。那是出自 Microsoft 的開放標準，VS Code 會偵測目錄裡的設定，然後在容器裡重新啟動自己。設定檔正好落在幻覺的甜區：夠新、不夠普及，但又普及到 agents 會幻覺出那份設定，很挫折。方案不錯， maybe 不夠成熟。他看過企業開發者花上小時、甚至數週調 dev container，無法往前。他希望 stdio 的 MCP servers 預設就跑在容器裡。Docker 已經很久了，若一切開箱就安全會很好。他跟以前的同事、Docker 的 developer advocate Oleg Slav 聊過 Docker sandboxes，覺得正好適合。他認為在容器裡開發，負擔沒有大到不行。企業開發者常常被功能壓著，沒有時間試工具、試新做法。若環境不給你空間探索，心態是一年學一件事、公司出錢送課、拿一張證書，那容器、dev containers、從很肥的圖形 IDE 改去終端機，會很不舒服。還要跟 Claude Code 認證，URL 裡有換行，容器裡轉不回 localhost 的 port，還得複製 token。這些小摩擦會把人嚇跑。值得帶人走過去，免得他們在看見這些工具能有多有生產力之前就彈開。真正要放進容器的，是 dangerously skip permissions、YOLO：讓 Claude 或任何 agent 去做它想做的。其他情況你還有機會說可以或不可以。

[18:53](https://www.youtube.com/watch?v=SEAVE9XgBbM&t=1133s) 給 agent 的 story、那一單位的工作，細節的程度極重要。Agents 愈進到流程裡，愈暴露出我們做軟體時視為理所當然、存在腦子裡的知識有多少。Donald Norman 在 *The Psychology of Everyday Things*，後來改名 *The Design of Everyday Things*，談 knowledge in the head 和 knowledge in the world。World 是找得到的、寫下來的。Coding standards 在 Confluence 上，agent 也許碰得到。寫得好的 story、帶 acceptance criteria、可以據此寫測試，也是 world。Head 是上週跟產品經理講過、我知道他們想怎麼實作，但沒寫下來。缺了那種資訊、需要很多人類 context，或你習慣去 Slack 問清楚，對 agents 是很糟的位置。它們做不出你要的結果，要不就編，要不就問一堆問題。所以要有夠的具體。他跟一個組織合作時，請他們把 coding agents 接到 Atlassian 的 MCP server，開始批評 stories。產品經理也許會挑眉。這是把壓力推回產品：這些東西規格寫得好不好。不一定是產品做得差，而是他們習慣比較非正式的關係。軟體開發一加快，幾乎立刻壓到產品。他們會發現事情沒想夠，餵不飽 agents，得大幅加快，而且人習慣不必把乏味的細節全寫出來，因為不懂的人可以來問。

[21:48](https://www.youtube.com/watch?v=SEAVE9XgBbM&t=1308s) 2025 年是技術領導說讓人用想用的。這裡有人用 GitHub Copilot，那裡有人用 Claude Code。一部分是領導跟不上、不舒服，不想押錯一匹馬。也怕指定一個工具，開發者不喜歡，會反彈，因為工作裡有很多自豪和身份。所以 2025 很多是輕觸、有機、沒有組織的試用。聖誕節 Anthropic 的行銷做了一件好事：免費使用。很多無聊的 CTO 和工程 VP 試了 Claude Code，說這真的有用。2026 明顯轉向更有結構：看見可能了，要在部門、團隊、組織裡鋪開。人在試圖把工具標準化。企業層級選哪個工具，仍有很多焦慮。可悲的是，很多由授權和怎麼付錢驅動。當時有猜測，Claude Code 的訂閱授權會不會對企業使用被收回。他看過一些討論。一千個開發者每人每月報銷一次 Anthropic 訂閱，overhead 很大，對比一份企業合約。所以不少人選 GitHub Copilot，只因為它在 GitHub enterprise 裡。對每家組織是不是對的選擇，是另一件事。Simon 問最糟的決定是不是不決定。Daniel 說有很強的理由這樣看。面對轉化性的改變，要嘛兩腳跳進去、沒有計畫。2024 很多是：我們要做點 AI。做什麼？不知道。就做點 AI，這裡有預算。大型金融機構發生過，然後沒有投資回報。另一個極端是等到這變成定論、不要浪費錢跟上。變化的速度還在加快。拖著他認為不可行。要有一些預算、一些時間、系統裡一些餘裕去探索和試，才是最合理的。他不想恐嚇，但有相當機會你會被擁抱這些東西的新創超過去。他合作過的一些 SaaS，二十年沒有競爭者。過去六個月冒出兩家，把功能集整個複製出來。全新的新創，他推測是用 agentic coding 很快複製。不跟上，有機會落後。就算以後變成定論，你想從靜止起步嗎。Context windows 就是例子。若 models 繼續以現在的方式工作、架構沒有根本改變，這會是往後所有 agentic 軟體開發的底層限制。就算最後是蓋在上面的 software factories，也得懂底下的基本。

## 三萬 tokens 之後推理會掉，AGENTS.md 什麼都塞會更差

[26:33](https://www.youtube.com/watch?v=SEAVE9XgBbM&t=1593s) 學術研究上，2024 年一篇字幕寫成 No Leema 的論文說，context 超過 30,000 tokens，推理能力掉大約 15%。另一篇他一時想不起名字，2025 年對 GPT-4.1 那個時代的 models 重做實驗，30,000 到 60,000 tokens 之間推理又掉。這不多。Claude Code 有時一天三個版本，事情一直在變。他一定開過 Claude Code，沒裝 MCP server、沒有 CLAUDE.md，系統 prompt 已經用了大約 40,000 tokens。不用加多少，就會把 model 推進會混亂的區間。

[27:51](https://www.youtube.com/watch?v=SEAVE9XgBbM&t=1671s) 他開始做 agentic coding 訓練時，聖誕節在一個遊戲網站上。玩家往往恨生成式 AI，覺得它會毀了一切。他想解釋為什麼不全是壞事。有人很刻薄地回：教人用 coding agents 幹嘛，它們不是就能用嗎。他覺得這其實是好問題。因為這些東西就是能用，要到出問題，你才需要懂底下發生什麼。Context window 和 context 管理就是例子。一切正常時不必擔心。對話變長，事情開始散，你更挫折，但不明顯的是 context 超過了有效上限，或你在一個聊天裡談了太多事、把它分心了。對這件事很聰明、但剛接觸的工程師，這不明顯、也不會立刻懂。Simon 說開發者知道自己在 context 的 Goldilocks 區：one-shot 得了，給夠了，又沒多到讓 agent 混亂。Daniel 當時認為人該主動監控，也該有工作習慣。到一個乾淨的斷點就清 context。要問離題的事，換一個聊天。他自己的思路留不久，通常同時想三件事。Linux 那類命令列他用 Warp，一個 agentic terminal。在 Claude Code 裡做功能，就盡量留在題上。要研究，去瀏覽器，用 ChatGPT 或 Gemini。拆開對話的好處是不讓太多概念分心，也不把 context 拉長。經常清、不要離題，是有價值的。

[30:38](https://www.youtube.com/watch?v=SEAVE9XgBbM&t=1838s) 另一件稍有不同：不要把所有 MCP servers 都加進去，也不要把每一種寫軟體的可能都寫進 agent 的指引或 AGENTS.md。蘇黎世大約兩週前有一篇論文，往 AGENTS.md 加東西，結果品質比完全沒有指示大約低 20%。幾個月來流行過的東西很有意思。他記得九月左右，人們說把所有東西放進 AGENTS.md，它每犯一次錯就再塞一條。那是在多數時候無關的事情上說話，希望這一次剛好相關。然後是為每一種可能加上所有 MCP servers。很多人不知道 tool calls 怎麼工作：每一則 prompt 都得把完整的工具菜單交給 model，以防萬一它想用其中一個。Skills 和 progressive disclosure 好得多。不是把 skill 的全部細節送進去，而是一小段摘要，model 想要再要更多。Simon 分兩層：蓋子底下的行為，以及 activation。加進 AGENTS.md 的，agent 會整份讀，不表示它會照做。MCP 有描述，它選擇何時啟動，skill 也類似，比較是 on demand。幾百個 MCP servers、幾百個 skills，它會混亂，大概也不會選你要的。Daniel 的建議是審慎地加。你可以依賴很多，但 MCP servers 不要一次全部註冊。若必須同時註冊，就選擇性地濾掉工具。Agent 原生不支援的話，可以用 MCP gateway。Skills 因為 progressive disclosure，問題稍小，但仍可能多個 skills 的描述很像，model 不確定要向哪一個再要資訊。他跟 Tessl 的 Amy Heineke 談過，讓 model 選中你們在做的東西，是棘手的。Activation 今天是棘手問題。他覺得隨著時間、agents 更習慣用 skills，會減輕。

[34:43](https://www.youtube.com/watch?v=SEAVE9XgBbM&t=2083s) 一個開發者的環境怎麼複製給團隊。大團隊裡有時被允許的迴避衝突，會製造問題。Agentic coding 之前，Rachel 有她的寫法、Steve 有他的，也許可以接受。Agent 走遍 codebase，被兩種 code style 搞混，就成了問題。他一般會說愈全域、愈一致，結果愈好。實作愈交給 agents，code 是照你喜歡的方式寫還是照我喜歡的，只要 agent 能更快交出有用的結果和功能，還重要嗎。所以要標準化，並在 agents 需要時拿得到。可以放在 Confluence 或 wiki，再給 agent 一個 MCP 去讀。問題是 drift。改了之後，你最好把它放在 code repository 裡，指引釘在某個版本上，演進時很清楚。Wiki 常常是文件去死的地方。想要過期的資訊，放那裡很合適。所以主要該在 repository。若有人把 context 和指引只留在自己機器上，他能想像會出問題：資訊衝突，一個人的機器上 agent 做一種，另一個人做另一種。計算裡我們一直知道這種模式會導致壞結果。想要在團隊裡、或至少在一份 codebase 裡，做得一致。Simon 補 Tessl 是 skills 和 context 的 package manager：版本、repository 裡的 manifest，按釘住的版本拉進對的 context。他說沒聽過 agent 爭論該用空白還是 tab。仍然重要的是 stack、方法，例如怎麼做測試驅動。那比 code 的外觀重要。

## 幻覺的甜區，以及 agent 只是一個迴圈

[38:25](https://www.youtube.com/watch?v=SEAVE9XgBbM&t=2305s) 很多人不知道什麼情況容易導致幻覺。他們的訓練讓人用一個很舊的 model，他說是 GPT 3.1，故意誤導它、讓它幻覺。問《星際大戰》第十集，model 會說那不是真的電影。大的、眾所周知的概念，它偵測謊言還可以。問倫敦的 thrash metal 樂團 Simon and the Maples，它大概會說沒有這個團。同一個 model，若說那是 thrash metal 兼 hardcore 的 Simon and the Maples，1997 到 1999 年在 Camden 活動，它就更可能開始吐一段生平。這個練習裡，大約一半的時候，從一個首都改成一個特定地區、再加一段日期，先前會說沒有這回事的 model，接著吐出樂團生平、解散、誰跟誰鬧翻。靠著大概念、又非常具體，就是幻覺的甜區。若還挨著 model 很可能被訓練過的東西，也是。他有過 Tessl 的 tile registry 就是要解的那種經驗。受訓的一個開發者說，自己在用某個程式庫的最新版，model 在幻覺。它知道是新版本，沒有給舊的 API endpoints，但在編一些不存在的新 endpoints。One-shot 的例子會誤導人：做一個待辦 app，或做一個 Flappy Bird。哇，真厲害。真實工作不是那樣。是一份你從未見過、從未被訓練過的內部程式庫，而我需要這些具體細節是對的。細節一收窄，似乎就更可能幻覺。

[41:43](https://www.youtube.com/watch?v=SEAVE9XgBbM&t=2503s) 幻覺來自 LLM。很多人剛接觸時分不清 agent 和 model 的責任，他自己在談話裡也常把兩者混在一起，因為你介面的是 agent。Agent 本身不太聰明，裡面沒有多少邏輯。它只是一個迴圈在跑，做決定的是 model，包括用哪個工具。訓練裡做完練習，會在白板上問剛剛做了什麼，把元件、它們住在哪、tool 定義怎麼到 model，都畫出來。過去幾週很多資深工程師直接找他，覺得自己落後，請他幫忙跟上。他們通常很快跟上，跳進 Claude Code 或某個終端機 agent，用得有生產力，但仍不知道引擎蓋底下是什麼。於是人擔心哪個 agent 最好。功能上的差別，是各家 system prompt 多大、留給你的有效 context window 還剩多少。更像個性，像不同品牌的可樂，都是糖和氣泡，只是味道略不同。最新的 GPT 和 Opus 4.6，能做的事大概相當。從 Opus 換到 Haiku，會注意到差別。前沿的 foundation models 大致都有能力、大致相當。人看到品牌和工具，會覺得 Codex 會比 Claude Code 好很多。他認為更重要的是人體工學：有沒有讓你用自己想要的方式工作、不必坐在那裡照看 agents 的功能。支不支援 skills，UX 是不是你要的。從那些功能和體驗得到的生產力，比正確性重要。正確性你控制不了多少，model 訓練得好或不好。功能、體驗，加上 context 管理，比你用哪個 model 更決定你能不能得到有用的結果。前沿實驗室都在很努力跟上彼此。Simon 說，你怎麼問、怎麼給需求，models 接法不同，activation 也不同。也許這就是為什麼這麼多人在吵誰從哪個 model、哪個 agent 得到最多。

[46:10](https://www.youtube.com/watch?v=SEAVE9XgBbM&t=2770s) Agentic coding 在這裡有問題，是因為非確定性。它是迷信的溫床。人機互動和使用性工程的紀錄裡，人得到不一致的結果，他一時找詞，說是 intermittent incoherence，就會生出迷信：我得先點這個，那個才有用。所以人會對哪些 prompt 有用、哪些沒有，生出一堆迷信。這就是為什麼 Amy 跟他講的、對東西跑 evals，這麼重要，要在這裡放進一點科學。以他自己、以及他合作過的數百個開發者，prompt engineering 似乎沒那麼重要。更要緊的是 context 管理，以及你怎麼說需求。問題怎麼措辭、要不要給它一個人設，他沒看到太大差別，即使那對人立刻很有吸引力。更要緊的是把 context 框好、對的資訊在、agent 能感知自己做錯、以及你的需求連不連貫。

[47:38](https://www.youtube.com/watch?v=SEAVE9XgBbM&t=2858s) Simon 問怎麼把資料帶進來。Daniel 說這是個預設好的問題：你們有一個 skills 的 package manager，同時評 skills 寫得好不好、以及有沒有效。他認為非常有價值。昨天 Claude Code 在替他做 Go。他裝了 Go Language Server plugin，讓它跑，自己在做別的事，根本不確定它有沒有在用、有沒有讓事情更好。更科學的資料會非常有價值。再遠一點，software factories，人參與少很多。他對那個想法興奮：把需求送進一個工廠，多個 agents 合作，對一組需求輸出完成的軟體。若全部在版本控制裡、有完整的可觀測性，就可以做有方法的實驗。人的團隊做不到，你不能叫人假裝剛剛沒實作那個 story、再換一種做法。工廠也許可以，慢慢迭代、調 prompts、調 skills、用哪些、怎麼寫，自動把自己推到那個工廠的最大生產力。在那之前，終端使用者幾乎看不見自己在做什麼、何時啟動 skills、為什麼、效果如何。Agentic coding 工具的魔法感，有時是在跟使用者作對。能用的時候很好，但我們也需要看見儀表，才知道發生了什麼。

[50:00](https://www.youtube.com/watch?v=SEAVE9XgBbM&t=3000s) Simon 說 activation 很多時候是 skill 怎麼寫。Anthropic 有一整份怎麼寫 skills 的 best practices，放在一篇文章裡。Tessl 的 review skill 用 LLM as a judge，看那些實務有沒有被遵守。從 activation 看，事後要知道 skill 好不好，現實上只能看 logs：這個 skill 該被啟動幾次，實際啟動幾次。Tessl 在看這件事。另一件是他們說的 task evals：有 skill 跑一次，沒有再跑一次，看用了之後提供什麼好處。對寫 skills 或 context 的人，相對於消費者，資料會顯示 skill 可以改哪裡。80% 或 85% 的提升，對他是一種模糊的感覺良好。價值是作者回去看見哪些情境在失敗，哪些情境 context 沒提供多少價值，因為之前就做對了。回到用 context 把 agent 淹沒：若 agent 開箱就做得好，還需要那段 context 叫它用同樣方式做同樣的事嗎。資料讓你迭代、把 skill 優化。

## 一萬兩千個開發者，以及三條給人、三條給組織

[51:58](https://www.youtube.com/watch?v=SEAVE9XgBbM&t=3118s) 他覺得企業裡會冒出新東西。過去十年，platform as a product、platform engineering、給工程師一個部署的底層，非常重要，人也在看 developer experience。他剛說的那種實驗，一般企業開發者沒時間做。他們不會把一個 story 做兩次，或在一個 work tree 裡帶 skill、另一個不帶，再自己評。功能的壓力太大。他能想像、而且在一些組織裡看見，一個不完全是 platform team 的團隊，像是 DevEx 加一層 AI 的抽象，在弄該用哪些工具。更早他提到企業很難管理哪些 skills 在用，以及你們在看的 package management。他絕對聽過 CTO 很直接地問：這些 skills 到底怎麼管。就是腳本在人的機器之間飄。我們要能稽核、要有版本、要看見什麼在哪裡跑，因為我們受監管。工具用得愈多，就會有團隊試著給其他開發者一個合理的基礎抽象，並弄清楚該用哪個 skill。Simon 問這是不是新角色。Daniel 說感覺是 platform team 的延伸，但 platform team 也許還沒有那些技能。他希望是 platform team 來做。Platform teams 多半從基礎設施團隊長出來。基礎設施在企業裡常常很票據導向，ServiceNow，票進來，做一件事，出去。不是在做每天變好、面向未來的東西。然後注入產品管理和軟體工程：不，我們要做耐久的解法，不要做苦工，票進來票出去。要做一點自動化，讓那張票再也不必做。已經見過從基礎設施到 platform、並引入新技能。他希望 platform team 的身份再演進成：怎麼用在本地跑的 agents 和他們在用的 skills，支持開發者面對近未來。更長遠，platform team 也許變成 software factory 的團隊。

[54:55](https://www.youtube.com/watch?v=SEAVE9XgBbM&t=3295s) 大型組織的鋪開，他認為會從那個團隊出來，因為他們是賦能者。他們正在談的一個客戶有 12,300 個開發者。要鋪一套一致、合理、可稽核、在監管上安全的 agentic coding 實務，需要協調，而且要從某個中央來。若大家自己訂規則、自己拉 skills 和 plugins，會變成稽核上的混亂。他想的一個特定客戶裡，對 production 路徑有興趣的人、以及平台，通常有興趣把回饋迴圈和 value streams 收緊。他們這集沒談 value stream mapping，但採用 agentic coding 時那非常重要：軟體交付作為一個系統怎麼運作，把其中一段加快會發生什麼。對 DevOps 和平台有興趣的人，本來就在乎生產力，把想法盡快送進 production，讓產品的人學習那是不是該做的東西。他們接著想怎麼加快交付的其他部分，是自然的延續。

[56:42](https://www.youtube.com/watch?v=SEAVE9XgBbM&t=3402s) 給想用 agentic coding 成功的開發者三點。一，投入，開始用一個東西。挑一個工具。它們大同小異。不要拖到你覺得這會變成定論，因為一切在加快、還在往前。二，context 管理，要懂。引擎蓋底下不明顯。經常清聊天，留在題上，不要給 model 混亂的藉口。不要把廚房水槽全倒進 AGENTS.md，那只會更糟。三，感知。若 agent 在 CI 裡弄壞東西讓你挫折，它得看得見 CI 在發生什麼。加一個 MCP server，讓它能查最新的 build。否則它弄壞東西時，你不能怪它。

[57:42](https://www.youtube.com/watch?v=SEAVE9XgBbM&t=3462s) 給想在全公司鋪開的組織三點。一，用一個成熟的團隊，他們熱衷、願意接受改變。二，他們要對齊，有寫下來的、什麼叫好。三，後面要有好的產品管理，事情具體、想清楚，而且有一份夠用的待辦可以動手。從一個已經熱衷、已經表現好的團隊開始，他們更可能變快，然後你有可以在組織裡重複的較好結果。人看同儕什麼奏效，會被那些結果說服。若大家對什麼是好 code 想法不同，agent 不可能一致地產出讓所有人滿意的結果。那要寫下來，每個人要在什麼是好工程上同一頁。產品管理是人常忘的。事情要規格清楚，agents 才拿得起來。除了規格清楚，還要有夠用的待辦，以及對該做什麼的理解。開發者一變快，stories 的待辦會很快乾掉。他在不少組織裡看過這件事。

[59:01](https://www.youtube.com/watch?v=SEAVE9XgBbM&t=3541s) 往前看，組織變化的潛力可以很大，而且是一步步的。工程師開始用 spec-driven 侵到產品的地盤。產品的人開始用「原型即需求」侵到工程。大的潛在變化是 software factories。已經聽得到 hive mind 新創：寫下來太慢，因為多個 agents 合作的工廠交付軟體快到，寫下來會把整個系統拖慢。他們在跟客戶談那個世界：一個 value stream 一個 product engineer，不再是一個 two-pizza team。很多好的 Agile 軟體開發，在那裡可能出局。若能走到 dark software factories，沒有人在讀 code、沒有人在寫 code，卻可靠地產出對的東西，產業的未來會很不一樣。他真正希望的是更多量身、能用的軟體，而且很充裕。針對個別的人和團隊，有大量獨特的解法。不必再等 SaaS 廠商十八個月才做一個功能。可以有人幾乎立刻、以小規模幫你做出來。他認為那是樂觀的理由。

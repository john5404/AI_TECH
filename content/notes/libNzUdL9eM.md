# Dave Farley - Vibe Coding - Is this really the best we can do? - AI Native DevCon June 2026

Dave Farley 在 AI Native DevCon June 2026，當天最後一場，後面就是派對。片長 32 分 5 秒，英文手寫字幕。這份筆記依英文原稿整理，專有名詞保持英文。

- 原片：[YouTube](https://www.youtube.com/watch?v=libNzUdL9eM)

## 一句話

他在意的是還站得住的事。用自然語言 vibe coding 有位置，但單獨做不夠精確、不可重複。若測試只看現有 code，它只會證明 code 仍在做它已經在做的事，包括錯的事。生成變快之後，瓶頸仍是講清楚要什麼、以及每次變更之後還能不能驗證。他要的程式是 executable specification：用 BDD 風格把行為寫成規格，AI 像 compiler 一樣填實作，人不必再盯生成出來的 code。

## 測試是捲尺

[0:44](https://www.youtube.com/watch?v=libNzUdL9eM&t=44s) 他說自己夾在聽眾和啤酒之間，會盡量不拖。AI 寫程式是很大的改變，做軟體的人某種程度上是其他人的探路者。他故意挑幾句：用自然語言 vibe coding 有一席之地，也是壞主意；裁掉所有 junior、AI 會寫完全部 code、不再需要 programmer，有些對、有些真、有些很糟；AI 生成的測試也是壞主意。這些話都有細微差別，因為每一句裡也有真的部分。

[3:14](https://www.youtube.com/watch?v=libNzUdL9eM&t=194s) 他自認是老派、帶著證件的 TDD 開發者，所以從測試開始。測試不是為了證明成功，也不真的是為了抓錯，更不是為了挑戰程式員的天才。測試是測量，像木工口袋裡的捲尺。用它確認正在做對的事，以及做完之後仍然對。那就要先定義目標。解法永遠可能是錯的，不能從解法反推目標。

[4:25](https://www.youtube.com/watch?v=libNzUdL9eM&t=265s) 有人賣「免費的 AI 測試」，進來看你現有的系統再測它。那也許有點價值，但不是開發過程裡需要的那種測試。他舉 `calculate tax`：若函式回傳輸入的 50 倍，那是很糟的稅。Agent 只能看著這段 code 寫出一個測試，把寫進去的錯誤再強化一次。唯一的輸入是能跑的 code 時，測試只驗證這段 code 做它已經在做的事。重構、做不改變行為的修改時有用；要開發新系統、確認它做對的事，就沒用，因為起點就是錯的。所以若 code 是唯一輸入，AI 生成的測試只能確認 code 沒變。他說這大多是笨主意，是懶得寫出目標的人的退路。寫出目標，才是軟體開發者的工作。

## 程式語言在做的三件事，自然語言做不到

[6:38](https://www.youtube.com/watch?v=libNzUdL9eM&t=398s) 程式不是為了定義一串指令，那是它的樣子，不是目標。也不是為了把演算法編碼，或實現自己覺得很漂亮的設計。別人付錢不是為了那個。他說程式語言作為工具有三個目標：幫我們組織對問題的思考、探問題的表面，語言難不是為了故意晦澀；在程式員之間溝通，讓團隊能談問題和解法的深度；最後才是告訴電腦做什麼。組合語言已經能把最後這件事做得很好，多數人並不寫組合語言。

[8:52](https://www.youtube.com/watch?v=libNzUdL9eM&t=532s) 裡面還有三個技術：簡單一致的文法，具體、精確到電腦能執行，意圖沒有歧義；以及執行可重複、確定。同樣輸入跑兩次，結果相同，才能推理、才能測。當天有人引 Andrej Karpathy，說未來的程式語言是英文。他不喜歡。自然語言太模糊，容易誤解。他說若你也有灰鬍子，大概遇過上面丟下一句很模糊的指示，程式員做出來，對方很失望。他舉 “time flies like an arrow” 這種句子可以有另一種讀法。

[11:19](https://www.youtube.com/watch?v=libNzUdL9eM&t=679s) 所以只靠 vibe coding、只跟電腦聊天，不夠。需要更能講清楚要達成什麼的工具。這不表示必須看完所有 code，或只能用程式語言。他自己已經很久沒手寫 code，agent 寫全部。他用的是比日常自然語言更精確、更規定性的說法來下 prompt。自然語言用來跟人溝通太有歧義，用來告訴電腦做什麼也不夠準。除非要求非常明顯，否則每次結果會有一點不一樣。早期的 AI coding assistant 他遇過：同一句再問一次，得到很不一樣的東西。

[13:12](https://www.youtube.com/watch?v=libNzUdL9eM&t=792s) 對回那三項：自然語言文法複雜且不一致，意圖模糊，不可重複、不確定、也不能靠版本控制。就算把 prompt 放進版本控制，單靠那樣也回不到同一個結果。

## 加速的是容易的那段，瓶頸換了地方

[13:48](https://www.youtube.com/watch?v=libNzUdL9eM&t=828s) 要取代傳統程式設計，有三個問題。怎麼精確說出要什麼。怎麼確認拿到的就是那個，這是驗證。以及人和機器的工作方式不同。人受自己 context window 的限制，一次只能裝下腦中放得下的東西。心裡有一幅要做的圖，然後一小步、評估、再下一步。他說高品質的軟體開發永遠是增量的學習和發現，所有工程都是這樣。然後還要驗證它以可重複、可靠的方式做了我們要的事。

[15:51](https://www.youtube.com/watch?v=libNzUdL9eM&t=951s) 我們加速的是寫 code，那是軟體開發裡容易的部分。瓶頸被移走了。他引 *The Goal* 和 Theory of Constraints。若本來就擅長交付，瓶頸幾乎總是驗證、發布，以及搞清楚真正要什麼，而不是把解法編碼。AI 的做法是先建起一整幅 context，然後一下改很大。直到不久以前，幾乎每次都重寫整個系統。若沒定義目標、也還沒法評估，沒有東西能在它寫的時候把它停住。他說它可能去寫 Space Invaders，而不是你的庫存控制系統，字幕把 stock 寫成 stuck。他自己用 agent 寫過 Space Invaders，也做過簡單的東西。談 AI 寫程式的人常常站在小而簡單的系統上。那不是他職業上在做的。用手看一眼，離「確認拿到我們要的」還差很遠。

[18:02](https://www.youtube.com/watch?v=libNzUdL9eM&t=1082s) 若每一步都很大，又驗證不了，就無法學習、無法可靠地改解法；若每次都從零再生，也幫不上。後兩個問題讓人失去增量工作的能力，而那是做複雜系統的根本。驗證和保證的速度必須趕得上產生軟體的速度。他不久前遇到一個人，用多個 agent 寫遊戲，估計一天 12,000 行。沒有人能一天審 12,000 行，也沒有人能用手測那些行為。不把驗證加快，就會吃到 Theory of Constraints。確認永遠拿到要的東西，是先以可重現的方式講清楚，再在每次變更之後重複驗證。做過 continuous delivery 的人會覺得耳熟。他說這就是 table stakes。

## 程式從解法，改成對問題的精確描述

[20:41](https://www.youtube.com/watch?v=libNzUdL9eM&t=1241s) 過去，程式是編成演算法的精確解法。問題是什麼反而丟了，隱含在解法裡，留在腦子裡。他舉一個找路演算法，要的結果是找到回家的路。未來他認為程式會是對「我們要什麼」的精確描述，編成 specification，由 AI 翻譯成可執行指令，並驗證拿到了。想要的東西明確成為程式的一部分。重心從解法轉到對問題更準的描述。他說這是一種 spec-driven development，字幕寫成 spectrum。規格的形式是 executable specification，也就是測試：既說明要什麼，也驗證拿到了。

[22:28](https://www.youtube.com/watch?v=libNzUdL9eM&t=1348s) 要做到這樣，是設計一種領域語言，一直以相當的精度寫出要達成什麼。而且是系統的全部行為，不是草率地只測一般使用者行為。效能要多快、要多安全，都是情境。不能叫 AI 自己推。把銀行等級的安全用在單人遊戲上是蠢的，遊戲會過度設計，銀行可能還不夠。架構和設計的每個面向都要講具體。

[23:45](https://www.youtube.com/watch?v=libNzUdL9eM&t=1425s) 過去我們希望解法解了問題。語言能查語法，尤其是有型別的語言，但查不了功能是否正確。規矩的 TDD 開發者用測試補上這個洞。未來 executable specification 同時是驗證和規格。他說這可以用人的語言做，不必很難。他教 AI 做他喜歡的 BDD 風格測試，自己用相對簡單的英文寫要什麼，AI 補上缺口，生成符合規格的解法，再跑那些測試。要確認 AI 沒有作弊，就給它沒看過的測試值。程式員發明問題專用的 DSL，把想要的行為全部定義成給 AI 的 BDD 規格；AI 做出讓規格可執行的測試基礎設施，再生成滿足它們的 code。

[26:11](https://www.youtube.com/watch?v=libNzUdL9eM&t=1571s) 要找回增量，過去和未來幾乎同一句話：一小步一小步，加上新的測試和 code，把每次變更當實驗，重視經驗學習。差別是 code 由 AI 生成，每一變更都要收集回饋來驗證。當天至少有兩位講者暗示過：若本來就在做 continuous delivery，會比較容易，因為人和 agent 隨時都知道自己在哪。規格要進版本控制，因為它們實際上就是程式。測試要在 deployment pipeline 裡跑，否則 AI 會作弊。可以把一部分測試留著不給 AI 看。字幕把 test suite 寫成 test cells。他說這大部分就是 acceptance testing 配 BDD 已經在做的事，不是新東西。

[28:11](https://www.youtube.com/watch?v=libNzUdL9eM&t=1691s) 例子來自一門課的練習，不是真實系統，不過他說這套他在真實系統上做過很多次。從模糊的願望，到比較正式的 user story，再到能證明那個功能存在的 examples。那些 examples 就是 executable specification。畫面上那一組 prompt 出了一個會做 flight planning 的系統。字幕沒有把畫面上的例子念完。

## AI 像 compiler，核心是把問題拆開

[29:05](https://www.youtube.com/watch?v=libNzUdL9eM&t=1745s) 結論：只有自然語言不夠。BDD 的領域語言是比較好的 prompt 方式，同時給精確規格和內建驗證。從解法自動產生測試有一點用，但是利基、是角落案例，像笑話，解不了真正的問題。真正的學科核心是分析問題、拆問題的技能：角落案例，以及架構那一層。他說我們等於在叫起一種第五代程式語言。AI 助手比較像 compiler。只要能驗證行為就是要的那個，就不必再在意它生成的 code，就像從組合語言走到高階語言。他做過一陣子組合語言，曾經會去看 compiler 產生的組合語言，已經很多年不看了，多數人從來沒看過。

[31:09](https://www.youtube.com/watch?v=libNzUdL9eM&t=1869s) 想看實際示範，他推薦一個開源專案，字幕聽成 NYSE，用的就是這套想法。結尾他跳過一些投影片，字幕沒有那些內容。

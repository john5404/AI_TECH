# Justin Cormack - When Tests Lie: Using Observability to Keep AI Honest - AI Native DevCon June 2026

Justin Cormack 的舞台演講，片長 32 分 3 秒，英文手寫字幕。主持人說這場要談的回饋迴路，是怎麼知道 AI 有沒有真的幫上生產程式。線上觀眾他也打了招呼。這份筆記依英文原稿整理，專有名詞保持 English。字幕把 MinIO 聽成 Mineo。

- 原片：[YouTube](https://www.youtube.com/watch?v=xHxfeWtkXrM)

## 一句話

小工具用 AI 半天就能寫完，物件儲存通常要兩年到十年。Justin 用 AI 反過來做一套 S3 相容系統，現在大約 35 萬行 Rust，而他只半懂 Rust、也不打算把 code 讀完。測試在小專案裡夠用；系統一大，100% coverage 會寫出他不在乎的測試，文件也多半是錯的。他要的是對著真的 S3 鎖住行為、立刻修掉 flaky tests，再用 tracing、型別和安全審查去看測試看不到的地方。人留在迴路裡，是因為品質是他的責任。

## 用對話把 S3 逆向回來

[0:19](https://www.youtube.com/watch?v=xHxfeWtkXrM&t=19s) 他住在英格蘭東部、很偏的地方。投影片上的在地基礎設施是一條羅馬道路：不維護會變成那樣。他愛基礎設施軟體。去年年中，MinIO 停止維護他們的 S3 相容物件儲存，很多人抱怨喜歡這個產品。他對物件儲存很執著，幾年前在 KubeCon 講過，那是 KubeCon 上觀看數很高的物件儲存演講之一。今年稍早他在找一個實驗專案：小工具用 AI 寫很快、半天、很興奮，但真的能做巨大的東西嗎。他看過的實作至少兩年，有的十年。他想，有多難，也許一週。他也知道這是大專案。

[2:04](https://www.youtube.com/watch?v=xHxfeWtkXrM&t=124s) 現在是 35 萬行 Rust。他說自己是新手，Rust 只學過一半，不打算讀那些 code，讀起來也很煩。它會又大又複雜，他不必全懂，但要高品質，而且知道有很多地方會錯。他在做分散式系統，打算整個反過來：跟 S3 說話，看它怎麼運作，讓 AI 跟著做。他要大致懂 code、一直留在迴路裡、真的知道哪裡錯了。他有架構意見，不想它變大之後塌成一片混亂。很多人告訴他，過了 10 萬行 AI 就什麼都做不了，很糟，放棄吧。他做過很多安全和效能工程，對安全有意見。他刻意不先把一切自動化，因為要知道哪裡出錯，這是真正的 human in the loop。他想回答：不寫 code，我們能做成什麼。能不能野心大到去做以前不會嘗試的東西。他認識做資料庫新創的人，要十年，是硬扛。若能用更少時間做成，就能做更多有趣的系統。

## 測試很有用，100% 不是目標

[3:53](https://www.youtube.com/watch?v=xHxfeWtkXrM&t=233s) 他喜歡 Deming 談品質的話。Deming 在戰後把品質管制引進日本，靠的是檢驗。看程式行數找不到 bug。品質要邊做邊建進去，測試是其中一件重要的事。小的 AI 專案上，只用測試就很好：可以測得很兇、很放心、因為它簡單。專案一大，測試變複雜，尤其進到系統、race conditions 和各種怪事。他一直聽到有人說，有了 AI，100% statement coverage 就夠了。他試了。一開始就追 100%，也量了不同算法、包括 integration tests 的 coverage。幫助不大。時間有更好的用法。他請 AI agent 做到 100%，它寫出他覺得蠢、不在乎的瑣碎測試。很多奇怪的錯誤路徑很難蓋到。他問為什麼還沒 100%，agent 說沒有「系統裡的亂數產生器失敗」的測試。他不想寫那個。錯誤注入太多了。它會報錯或 panic，那就是對的行為，不必讓整個測試套件都蓋到。

[6:22](https://www.youtube.com/watch?v=xHxfeWtkXrM&t=382s) 測試仍然很多。他說 codebase 有 75% 是測試，每個檔案的 coverage 在 75% 到 100%。可以有很多測試，而不必執著 100%。他認為那不是對的目標。

[6:46](https://www.youtube.com/watch?v=xHxfeWtkXrM&t=406s) 複製 S3 這種現成系統的好處是有 test oracle。想知道做了某事會怎樣，就把測試拿去對 S3 跑。他有 1500 個對 S3 跑的測試，把行為鎖住，再告訴 AI 必須一模一樣。這樣它好得多，因為有一條乾淨的基線。他甚至覺得，寫複雜系統的一種起手式，是先寫一個行為相同、幾乎瑣碎的版本當 oracle，再建複雜版時才不會把它弄壞。測試套件可以先對著簡單版建。

[7:42](https://www.youtube.com/watch?v=xHxfeWtkXrM&t=462s) 這並不百分之百容易。指著 Amazon S3，會發現各種怪事。S3 的授權有很大一部分是 eventually consistent，不是立刻一致，所以測試裡要很多 retries，不然會看起來行為不同。就算有精確的 oracle，也得做一些解釋。它不算規格，但會把你牢牢按在地面上。另一件事是，公開 API 蓋不到背景裡你看不見的行為。你得從觀察得到的東西推論，或另找方法測。你看不到 S3 裡一個物件真正何時被刪掉，它會在某個時刻發生，沒有 API 讓你看幕後。

[9:16](https://www.youtube.com/watch?v=xHxfeWtkXrM&t=556s) S3 文件看起來很漂亮，幾百頁。一追究細節，文件大多是錯的。跑測試、靠 oracle，比讀文件重要。文件也許曾經為真，也許大概為真，能提示有趣的地方。他的說法是：完全不要信任任何人的文件。但這樣你才有落地的測試，對上真實行為和真實邊界。

## 邊界、flaky，以及測試找不到的東西

[10:02](https://www.youtube.com/watch?v=xHxfeWtkXrM&t=602s) 他在改進 code 裡的型別系統時，AI 對著 S3 寫了一些隨機測試，找到一個可重複的 500。這很興奮：Amazon 沒有這個測試，他有。他立刻覺得測試套件、或其中一部分，現在是好的，因為他在找到真正怪的錯誤和邊界，表示測試的宇宙被探過不少。做這種複雜開發，有時覺得一切很糟、永遠不會成；有時又覺得其實又在動了。測試給的就是這種信心。後來另一個怪邊界又出現一個可重複的 500。他問到目前有幾個，兩個。

[11:44](https://www.youtube.com/watch?v=xHxfeWtkXrM&t=704s) 他自己找邊界找得比較好，尤其是它在寫 code 的時候。他讀 AWS 文件，問這是真的嗎、我們有測試嗎，再請 AI 寫測試，就會找到和文件大約相符、或只是文件暗示的怪事。把 AI 指到文件上、請它做同樣的事，它很差，沒辦法像他那樣從文件裡找出邊界。有時邊界來自 coverage 的缺口。請它想想常見邊界，例如長度 0、1、以及 10001，有一點幫助。你得自己迭代，像測試者那樣想，對哪些區域可能有怪錯誤要有想法。字幕裡還有一句像 “think like a shape”，沒有聽成清楚的方法名。

[13:12](https://www.youtube.com/watch?v=xHxfeWtkXrM&t=792s) Flaky tests 很有意思。AWS 是隨時間收斂到真相，這很煩，浪費大量時間。他的硬規則是：跟 AI 一起時絕不容許 flaky tests，立刻修。有時它會怪事：訓練資料說開發者從不修 flaky tests，所以忽略。他會對它吼：這個 codebase 要修。`agents.md` 寫了，你又忽略。訓練資料說沒人修，而那確實曾經為真。他待過很多地方，flaky tests 一大堆。對 AWS 的測試，它有時認定 AWS 每天改行為，於是把 code 再改成相符，因為必須匹配 AWS；然後又改回去。他說不，測試有問題，先修測試。這正是把 flaky tests 修掉的機會。AI 擅長這個，也會真的幫到測試。全部清掉，並把測試盡量做快、常常跑，flake 會更快出現，因為多數 flake 不常發生。他目前 5000 個測試，兩分鐘跑完。兩分鐘是他勉強能接受的邊界，也許還會再加速。你得常常跑才找得到。有些變更會帶來很多 flakiness。他會過夜、在多台機器上反覆跑，找錯誤。慢、或真的很 flaky，就不好受。

[15:46](https://www.youtube.com/watch?v=xHxfeWtkXrM&t=946s) AI 對各種測試都很好。他隔一陣子會問：剛剛那些問題，我們該有哪種測試才能修。它會提出新種類，很多真的找到問題。Fuzz tests 不錯，property based testing 也找到一些。你可以做以前不會想到的測試，種類也該變多。測試找不到的東西要知道。有時它們找得到 race conditions，測試愈多愈快愈好，但仍然難。持續做出好的效能測試很難，不過做得到。測試找不到安全問題，也不能決定架構好不好。現在量不到的，就很難測。有很多東西在測試外面，你得想辦法把牠們拉進來。只盯 coverage，就會不夠想安全。

## 從黑盒裡多聽一點聲音

[17:35](https://www.youtube.com/watch?v=xHxfeWtkXrM&t=1055s) 要讓東西更好測，黑盒裡任何訊號都算。他說如果有一聲貓叫，那也是你需要的資訊。擴大能測的範圍，做更多可測的介面。他後悔沒有好好做管理、報表和後端介面，否則可以對那些跑測試，更懂裡面在發生什麼。他當時盯的是公開 API，因為那是要複製的東西，不是內部。內部有 unit tests，但那個 API 是內部的、沒有結構。他不確定能多信任，因為看不到，只能透過測試看，也不能坐下來玩。能多做出來就更好。

[18:37](https://www.youtube.com/watch?v=xHxfeWtkXrM&t=1117s) Tracing 和典型的 observability 很有用。就算只讓 AI 做一套手寫、手維護的 tracing framework，也非常有用。不必接到生產系統。任何它能看著除錯的 trace 都驚人地有用。這套有額外開銷，拿去做效能測試會有點誤導，但能指出大的效能缺口在哪。除錯時他可以跑測試套件找 race 或錯誤，把 trace 給它，說這是過夜跑出來的，要修。它就能鎖住真正的問題，而不是猜。若你給 AI 一個 bug，卻不知道怎麼重現，而且很罕見，它會浪費很多時間：自己重現失敗，或猜一個解法然後猜錯。給它 trace 和 trace 工具，讓它坐在那裡試著重現、看是不是同一件事，通常可以。所以不一定要接到生產環境，讓 AI 做一些 tracing 工具就行。

[20:27](https://www.youtube.com/watch?v=xHxfeWtkXrM&t=1227s) 效能測試上，AI 很像人。它做了改動，效能沒變好，或變得更差，因為它覺得這一定是修法，其實不是。效能工程就是這樣，靠過去就好。這是便宜的工作，不行就丟掉。不要因為當初看起來是好主意就留著。說不，丟掉，試別的。拿去跟其他系統比很有趣。他對另一個 S3 實作做效能測試，讀的效能做到一樣。寫為什麼很慢，它想了一陣，最後說對方 code 裡有註解：寫的時候不做 fsync。沒有同步寫，當然更快。不要再浪費時間，去追一個在做我們不想做的事的東西。

[21:48](https://www.youtube.com/watch?v=xHxfeWtkXrM&t=1308s) 早期權限檢查出了很多問題：time of check、time of use，權限在不同地方測了兩次。他試過用 tracing 修一些，最後改叫它在型別系統裡修，而不是靠 tracing。做一個 authorized request 型別；字幕說 “that can't be authorized”，這句沒有聽順。重點是進這個關卡的東西都必須已授權，這些函式只收 authorized requests，全部用型別逼過去。省很多力氣。一旦建構到你做不到錯的那件事，就不必再為它寫測試，型別在強制。他花很多時間看模組之間的介面型別，看它們看起來正不正常。

[22:52](https://www.youtube.com/watch?v=xHxfeWtkXrM&t=1372s) 安全審查他喜歡 Codex Security，找到很多問題。他的做法是把發現 check in 到 repo，再請 AI 審查。四分之三是有效的，但不一定百分之百是安全發現。他會隔一陣子做審查會：我們怎麼能避開這些，該有什麼測試才能修。這很有價值。他當時已經做很多 AI code review、找到很多問題、也迭代很多次，它仍然找到被漏掉、而且重要、相當大的東西。他後來做了更多種 AI 安全審查。Codex Security 審查 pull requests 沒問題，但你也該坐下來，把 code 當時的整體狀態拿來找問題。

## 外層的 harness 是人，以及兩則提問

[24:03](https://www.youtube.com/watch?v=xHxfeWtkXrM&t=1443s) 他覺得 human in the loop 很有價值。他把自己看成回饋迴路的一部分。他有意見，在這裡就是要找出哪裡錯了。他不把事情自動化得太過，因為要真的懂哪裡出錯。品質是他的責任，他在乎這份 code，想知道它是好的。學到的是：test oracle 或模型非常有用。複製已存在的東西是很好的活動，開源有很長的歷史，GNU 計畫就是去複製 Unix。好玩，而且頗行得通。

[25:13](https://www.youtube.com/watch?v=xHxfeWtkXrM&t=1513s) 他秀 GitHub commit graph。重構得做正常的量。中間有荒謬的一週：加 12 萬行、減 7 萬 5 千行。那是重構週，開頭還有另一週。當時有一個 4 萬 3 千行的單一檔案必須拆，agent 就是走到那裡。重構是回饋迴路的一部分。不必覺得要 one-shot。你是在收斂到更好的答案。接著有一句字幕沒聽清。你要坐下來想：有進度、功能做完了，還有什麼可以更好。那個迴路是工作的外層 harness，不能忽略。

[26:23](https://www.youtube.com/watch?v=xHxfeWtkXrM&t=1583s) 測試是發現工具。不是說有一個答案，只要測試對了它就在那裡。你要在不確定、起疑、覺得可能還有錯的地方擴測試，想出還能加測試的新東西。這是品質管制的一部分。我對這份 code 滿不滿意，還是擔心。若擔心，就加更多測試，花更多時間試著弄壞它。你的角色就是在那裡、把東西弄壞、再讓它們被修好。他打算大約一週後開源，等分散式系統那截做完、他自己滿意的時候。想看的人可以登記，好了他會寄信。

[28:03](https://www.youtube.com/watch?v=xHxfeWtkXrM&t=1683s) 有人問分散式系統那部分有沒有試過形式驗證或測試工具。還沒有，他還在做。他想等大致完整實作之後就看驗證工具。他有一份很大的轉換計畫，從單機到多機，各塊都在處理。他希望下週能以完整分散式的方式跑起來。他覺得那裡大概會有 bug。那些工具他看了頗久，很有興趣能驗證什麼、能形式驗證什麼。形式驗證是他想多做的事。AI 在這上面好不好，報告不一，他很著迷。

[29:21](https://www.youtube.com/watch?v=xHxfeWtkXrM&t=1761s) 另一人說自己的做法相似，而 test oracle 有個難處：AI 很愛說那會是 tautology。Oracle 必須用完全不同的方式做同一件事，才不是把邏輯跑兩次、自然得到相同輸出。他的困難是用 AI 做系統，再用完全不同的路做 oracle，讓兩邊互相牽制。Justin 說他稍容易，因為 S3 是外在的、就在那裡。不過有些模型測試的設置他也遇過類似問題：我到底在測什麼，是不是任何和 code 不同的東西。他說就算在做複雜軟體，他也會做一個 oracle，但也許會放在 repo 外面，做成一個固定的、很模型化的版本。否則你會發現自己根本沒在測任何與被測物不同的東西。你需要一個固定的保證，那就是你要的。有一個你能釘死的外部系統可以複製時，確實容易得多。提問時間到此結束。

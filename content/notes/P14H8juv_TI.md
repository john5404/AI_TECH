# Monthly Roundup: AI Tool Effectiveness, Context, Fin, and AI Autonomy.

Simon Maple 和 Guy Podjarny 做 AI Native Dev 的第一次 monthly roundup。片長 41 分 23 秒，英文自動字幕。他們用這個月接近 10 集裡反覆出現的話，談工具到底好不好用、context、Intercom 的 Fin，以及自主程度。Tessl 常被聽成 Tesla、tessla。這份筆記依英文原稿整理，專有名詞保持英文。

- 原片：[YouTube](https://www.youtube.com/watch?v=P14H8juv_TI)

## 一句話

這個月最一致的學習是：LLM 產品好不好，做的人自己也很難事先知道，常常要 ship 了才明白。Context 是準確度的來源，也是把過時知識、壞習慣和漏洞再製一遍的來源。廠商幾乎都說自己什麼都做，因為懂 code 之後，測試、文件、補完只是上面一層很淺的東西。Fin 則把信任和創造力的拉扯先碰到了：幻覺少，解得掉的案子就少。

## 回到節奏，然後問產品到底有沒有用

[0:16](https://www.youtube.com/watch?v=P14H8juv_TI&t=16s) 中間隔了很久。他們已經錄了接近 10 集，不少已播出，有些緊接在這集之後。Guy 說回來像騎腳踏車。有趣的是找到人、問自己真的想問的事。別人願意把學習分享出來，他覺得謙卑，也感激，因為知識仍然是一種優勢。每段談話他都難收尾，因為還想再問。Simon 把 podcast 當成藉口：直接溜進別人的私訊說想聊一小時，聽起來很怪；有一檔節目就合理。他們開玩笑說如果錄了卻永不播出，信任很快就沒了。

[2:27](https://www.youtube.com/watch?v=P14H8juv_TI&t=147s) 這集的形式是從本月幾集裡抓主題，放進他們自己的學習，再跳回來賓怎麼說。第一個主題是這些產品到底表現如何。有的承諾遠超過做得到的，有的承諾得體、也交得出來，還有往後怎麼變好的路線。最稀罕的一塊是評估：一個模型對 prompt 的回答，在不同情境裡算不算好。

[3:30](https://www.youtube.com/watch?v=P14H8juv_TI&t=210s) Guy 說這個月非常一致，而且要自己做過 LLM 產品才會懂有多難。就算你知道想達成什麼，答案也不穩。產生的是 code 還是測試，有沒有產生對的東西，有沒有聽懂問題，事先都難判斷，範圍一廣更難。也難預測下一次它會怎麼反應。他把話說得最好的是 Des（字幕 Dez）。好案例和他們稱為 torture test 的東西不一樣。每個人的測試套件都該有一組 torture test，就算只是為了這個名字。原有的測試很難定義，那些好案例已經是最容易、也可以比較快做完的。真正難的是有人要同一份資訊的七個版本，或一個指令裡塞 20 條指示。連那些都不夠。用 Des 的話：產品有沒有用，要 ship 了才知道。這在很多談話裡出現，包括還沒播出的。Tessl 自己在產品上也有同樣的感覺：這段生成的 code，到底對不對。

[5:32](https://www.youtube.com/watch?v=P14H8juv_TI&t=332s) Simon 問，把測試做成盡量像正式環境，是不是人人一樣。Guy 說模仿智慧時，很難知道自己打中了那個和弦。可能性愈廣愈難，torture test 離現實有多近也是問題。對比一個 wizard 或某種 UI，那裡的可能性是有限的。Des 還說得好：在這個世界裡，變的不只是你的能力，底下的技術也在變。新的模型一出來，工具商面對兩個都不怎麼令人興奮的選擇。一是樂觀地丟進去，希望它能用。短期有賺頭，風險高，幾乎是行銷賽，看誰先上。Des 看到很多競爭者在新模型出來時立刻切過去。字幕裡的例子聽成 40。切模型很容易，難的是不放進正式環境就判斷它會變好、持平，還是變差。丟出去也很誘人。消費者本來就不知道工具有沒有用；廠商因為某些情況很好就在腳下換模型，更難信。Tessl 帶 AI engineering 的 Amy 常說 AI 的 Jagged Edge：有時好得驚人，有時糟得嚇人。另一個選擇是謹慎、慢慢放。你不能完全信一套測試。Des 的團隊做了 torture test，連那個都不夠，而且美元和時間都很貴。

[8:16](https://www.youtube.com/watch?v=P14H8juv_TI&t=496s) Sourcegraph 那邊，以及 Tabnine 的 Peter 和 Rishabh（字幕 rishab、rashab），也把評估講得很重。Rishabh 是 AI 負責人，工作很大一部分就是評估：給定輸入和 context，輸出到底相不相關。他談的是那裡的 zero to one。Context 在 code search 裡是王。

## 用的人也信不過，所以先當助手

[9:06](https://www.youtube.com/watch?v=P14H8juv_TI&t=546s) 聽眾裡只有一部分人在做 LLM 工具，以後會更多。就算站在最前面、自己在做這些工具的人，也很難把別人的工具接進來用，原因相同：不能真的信任它會好好運作。Des 的句子他們一直引用。Amir（字幕也聽成 air）從不同工具、不同領域談你在哪裡也許可以放心。

[10:05](https://www.youtube.com/watch?v=P14H8juv_TI&t=605s) Simon 自己用很多 AI 工具剪這檔節目、也幫 Tessl 做內容。有些地方很省時間。叫它從一集裡挑五段或十段最有趣的 short 和引言，很少挑中他會挑的那十段。可能是沒懂 intent，也可能是 prompt。他仍得把自己的判斷放進去，工具只在幫得上的地方省時間。整體還沒到。Guy 說這令人挫折，因為他們想早用、相信目的地，也先花了時間挑工具、甚至自己做。近得誘人，跑的時候仍有驚艷，平均卻不過線。消費者能做的是繼續試、把使用收斂，不要依賴它一定會動，但要一次次回到井邊，找它真的有用的情況。今天最好的情況仍是助手：有時省時間，不要把計畫建立在它一定成功上。Simon 同意要回井邊。六個月前，他們甚至不會覺得能接近今天。六個月前的假設，現在未必還成立。

## 對的 context，以及會讓歷史重演的 context

[12:13](https://www.youtube.com/watch?v=P14H8juv_TI&t=733s) Code generation 是較早談的類別，context 一再出現。它要能聽懂 intent，再依對的 context 給出有用的答案。Simon 和 Tabnine 的 Peter 談過多少才叫太多。給太多，模型被資訊淹沒，反而答不準。給對的量，準很多。

[13:03](https://www.youtube.com/watch?v=P14H8juv_TI&t=783s) Des 也談壞的 context。Intercom 客戶試他們的自主 agent Fin（字幕 Finn），常發現 Fin 把知識庫反映得很好，知識庫本身卻過時。支援團隊裡有一套 voodoo、shadow knowledge，讓真人知道哪些資訊還新、哪些不是。Fin 沒有那種細膩，所以得回去修。文件過時，大家都懂。更細的一層是 code。他說 crap in, crap out。Code 裡滿是你其實不想再維持的壞做法，拿它來訓練，就會複製你不想要的慣例。預設心態是 context 愈多愈懂你、愈能客製。同時也有淹沒，分不出重要的。他說小心許願：歷史給太多，它會讓歷史重演。

[14:48](https://www.youtube.com/watch?v=P14H8juv_TI&t=888s) Code completion 得在既有 code 上訓練。很多工具從開源函式庫拉，裡面有好 code、差的 code、也有安全問題，它會試著複製看到的東西。你再把自己的 code 當 context 疊上去，它看到類似的 antipattern、寫法問題、安全問題，就會說你那邊這樣寫，這裡也用類似風格。這發生在好幾層。模型訓練在全世界的 code 上，世界上重複的問題和模式會進到模型裡。再往下客製、用客戶的 codebase 訓練，就複製那裡的模式。Guy 提到 Simon 在 Snyk（字幕 sneak）最近的一份研究：如果開著一個分頁，裡面的 code 模式剛好有漏洞，Copilot 更可能把它複製出來。本地或全球都一樣，LLM 在資料上複製、在資料上建造。

[16:20](https://www.youtube.com/watch?v=P14H8juv_TI&t=980s) Simon 和 Devin 談 context 時還有另一面。Devin 做了 Dosu（字幕 dosu、do），給開源維護者和使用者。使用者對專案開 issue，維護者可能要很久才開始看。有對的 context，Dosu 可以在幾分鐘內回答：答案在文件裡。更有趣的一次，答案不在文件，而在測試：測試寫著這是我期待的行為。Dosu 就告訴使用者應該這樣做。壞的 context 是它從 code 推論行為。那個行為是一種可行的 workaround，卻不是維護者希望人用的方式。Guy 說這正是：今天能動、今天的模式是這樣，但我正想改掉它，讓人走對的方式。

[17:40](https://www.youtube.com/watch?v=P14H8juv_TI&t=1060s) 一旦給更多資訊、更多選項，挑選和排序就變成問題，要發現較好的那一個。Snyk 的漏洞也一樣：告訴你太多，也許都對，人處理不了，想知道哪些才該管。像 Spotify 要挑對你最對的歌。Code 和系統的知識變多之後，問題不再是知識在不在，而是哪一份更重要。使用者怎麼提出請求，也會因為工具差很多：在 IDE、在 PR，或其他地方。

## 補完也是一種聊天；延遲決定你能問多深

[18:31](https://www.youtube.com/watch?v=P14H8juv_TI&t=1111s) 他們一直回到和 Des 的那集：聊天介面，對上逐行、很快的自動完成。Des 的論點是，完成某種程度上就是聊天。你不是用話告訴它要什麼，而是打字時不斷給它更多 context。Guy 覺得很有趣，還不確定自己同意，仍在消化。他收到的比較上層的理解是：跟 LLM 的任何互動，都是你選擇給什麼資訊、在 context 上投了多少，以及 intent，你用話或其他它懂的資料結構解釋你要什麼。做得愈好，結果愈接近你要的。聊天裡你可以更明確，但 context 也許較少，而且你期待它馬上給對。完成的環境裡 intent 是隱含的，你一邊打一邊給資訊。聊天裡發亮的是你怎麼寫 prompt。自動完成裡，則是你把 code 寫得怎樣：先寫註解再期待它補，其實已經很接近聊天；只是一直打 code、期待它推論，則是另一種變體。

[20:28](https://www.youtube.com/watch?v=P14H8juv_TI&t=1228s) 這些話出現在一個問題裡：把 LLM 放進本來就是聊天的工具，是不是比較容易成功；PR 那種比較像非同步聊天的地方，是不是比 code completion 更容易。若你在做 LLM 能力，該問的是：使用者用哪些正確的方式告訴我他要我做什麼，以及我成功所需要的 context。Rishabh 談 Cody 時，差別在於你怎麼向模型要東西。Code completion 期待答案非常快，延遲一過線，開發者就煩。測試生成這類更大的任務，可以給模型多很多時間，換更準的答案，那是可接受的。聊天和自動完成，差的就是能花多久、以及準度。

[22:09](https://www.youtube.com/watch?v=P14H8juv_TI&t=1329s) Intent 還有另一層。問 ChatGPT，它預期會接到的範圍寬得多。在 IDE 裡問，多半是寫 code 的問題。這帶到這些助手的範圍該有多大。

## 類別畫得很整齊，廠商都不肯待在格子裡

[22:44](https://www.youtube.com/watch?v=P14H8juv_TI&t=1364s) Amir 從消費者和投資人看市場，把能力畫成一類一類：coding assistance、code completion、AI 文件、AI 測試、維運。Guy 覺得這些界線有用、也說得通。然後幾乎每一個他們聊過的廠商都說自己全都做。不一定直說，但技術上一疊，產品範圍該到哪仍是開放問題。Cody 從 code search 開始，懂了 code，現在談的是 coding assistance，也做測試，談話很多在測試上。Tabnine 也會索引 code，也有測試。Guy 看到兩件事。技術纏在一起：一旦懂 code、懂該做什麼，很多路都開了，大家都想抓。第二，客戶還沒有固定期待。還沒有人有時間證明自己在某一薄片上好到值得單獨當 best of breed。很多價值仍在那個 80/20：用 LLM 產生文件，也許已經到得了那裡。廠商在搶更寬的範圍。線會畫在哪，他不知道。談開發時仍適合談分立的功能，即使最後是同一家廠商提供。現在很難找到願意把自己關在一個範圍裡的廠商。

[25:29](https://www.youtube.com/watch?v=P14H8juv_TI&t=1529s) Simon 從他們做過的工具公司看，整併一直很關鍵。開發者本來就要測試、文件、補完、助手。要三個工具，還是一個整合的？不同廠商各自強一點時，單一體驗是不是更舒服？自主也有關：是你直接用，還是背景裡有個流程在跑。Guy 說，一個更好的工具能多給多少價值，消費者還不知道。所以問題先變成：我們要不要 AI 幫我們產生文件、產生測試。若手上已經有一個、尤其已經在你的 codebase 上訓練過，它就方便，而你還不知道好長什麼樣，於是它生成測試的樣子，就染上你對「做得到多少」的感覺。這些能力共享一個錨：懂 code。錨以上，很多只是核心 LLM 上相對淺的一層，公司補上的成本不高。他賭會看到很多整併和 all-in-one。有些會纏得很緊。Cody，以及即將播出、Codium 的 Itamar 那集，都很多在談測試和 code generation 的關係：懂了 code、知道什麼是對的，能不能產生對的 code。他買這個帳。文件也許有夠多獨特需求，會有一批工具明顯更好。現在不知道。會先合，再有一些長出來。幾年後就回到熟悉的整併：知道好長什麼樣，再有意識地選 best of breed，或選較少的廠商。

[28:36](https://www.youtube.com/watch?v=P14H8juv_TI&t=1716s) Simon 說這裡資料會是王，指的是應用怎麼被使用的行為。監控工具有正式環境裡哪些 code path 是熱的。行為資料可以看出開發者最常改哪一塊。測試資料可以看出哪些區域抓到最多問題。還有漏洞的安全資料。這些能告訴別的工具該把力气压在哪。監控若懂使用者走的 golden path、hot path，AI 測試就該聚焦那裡。若測試在某一種 flow 上抓到問題、而且因此在修 code，補完助手就不該再建議同一類寫法。資料若能共享，整併的價值就很大。

[30:05](https://www.youtube.com/watch?v=P14H8juv_TI&t=1805s) Guy 用 Hamilton Helmer《7 Powers》的鏡頭。資料是其中一種力量：你是不是更有位置把價值交給客戶。有時你已經有有用的資料。有時只是通路：已經裝在每個人的桌機上，順便拿到資料，也順便把工具遞出去。有時是商業關係。有時是已經投資去索引 code。那種資料技術上別的廠商也拿得到，但客戶得花時間接上對的地方、調整、定義政策。於是回到經典的新創問題：破壞者會不會先拿到通路，在既有廠商拿到創新之前。他從這些談話得到的主要結論，幾乎是一種衝突。很前面的一集，Amir 把工具分得很漂亮；每一個廠商都把這個分類弄亂，幾乎不願接受被捆成一包。所以要評估它們，也要預期它們不會乖乖待在格子裡，直到界線變清楚。Simon 說，期待每個工具只待一個類別，大概是夢，或者是幻覺。

## 幻覺可以多解一些案子，也可以騙到你

[32:29](https://www.youtube.com/watch?v=P14H8juv_TI&t=1949s) 他們願意接受到什麼程度：工具會幻覺，給你不正確的東西。Des 的討論是，你願意接受幻覺，是因為它也給別的價值；痛是你會拿到無意義、胡說，或直接騙人的東西。Guy 覺得 Intercom 在做 LLM 工具上比多數人走得遠，學習也超前一步，因為他們面對過現實並讓它運作。他們很多工作是把幻覺關住，讓你跟支援機器人互動時，拿到的答案信得過。但也很清楚：若讓 Fin 多幻覺一點，它可以解決更多案子，也可以更有創意。問題是怎麼更有創意，同時不丟掉可信。他的產品腦開始轉：產業有沒有模式，能把客戶拉進這個選擇。問 Fin 一個問題，它說不知道；或者給一個對上你在做的事的答案，再問你要不要讓它更有創意，但答案可能更不準，甚至幻覺。他不覺得客戶一定不肯接受。也可能複雜度太高。也可能這時該轉給人，而那樣也可以。

[34:45](https://www.youtube.com/watch?v=P14H8juv_TI&t=2085s) Simon 特別澄清：他說的 Devin 是 Dosu 的 CEO 兼創辦人，那個 AI 工具跟名叫 Devin 的 AI 軟體工程師無關。他沒有去做一集跟那個 AI 工程師的對談。Devin 說的一點是，LLM 不喜歡回答「我不知道」。訓練時必須講很清楚：信心低於某條線，就該說不知道，叫人去找人類。它不知道時會編一個答案，不喜歡說不。

[36:05](https://www.youtube.com/watch?v=P14H8juv_TI&t=2165s) Simon 在 Tessl 做部落格內容時試過。他在他們用來做內容的工具裡寫了一個小 agent，字幕把工具聽成 cre aai，比較像 CrewAI。Agent 看 Tessl 的部落格，找相關內容。那裡「沒有」是完全可以接受的答案。部落格還沒上線，沒有相關文。它不願說沒有，回了五六篇不存在的文章，標題很好，還有 URL，說這是很棒的相關內容。它找不到答案，但想取悅他。Guy 補了一點：它還在發明一些 Copilot 的功能，發明的是新的現實，不只是新內容。有時幻覺出來的東西，其實應該存在。他一個朋友問某個函式庫怎麼用，模型說該用這裡的 API，把長相和呼叫方式都寫了。那個函式庫根本沒有 API。朋友先煩它在編，然後覺得也許真的該有這個 API，因為會很想要。Guy 說 Fin 在成熟的路上會告訴你它對答案有多有信心。他沒親眼看到，是 Des 在講。那幾乎是在平衡「我不知道」：若要猜，這是我有的資訊。不該編造，但至少標出低信心。他認為 UX 模式找得到。人也得更習慣：背後是一個 agent，temperature 拉高就會多幻覺，信心很重要，回覆要自己留神（字幕說 comply）。若 UX 沒弄清楚，結局是要嘛必須完全準確，LLM 的用處就變小，要嘛有時在騙使用者。

## 一個人，一天兩集

[38:57](https://www.youtube.com/watch?v=P14H8juv_TI&t=2337s) 他們依學到的和回饋在改節目。Simon 的集會變成同一天、同一位來賓連發兩集：先聊要覆蓋的題目，再做 hands-on、螢幕分享，比純音訊更適合看影片，也更偏開發。Devin 那集已經是這個形狀。播客聽眾仍可以聽前面那段談話。怎麼改，他們歡迎回饋；聯絡方式字幕聽成 contact tess，沒有聽清完整地址。已經錄好、即將出來的有 Itamar，Codium AI 的共同創辦人兼 CEO，談 AI 測試，Simon 會加一段現場。還有 Jason Warner，前 GitHub CTO，在那裡時做了 Actions 和 Copilot，現在經營 poolside，他說那是專注在 code 的頂尖 foundation model 之一。他們會談 code generation 為什麼有效、往哪走、通用模型和專為 code 的模型。這個月還有幾集。

# Why Developers Hit a Wall at 4 AI Agents

AI Native Dev 播客，片長 47 分 50 秒，英文手寫字幕。主持人 Simon Maple。來賓是 Jellyfish 的 head of AI and research Nicholas Arcolano，節目裡多半叫他 Nick。開頭還預告六月一日、二日在倫敦 The Brewery 的 AI Native DevCon，現場或直播，折扣碼 POD30。這份筆記依英文原稿整理，專有名詞保持 English。

- 原片：[YouTube](https://www.youtube.com/watch?v=GbHfzFcIa0o)

## 一句話

Jellyfish 用企業裡真實的工程訊號，而不是 X 上的情緒，來看 agentic coding。沒有改流程裡其他實質的東西，原始的 code 吞吐量大約是兩倍，被合併的 pull request 也在變多。但 AI 開出的 PR，第一季只有大約六成會合併，人開的大約八成。多數人互動式地看一到兩個 agent；最有經驗的人卡在四個，很少到五個。2026 年 CFO 要收據。噴射引擎已經做出來了，車身還是舊的。

## 他們量的是結果，不是感覺

[2:01](https://www.youtube.com/watch?v=GbHfzFcIa0o&t=121s) Jellyfish 在 AI observability，特別是組織層級的 AI 轉型：客戶用哪些工具、agent 怎麼用，以及這些怎麼接到結果，code、推上去的東西、code 的品質，最後是業務結果。公司快十年。很長一段時間拉的是工程機器的基本材料：git 的 commit 和 pull request、留言，以及 Linear、ADO、Jira 上的任務。大約兩年多前，Copilot 開始起來，他們才從那些 API 拉基本用量。現在是一大堆 API、hooks、open telemetry。不只知道有沒有人用，還看 token 花費、用哪些 model。最近才開始拿到 agent 每一輪的資料，包括規劃和 tool call。Nick 說這能把終端機前的人在 X 上讀到的，和真實公司裡發生的分開。Simon 說這不是情緒資料，也不是很小的子集，他講到上千萬、以及他口中被評估的大約 4000 萬。

[3:43](https://www.youtube.com/watch?v=GbHfzFcIa0o&t=223s) Simon 說該叫他 doctor Nick。Nick 的 Slack 頭像是那個小 doctor Nick，辦公室有人這樣叫。學位是應用數學。data science 還不是一個頭銜之前，他在美國的國家研究機構待了多年，做大型網路上的推論和訊號處理，給網路安全防禦用，後來才開始稱自己是 data scientist。那個頭銜現在過時了，興奮的是 AI engineer。Simon 念履歷：哈佛，統計訊號處理、圖論和網路分析；MIT Lincoln Laboratory 的 technical staff；Runkeeper 的 senior data scientist；True Motion 的 director of data science；然後是 Jellyfish。

## 兩倍發生在新而小的 codebase

[7:16](https://www.youtube.com/watch?v=GbHfzFcIa0o&t=436s) 最大的一句是變得有多快。去年此時，氣泡外面的人還在辯 AI 有沒有用。客戶不確定該走多快，因為 AI「還沒真的能用」。去年秋天出來的模型把工程往前推了。現在這份資料把一件事釘住：野外看得到真正的原始寫 code 增益。人在用 Cursor 和 Copilot 這類愈來愈 agentic 的 IDE。若流程裡其他實質的東西不變，原始 code 吞吐量大約能做兩倍。那個兩倍，他先說是建立出來的 pull request 變多。Simon 追問是合併還是開出。他說那些是被合併的 pull request。

[8:39](https://www.youtube.com/watch?v=GbHfzFcIa0o&t=519s) 哪裡更快，有一部分符合預期。較小、較新的 codebase 更快。語言也有差。大家覺得比較 AI 友善的語言更快：Python、TypeScript，以及很重的設定、markdown、YAML。較慢的是舊的、又大又亂、分散的 codebase。資料顯示，codebase 變得非常分散時，AI 帶來的增益少到幾乎沒有。那裡有大量人的工作，要把這些 code 怎麼相關的 context 對起來。資深工程師知道部署時「屍體埋在哪」：要在這些 repository 的十個地方改 code。他說那些最佳做法對又大又散的 codebase 還沒被操作化。Agent 不知道該做什麼，仍重度 human in the loop。Simon 不確定這是應用風格真的決定 AI 幫不幫得上，還是人只在自己熟、知道連帶效應的地方才用。

[10:47](https://www.youtube.com/watch?v=GbHfzFcIa0o&t=647s) 讓人困惑的是，過去一年、甚至六個月，下游沒有跟著增加。看不到上線的功能變多。他們看得到 issue，也看得到 epic 往上捲成 initiative。客戶花很多力氣把這些對到他們在乎的業務單位、產品線、客戶。那些東西以前沒在動。現在開始有了。容量變多，那些容量去了哪裡，是他們好幾季想拆開的謎。

## 八成對六成，多出來的是死在藤上的 PR

[11:59](https://www.youtube.com/watch?v=GbHfzFcIa0o&t=719s) Simon 在 Snyk 時很會找出問題、開 PR，有些會合併，很多不會，即使 PR 是有效的，合併仍要額外力氣。Nick 最近公布的結果：第一季，人開的 pull request 大約 80% 最終合併。另外 20% 維持開著，或關掉但不合併。原因很多：沒達到品質，或後來決定這不是好主意。AI 的 PR 是 60/40，不是 80/20。死在藤上的大約加倍。他們還在挖原因。軼事上，有些是流程不同。客戶需求進來，你叫 agent 去修，東西就在那裡，之後才決定要不要。也有人同時做兩種、三種、五種做法，架構不確定、功能該怎麼動不確定，做出一批候選再挑一個，那是故意丟掉的工作。還有一種常聽到的：backlog 上看到變更，用那個正在退流行的詞，vibe code 一個修法，然後發現比想的複雜，達不到品質。資深工程師進來說不不不，我們沒修這個是有原因的。你在挖出惡魔，看似簡單的東西下面有很深的技術問題。這些疊起來，就是那個加倍的比率。

[14:37](https://www.youtube.com/watch?v=GbHfzFcIa0o&t=877s) 他覺得有趣，是因為這碰到大家都想知道的問題：好的工程最後長什麼樣，要花多少。高度自主、一組 agent 一起做的時候，浪費和額外開銷會有多少。那不是把今天一兩個互動式 agent 的做法簡單放大。Simon 原本以為是 agent 更自主、依觸發自己開 PR；聽起來其實是人發起，再從裡面挑。他問這是不是流程的缺陷：GitHub 這種 git repository 根本不是為 agentic development 設計的，中間該有一層，預期一個修法有多個版本、讓人挑一個。現在的變通是不送一個修法，而送好幾個再丟掉一些。Nick 完全同意。軟體世界到處是沒被用在設計目的上的工具。有些會永遠以奇怪的新方式用下去，有些不會。歷史會告訴我們，他的孩子做 agentic engineering 時，會不會問為什麼還要做這些奇怪的 git。那東西存在幾十年，不會消失，但不是對的模式。Pull request 長什麼樣，他覺得是軟體工程的核心單位，現在和出貨的價值綁太緊。整條 SDLC 正在以新的方式塌掉，在真正的 agentic 世界裡不一定還說得通。

## 71% 是每週有打開，自主合併還差很遠

[17:27](https://www.youtube.com/watch?v=GbHfzFcIa0o&t=1047s) 報告裡 Simon 讀到 AI 採用的中位數是開發者時間的 71%，他覺得很多。Nick 解釋那個 71% 是每週活躍使用者，橫跨他們追蹤的大約 25 萬名開發者。中位數 71%，P90 是 90%。第九十百分位的人幾乎一直在用，除了休假或整天卡在會議裡；就算在會議裡也幾乎在用。對氣泡裡的人，這題甚至不該再談，大家都一直在用。Jellyfish 看得到很寬的一群公司。客戶都知道要做 AI coding、要做 agentic coding。基本的採用障礙對很多公司仍是真的。多數跨過了最基本的安全開通、甚至拿到授權。有些仍只在量人到底有沒有用。若有命令要用，他們是表演性地打卡，還是真的嵌進流程。高度抗拒的人是正在消失的少數，也許登入了、用了，但其實不想用。常見得多的是前面那種。

[19:26](https://www.youtube.com/watch?v=GbHfzFcIa0o&t=1166s) 這 25 萬人是付費客戶的人，公司付錢讓他們追 AI 轉型怎麼對到業務結果。他們做軟體來賣，或軟體是做生意的一部分。也可能是服飾公司，仍有 200 個工程師，因為有營運和數位門面。大約幾十個工程師就會需要 Jellyfish，客戶大到數萬個工程師。他們看不到矽谷裡五個人、昨天剛成立的 AI native 公司。那些人剛開始，還沒撞上這種能見度的問題。他希望他們以後會。開源模型他們看得不多。這些公司買的是大型企業工具和授權：Copilot、Cursor、Claude Code。Cursor 和 Claude Code 占主導，Claude Code 過去六個月如預期地升起。模型經由那些供應商，也用 Bedrock。現在 Amazon Bedrock 上能用 OpenAI 的模型，他期待採用再上去。很多客戶已經用 Bedrock。

[21:56](https://www.youtube.com/watch?v=GbHfzFcIa0o&t=1316s) 使用深度有幾層。最基本是有規律地碰到這些工具，那是門檻。然後是可靠的習慣：一天又一天、一週又一週。他們的一個 benchmark 是每週三次或以上。那種持續、頻繁的使用，才對得上能把持續使用拉高、並看到他說的兩倍生產力的公司。再上一層是自主和 agentic workflow：有多少 PR 是自主生成的。Agent 拿到一份 spec，把工作做完，以很少的人為互動開出 pull request。精英公司，他們看的第九十百分位，上個月跨過 20%，這個月數字還在算，看起來更接近 30%。基本上是指數成長。大約一年前他們說是 2%。中位數的公司最近才剛過 2%，現在大約 2.5% 到 3%。搞懂 agentic development 的人在很多方面跑開了。其他人還在想怎麼讓這些流程可重複、可擴。也許有一個小的試點團隊做得到，但沒有擴到整個組織。這和以前推任何技術很像。

## 四個是人的注意力，不是工具的上限

[24:37](https://www.youtube.com/watch?v=GbHfzFcIa0o&t=1477s) 他稱為 barrier 的東西，是他的團隊觀察到的。同事 Tomas Pardiñas 把這些流程挖得很深。多數人是互動式地跟一到兩個 agent 工作。最有經驗的工程師，只要還得跟這些 agent 有任何互動，就卡在四個，最多。很少人到五個。這和每天用 Claude Code 的人體感一致。人的注意力有限。你只能照顧這麼多 agent，不可避免會忘掉一個。然後才發現，喔，我忘了那件事。你錯過要去點那個終端視窗的通知，也忘了回去。就算四個同時跑，你仍把 80% 的時間放在其中一個。互動性有它的限度。要突破，得進到完全自主：把工作整個交出去。若還得一路推著 agent，事情一停住，總並行就有硬上限。字幕末了有一句 in two minutes，沒有聽成清楚的條件。Simon 說那幾乎是不再由人當 orchestrator，而是讓另一個 agent 做編排，等於把整件事交出去。

[26:18](https://www.youtube.com/watch?v=GbHfzFcIa0o&t=1578s) 這題難答，是因為顯然有技術問題。Agent 介面在進步。很多人也同意，用來管 code、管 agent、檢查發生了什麼的工具是有限的。這個領域的玩家都想發明新的介面、新的開發 IDE。那會是一項一萬億的發明。他也有自己的懷疑。他拆 SDLC 資料時想懂的，是業務和產品結果上的限度。做商業決定有速度上限，從市場拿回饋、讓 go to market 動起來、改變產品，都有。他聽到產品負責人開始在處理使用者疲勞：產品變太快。你甚至沒時間知道這些功能是不是更好，因為人沒時間用，而且愈來愈挫折。所以先有「我們到底能多快做產品」的節流，然後才是「軟體做到多快還說得通」，以及你真正想要多少互動。Simon 說得不斷提醒自己，使用者仍是使用者。有時客戶是技術或 agent，多數時候仍是終端的人。慢一點、互動多一點，可以把我們的判斷放進去，有時更好。

[28:59](https://www.youtube.com/watch?v=GbHfzFcIa0o&t=1739s) 很多客戶在實驗更小的團隊，以及產品的人和建造的人的比例。一個工程師現在能做的比以前多很多。他相信一個好的產品負責人，有使用者和業務的判斷，值他的體重的黃金，或 token，看當下最貴的商品是什麼。他自己坐下來也會問：該先和 agent 腦力激盪、弄清我想要什麼，再整件交出去；還是一路做下去，讓 agent 幫我弄懂我想要什麼。他和很多開發者、創作者一樣：就算以為自己知道要什麼，很快就發現並沒有以任何有意義的方式想透。工程有很多高賭注的決定，架構、灰色地帶的取捨。那才是真正工程和真正產品開發的肉。大家都在弄：多少洞察來自摩擦、探索、把頭去撞；若把太多外包給 agent，因為你不在裡面，那些洞察的機會會不會丟掉。

## CFO 要的是結果，公司卻還在用編制思考

[31:23](https://www.youtube.com/watch?v=GbHfzFcIa0o&t=1883s) 2026 是 CFO 進來的一年。2025 比較是鼓勵什麼都試，因為文化不同，只有自己試才知道什麼適合。現在對花費更謹慎，仍想花在 AI 上，但預算更經思索。Nick 說他們已經在建議：太多工具已經夠好，風險是分析癱瘓，一直找剛好的 agent、剛好的流程。要不要 spec-driven，用 Codex 還是 Claude Code。絕大多數情況，選一匹馬騎上去、把那塊肌肉練好，才是對的。他們看到很多這種。今年的大差別是往擴大規模走。以前有預算、有急迫性去探索。公司要擴的時候，agent 複雜得多、能做的多得多，token 也多得多。模型更壯，回合更多，code exploration 更多，token 消耗暴漲。工程主管感到的張力是：對話裡仍是把 token 用到最大。仍有一種看法，採用和規律使用必須被推動、被支持。用得不夠就到不了。你得燒夠燃料，證明能達到逃逸速度，但你得拿出收據。工程主管還得解釋這些 token 都去了哪，那是很多錢。

[34:34](https://www.youtube.com/watch?v=GbHfzFcIa0o&t=2074s) CFO 說錢花了，要看到效率或生產力、團隊能更快做、更快交。工程經理該交回什麼。Nick 說這真的是一團亂。有好的指標。原始 token 花費是基本訊號，像心跳。有心跳代表你活著，並引出更細的問題：每個 PR、每個上線功能、每個結果花多少 token。那告訴你實際在花什麼。說它是一團亂，是因為企業真正在乎的是營收，是會改變業務軌跡的事。公司一般還沒適應「基本上有無限容量」是什麼意思。我們進入一個世界，你可以花無限的錢讓東西更快被做出來，可以雇無限的機器人承包商。公司不是為無限容量的世界設計的。它們想的是：我們有這些編制，能做這麼多東西，什麼會把業務放到最大。什麼真的要緊，那個回饋迴路還在建。人很難推論槓桿該用在哪裡最大。

[36:35](https://www.youtube.com/watch?v=GbHfzFcIa0o&t=2195s) Simon 總叫團隊看結果，不看產出。資料裡 pull request 合併的兩倍，對他是產出。結果是好的 code、有品質的 code、code 有沒有被修、第二張 PR 是不是在修第一張。怎麼知道我們真的更快、真的比沒有 AI coding 時更好。Nick 說那些對工程機器是重要的結果。很多人擔心品質。現在品質上還沒有巨大的冒煙證據。主因是工程團隊大體上仍是品質的負責任管家，他們不合併壞 code。你看得到合併率的差別。revert 有一些上升，但難分析，因為也看到 fixing forward 在成長。團隊變快之後，也許不開 bug、也不 revert，只是往前再修一版，於是看起來像更多建造，不一定是在修問題。這些仍是工程產出，不一定是業務產出。你是做出了產品，還是只在撥弄工程以外沒人在乎的東西。就算做出新產品，還有 go to market。他說若揮魔杖，明天為 Jellyfish 做出五倍的產品，賣得出五倍嗎。大概不會。得有一種全新的 AI enablement，把 go to market 那隊加速到抓得住那些價值。這就是他說的：我們發明了噴射引擎，仍把它們裝進以前的車。車的其餘部分還沒為這個設計。被大幅加速的那一件，是 code generation。

## 中間的公司沒有專職的人，長跑也不是優點

[39:54](https://www.youtube.com/watch?v=GbHfzFcIa0o&t=2394s) 誰在組織裡推動採用。他看到一種 uncanny valley。小團隊因為小，也因為往往更年輕、codebase 更年輕，公司本身沒有老公司的包袱，動得快是因為小。非常大的公司若有 Simon 說的那種團隊，能做大投資。最成功的是有目的、經過考慮地去賦能。他們懂：要投資工具，要投資 context engineering，最好的訓練你做得到。這不會免費發生。掙扎的是中間：沒有那些團隊，也許連一個 experience 的主管都沒有。那個人當然沒有一整隊能做工具的人。每個團隊自己摸，會非常難。他見過的成功是：放專職資源，讓一個人或幾個人的全職工作就是弄清組織怎麼轉。用錢、訓練、時間做清楚的投資。慢，是為了快。挑一些東西，不要分析癱瘓，也不要焦慮明天一定有新東西讓你剛做的不再最佳。練那些肌肉。歸根是持續學習、持續演變。若組織練不出不斷演變的肌肉，我們會在這台跑步機上好一陣子。它會一直加速，你得一直學新工具、演變你的做法。字幕末了說的是 evolving your alerts。

[42:06](https://www.youtube.com/watch?v=GbHfzFcIa0o&t=2526s) 工程主管今天最大的誤解，是剛講的那件事的反面：以為有銀彈。把工具交給人，它們就會魔法般運作。誤解的一部分是，容易的部分我們已經做了。給了很多人更花俏的 IDE，真的有增益，更花俏的自動完成，幫很多 coding 起步，也有一些訓練。大體上，把 Copilot 或 Cursor 交到開發者手上、然後流程裡其他一切保持原樣，已經有真的增益。要到下一層，到他和 Simon 相信 AI native development 會變成的樣子，那是很大的文化改變、技能改變、架構改變。要搬的石頭大得多，要的投資大得多。回報會很大，他們相信。有些人還沒準備好，那和到目前為止做的有多不一樣。

[43:33](https://www.youtube.com/watch?v=GbHfzFcIa0o&t=2613s) Simon 說幾乎是質疑一切。不要因為過去十年這樣做沒事，就假設那仍是有 AI 時的對的做法。同時也有很多該刻意留下的。AI 有時讓人很容易丟掉典型的最佳做法和良好衛生。Code review、也許沒那麼要緊的 style guide，但流程裡的好做法，很多要留。vibe code 然後丟出去太容易，然後假設這裡沒有安全問題。Nick 說人在做這種靈魂搜索。Jellyfish 內部有過很多人也有過的爭論：兩個人的 code review，我開了請求，得由另一個人批准。我不能批准自己要上 production 的 pull request。若 code 是 agent 寫的，那算另一個人嗎。我能不能審查一個機器人寫的、我從沒讀過的 code。邏輯上有點說得通。Review 正在變成瓶頸。那值不值得兩雙眼睛。他喜歡 Simon 怎麼問我們想抓住什麼。他的一個煩惱，是對 agent coherence、以及 agent 能自己跑多久的執著。他懂為什麼用這個給 agent 評分和做 benchmark，但搬到真實世界：你會不會把團隊裡最好的工程師，定義成進洞裡最久、完全不問你的那個人。我們通常抱怨的是不知道何時該上來喘口氣的人。回饋和溝通是一個運作良好的工程團隊的核心。Agent 的世界裡那長什麼樣。何時是 agent 彼此溝通，何時它們得來跟我們溝通。讓它們自己跑非常久，是一種反模式，是功能失調。

[46:15](https://www.youtube.com/watch?v=GbHfzFcIa0o&t=2775s) 想跟上報告，去 Jellyfish Engineering Trends。他們每月更新 benchmark，有前幾個月的歷史，圍繞採用、影響、品質、工程的成長。每個月加新東西。剛加了 token 的洞察，下一版還會再加。一天的小時不夠，世界上的 token 也不夠，看不完這份資料裡令人興奮的事。片尾說節目由 skills 和 context 的 package manager 帶來，主持人是 Guy Podjarny 和 Simon Maple，製作人 Tom Dowler，並在倫敦市中心的 Tessl 辦公室辦每月聚會。

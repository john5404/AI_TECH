# Adapting your team culture for AI: DevOps Lessons Learned with Hannah Foxwell

AI Native Dev 播客，片長 41 分 40 秒，英文自動字幕。主持人 Simon Maple。來賓 Hannah Foxwell，獨立顧問，範圍是 platform engineering、security 和 AI。這份筆記依英文原稿整理，專有名詞保持 English。字幕把贊助方聽成 Tesela。

- 原片：[YouTube](https://www.youtube.com/watch?v=jGgqYLSLs8Q)

## 一句話

DevOps 是工程師由下而上把自己的房子整理好；AI 不一樣，每個角色都被碰到，CIO 還要昨天就放進每個人口袋。Hannah 的對照不是再講一次工具，而是文化：資深的人一天做完幾個月的事，中間那段學習中的人最難判斷答案對不對，所以要有 mentor 和安全網。速度一上去，瓶頸就不再是寫 code。她要團隊把力氣從 build 挪到 measure 和 learn，否則功能會攤成她稱為 enshittification 的那種腫脹。

## 坐在那堵牆上的人

[0:42](https://www.youtube.com/watch?v=jGgqYLSLs8Q&t=42s) Simon 說他們很久以前一起在 Snyk。Hannah 當時是 container security 的 product director，更早是 VMware 的 director of platform services。她也辦 DevOps Days、是 OpenUK ambassador。空檔不多，她還單手在五個月裡辦了 AI for the rest of us，Simon 他們去年去了、也贊助了，辦得成功，所以今年還得再辦。她本來要 career break，悶了，就決定辦一場 AI 會議。她說自己不擅長坐著不動。做好工作的獎品就是更多工作。

[2:16](https://www.youtube.com/watch?v=jGgqYLSLs8Q&t=136s) DevOps 的起點是她早年當 release manager。大家都講 dev 和 ops 的 silo、那堵 wall of confusion。二十出頭的她就坐在牆上，試著翻譯兩邊聽到的話，拼出大家願意買帳的計畫。運動很早的時候，她把 DevOps 看成自己親身痛過、而且幾乎所有組織都在痛的問題的解法。她沒有答案，但知道問題是真的。若要描述職涯，一直是在建更好的工程團隊、更好的組織：不只一個 dev team，而是軟體開發周圍讓它成功的那些機制。這自然拐去 product leadership，因為做得多好都得做對的東西。仍在開發者工具，仍繞著 developer experience 和生產力，那就是他們在 Snyk 一起工作的地方。

## 工程師先動，老闆這次也在推

[4:58](https://www.youtube.com/watch?v=jGgqYLSLs8Q&t=298s) Simon 說行業正坐在另一次團隊文化改變的邊緣，很多問題和 DevOps 一樣：怎麼在團隊裡正確採用、怎麼改團隊才能把 AI 用在做出的軟體上，也用在團隊自己變好。Hannah 覺得產業做得好的一點，是由下而上、工程驅動的採用。DevOps 非常是工程領導的運動：這是更好的做法。她看到 AI 幾乎一夜之間也是。一两年在科技裡不算長，絕大多數軟體開發者會把 AI 工具放進每天的流程。這是立刻感覺到生成式 AI 好處的角色和產業之一。

[6:01](https://www.youtube.com/watch?v=jGgqYLSLs8Q&t=361s) 差別是 AI 碰到每個角色，不只開發者。DevOps 孵在開發者社群裡，她不覺得很多企業真的很在乎，那只是我們把自己的房子整理好。2012 年，十多年前，她當時公司的 CIO 說：別跟我談 DevOps。每次工程主管或架構師說未來就是 DevOps，他就叫他們停。他看不到投資報酬、看不到商業理由，因為又新又沒被證明。今天 CIO、CTO、CEO 說的是：我要生成式 AI 在每個人口袋裡、每個人的工作裡，我要那個生產力，我昨天就要，去。由上而下的壓力，配上由下而上的工程熱情，這是新的，她覺得很興奮。

[7:14](https://www.youtube.com/watch?v=jGgqYLSLs8Q&t=434s) 懷疑者也像 DevOps。總有對改變的恐懼，腦子裡那個聲音：這對我意味著什麼、我會不會失業、我喜歡的部分會不會消失。不幸的是，選科技這一行，對改變和模糊感到自在，是讓你成功的條件之一。她把問題丟回 Simon：你在悲觀、甚至災難化，和樂觀、甚至把挑戰與限制都刷掉的那種近乎邪教的 hype 之間，站哪。好的版本過幾年就來了。Simon 說自己想當現實主義者。好處相當明顯，叫它做事、它給出答案，今天仍覺得像魔法，也遠不完美。今天仍得用一種輔助的方式用它。未來會更自主，但還有很長的路，談 AI 時得小心一點。他看到很多人很輕率地講自己的 app 或技術能做什麼。他和 Guy 前幾天還在說：demo 和真實世界差很大。任何產品都容易在 demo 裡表現好；日復一日在真實應用上做好，難非常多。他覺得今天仍很像停在 demo，除非工具有人好好照看，信任才能往前堆。

[10:00](https://www.youtube.com/watch?v=jGgqYLSLs8Q&t=600s) Hannah 接的是信任、可靠性。這些工具得用一致性把信任賺來。AI 並不做一致性，那就是重點，它是 non-deterministic。一致性、準確、可靠，其中一個詞或組合才對，但都是在堆信任。一旦證明它好，就能建更自主的系統。她對 AI agents 很興奮，也知道自己會把大家都在談的題目再談得很無聊。若能把大量重複、乏味的工作卸給一個 agent，或一組一起做的 agents，對人有多解放。她在幾萬人的大企業待過，經營那些公司的機制絕對痛苦。她認為那是 AI 會徹底改掉遊戲的地方。

## 一天做完幾個月，以及中間那段人

[11:36](https://www.youtube.com/watch?v=jGgqYLSLs8Q&t=696s) 她先談人。很有經驗的 principal engineer 手上有 AI 工具，因為你確切知道自己在要什麼，知識和自動化一起用，要對的東西、出來的就是對的東西，一天可以做完字面上幾個月的工作。她覺得不可思議。另一端不是 principal，是新進的工程師。這檔節目叫 AI native dev，那些人才會是 AI native dev。今天進軟體開發，學習方式不一樣，工具在手邊，學習旅程會很不同。中間那些 in-betweenies 最難：他們在一條學習路上，原本是一種運作方式，現在得切換。他們不一定有 principal 和 staff engineer 那種深度，能要對的東西，也能有信心判斷給回來的是對的。

[12:48](https://www.youtube.com/watch?v=jGgqYLSLs8Q&t=768s) 不同技能混在一個團隊裡怎麼成功，和今天沒有差很多。你要 senior、principal、staff 去 mentor 不同階段的每個人，讓他們放大影響，而不是只從 backlog 拿任務來做。對還沒有那種深度、不能有信心說工具給的是對答案的工程師，轉換會不舒服。得有 guard rails 和安全網，理想上來自 mentor 那樣的人。Simon 常被剛進產業的人問：今天該學什麼，程式語言還值不值得學。Hannah 說教育很早就要放，但和你本來會做的教育沒有那麼不同，也許是重新框。不是一張白紙、你從頭寫程式，而是面前有一個東西要你回應。要確定它有品質、沒有愚蠢的錯誤、做它該做的事，需要的是同一套知識。Simon 覺得實作的細節會丟掉很多：若能靠 AI 給實作，就要少想實作、多想架構和模式。對 junior 來說，學什麼讓應用變好，會不會比學讓 code 變快更要緊。Hannah 說手上工具已經很多，lint 找結構問題，安全的靜態分析抓明顯問題。他們錄前聊過，自己是在沒有網路的年代長大的。做一個軟體開發者，若你的年紀是這些工具還不在手上的年紀，沿路會不會丟掉什麼、職業會怎麼變，會很有趣。網路已經完全改變了社會。

## 願意實驗的人，以及不要為了用而用

[15:50](https://www.youtube.com/watch?v=jGgqYLSLs8Q&t=950s) 怎麼讓團隊更懂 AI、買帳，又避開慣性。她總回到那個簡單迴圈：build, measure, learn。做一個假設、測它、量影響、學習、再改。Agile、DevOps、platform engineering 都能這樣談，因為那是把使用者體驗和產品管理用到內部工具上。這完全可以搬到給開發者的 AI 工具。要留空間實驗，也要允許學習的結論是：那是錯的路，別再做。一切變得太快。很難回頭記得 15 年前、10 年前自己在想什麼，因為沒有後見之明，也有 confirmation bias。她認為 DevOps、cloud native、cloud engineering 裡真正領先的團隊，是願意試不一樣的、扔掉舊做法、孵新做法、量成功、從中學的人。他們接受第一次不對、手上沒有答案。她不管自己是樂觀還是悲觀，她是來坐這趟雲霄飛車的，有上有下，但會很好玩。若能回到 DevOps 的十年前，她會更公開地講自己在做什麼、學到什麼。當時有一點冒牌者的感覺：若沒有別人這樣做，也許我錯了。其實大家都在發明、都在實驗，分享所學，大家才會更好。現在就是那個混亂的實驗孵化期，沒有正確答案。

[18:45](https://www.youtube.com/watch?v=jGgqYLSLs8Q&t=1125s) Simon 補：若能量到並分享，以前要這麼久，現在用少很多力氣、還能和其他工作非同步，只要這麼久，懷疑的人就不只看到時間。拿掉人不想做的工作，給他們更有趣的事，也是一個區域。DevSecOps 裡他喜歡看到的是 security champion 這種小組：靠近出血邊緣的人先學，再分享給其他團隊，不必每個人同時絆到同一道障礙。Hannah 說 communities of practice 很好，內部的 champion 和 advocate 也很好。把人聚起來要一點力氣，因為大家都忙。ChatGPT 出來後的第一年，她幾乎沒碰。她戴著眼罩：有很多工作、很重要的工作，沒時間抬頭看。很多人仍是這樣，或實驗還沒到能影響每天生活的程度，只刮了表面。也許它對你幻覺過一次，你就少了一點信心。也許你還沒花時間學怎麼寫好的、有結構的 prompt。Hackathon 大舉回來了。幫人學的最好做法之一，是低壓力、不要綁交付、實驗、好玩、社交，人就會參與、就會試。她真心覺得 hackathon 回來，是因為它很有效：在沒有壓力、不怕失敗的環境裡讓人撿起新工具。

[21:17](https://www.youtube.com/watch?v=jGgqYLSLs8Q&t=1277s) Simon 看到一則貼文，也許在 Bluesky：用 AI 之前，先想能不能用 AI 之前的一般寫法做。他覺得用詞也許不好，意思該是：若傳統程式設計有更好的做法，就不要為了用 AI 而用 AI。人會不會因為被推得太狠，反而得到更差的工作方式。Hannah 說有很多 LLM washing。不知道問題是什麼，答案就是用一個 LLM。它是革命性的技術，因為你用自然語言跟它互動，很多以前寫不了 code 的人碰得到。流程自動化工具還在，如果這樣就那樣，你想畫一張流程圖，蓋住所有輸入情境，把每種輸出的排列都寫得很徹底，技術上做得到。或者把那個流程丟給 LLM，告訴它到沒到對的答案，很快就有一個能動的原型。她完全看得出為什麼這麼誘人。它不是決定性的。若流程必須可預測、必須特定，也許不適合。但支援台、客服中心那種輸入不可預測的地方，它可以很好。你也可以說我仍要很特定的輸出，但需要這一層過濾，把輸入整理進桶子。如果這樣就那樣的程式，不會像 LLM 那樣什麼都試著接。它們很會試。

[23:43](https://www.youtube.com/watch?v=jGgqYLSLs8Q&t=1423s) Simon 說我們自己也得改，承認它以非決定性的方式出錯。早前節目裡 Caleb Seaman 談過：讓 LLM 告訴你 code 裡有多少漏洞，跑五次它說有一個，第五次說沒有。我們習慣的是決定性的：這段 code 有漏洞或沒有。得更在意 LLM 輸出的限制，並在工作方式裡處理它。

## 鋪好的路、蔓延，以及什麼不能餵進去

[24:28](https://www.youtube.com/watch?v=jGgqYLSLs8Q&t=1468s) Platform engineering、DevOps 這類角色，很大程度是每個人什麼都自己做之後，才出現一條 paved road。可以偏離，但偏離就要自己撐；這些團隊幫的是那條鋪好的路。對到 AI，是 AI engineer 加入同一批團隊，還是開發者像當年 DevOps 那樣自己扛起來。Hannah 同意有兩種使用者。技術使用者這邊，platform engineering 提供共享平台，人能用、能接、能把應用的一部分、流程的一部分插進去。這個模式絕對會演進。後端是自己架開源 LLM，像 Llama 或 Mistral，還是接到 Microsoft 或 Google 代管的 API，其實沒那麼要緊，因為使用者介面是你在內部提供的入口。另一面會蔓延的，是會寫 prompt 的業務使用者。他們不在工程裡。很多新創對著某個垂直、那個使用者解決問題，而且提供整疊。她認為會有很多 shadow IT：為企業裡某個角色量身的 AI 工具。那遠遠在 platform engineering 外面，也許是 SaaS，也許你每天用的工具，引擎蓋下是不是 AI 你甚至不知道。就像很難搞懂 software bill of materials，搞懂整個 AI 版圖、各工具和平台、各角色和業務流程上的蔓延，會非常難。已經在發生。你得決定什麼可以、什麼不行，放上 guard rails。更重要的是教育團隊，在這個組織裡什麼可以、什麼不行。例如不要把客戶資訊餵進某個 SaaS 的免費層，因為他們大概拿免費層使用者當訓練資料。反正也不該把客戶的個人可識別資訊交給任何第三方。這是很大的教育。若這些工具能讓人把工作做得好那麼多，不把它們交到人手上是不行的。但你得看得到組合裡有哪些工具。這已經偏離開發者工具：platform engineering 對工程領域的能見度，也許高過對業務領域正在發生的事。安全的人大概正在跳腳、快要失去理智，也在想怎麼降低這些風險。

[28:14](https://www.youtube.com/watch?v=jGgqYLSLs8Q&t=1694s) Simon 收成兩點。這比 DevOps 寬：DevOps 是幫軟體交付和開發，重重坐在工程和維運裡。AI 的影響和好處跨過整個組織。第二是能做什麼、不該做什麼，公司的 guard rails 限制你能餵給模型什麼。一走出工程和更技術的空間，人就失去對 LLM 引擎蓋下在發生什麼的那種機械同情，可能不小心餵太多、餵了業務敏感資訊、洩了公司資料。這還在「最好的做法是什麼」之前，先是我們能不能做。Hannah 說這是 day zero。她一直在很複雜的企業裡工作，真正難的挑戰在那裡。有些團隊不能用 SaaS，受管制、資料很敏感，也許是銀行、電信，他們走自架，非常以平台為中心。她正在合作的其中一家叫 Helix，在做一種私有 AI stack，使命是讓這些公司在自己的硬體上，得到接近 SaaS 或 IaaS 的體驗。他們不能為了那些事去找 Google、Microsoft 或 OpenAI。她在想的是，這也許是 and 而不是 or。不是向左或向右。每個企業都有非常敏感的資訊。是不是每個企業都得為某些流程支撐自己的私有生成式 AI stack，然後較不敏感、較日常、也許更有創造性的，例如行銷，再用一些 SaaS，那才是對的答案。要留意組織裡 AI 方案的版圖長什麼樣。走在它前面，決定你需要什麼、不需要什麼，而不是讓它有機蔓延、新方案到處冒出來。

[31:09](https://www.youtube.com/watch?v=jGgqYLSLs8Q&t=1869s) Simon 再拉回安全 champion。他以前常聽到同一個問題：公司想要一個 champion 計畫，教育每個部門的安全衛生；另外還有一群人只盯開發，從漏洞到資料放哪。該不該是同一群人。試著做成同一群的，常常對每個人都變得較不相關。行銷的人聽到怎麼用第三方函式庫，根本不知道那是什麼。反過來，開發的人聽極高階、他們已經很懂的東西，會覺得尷尬或無聊。AI 的教育會不會也要拆開：一套給整個組織，一套很特定，幾乎是分開的教育計畫，也許也像平台團隊那樣分開。Hannah 說一定會。她想到的例子是，每個人都上實體安全訓練，硬體該做什麼不該做什麼，那是共同的；然後她可以想像依角色的賦能：我們這裡用的這套 AI 工具，以及我們找出來的、讓你把你的工作做到最好的做法。不是每個工作，是你的工作。技術團隊和非技術團隊會根本不同。這是投資，而且很難投。她坐在這裡說我們不知道未來長什麼樣，每五分鐘都在變，很興奮。你可能花六個月做一套訓練，一推出就過時。她覺得像 Simon 說的，更有機、會演變的東西，community of practice 或 champion 計畫，現在可能才對。等一些做法變硬，弄清什麼對我們有用、什麼沒用，也許再放進新員工的 onboarding，也許再做更正式的訓練。她不確定。她很想聽正在聽的人，大組織實際怎麼處理。她知道自己會怎麼想，但她沒有在真實世界裡做這件事。

## 寫 code 不再是瓶頸

[34:16](https://www.youtube.com/watch?v=jGgqYLSLs8Q&t=2056s) 若聽眾是團隊裡的開發者，在想一兩年後工作會怎麼變。兩人都同意 AI 當然不是把開發工作拿掉。最大的改變會是什麼。她說這是個值很多錢的問題，然後講她怎麼想。她活過從瀑布到 Agile：發布曾經是每六個月、每三個月，很僵。她經歷那時，壓力加到維運團隊身上，直到他們變成瓶頸，應付不了開發團隊多出來的速度。然後 DevOps 來了，還有雲，因為基礎設施是隨需的，不必提前幾個月訂。速度再上去，維運的規則書得整個改。工作變得更關於自動化、自我修復、resilience engineering。現在是 AI。

[35:38](https://www.youtube.com/watch?v=jGgqYLSLs8Q&t=2138s) 所以，寫 code 的那一段。我們一直把工程團隊最佳化成：盡量有專注時間在寫 code。她當 engineering manager 時的任務就是這樣：不要讓團隊分心，要他們盯著任務。若那不再是瓶頸呢。不是寫 code 的時間。寫 code 是容易的部分。她認為你要再往流程上游看，看產品，看需要哪些產品管理做法，才能讓 build, measure, learn 盡量有效率。若一天就能做出原型，然後呢。是直接送給所有使用者，還是得真的變得很會做 A/B testing。她知道很多公司並不會。你得更會測假設，更會做 progressive delivery，把功能推給使用者群的一小群，真的測你在做對的東西。她認為開發速度再階梯式上升，很多地方會鼓勵功能蔓延。想得到的功能都做出來，每個產品走過她稱為 enshittification 的過程：功能腫到它變成另一個產品，變得不能用。她感興趣的是怎麼把那個迴圈調好，把 measure 和 learn 做得比現在好很多。她做軟體開發很久，連她自己都把 measure 和 learn 做得非常糟，因為絕大多數時間在 build。那是瓶頸。你把精力放在 build，做完就沉進下一個 build。

[37:46](https://www.youtube.com/watch?v=jGgqYLSLs8Q&t=2266s) Simon 喜歡這個看法：預見下一個瓶頸。這一輪會把一個瓶頸拿掉、加速到我們被下一個絆住。我們看一堆可以做的功能時，從來沒想過若全部都能做會怎樣。不該全部做。能力愈大責任愈大。因為我們能，不表示我們該。有些做法沒有你想的那麼普遍：勤奮的 A/B testing、量成功、使用者回饋。有多少人在把新功能推進 production 之前，做過一輪使用者回饋。以他的經驗，大家都在執行模式。做東西是焦點，我們只能做這麼多，然後 confirmation bias 說你一定做對了，於是出貨、行銷，然後非常驚訝沒人用。於是我們離開「不必排優先順序，因為只有時間做這麼多件」的位置，改成依人的需要來排。有些人今天就幸運到兩邊都能做，因為團隊大。未來已經在這裡，只是沒有均勻分布。有些團隊必須看這個，他們已有很資料驅動的決策。若她要下注，她會說很多團隊和她類似：build, measure, learn 裡，build 吃掉大部分時間和精力，因為瓶頸目前在那裡。Simon 認為開發者多想這一點是非常好的事。焦點不該在 build，該更圍繞使用者需要、使用者想用這個做什麼，做出為開發者設計的工具和應用，而不是在怎麼設計、怎麼建造這件事上轉太深，卻不夠看體驗。移向那個、並且做進 measure 和 learn 的移動，很多組織非常需要、也非常有價值。

[40:20](https://www.youtube.com/watch?v=jGgqYLSLs8Q&t=2420s) Hannah 把它拉回開場。DevOps 的教訓之一：轉型十五年、這個社群建起來之後，我們在談什麼。Developer experience。使用者體驗。讓做對的事變容易。這是一堂會一直忘掉、再重新學的課：使用者體驗高於一切。Simon 把迴圈再念一次：build, measure, learn。

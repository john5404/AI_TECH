# Crossover episode with The Infra Pod - AI Native Development with Guy Podjarny

片長約 56 分鐘，英文自動字幕。Simon Maple 把 The Infra Pod 的一集引進來。主持是 Essence VC 的 Tim Chen，以及 Ian Livingstone，字幕把姓聽成 Livingston。客人是 Guy Podjarny，Tessl 的 founder 和 CEO，先前創了 Snyk，更早創了 Blaze 並賣給 Akamai、在那裡當過 CTO。字幕把 Tessl 聽成 tessle、Tesla，把 Snyk 聽成 sneak。這份筆記依英文原稿整理，專有名詞保持英文。

## 一句話

Guy 離開 Snyk 去創 Tessl，不是因為實用，是因為滿足來自可能失敗的掙扎，而且他在想 Snyk 的 AI 策略時，對軟體開發要去哪裡形成了一張圖。他用一張兩軸的圖放公司：你得改變多少工作方式，以及你得信任它多少。左下角是自動完成，很容易採用，也很容易被取代。右上角要同時改變做法、又信任它，今天沒人會用，但每間公司都該知道自己的右上角是什麼。他認為開發的右上角是 spec-centric：人規定要什麼，AI 做實作，維護因此可以自主。

## 第三次創業，因為滿足來自掙扎

[0:50](https://www.youtube.com/watch?v=SsOaOVPwW5I&t=50s) Tim 問，Snyk 成功之後，為什麼還要從零再進壕溝。Guy 說決定不容易。個人面上，他在 Snyk 最後一年多比較兼職，在想自己在公司做什麼。他創立時是 CEO，大約五年後請 Peter McKay 進來，他說 Peter 做得很好，自己轉去產品策略。興奮過一段之後，他覺得要重新評估角色。一邊是家庭的慈善，要不要全職做；天使投資要不要全職；或在一家相信的公司做舒服的兼職，然後去宣傳。他抗拒「再創一間」這個結論，因為從實用看說不通。他們仍會把在 Snyk 還有的資金捐出去，他需要的門路都有。花了一陣子才接受：可以做，因為那是他想做的。滿足來自掙扎。要那種意義，就得把自己放進可能失敗的事。天使投資學到很多，但你不擁有、不在壕溝裡，不一樣。

[3:57](https://www.youtube.com/watch?v=SsOaOVPwW5I&t=237s) 同時他在看 Snyk 的 AI 策略。Snyk 保護的是軟體開發，要判斷 Snyk 該對 AI 做什麼，就得假設軟體開發往哪走。圖在腦子裡愈清楚，他愈想自己去建。那個領域對上他的技能和熱情，又不和 Snyk 競爭。他太太大概早他一兩個月就知道。他想再談，她笑說你講吧，反正就是往那裡去。

[4:49](https://www.youtube.com/watch?v=SsOaOVPwW5I&t=289s) 驅動他的是衝擊，是在宇宙上留下一個凹痕，不是錢或產品本身。他覺得 Snyk 那份使命的核心已經做到很多：把安全嵌進開發、讓它成為好做法的常態。生意還有很多要建，但那個核心他覺得達成了。有人跟他說，創辦人是循序學，投資人是平行學。他覺得看你涉入多深。對他，兩者合起來很有用，練出模式辨認。他投 AI 開發工具時看到兩件事。人很短視。AI 裡有太多立刻能改善的機會，人被拉向當下。新創也不夠有差異。兩家公司在做的其實一樣，卻以為自己會有 data moat。你在打既有者，也許做了一年、七個或七十個客戶，對方有七萬個，你怎麼會有 data moat。暫時有差異，策略仍是短的。大家都想得小。想得大的那些，是技術優先，不是產品優先。AI 開發裡要做大的名字，他點 Magic、Cognition、Poolside。他說這些是很棒的公司和人，但他的感覺是他們先做驚人的技術，再從那裡長出產品。他自己是產品的人：需要什麼產品、使用者怎麼變、生態系和市場怎麼變，技術是為產品服務。他覺得缺的是長期、想得大、產品優先，以及夠強的差異。他心裡的圖對這幾樣都有答案。不是全部能在 podcast 上說，有些策略還在家裡。沒有那個，他認為現在創一間 AI 公司，其實比一般創業更險：一切在變，地面在腳下移動，而且過度有資金。

## 兩條軸：你要改多少，以及你要信多少

[8:52](https://www.youtube.com/watch?v=SsOaOVPwW5I&t=532s) Tim 讀過他兩篇長文，一張 2 by 2，Tessl 在很右邊、幾乎沒有別人的那個新類別。Guy 說那張圖的標題是 charting your AI native journey。AI native 這個敘事他釀了快兩年：看投資、想點子，然後是 Tessl，當然也有 Snyk。外面很多 AI 方案，有的短、有的長，在兩個感覺之間晃：這不就是 OpenAI 或 Anthropic 的下一個功能，或這是科幻、永遠不會動。圖是給公司、或至少給它們現在的產品一個位置。一軸是改變：這個工具要我改多少工作方式。一軸是信任，從 attended 到 autonomous：它要做對到什麼程度才有用。

[11:25](https://www.youtube.com/watch?v=SsOaOVPwW5I&t=685s) 左下是低改變、低信任。開發裡是 code completion。你本來就在打字，也習慣 IntelliSense 那種自動完成，這只是更好的自動完成。你眼睛看過，對就繼續。別的領域也許是在 X 光上指出可能的問題，或寫一封很短的 SDR 開發信。都是你已經在做的小單位。有用就該用，沒用、沒有業務價值就仍一文不值。這是他看到採用最高的一格，也競爭最烈。一個 coding assistant 為什麼比另一個好，會有非常多個。幫你生測試、抓文件，常常很難不同，因為它們沒有發明新方法，只是在小單位裡做腿的工作，讓你審查。

[12:50](https://www.youtube.com/watch?v=SsOaOVPwW5I&t=770s) 往信任那軸走，是 IP 的演化，從有人看著到自主。Intercom 的 Fin 要自己解決進來的票。若每句回覆都要人確認沒有幻覺，產品就沒用。你得信任它做對，它才有用。更極端是 robotaxi。改變很少：你還是跟客服聊天那樣互動；在車上，你打開 Uber、叫車、上車、在別處下車。需要的信任很高。開發世界裡，這是自主開發，他認為還沒被破解。Magic 和其他公司，至少從對外的說法，是在試著破解：我來替你解決。信任裡還有任務的規模。寫下一行，你可以每行看。寫整個應用，你不能每次都看。要有用，你得信任它能動。很多被叫做 AI engineer、agent engineer 的東西，他說這些詞已經超載，其實是在信任軸上往上，因為它們想更自主地做事。這是 IP 的遊戲。你在那裡建公司，是因為相信有很難複製的 IP moat。兩年前，人還可能覺得可以真的領先。現在每次有人領先，只是領先三個月或六個月。他聽 Cursor 在 Lex Fridman 的 podcast 上說，字幕把名字聽成 Lex Freedom：他們只需要領先幾個月，那就可以很顯著。那是他們的策略。他仍嚮往領先，但覺得那很難當成策略。

[16:10](https://www.youtube.com/watch?v=SsOaOVPwW5I&t=970s) 改變那條路更難。最好的比喻是文字到影片、文字到圖。他投資了 Synthesia，做訓練這類的 text to video，是這個空間的領先者之一。在 Synthesia 裡做影片，和以前完全不同：搭棚、找演員、拍攝，和寫那段文字沒有共同點。誰能成功操作、需要什麼技能、業務裡的 workflow 是什麼，都劇烈改變。AI 生成影片的贏家，幾乎不可能是今天真人製作影片的那些公司。難的是你什麼時候開始用、怎麼用。Synthesia 找到一個具體的切片：訓練影片本來就很有方法，還有不同語言。走到 Runway 或更鬆的生成，就有全新的問題。角色不一致：突然是另一個人。拍真的影片時，你不會遇到演員的分身突然出現、很像但不是同一個人。新問題、新 workflow。若你真的做出更好的新方式，文字到影片若成功，會戲劇性地更便宜、更快，就能解開很大的價值、贏下那個空間。那是顛覆的角落，可以重想一個產業。慢下來的因素不只是信任，是改變。人改變得很慢。他認為你發展 IP 可以快過讓人改變。拉回開發：大家立刻懂 code completion，但對用聊天來生成，意見衝突，有時敵意。那是新方法。我怎麼談我的文件、怎麼跟它工作。採用更久，也許更好，也許不是。v0 或用這種方式把應用 bootstrap 起來，也是不同的做法。它把你帶到某處，但是不是對的起點。設計師有的意見很兇，有的愛上它。

[19:22](https://www.youtube.com/watch?v=SsOaOVPwW5I&t=1162s) 右上角是兩者相加：新的做法，又假設信任。現在若只為右上角做，沒人會用。你同時要求人改變和信任，不會發生。但每間公司最後都該知道自己的右上角在哪。要建公司、買公司、進任何領域，都得有一個論點：右上角是什麼。因為我們最後會到那裡：技術被信任，有用的改變也被採用了。AI native 是先想像右上角，然後有很多條路走過去。得先在方向上同意右上角是什麼，而且那是活的對話，很多人參與、去試，才形成目的地。若你只為左下角建，也許立刻有一些錢，公司會變得無效或無關。

## 自駕車有兩條路；軟體可以讓旅程本身快一百倍

[20:38](https://www.youtube.com/watch?v=SsOaOVPwW5I&t=1238s) Ian 用自駕比。輔助駕駛、cruise control 像 co-pilot。他的 Subaru 把手放在方向盤上，車會自己開，人還在。完全自駕像 Tesla，你可以做別的事。未來是 robotaxi。他去過 Waymo，字幕作 weo，覺得不可思議。他問 AI native 的開發會不會像 Waymo 版的軟體開發。今天的例子是 co-pilot、自動完成、或聊天，開發者在 IDE 裡的工作方式變了，他說看過 50% 的加速。那 native 的未來長什麼樣：從眼睛盯著里程表和前車，到計程車載著你。

[21:40](https://www.youtube.com/watch?v=SsOaOVPwW5I&t=1300s) Guy 說自駕裡兩家大公司走不同的路，很有意思。Waymo 走 IP：沒有 co-pilot，直接跳進自駕，畢業的方式是距離或城市。Tesla 走輔助駕駛，把功能往前演進。時間會告訴我們哪個更好，也許都可行，但非常不同。軟體的比喻有點難，因為自駕有物理限制。你不能真的讓自駕車快十倍。你可以在很多方面變好，時間久了想像一個好一百倍的現實：不再有停車場，城市把空間收回來，意外更少，擁有車子不再是問題，因為大家都在重用這些車。駕駛體驗本身比較短。軟體開發的機會更好：從 A 到 B 可以快 100 倍，生態系和整體還可以再乘一個因子。

[23:04](https://www.youtube.com/watch?v=SsOaOVPwW5I&t=1384s) 他說這是社群的定義，新範式要一起做。順帶一提他們在辦、也在出資營運一場會，很多鮮明的意見。他認為這集會在播出那週稍晚、11 月 21 日，叫 AI Native DevCon。他的定義：今天的開發非常 code-centric。拿到需求，寫 code，很快在 code 裡做一百個決定，那些決定去不了別處，或解析度太低，懶得拿出去。Code 把要做什麼和怎麼做纏在同一行。你讀 code，得把做什麼和怎麼做拆開。試圖學 code 的 LLM 也得做同一件事。他相信會走向 spec-centric：兩者分開。使用者規定要什麼，這不是小事；AI 處理實作。

[24:17](https://www.youtube.com/watch?v=SsOaOVPwW5I&t=1457s) 那個世界裡很多事會戲劇性地變好。AI native 的軟體會被自主維護。維護的定義是改軟體、不改 spec：行為一樣，但換作業系統、換依賴、修漏洞。若你錨在 spec 上，又有好的驗證知道軟體運作正確，就不必再維護。維護是生產力的殺手，光這一件就極有價值。它也戲劇性地更可及，因為能規定自己要什麼、能當裁判、甚至有時能想架構、但寫不了 code 的人多很多。它也能適應你的環境：在 Ian 的基礎設施上為那個最佳化，在 Tim 的上為他們的環境最佳化；從你的使用者怎麼用、你的業務需要學習。你現金很多、要最好的體驗、要最佳化延遲，或你更擔心成本；一天裡不同時間、不同使用者要不同的東西。極端的適應、個人化、自動化都可以在。它和資料可以有深的關係。他讀過一個他不確定是否站得住、但符合他想法的統計：軟體若把每一面都擠乾、最佳化，一般認為可以快 10,000 倍，但那很貴，因為人的時間貴。若和 AI 綁在一起，也許就不是。

[26:05](https://www.youtube.com/watch?v=SsOaOVPwW5I&t=1565s) 他們的信念是：能規定你要什麼，能提供並演進驗證、好信任軟體依你要的方式運作，然後想它隨時間怎麼運作。怎麼寫規格、怎麼寫驗證、怎麼改未來的版本、怎麼打包、怎麼做版本。這與語言無關。可以有 JavaScript 版和 Python 版，它們是不是同一個版本，某個語言的生態系變了，算不算兩邊都是新版本。這樣的系統怎麼觀察、怎麼知道發生了什麼。這些需要不同的 software factory、不同的開發範式、不同的開發平台。他認為他們不會是想出答案的人，也不會只有一個答案。軟體和世界很複雜。驗證手機遊戲、電商網站、內部自用的應用，方式可以很不同。也不是一個時間點。也許某個魔法世界裡，各種組織 context 的做法都被想完了，但新技術會來，有意見，有多種做法。所以 AI native 是一套方法，像 DevOps、像 CI/CD：有反覆出現的主題，有跨生態系的做法，也有很多工具接在一起。所以要有一個開發者運動。他們辦會、想扶起社群，是在問開發的右上角是什麼。公司這一側是：那個開發平台長什麼樣。怎麼寫那些 specs、怎麼推進、沿路怎麼接工具。產品得能用，不能只依賴別的東西才有用。怎麼讓它促成別人參與，而不是把人排除。

## 機器會補規格，而且規格不會只有一種

[28:45](https://www.youtube.com/watch?v=SsOaOVPwW5I&t=1725s) Tim 說，一旦能完全信任這輛車把你從一點載到另一點，整套生活規則都會變。最大的挑戰是 spec：創造、維護、迭代，以及團隊圍繞 spec 的動態。我們從 test driven development 這種小的範式移動走來，沒有一個覆蓋得夠、跟得上變化和複雜度。很難想像有一份 spec 能照顧一切。Guy 同意，很難想像。他還加一件：怎麼讓寫 spec 是有趣的。若過程很痛苦，也許能用，但沒趣就沒人做。所以它得有力，也得讓創造它是有趣的，或有一個讓創造變有趣的過程。

[30:57](https://www.youtube.com/watch?v=SsOaOVPwW5I&t=1857s) 他認為會走向 spec-centric 有兩個原因。比較明顯的是機器現在會寫 code。一樣重要、也許更重要的是機器會把 spec 補完。你跟 LLM 說做一個 tic-tac-toe，那就是一份 spec，而且是很糟的 spec。它仍是 spec，因為 LLM 能補缺口：網頁還是手機、要不要守規則、規則是什麼、多人還是對機器。聰明的系統還會跟你互動，知道何時問：你要網頁還是手機。無論如何，它能弄清該問哪些問題、怎麼把 spec 補完。他認為這是巨大的解鎖，打破今天的模子。今天一邊是正式規格，寫起來是噩夢，只在最嚴苛的條件說得通，他舉的是字幕聽成 deep device 的那種裝置，以及航太。即使那裡也很有限、很痛。從經驗看，你寧可直接寫 code。另一邊是 no-code，像玩具：很聰明的設定，活動和點子都預先做好了，你只是選怎麼組織、哪些流程要跑。一直很有限。它們演進之後會變成 code，例如 Salesforce 的 Apex。補缺口的能力，是 LLM 帶來的解鎖，和寫 code 的能力一樣重要，也許更重要。系統把缺口補對的能力，會是這類平台的強項之一。

[32:38](https://www.youtube.com/watch?v=SsOaOVPwW5I&t=1958s) 行銷代理已經為你做過五個網站，第六個你只要很小的 spec，因為他們熟你、熟這個領域，補缺口補得好。同一個人，你要他做手機遊戲，可能得給很細的規格。從未合作過的低價代理，做同一個行銷網站，你也可能得給很細的規格。第二，他不認為有「一份」spec，會有很多份。手機遊戲、軟體函式庫、行銷網站，規定的方式大概很不同。有共同特徵。更視覺的，也許需要更視覺的東西。很演算法的，也許要能把那些提供進去。這又回到運動、範式、生態系。今天沒有一種語言、一種開發環境。方法依強項和弱點不同：更重迭代，還是更重安全。AI 時代不會改變這一點。一切變快，你仍要選取捨，仍需要能適應新技術、新偏好、產業偏好的平台。驗證是 spec 的一個子集。手機遊戲、演算法交易、行銷網站，驗證方式不同。他沒有完美答案。能陳述出來很重要。TDD 有幫助，mocks 有幫助，我們一直在建的歷史有幫助。字幕把 TDD 聽成 tdda。也不必全部事先寫完。有一個從資料學習的成分：系統先夠好、你跟它的互動夠好，然後它用資料學習、演進、變好。例如你說要一顆按鈕，LLM 決定它是紅的。你也許不在乎紅或藍。下一版你改了標題，你可能不能接受按鈕從紅變藍。於是你可能想看見 LLM 的決定、那些決定是否持續、它們是否快要變。這些是他們認為需要不同 software factory 的原因。不是今天一般工具裡的問題，不是 git 裡多一個檔，不是建置裡多一個測試。是不同種類的互動。

[35:54](https://www.youtube.com/watch?v=SsOaOVPwW5I&t=2154s) Ian 用雲的那一波比，大約 2010 到 2020，大家協作的執行期作業系統，雲變成 Kubernetes，那是社群的核心，大家圍繞 GitHub 和某種 CI/CD 貢獻。他問 spec 是社群的東西，還是公司專有。哪些是像敏捷宣言那樣、從瀑布轉到敏捷的方法，哪些是要在開源裡協作的軟體。Guy 說是很多東西的組合。Spec 不是單一標準，會有多個。有些會是公司專有、比較封閉，也許 SAP 有自己的規格方法，和他們的系統有關。Specs 也許會隨時間組合、接上不同格式。有些會是標準，有些不會，有些希望自己是標準。社群協作其實比 Ian 說的更大。我們也許停在 Kubernetes，在那之前也許先停在容器。還有 microservices、mesh、它們怎麼互動、API 標準怎麼溝通、軟體授權、東西放不放上雲、存取權限和 IAM、Bastion hosts。他想雲的時候，不只想 infrastructure as a service，還想 CI/CD、microservices、DevOps，以及我們開發軟體的整套方式，那已經劇烈改變。

## 信任軸利於既有者，改變軸仍留給顛覆者

[48:01](https://www.youtube.com/watch?v=SsOaOVPwW5I&t=2881s) 他相信要讓更多人用這種方式生產軟體。這是新範式，很大。他相信得把產品送出去，讓使用者有機會告訴你它很爛，你再問為什麼、修、演進。新的開發範式和平台，連那個 MVP 都要一陣子才建得出來。他們一開始要建的仍是那個 MVP。若這有趣、想參與軟體開發的未來、想在裡面有聲音，就加入社群、去了解、分享意見。若想試他認為會是這個領域裡第一個、也希望是關鍵工具之一的東西，就加入等候名單。期待是要早期採用者。會有讓你覺得哇的地方，也會有讓你說這很爛的地方。他希望人不是只抱怨、或關掉瀏覽器就走，而是告訴他們這很爛，一起修。Ian 說自己等了快一年。

[49:06](https://www.youtube.com/watch?v=SsOaOVPwW5I&t=2946s) Tim 問這波是創造性破壞、長出很多新公司，還是變成既有者的持久優勢。Guy 說信任軸比較利於既有者。根本是在建 IP，要有資料才能把那個 IP 最佳化。你可以在那裡贏，但若談的是左下角、或沿著信任軸往上，他認為最好把它想成收購。你只是跑得比大公司快，因為它們仍更大，你試著對它們友善，它們可能買你，數字很大。對找公司的人這是正當策略。對他這個創過 Snyk、要做大東西的人，沒那麼有趣。他第一間新創不完全是故意的，但結果不錯，把他放到能開始 Snyk 的位置。改變那條路仍對顛覆者有利。人創公司最常見的錯，是想得不夠長。這個空間動得很快。你得有一點反常識、有點難以相信的看法。若你講故事時每個人都點頭，就缺了什麼，你想得不夠遠。既有的動態仍在：既有玩家控制既有 workflow，盡量維持愈久愈符合他們的利益，公司的一切都接線去維持它。有些會跳出創新者的兩難，那種反定位，大多數不會。那些是該追的機會，更可怕、更難。他仍說現在在 AI 裡創公司，風險比典型更高。他認為真正可行的路只有兩條：建一間跑贏大公司、計畫被收購的公司；或建一點野的、走得更遠的東西。他現在做天使投資，會算信心的跳躍。要十個跳躍才知道投不投，是問題；一個都沒有，也是問題，表示這裡有什麼太明顯。在 AI 的世界，那大概意味著有一百家資金還算夠的公司，你没聽過，因為太小，時間還不夠讓任何一家變成玩家。但資金在、聰明人在、注意力很多，會有更多公司。所以你得有一點野、一點反常識，而且你真的相信，不是只編一個怪故事。你要把時間投進去，才值得。

[52:47](https://www.youtube.com/watch?v=SsOaOVPwW5I&t=3167s) 他給創辦人的另一句常說的話：沒有人在乎你的產品，他們在乎你為他們解決的問題。在 AI 的世界，要想那些會隨時間變大的問題，真的問題。很多人找的是今天 AI 生態系裡的問題。那些是高執行的模式，很多人看得出是問題，也許會被平台解決，也許是鏟子和鶴嘴鋤。要贏就是執行的遊戲。有趣的是去想：法律審查若因為 AI 變得非常常見、或容易得多，司法系統會不會垮，那我該不該為法官做點什麼；或製藥裡會發生什麼。從你的空間看：懂生態系、懂痛、盡力預期痛會怎麼演變，再去弄清。這裡仍有很多信心的跳躍。你得有信念，也得能說服人，然後才可能建一間能持續、長期有差異的公司。

[54:02](https://www.youtube.com/watch?v=SsOaOVPwW5I&t=3242s) 公司是 tessl.io。也可以去 AI native dev。他喜歡 .io，覺得它代表 development。他們買了網域，重點不是 AI，是開發，所以路由到那裡。個人是 Guy Podjarny。姓夠少見，Twitter 和 LinkedIn 找得到，他大概在 LinkedIn 最活躍。也有電子報。到網站可以訂電子報、參加那場會、或登記等候名單。他還沒真的找到有人覺得這段對話無趣：你可以相信、可以不相信、可以覺得路不對。

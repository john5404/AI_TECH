## 一句話

AI 測試生成不是只幫你寫幾行 unit test。軟體的輸入輸出多半是人對人，規格常常模糊，所以難的是先用自然語言講清要測什麼。生成那十行測試是挑戰，但描述意圖更難。回歸測試可以把既有 code 當 source of truth；新功能的 source of truth 是自然語言。信任不是一個信心分數。你要看得到流程裡做了哪些決定，也要看得到測試對上了哪段意圖。他認為企業裡可用的自主 AI developer，最早也要三到五年。

## 晶片能證明，軟體常常說不清

[0:16](https://www.youtube.com/watch?v=l9ed6cP8qhs&t=16s) Guy 介紹 Itamar 做過 Mellanox 的晶片驗證，也做過銷售。晶片和硬體裡，測對沒有軟體世界那麼常被輕忽。Itamar 說，確認 code 照預期運作已經是大問題。他在某家公司至少要為一個 bug 負 49% 的責，那個 bug 讓公司花了 8800 萬美元。他也覺得這是生產力的大瓶頸：sprint 裡的 user ticket，大約一半和 bug 有關。測試是試著減少被引進的 bug 和低品質 code。但 testing 是一整個領域：unit、component、integration、system、end-to-end。很多類型、若不是全部，都有 AI 幫得上的沒效率。有的在規劃和策略，有的在造測試資料，有的在生成 code 或 script，有的是為某個 user story 或某次 code 變更選對的測試來跑。大家想測、也在試，production 裡的低品質和 bug 仍在。所以 AI 和測試，先是辨認怎麼測、策略是什麼，再拿 AI 去生成測試，並隨時間維護。

[3:59](https://www.youtube.com/watch?v=l9ed6cP8qhs&t=239s) Guy 問，軟體相當確定，為什麼需要 AI，而不是更確定的系統。晶片驗證裡，一個模組多半有很清楚的規格，bit 進、bit 出，甚至可以用形式驗證、數學證明說它照預期工作。軟體雖然確定，輸入輸出卻常常是 human in、human out。定義可能是一份 PRD，沒有正式蓋到所有 happy path 和 edge case，甚至更模糊。輸出也一樣。介面和結果要服務人，就必須用 AI 去蓋那些得跟人溝通的情況。若像硬體那樣試著蓋所有、或足夠的選項以保證沒 bug，軟體會有兩個問題。一是很沒效率：每晚跑完全部測試，仍可能蓋不到你要的，和某個硬體模組不一樣。二是你到底要蓋哪些選項，本身不清楚。AI 可以幫你決定哪些 happy path 和 edge case 值得測，再幫你把測試生出來。

[6:00](https://www.youtube.com/watch?v=l9ed6cP8qhs&t=360s) 他講一個後來成為客戶的朋友。那人推團隊做到 80% code coverage。有一個團隊到了 85%，他很驚訝，一看，裡面沒有 assert。測試蓋了很多行，過程裡沒問任何問題。崩潰或不崩潰會被檢查，功能上的結果是不是照預期，不會。硬體驗證幾乎不會這樣，因為定義就是輸入輸出。軟體即使確定，仍有很多 test smell 和測試的 know-how。AI 連這個也幫得上。Guy 收成兩類：定義上什麼叫對、什麼叫不對，這道缺口，AI 可以從 code 推你原本想做什麼，晶片的定義沒有這道模糊。另一類是可能性太大，軟體太有彈性，AI 幫你選該專注的路徑。

## 十行測試不是最難的那段

[8:02](https://www.youtube.com/watch?v=l9ed6cP8qhs&t=482s) 多數軟體不是一個你可以寫成演算法再證明的東西。硬體幾乎可以，例如網卡上的 quality of service 模組，近乎寫一段演算法去證。很多商業邏輯不能。加密也許是例外，那裡 AI 甚至有機會引入更多形式方法，因為要分析最少該蓋哪些 flow、才能對某類錯誤有 99% 的把握，並不瑣碎。他主張：最後那十行測試不是寫測試最難的部分。AI 可以幫忙，更重要的是你想測什麼、商業邏輯是什麼，先用自然語言描述。

AI 生成測試大致分成兩段：要測什麼，然後把那個測試生出來。生成是挑戰，更難的是自然語言描述。要測什麼來自意圖：這段軟體想做什麼。資訊要從規格、文件、其他 code 拿。怎麼測、flow、資料要不要從資料庫拉、對的結構、對的輸出，都還不是 code，是你得寫下的邏輯。再轉成 code 仍然難，因為要對的 import、對的 mocking。兩步都難，他認為第一步更難。

[10:42](https://www.youtube.com/watch?v=l9ed6cP8qhs&t=642s) Guy 把層次排開：先懂你想做什麼；再懂要生哪些測試才能驗證，可能性近乎無限，資料、系統行為、狀態；最後才生成測試。他覺得生成是較新的一塊，也是能用的關鍵。系統若回來說你該寫一千個測試，人會說謝謝、然後不做。Gen 的解鎖，是讓像 Codium 這樣的公司對客戶有用。Itamar 不同意，但不是為了抬槓。電商，他不點名。2024 年要做一個新功能：按一下，收集你買過的類似商品，帶你去買類似的東西，而且已經幫你選好顏色，顯示在購買頁。你可以說難的是生成 Playwright 或 Cypress 那種會跑的 script。他主張更難的是想出所有相關 flow。

愈靠近 code，unit、component、integration，多半是開發者在做。愈到 end-to-end、手機和介面，愈多是 QA 或 QA automation。他覺得 thanks to AI，這會 shift left，但那是另一點。QA 最難的事之一就是想出所有該查的 flow。Bug 進 production，常常不是不會寫 code、也不是沒時間寫，而是忘了、或沒想到不同的 flow。例如購物車裡已經有一件這樣的商品，沒人去查那個選項。Gen 不只是 AI，有機會重做這塊：爬網站、懂使用者行為，這在 Gen 之前就有；再發明 flow，拿產品經理的描述，加上先前爬過網站的經驗，生成測試 flow，最後也生成測試本身。所以 Gen 也會進到「分析你要測什麼、怎麼測」的前半。

[14:53](https://www.youtube.com/watch?v=l9ed6cP8qhs&t=893s) Guy 覺得最後那段不是最難，但是苦工。造出一千項，它們不會被做完。他在 Snyk 看過：給你一千個相依更新，相對容易做，若沒有把精確的變更放在銀盤上交出去，人不會動。不是惡意，是因為瑣碎，而且不想重複做。他把 Gen 分成兩種。一種是 LLM 用來理解系統，被歸在 Gen 這一代技術裡，但本性仍是分析。另一種才是真的生成一個會流過去的東西。Itamar 同意有些情況你知道要做什麼，但執行要靠生成。Codium 的另一個強項他很難說哪個更強，是 code review：多一雙人工的眼睛，提高 pull request 的品質。很多公司已經知道要現代化某一段舊 code。他用 Gartner 的詞。他們已有符號式或其他不一定是 AI 的工具，給一份食譜，例如 Spring 2 升到 3。然後需要 Gen 去收最後幾處變更、做最後的 review。食譜以外的幾行，以及讓審查者先有 AI 看過前幾件事，在一萬名開發者的大公司裡必須做很多次，才有效率。世界就分成：很難弄清到底要測什麼、要改什麼；以及若沒有生成去執行，你就無法有效率地交付價值。

## 回歸的真相在舊版，新功能的真相在話裡

[18:56](https://www.youtube.com/watch?v=l9ed6cP8qhs&t=1136s) 他想搖一搖大家對測試層級的看法。常見是三角形，有時是鑽石。三角形最底下是 unit test：四行程式、一個 class 裡最小的元素，甚至 function 裡的一段，盡量隔離。愈隔離愈好，而且快。上面是 component test，比較像一個 class、軟體裡最短的一條 flow。Unit test 很技術；component test 開始有一點意圖，但意圖仍很技術、仍是很小一塊軟體。再上是 microservice，可以是兩個 component 接在一起，也可以是一百個，重點是它在服務一段完整的商業邏輯。這裡通常有 integration test，是三角形的中間。最上面是 system test、end-to-end、UI，測整個應用、整個系統。他沒展開 functional 和非 functional。2010 到 2020 愈來愈多人說該看鑽石，大部分價值在 integration test。原因之一是 unit test 太嚴：要一個 function 一個 function，也很難維護。他主張 AI 可能改變這一點，讓 unit test 更好做、更好維護，也許最後又回到三角形。

[22:25](https://www.youtube.com/watch?v=l9ed6cP8qhs&t=1345s) Guy 把非功能測試放在這次之外：效能、安全，等等。他在意 source of truth。功能測試難，因為正確行為圍繞使用者的意圖。回歸測試不同，source of truth 是上一版，你幾乎想把 bug 也保住。Itamar 把這個維度分成測新功能，以及測沒有把東西弄壞。回歸是在 integration、unit 這些層級檢查已知該工作的行為沒有退步。Smoke test 之類也可以放這類：改了 code，只查簡單輸入是否給出簡單輸出，不必密集查行為，而是沒有弄壞大的、基本功能還在。用 AI 時這很重要。回歸測試裡，code 是很有用的 source of truth：這應該能動，我怎麼測。要測你想放進去的新 code 時，要對上的是自然語言描述，可以是比較結構化的，像 BDD、某類商業描述。AI 很能享用 code 是形式語言、可以編譯這件事。新 code 的 source of truth 是自然語言，也許被整理過，仍不是形式語言，於是有犯錯的空間。無論你在做 AI 生成測試的產品，或在用 AI 生成測試，行為會不同，甚至 UX 不同：它住在 IDE 還是 Jira，介面一個可以很嚴，一個可以比較像聊天。

## 誰來 QA 那個 QA

[25:55](https://www.youtube.com/watch?v=l9ed6cP8qhs&t=1555s) 信任很棘手。範圍從 unit 到 component、microservice、integration，愈來愈要懂整個系統。回歸和 smoke 也許比較容易知道什麼叫失敗。但要知道對不對，我們通常用測試。若測試是你寫的，後面可以很野，生成完再測。若測試本身是 AI 擲骰子生的，verify 該由測試來做，你怎麼信任。Itamar 同意。最後得有一個權威說這是對的。Buck 停在 AI，還是停在開發者。他把問題換個問法：我們怎麼解決軟體。生成能用的軟體，幾乎是同一個問題，因為測試和 code review 就是為了這個。解決軟體不只是 code 能跑：要有效能、要安全、可維護、可延伸、符合公司的 best practice，甚至公司的價值。他不是在開玩笑，尤其在 AI 的時代。Guy 說測試是必要的一部分，但解了測試還沒解軟體。還要更好的「什麼叫正確」、軟體怎麼隨時間演變、真正把 code 寫出來。Itamar 說測試是我們二十年來偏愛的辦法，可能不是唯一的辦法，而且仍是子問題。你要 code 能動，是因為不想傷害使用者、想有信心地走快。還有別的面向。

[30:37](https://www.youtube.com/watch?v=l9ed6cP8qhs&t=1837s) 他先舉一種不是舊式測試的做法：testless testing。技術產品經理或開發者把要達成的事寫得精簡但精確。你不從 code 生測試，而是從 code 生出規格，格式和那份規格一樣，再跑一個比對。可以是 AI，可以是 Gen。它告訴你哪裡不合。這是生成式 AI 打開的新測法。做測試，是要檢查軟體符合需求和 best practice，不是「這段 code 過了一個測試」就結束。具體的信任他收成兩點。有意義的測試通常不是抓一點 context、做一次推論。是一整條 flow，一個真的有用的產品。Codium 把幾條這樣的 flow 開源，還在程式競賽上做到比 DeepMind、OpenAI 等對手更好。字幕把那個競賽的名字聽成 codenation。和那些對手不同的是他們設計了一條 flow。做工具的人可以把這條 flow 裡做過的決定浮出來。開發者可以審查走到最終測試的過程，從而更有信心。簡單例子：系統去找 codebase 裡已經實作、而且被信任的 mocking，因為它們在 CI/CD 裡跑過，生成測試時選用它們。開發者看見這個 mock 不是現在生的，是從另一份他信任的測試拿來的，就比較會信任這份新測試。完美測試、精確知道要蓋什麼、完美生成，那就等於解決了軟體，所以沒有魔法答案。不是因為它給了一個信心數字，或做對了五次。這和你對一個開發者一樣：看同步的過程、看 PR 描述，然後學會信任這份輸出。第二點是意圖。系統讓你看見：這份測試是因為這段意圖而生的，實作如何蓋住這段意圖。選方案、或自己做這些系統時，這兩點有用。它們依賴 attended 的過程。還有：測試若能跑、能編譯、沒有弄壞東西。Meta 發過的工作，他一時想不起全名，他們重現了，Meta 沒有開源，他們放出的叫 Cover Agent，對上的是 TestGen-LLM 那類做法。給開發者信心的兩部分是：測試能建、能跑，以及提高了 code coverage。注意這只對回歸測試成立。能建、能跑、沒弄壞系統、還增加 coverage，只適用於回歸。每個測試類型可以有更戰術的做法。高層仍是：給你看過程，以及你確實做了有意義的事，例如提高 coverage、提高意圖的覆蓋。

[36:29](https://www.youtube.com/watch?v=l9ed6cP8qhs&t=2189s) Guy 把層次再數一次。先同意要測什麼，那份 spec 本身也要被看過、有人說它是對的，這是 attended。然後生成測試、看它通過。Code 比別的生成領域好一點，因為你可以跑。但仍有一跳：跑得起來的測試，是否真的確認了你定義的需求。實作上可以把信任委給已經被人手驗證過的 mock。再往外，coverage 是一種量法，但是不是該跑的那些測試，是另一件事。有了這些，無論用 AI 還是手寫，才能有信心地開發。過程裡仍有很多 attended 的驗證。目標是把瑣碎的部分拿走。維護還沒展開。回歸測試比較能跳，是因為你相信現在的跑法是對的，既有系統是可擴展的外部 source of truth。

## 自主的開發者，要等那些小流程先蓋住

[38:55](https://www.youtube.com/watch?v=l9ed6cP8qhs&t=2335s) 儘管 X 上有很厲害的影片、台上有 demo，實務上多數自主 agent 依某個意圖生出的軟體非常簡單。他甚至說，那些 demo 你大概能在 GitHub 上找到一個 repo，做的就是那件事或很像，五分鐘可以自己做出同樣的。也許有一點轉換成你的特定請求，有一點魔法，但離對企業有用還遠，連稍微接近都沒有。同時他主張五年內會在企業裡看到 AI developer。

他稱那些 demo 為 AI developer。有人叫它 AI engineer，容易和調 AI 的人搞混。自主的 AI developer，最早三到五年。他想的路徑是：AI 工具先嵌進既有的軟體開發工具鏈、流程、workflow。例如他們的 PR agent 接到 GitHub、GitLab、Bitbucket，幫你 review、查 best practice。他說這是 shameless plug，但他真的相信。另一個工具接 IDE，幫你測試。另一個接 CI/CD，幫你選測試。另一個接 build，幫你分析失敗的 log。這些目前他放在 AI assistant 的範圍，雖然也可以說是 agent。即使是 agent，它們做的是整體 workflow 裡很小、但關鍵的子程序。它們可能自動幫你選要跑哪些測試，甚至分析 build 錯誤、建議一個修法、再 build、看它過了沒有。可以是 agent，但會有很多條這樣的 flow。他把開發有用 agent 的方式叫 flow engineering。等到這些子流程有一定比例被 AI 嵌進去，80%、90%，也許得 95%，忽然可以再做一個 agent，一個 AI developer，和技術產品經理一起把意圖形式化、修到某種程度，然後生成軟體。因為那些守護的 agent，已經很辛苦地接到對的資料庫、對的 framework、對的 best practice，可以形成回饋和打磨。這是一條路。

[43:11](https://www.youtube.com/watch?v=l9ed6cP8qhs&t=2591s) Guy 復述：不是一步跳到自主，而是把今天的每一小段做更好。補全更能解釋意圖，code review 更能抓錯，Cover Agent 這類幫你測、看出變更有沒有弄壞，Codium 幫你建功能測試，都還是 attended，再加上分析 log。各段一起變好，才有信心去建東西。難處是每一段若 95% 準，串十段，大約一半時間會壞。最好想像的路徑仍是每一段變好，直到你每次都說對、對、對，然後假設它是對的、繼續，錯了再退。Itamar 同意，也同意這條路的缺點：它可能沒有用盡 AI，只是在既有東西上做到最好。另一條是重想。漸進這條可能不收斂：若 workflow 裡有一個子程序 AI 跨不過去、agent 自動化不了，你就過不去，自主的 AI developer 仍會有阻力。優點是，企業很難說把已經在用的幾十個工具、流程、workflow 全丟掉，換一個全新的東西。不是沒發生過，尤其那個東西本身很大的時候，但很難。還有一個他覺得說出來會棘手的理由：我們可能有點誇大 AI 現在能做的。所以拿現有 workflow 裡的小段來改進，也許更可行，同時拿到真的價值。沒跳到自主，不代表沒有價值。今天的 code completion 就非常有價值，讓人更有生產力。漸進路徑的另一個好處是，因為立刻有好處，你本來就會做。

## 重想開發，是讓規格一寫出來就錨在 code 上

[46:49](https://www.youtube.com/watch?v=l9ed6cP8qhs&t=2809s) 若不是漸進走過去，而是扔掉重想，鏡頭仍放在測試和驗證。他重複的觀念是：尤其不是回歸、而是要測新 code 時，一切關於意圖。Gen 給你最後一哩：我知道要測什麼，這種東西有一千個，沒有 Gen 做不到。但他仍認為多數情況下最難的問題之一，是一開始就有對的意圖、可測的意圖、一份已經錨在現有 code 上的 spec。你在開發新 code，新規格在你寫它、發明它、開一張新 user story 的時候，就已經錨在你描述它的語言裡。例如技術產品經理對 code 的描述方式。重想軟體開發，把光譜聚焦在測試和驗證，就是意圖。和 AI 一起重做研發和產品整體怎麼寫規格、怎麼定義意圖。利用 AI，一開始就做出更容易被 AI 接著用的 PRD、技術 spec 或產品 spec，然後生成 code、生成測試、生成 review。把那一段重想了，AI 才更容易把 code、測試和驗證做完。Guy 說這和他們想的 AI native、以 spec 為中心的開發是對上的。今天的流程裡，測試就是那份規格。中間沒有、至少不常用一份意圖的中間表示。意圖和實作的測試是綁在一起的。

[50:15](https://www.youtube.com/watch?v=l9ed6cP8qhs&t=3015s) 沒有單一的測法。理想上測試是要驗證意圖被實作了。但軟體在多數情況下沒有形式方法，除非是可以數學證明的演算法。公司、團隊各有意見。讓人相信這些測試是好的，很大一部分是依照開發者給的 best practice 來生成。例如他們的 PR agent 可以讓團隊給一份 markdown：這個 repo 的測試風格要這樣，那個 repo 要那樣。一旦 AI 開發工具能照你的 best practice、照你的測試風格來生成，而且好用到比以前容易十倍、一百倍，不是按一個鈕，但容易很多，測試就可以當 spec 的來源。有 CTO 告訴他，他們偏好的文件就是能跑的測試。這和 Guy 說的對上，也有整個 TDD 世界把測試放在宇宙中心。但他再說一次，不是魔法。不是 AI 生了測試，這就是我的新 spec。要做的工具，是依照你的開發團隊、甚至技術產品經理會當成 spec 的那種風格來生成測試。若那些測試是可執行的 spec，風格是你的、對你容易，才能重想 spec，重想可執行的 spec。

[52:49](https://www.youtube.com/watch?v=l9ed6cP8qhs&t=3169s) 產品這集談得少。IDE 裡的 agent 他們叫 Codiumate，字幕聽成 Cod mate。Git 上的是 PR agent。還有 Cover Agent。IDE plugin、Git plugin、CLI plugin，這些要麼免費，有些還開源。唯一還沒找到怎麼做成免費的，是完整的 codebase 分析：你可以給 Codium 平台一萬個 repo，它跑各種分析。他們想把其中一部分移到免費方案，還沒做到。Itamar 說 Codium 是一套工具、一個平台，未來會看到更多聰明的 coding system。令人興奮的是開發者怎麼想像那件事，工具只是讓它發生。

# Transforming Debugging and Root Cause Detection with Sentry | David Cramer

## 一句話

他覺得 vibe coding 這個概念說不通。你還是在做軟體工程：設計系統、寫 spec、把測試做好、做 code review。Sentry 的優勢是應用本身高度結構化、彼此連得起來的資料，不是系統層那種倒進來的 log。他用這份資料做 root cause，也拿自己的 MCP 服務做實驗：大約八週幾乎不親手改 code。結論是人還是得在迴圈裡，而且 Cursor 這種能邊生邊看 diff 的介面，比終端機裡一長串輸出更適合現在的技術。

## 客戶是開發者，所以他們同時在用、也在做

[1:02](https://www.youtube.com/watch?v=CjokRM4u3lY&t=62s) Guy 把這集分成兩個角度：怎麼用 AI 來建造，以及怎麼把工具做進 AI。David 說 Sentry 關心的面很寬。客戶是開發者，所以他們想：軟體怎麼被做出來在變、有沒有新的開發者、那些人需求是否不同。他目前的答案是，還沒有真正不同。另一面是能不能用新技術做出新的或不同的軟體。這不是 AI 才有的問題，任何技術都一樣。也有一塊綠地：要不要做一件完全新的事，而不只是在 Sentry 上加一點。最近幾個月比較熱的是，它怎麼改變你的工作，能不能換到更高的出貨速度。他自己在這一面花很多時間。他不是學界出身，自學的軟體工程師，自認是很好的應用工程師。他大概知道 Markov chain 是什麼，但不懂那些學術。他很會除錯、很會弄清楚東西怎麼運作，所以就鑽進怎麼把這項技術推到最有用。Guy 說這是實作者的視角。做開發者工具的人自己也在用工具，這是特權，做給律師用的工具常常不是律師在做。

## 先用 embedding 去重，再用 Seer 找根因

[5:04](https://www.youtube.com/watch?v=CjokRM4u3lY&t=304s) 他記得的第一個應用大約一年前，用 embeddings。Sentry 的核心若壓到最簡：抓住錯誤、放進儀表板，中間做很多處理。很關鍵的一步是 deduplication，來自他們說的 fingerprinting。歷史上多半是大量正規表示式，或等價的東西。他舉 Ruby：匿名函式的名字裡會被塞進隨機整數，規則要把那些剝掉，錯誤才對得起來，因為比對必須是靜態的。他說這記憶可能已經過時。Embeddings 可以用少很多的總工作量，靠得更近。它們自己不夠，但早期改進很大。他們要的不是酷炫的噱頭。這是要持續下去的真生意，要真的應用。

[6:39](https://www.youtube.com/watch?v=CjokRM4u3lY&t=399s) 更近的是 LLM。他覺得在開發工具裡，LLM 最讓人興奮的是 code generation：能生成、也能理解 code，以前基本上碰不到。Fingerprinting 他們永遠解得了，只是繁瑣。自動修 bug 或自動生測試，他先聲明：今天還不能可靠地做。他們是在問，若走得到那裡會怎樣。論點是 Sentry 有很多資料。歷史上的護城河是關於應用本身、彼此連在一起的資料。很多做 application monitoring 的廠商在另一層，比較像系統層。他說去看 Splunk 這類 log 聚合，把資料全倒進去、沒有篩選和整理，那些資料就是垃圾。Sentry 的是高度結構化、高度語意的。他們在 LLM 之前就做了一份把 trace 接起來的資料集，再丟進 LLM，因為那本質是大規模的 pattern matching，問它能幫多少診斷。這件事做了快一年。產品他叫做 Seer，字幕寫成 Seir，他唸出來的字母是 S-E-R。

[8:28](https://www.youtube.com/watch?v=CjokRM4u3lY&t=508s) 幾個月前他問還能不能送。他覺得大概還不行，因為這些工具會編。他拿自己 side project 上一個連他這個專家都看不懂的 JavaScript bug 去示範：它不該懂。Seer 給了一個很怪的 root cause。這套主要做的是 root cause analysis，patch 是另外一回事。他拿給團隊看，說完全錯了，所以還沒好。第二天公司裡有人撞上那個 bug，把真正的錯誤給他看。他不記得細節，但那就是 Seer 說的問題，而且是對的。他真正震驚。他對工程師價值的單一信念是：去 Google 這種大公司，staff、principal 拿很多錢，很多時候產出沒有那麼多。他有朋友做那些工作，很舒服。他後來想通，價值是他們對系統的知識，以及能圍著「到底發生什麼」做理論推演，於是除錯非常快。這套居然也能做得不錯。他們還在做，非常早，跟所有這類東西一樣，做得沒有那麼好。但做得成的時候，就是那樣。

[10:09](https://www.youtube.com/watch?v=CjokRM4u3lY&t=609s) Guy 問幻覺和 context window 這兩個障礙，以及團隊要的是舊技能還是新技能。David 說很多技能是一樣的。產業一直有學界和真實世界。他記得 NoSQL 那個年代，學界說找到擴資料庫的新方法，實務上永遠不行，因為系統很大、很複雜、基礎設施很難。現在一樣。一開始多半是資料科學家在建，有 DAG 和很複雜的 workflow。很快演變。今天常見的模式是 agent，他說那就是一個 service，不知道為什麼改了名字。Tool call 就是 RPC，內部或外部。他們這條 workflow 還有點舊，比較像 pipeline，或早期說的那種圖。他覺得今天運用技術最好的方式，像 map reduce：你有很多資訊，能不能壓到不丢掉最要緊的部分，然後重複，直到得到要的結果。一年後再聽，誰知道還是不是這樣。Sentry 有大量資料，他們壓縮、摘要，送進 LLM。那個 LLM 有一批工具，跟這些 agent 一樣，例如讀原始碼。他不記得還有哪些，但讀原始碼很重要。然後問它能不能用那些工具和資料做出分析。再往下就變得不太科學：這樣看起來比較好嗎？它這麼 non-deterministic，要改進其實很痛。Evals 有幫助，他仍覺得最後多半是押 model 會變好，再加上工具鏈真的有效、資料品質高、訊號高。但最終很多仍在 model 身上。

## 八週不親手寫，核心程式庫不要這樣做

[14:08](https://www.youtube.com/watch?v=CjokRM4u3lY&t=848s) Guy 說他們之前聊過，David 六週沒有親手寫 code，卻在送 production 系統。David 先打斷：vibe coding 說不通。那是 YOLO，把東西打進 agent，出來是什麼就是什麼。這仍是軟體工程。你還是在設計系統、寫 spec、確認測試、做 code review。而且不幸，幾天前他還是親手寫了，因為它做不到他要的事。那之前大約八週。他的全職工作其實不是寫 code，雖然現在為公司寫得比以前多一點，更多是熱情專案。他做並維護的 MCP 服務對公司現在很有價值，但本質是 side project。那個 MCP 服務他是親手寫的。他的理由是系統沒有真的變，軟體到最後也沒有真的變。你若能推理軟體怎麼運作，看起來都差不多。MCP 是 plugin 架構，是一種反過來的漏斗：他可以做整合、插到任何地方，客戶也可以。這和典型的雲端服務整合不一樣。用途很多，他專注它對 Sentry 的意義。OAuth 的規格一宣布，他知道可以把 Sentry 插進 Cursor 或 Claude Code，價值很高。他很快做了原型。Cloudflare 也在做一些 MVP，他們把那個拉進來，幾天內就有能動的東西。他說這年頭什麼叫 production ready 本身就可疑，但它運作得完全沒問題。你丟一個 Sentry issue 的連結，它會拉對的 context。若你用 Seer，也會把 Seer 的 context 拉進來。這不是隨便做一個到處都能接的整合。他做的是讓 Sentry 在 coding agent 裡面高度能用，剛好是一個抽象的協定。Guy 說這像 middleware。David 說高一層看是，但更深。MCP 裡面嵌了兩個 agent。很多 tool call 只是把輸入翻成一次或多次 API，再把輸出翻成一個回應。另外有搜尋端點，找錯誤，或在 log 和 trace 上跑東西。Sentry 不只做錯誤，還有 log 和 trace，上面有很多 attribute，你可能想對那些聚合跑函式、問問題。在 Claude 或 Cursor 裡問「某個服務昨天總共花了多少 token」，可以透過 Sentry 的 MCP 回答。那不是對到一支 API。那是自然語言進到另一個 agent，再對到 API。他說一切都是 middleware，但若認真想產品體驗，可以深很多。他覺得很多東西的未來就是嵌進去的 agent，或 agent 對 agent，因為仍是自然語言、仍是 non-deterministic，不能指望它隨便寫出 API call。

[18:45](https://www.youtube.com/watch?v=CjokRM4u3lY&t=1125s) 這個實驗就是：能不能再也不親手寫 code。大量時間花在把對的文件放在一起、寫對的 context prompt、依技術的運作方式把系統弄好。答案是也行也不行。有時讓你驚訝，有時你只想叫它忘掉一切。還沒到。他鼓勵大家有機會就試一次這種練習。這樣做常常會讓你變慢。Sentry 的核心程式庫不要只用 agent 來寫。你可以叫 agent 生一個測試或一支 API，然後去審、去改，那仍是很大的效能提升；拿來除錯也是。你可以去開會，回來也許有一個起點。練習的用處是認識今天的限制，以及你怎麼改進那些限制。後者他願意賭會一直為真，因為軟體相當可靠，這裡面沒有魔法。系統變好的方式大致不變，只是變得比較容易，或比較不需要某一種行為。

## 不是任務太大，是它找不到常見的模式

[21:10](https://www.youtube.com/watch?v=CjokRM4u3lY&t=1270s) 流程是先要解決一個問題，也許有一張 ticket，把它收到一份很輕的 spec。他聲明自己什麼都不寫，百分之百是生出來的。連 spec 都是他用人類語言描述、再一再修。人類語言有時沒有效率。然後才實作。很多時候它做得還可以，而且很看任務。不是任務的大小。他說網路上很多恐懼來自根本不寫軟體的人。重點是這件任務的複雜度，相對於它有多常見。這仍是 pattern matching。若它不容易找到「這個總是靠著那個」的常見模式，它就不知道該做什麼，會去抓另一個看起來像的模式。他做嵌在工具裡的 agent 時就跑掉了：一個 MCP tool 呼叫一個 agent，再呼叫別的工具。祝你好運能把它留在護欄裡。它在字裡迷路。人也會：你說你在呼叫這個、又用了 agent 這個最新的詞，你也不知道會發生什麼。實作本身簡單得離譜。他可以給一份完整 spec，架構很好推理，就是一串函式呼叫。它還是會跑很遠。然後你進入叫它修自己的循環。他最愛的例子是，一出事它就往 TypeScript 裡插 `any`。你怎麼擋都一樣。他在 Claude 的環境最上面寫了關鍵規則：不要用這個。若每一則 prompt 都送這句，大概可以，但那不是你工作的方式。他猜是因為訓練資料裡太常見。他不是學界的，不確定。然後你坐在那裡跟它吵。這就是浪費時間的地方。不該依賴純 agent 開發，因為用 prompt 修，會比打開編輯器花更多時間。他賭，沒有認真修就能一次打中的，低於 10%。連一或兩則 prompt 就對的，也低於 10%。通常要大約 20 則，才會有一點點好。這是真實世界的軟體，要能維護、能測試，不是在生垃圾。不審更糟。有一次整合測試他以為審過了，他通常會掃過，side project 沒有團隊必須審的規定。人也会錯。他回頭發現它塞了一個隨機的東西，根本不是在測他要測的。別的檢查有蓋到，但這是根本問題。他從這裡學到的，也是你該知道的：不要當悲觀主義者。不要只是假定事情為真，要自己去過這些經驗。

[25:47](https://www.youtube.com/watch?v=CjokRM4u3lY&t=1547s) 他試了 Claude Code。終端機介面，他不確定會不會好。軟體本身他覺得出色。他最大的學習，而且網路上會有人說你不懂，是：以現在的技術階段，這是錯的使用者介面。Model 才是影響最大的，agent 彼此夠接近。用 Cursor 的 agent，變更即時變成編輯器裡的 diff，他可以很順地核准一塊塊 code、在檔案之間跳。Claude Code 是終端機裡沒完沒了的輸出。你可以逐筆核准，但那裡不好審。你看的是對 code 的編輯，不是原始碼本身。他認為以開發者現在要怎麼用在真實軟體上，那不是好產品。Cursor 對這種事好得多。

[26:56](https://www.youtube.com/watch?v=CjokRM4u3lY&t=1616s) Guy 問，Claude Code 會不會因為終端機的限制，變得更會解釋它改了什麼，於是你不必看變更。或者介面會變成商品，你只需要輕的整合。David 說他覺得你會永遠看所有變更。這項技術沒有在實現 AGI，也沒有在拿掉工程師，那些是網路上的話。他花在真正工程工作上的時間跟以前一樣多，甚至更多，因為他仍在設計系統。這些東西不聰明，只是在吐模式。Cursor 的流程好，正是因為他必須審 code，而且可以邊走邊審、可以打斷。他們雇 CTO 時，他討厭那種要主管做一份沒用簡報的流程。他仍想知道對方會不會說故事、會不會投入，所以改成：就你有興趣的事做一個短報告，再 Q&A。那位 CTO 之前在 Apple 的自動駕駛部門待過一段，想講自駕車。David 說沒什麼新意，但他同意一個問題：大家都想一路開到全自動，LLM 也一樣，人人想相信 agent 可以自己跑。正確答案是人要在迴圈裡。Cursor 的體驗是比較好的人在迴圈裡，因為他漸進地審，他自己的 context 比較小，原始碼就在旁邊。他不是透過終端機裡的一篇文章來寫軟體。他看不到今天的技術走到完全自主。也許可以，那是學術的部分，他覺得他們自己也不知道。不能假裝這些東西做得到它們做不到的事。若人必須在迴圈裡，最好的體驗不是生一大堆、到 GitHub 審、再回來修，也不是終端機在這邊、編輯器在那邊、再點檔案。那些摩擦很高。

## 測試、文件，以及把原始碼從保護名單拿掉

[30:26](https://www.youtube.com/watch?v=CjokRM4u3lY&t=1826s) Guy 說 Tessl 正在寫軟體單元的自主等級，比照自駕車的五級，很快會公開。其中一個前提是，測試若夠好、你信任測試，你就不必再回去審。那和 IDE 裡的人在迴圈是不同的位置。David 的規則是自己不能改 code，所以很麻煩。他很重視測試，但不做 TDD，不先寫測試再寫 code。整個職涯，能避免就絕不手動測 code。現實是 UI 無所不在，UI 的 code 比以前多，祝你好運。做過 JavaScript 的人知道，end to end 幾乎測不動，test harness 很難，大多數人並沒有用有效的方式在測。他有一批測試。他甚至為 TypeScript 的 Vitest 寫了一個 evals adapter，用測試去實作 eval 的規格，因為 CI 還是要做 CI。技術沒有變，驗證那一層還在，他只是要它把測試生出來。真的讓人印象深刻的是系統很簡單的時候。他用 oRPC，一種 JavaScript 的 API binding，伺服器那側對人很好推理，對機器當然也是，因為人容易推理的東西，機器也容易拿來對模式。他能把一整次從一個技術遷到另一個技術的遷移用 code generation 做完，因為 API 簡單。測試也生得出來，而且能驗證一切，因為一切清楚、boilerplate 不多。他覺得這很重要。接下來幾年，他希望複雜度會退掉，大家回去解決真問題。他現在活在 JavaScript 的世界，看到的是無限複雜。他沒看到產業因此得到更好、更可靠、更快送出的軟體。他看到更複雜的軟體、不常見的東西被放到正中央、人不寫測試、人不懂核心的系統設計。他相信這會被調回來。技術棧愈簡單，對人愈好，人愈好寫 code，它們也愈好除錯、愈好建造。這也會隱含地讓 spec 和文件更有價值。儘管大家想相信文件對人很有價值，其實沒有那麼有，因為人學得會 context、也留得住。進一個新的 codebase，你也許讀一次 onboarding，之後再也不回去。你看 code 就知道。文件對 LLM 超級有價值，因為它們不留 context。軟體設計裡一直重要的事，現在至少一樣重要，也許更重要。

[36:00](https://www.youtube.com/watch?v=CjokRM4u3lY&t=2160s) 最後大約十分鐘談到整個團隊。今天該做的第一件事，和 Sentry 已經解掉的那件有關：你得用得了這些工具，公司得允許消耗它們。大約一個月前，他拿掉 Sentry 在智慧財產上的那條合規：他們不再把原始碼當成受保護的東西。這不表示不執行授權。你偷他們的 code，他還是會追。他的意思是，就算 Cursor 不小心把原始碼漏出去，他也不在乎。很多本來就是公開的。他也不是在說 Cursor 會這樣做。有些人會，產業裡已經看過。他不擔心對方拿他們的資料去訓練。他不一定允許，但若對方做某些 model 供應商那種先做、以後再求原諒的事，他們不再把它當成業務風險。這是他一天內做的決定，對公司很重要，因為立刻就能採用一批工具。不是每家都做得到。做不到的話，你就得自己掏不少錢，他在 side project 上也是這樣付。他要大家告訴他想要哪些工具。大多數他不會給，因為是垃圾、沒有解決問題，你也不能有無限的工具。客戶資料仍是另一件事。他們把 Claude Code 和 Cursor 給了全公司，也把聊天給了全公司。重點是錢花在最有用的地方，以及先學會什麼。

[38:33](https://www.youtube.com/watch?v=CjokRM4u3lY&t=2313s) 再往下很難。最大的挑戰是一種資深工程師，不一定悲觀，但大致悲觀。他改口說 cynical 更準，而且他自己就是。他們打開 prompt，打一句，出來是垃圾，然後說你看，它不行。它確實那樣不行。不管誰想相信什麼，它不會那樣就動。你得強迫人過那個點：對，它不會動，這是你讓它動的方法。而且要變成大家互相教的循環。遊戲的名字就是把成功所需的資訊全部給它。你不把事實告訴它，它就答不了。你得當時就把答案給它。對方會看著你說，那我為什麼不自己做。你給它的是文件裡的那一頁，你並沒有自己把那頁寫出來。你是說：這是 UI，去拿，然後不要做那件事。你仍得把這些資訊餵進去，讓它有成功的條件。若你只是推理它怎麼運作，這很明顯；真的去用，也會很快懂。結果會差非常多。所以盡量用，弄清楚它需要哪種 context、怎麼傳進去，再找辦法做到。他們在跑的一個實驗是，能不能用有用的方式把文件全部露出來。有個他覺得很有趣、但還沒用過的 MCP，叫 Context7。它大致把開源產品的文件透過 MCP 露出來。這些東西並不知道軟體，不知道你在用的隨機東西，也不知道 API，它們只是在猜。這是大家不懂的：就是 pattern matching，你得把對的 library 的對的文件餵進去。有時它會去看原始碼。他們拿公開文件，docs.sentry.io，為每一頁產生整理過的 markdown，放在專用 URL，去掉很多版面和其他元素。可以把它想成 llms.txt 那一類。再透過 MCP 的工具露出去：一個搜文件，一個把文件拿下來，讓你找到相關文件再拉進來。原本的情境是想做幫你做 instrumentation 的 agent，若文件這關能過就很有用。他們也在試內部開發：讓文件可以被拿到，在對的時間拿到對的資訊，人少輸入一點。他覺得這些投資會非常好。又回到讓開發變好的那些核心：更好的說明或更好的 spec，而且現在有理由去用它們。結果會非常 anecdotally，不科學。他討厭 vibe check 這個詞，但沒有更好的類比。你其實是在感覺它比較好還是比較差。

[42:04](https://www.youtube.com/watch?v=CjokRM4u3lY&t=2524s) Guy 問，多少是今天就要看到影響，多少是在練六個月或十二個月後才有用的肌肉。David 說今天就有，而且已經有好幾個月。Cursor 剛出來、主要還是 type ahead 時，他跟大家說這只是打字，沒有魔法。他們的 agent Composer 當時還很新。他試著不要 cynical。他預設就是 cynical，因為加密貨幣那群人、整個網際網路一直有人在撈，預設懷疑在生活裡完全合理。他用一個任何認真的公司都有的正常流程試：有一支 API，長得跟其他 API 一樣，要再做一支；或要做一個跟其他東西一模一樣的東西。這就是軟體工程的濃縮。他用 Composer，給一個現成的當模型，它大致做了。再叫它依一個現成的測試生測試，它也大致做了。測試甚至比他會做的好，因為它加了他大概不會蓋的分支，他不在乎那些。它就是複製檔案、改一堆東西去對上新的東西。那本來就是他的流程。他粗算自己做要多久，對上幾乎相同的任務用這個做要多久，產出大約是兩到三倍。這和叫 Claude Code 幫你把東西做出來不是同一件事。那是他用 agent 做 boilerplate，而且是幾個月前，已經非常有效。Type ahead 也非常有效。價值已經在，但是另一種。還有一種現在正在發生、比較少被講的隱含價值。像他這樣的人，以及他們收購來的幾位創辦人。其中一位創辦人的名字字幕聽成 Inji，在 Sentry 管團隊，跟他一樣很久沒有為公司寫 code。這件事勾起興趣，現在又回到第一線在做東西。這很少被講，但重要得離譜。他認為驅動這個產業的核心，是會建造、對技術好奇的人，現在又回到細節裡。他們對變化感到興奮，因為這產業沉悶很久了，大公司在外面，你能做的不多。說實話，大多數難題已經解了。興奮和熱情會變成生意上真正的 ROI，因為它帶來想法。他覺得這無法衡量，但非常重要。對他個人，就是他會很樂意把晚上花在隨便一些事情上，他太太比較不開心。他又對技術感到興奮。實際的價值今天就有，只要人懂得怎麼用。另一種很難分析，是人怎麼想、怎麼做決定。你在公司裡做決定的人，不管在哪一層，愈能看見技術趨勢裡正在發生什麼，決定就愈好。那只是一個資料來源。他在 Sentry 的長處一直是人在細節裡，從資料裡拿到強的訊號。資料不是問卷。資料是他活在這個世界裡。人又回到細節裡，就有更好的意見、有品味。這些對做出好產品和好公司太重要。讓人去用這項技術，最重要的就是這個。當然，用得理性，也可以變快。

[47:16](https://www.youtube.com/watch?v=CjokRM4u3lY&t=2836s) 給外面開發者的一句話是 embrace it。懷疑是公平的。不要聽網路上的每一句。不要聽大公司 CEO 噴出來的胡話。它沒有在拿掉工程。他現在做的工程跟以前一樣多，甚至更多。但要接住它。你不能忽略。忽略的話，從職涯、從公司，你就是停在水裡。現在每一家公司都往這個方向移，經營那些公司的是很聰明的人。花時間去用這項技術。理想是用在工作上。不行的話，也許找一個用得了的工作。他不確定。Guy 說這和他的看法一致：你不能否認，就算回報不是立刻來，也得把那塊肌肉練起來。

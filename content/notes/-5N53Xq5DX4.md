# Datadog CEO Olivier Pomel on AI Security, Trust, and the Future of Observability

Olivier Pomel 是 Datadog 的 co-founder 與 CEO。主持人在字幕裡沒有自報名字，但說自己在 Snyk（字幕聽成 sneak）做過安全。節目由 Tessl 呈現（字幕聽成 Tesla）。片長約 59 分鐘，英文自動字幕。這份筆記依英文原稿整理，專有名詞保持英文。

- 原片：[YouTube](https://www.youtube.com/watch?v=-5N53Xq5DX4)

## 一句話

Observability 這個詞 Pomel 不愛，因為它聽起來被動。他看到 AI 的三層機會：建 model 的人消耗更多 GPU、建在 model 上的應用不再決定性、以及用 AI 把維運的行動自動化。自動化的門檻很高。客戶說想要 false positive，連續兩個就會把你關掉。LLM 不知道自己知不知道。所以他們挑信心極高的窄案例，例如 production 上的 500，而且前十年只收資料、不伸手。自己的時間序列 model Toto 第一版就在預測上達到當時的 state of the art，靠的是他們看得到哪些序列真的被拿來告警。他擔心的不是技術到不了，是賣得太滿，把信任再打破一次。

## 三層機會，人數是倒過來的金字塔

[0:47](https://www.youtube.com/watch?v=-5N53Xq5DX4&t=47s) 主持人簡介：Datadog 2010 年成立。市值他說遠超過 350 億美元，營收超過 30 億，字幕補了一句 2025 年可以到那個數字，沒聽清是不是同一筆。29,000 個客戶。他認為 Datadog 把 observability 這個類別做出來了。Pomel 說都對。

[2:03](https://www.youtube.com/watch?v=-5N53Xq5DX4&t=123s) Observability 是最難唸的類別名字，他說自己在各種場合唸了幾百次。他不愛這個詞，聽起來縮小、被動，很多實際發生的事並不被動。它是以前叫 monitoring 的現代版：看懂你需要看懂的一切，應用表現如何、裡面發生什麼、有沒有做該做的事。五到十年前是一堆小類別：infrastructure monitoring、application performance monitoring、log management、network monitoring。他覺得有一部分是他們的工作，這些收成一個端到端的類別，從伺服器上跑什麼、網路上走什麼，到終端使用者在做什麼、對業務做了什麼。

[3:37](https://www.youtube.com/watch?v=-5N53Xq5DX4&t=217s) AI 在每一層都有機會。最直接、他覺得最無聊的一層是更多應用用 AI 做出來，stack 不一樣，更多 GPU、更多資料。今天若吃很多 GPU，你大概是在建 model，或在給別人要用的 agent 供電。第二層是大量應用建在 model 上。應用沒那麼決定性，model 做的事多很多，你怎麼建、怎麼管、怎麼看懂，都不一樣。這是另一種 observability。第三層是這些新的 smarts 能自動化什麼，讓工程師不必自己去解，機器多偵測、多解決。三層他們都在重押：服務正在建 AI 的人、服務建在 AI 上的人，以及自己用 AI 做自動化。

[5:32](https://www.youtube.com/watch?v=-5N53Xq5DX4&t=332s) 主持人說受眾順序是倒的：大概每一個建在 model 上的應用，就有一千家公司會想要 AI 驅動的 observability；每一個 model builder，又有一千個那種應用。Pomel 同意。每家公司都會要自動化。夢是再也不必半夜起來修，問題已經被修好，第二天起來再看。多數公司會用 model，得懂它們怎麼運作。較小一部分自己建 model、操作一大批 GPU。今天需求最大的反而是建 model 的公司，因為他們在所有人上游，很快變成很大的維運消費者，要 uptime、inference 穩定，最後也要大量訓練。

## Watchdog、Bits、LLM observability、Toto

[7:21](https://www.youtube.com/watch?v=-5N53Xq5DX4&t=441s) 有名字的產品有四個方向。Watchdog 做異常偵測，看所有事情，告訴你某個服務錯誤暴增，或另一個服務的 request rate 階梯式變了。你不可能一直盯幾百萬或幾十億條時間序列。他稱之為 machine learning 1.0，大致不用 foundation model（字幕聽成 financial models），用跑起來很便宜的統計模型，全部資料、一直跑，已經好幾年。他說你問 ChatGPT，它會說這是老派 AI，他覺得很有趣。ChatGPT 還說他是滑雪冠軍，他從來沒滑過雪。

[8:13](https://www.youtube.com/watch?v=-5N53Xq5DX4&t=493s) 較新的是 Bits AI（字幕先聽成 Beats）。比較 agentic，跑調查，協助處理 outage，可以跟它互動，也可以自己跑。建在較新一代 LLM 和更新的 model 上。他們把它當客戶自動化的未來。用途先是 on-call 和 outage 的 triage、修 production code 上偵測到的錯誤、優化成本或效能、找 incident 的 root cause。再來是 LLM observability，幫建在 LLM 上的應用的操作者看行為。最後是時間序列的 foundation model，叫 Toto，取自綠野仙蹤裡的那隻狗。目標是盡可能好的時間序列預測。這是他們第一個 model，上面還會疊更多。

## 兩個 false positive，人就永遠關掉你

[10:03](https://www.youtube.com/watch?v=-5N53Xq5DX4&t=603s) 主持人問現在抓 root cause、決定半夜叫不叫人的準度，以及使用者容不容忍錯。他們剛拿滑雪的例子說明 model 不會總是對，這段沒有把滑雪例子本身再講一遍。Pomel 說 Datadog 創業最大的學習是：客戶會說系統若夠聰明，把 false positive 給我，我自己判斷。那是謊言。連續兩個，他們永遠關掉你。幾乎沒人願意因為機器指向錯路就追下去。人叫你追，還可能追。所以跟 observability 有關的 precision 要非常高。三、四年前，多數時候把 root cause 完全說對還是科幻。現在看得到，他們在做的東西和 evaluation 的進展都指到那裡。Evaluation 最難。地平線上，技術好到能在大量情境交到客戶手上，門檻仍要極高。安全的門檻低一點。使用者比較願意賭自動化的決定或通知，營運比較不願意。為了避開資安事件讓 workload 掛掉，可以；為了避免掛掉而讓它掛掉，不行。主持人用 Snyk 的經驗對上：客戶說不確定也告訴我，真正在意的是 false positive，只是不說。判斷是不是入侵嘗試本來就比較不確定，連人也不被期待每次判對。Pomel 把營運和安全跟其他 AI 比：自駕車現在剛開始能做 16 歲以上的人幾乎不用想就會的事。他們和客戶的 incident，要一大群很資深的人和 PhD，有時過了幾週還在想發生了什麼。

[14:23](https://www.youtube.com/watch?v=-5N53Xq5DX4&t=863s) 系統不可預測，找到一次不代表同樣資訊再找得到。怎麼前進。Pomel 分成兩題。第一是形式：copilot，還是自己做事的 agent；用語音還是按鈕。UI 設定期待。產業還在找。聊天打開想像，不是全部。長遠大多數 AI 功能不會從聊天長出來。第二是帶著信心進市場。較低 recall 換較高 precision，先做角落、所有 incident 裡很小一塊、真正高 precision 的。LLM 不擅長知道自己知不知道，總是樂意回答，而且常常錯。他們在做的是判斷何時對、何時機會高到可以主動猜，甚至直接幫客戶解。已經被用來做 observability 是優勢，可以挑要自動行動的案例。自駕車不能說我只負責左轉。

[17:35](https://www.youtube.com/watch?v=-5N53Xq5DX4&t=1055s) 行動是目標。最低的果子是錯誤：新應用上線，伺服器出現 500，明顯要修。產生能修的 code 通常不難，難的是送過去、驗證、跑在 production。這是他們正在做、可以相當自動也相當快的一塊。幾年前開始讓客戶能採取行動：workflow automation，以及讓客戶做內部營運自動化的應用。跟公司前十年很不一樣。前十年很小心，只收資料，從不行動、從不伸手回去。現在要關上迴圈。他堅信 AI 要顯出價值就得把行動自動化。一直催人，不會成功。令人印象深刻的 demo，他說你大概在 Twitter，或該叫 X，都看過了。LLM 的祝福和詛咒是：做出震懾的 demo 太容易，讓它對每個人、每次都可靠太難。瘋狂的錯誤、立刻看懂、寫出漂亮的修復 code，不是每次都這樣。把那段 code 真的 ship 出去通常很難。他們仍在把水管接好，讓它可靠。

## 日誌可以注入，端到端 model 不是他們要的

[20:39](https://www.youtube.com/watch?v=-5N53Xq5DX4&t=1239s) 主持人問 prompt injection。Log 和系統裡很多不可信資料，可能騙 Bits 或其他產品在不該動時動手。這是能力以外的信任，是對抗。Pomel 說一直都是問題。他們看過有人從 log、trace、幾乎任何送資料的地方注入。以前是 cross-site scripting，往 log 裡塞怪東西。所以一切都要重重 sandbox，對進來的資料防禦性寫 code。LLM 的攻擊面更模糊，只要最後還是把一些資料送進 model，就比較難完全圍住。修錯誤還得生成並執行 code。任何時候執行 code 都有很大風險，也要重重隔離，才不怕那些被信任的 code 到處跑。好習慣是想像任何處理外部資料的東西，最後都可能執行不該執行的 code。主持人提過另一集，來賓在一家安全公司，字幕把人或公司聽成 Mattel、Lera。那集談 LLM 裡 control plane 和 data plane 合在一起，資料被 model 執行，很難分開。騙 LLM 是騙人；agent 會照著行動，是上一層。生成並執行 code 更有力，也更危險。

[23:29](https://www.youtube.com/watch?v=-5N53Xq5DX4&t=1409s) 這會不會成為自主的上限，還是對 agent 決定的信任能追平對人的信任。重啟伺服器、重新部署，都是決定。Pomel 說這表示他們大概不會有完全端到端的 model，才能在 model 周圍建限制、建足夠的信任。自駕常聽到端到端：攝影機進去、油門出來。他們要建的系統不一樣，因為一路上要有檢查、平衡、驗證，才不會讓對抗或注入得出錯的行動。這對他們也是機會。他們為正確性、安全和效能做工具。客戶建自己的 agentic 系統時，有同樣的問題：怎麼確定沒被濫用、做對的事、信得過。他們也做那些工具。主持人問責任。自駕車犯錯不知道向誰問責。Agent 的上限可能不是技術，而是 Datadog 替本來該由使用者做的決定承擔多少合理責任，合規和法律，不只是技術。Pomel 說不是全新領域。自動更新已經有過非常公開的案例，一次更新對客戶有很可怕的影響。法律框架也許會再細。每家公司，或幾乎每家，都有過實習生為了修問題把 production 資料庫弄掉的一天。這些 agent 的早期版本也可能。誰負責是有趣的問題，但跟各種既有自動化差不了太多。

[26:28](https://www.youtube.com/watch?v=-5N53Xq5DX4&t=1588s) 主持人問雲端遷移：早期擁抱的人承受過缺口，容器 sandbox 漏洞、雲端初期的可靠度、不是非理性的恐懼而是真的缺陷。要接受一開始有點不穩，才能先拿到 cloud native 的好處。現在是不是一樣，想當未來的領先公司就得抱著 false report、甚至系統被刪掉的可能，不然會被落下。Pomel 說今天建應用的人，技術邊緣確實粗糙。所以真正發展快、大量 ship 的 AI native 公司相對少。更廣的、建在 AI 上的公司大多還在試水：驗證、早期測試、跟自己的客戶做 proof of concept、pilot。失敗模式還沒被看懂，技術變很快，新的暴露讓人不舒服，所以較難全部進 production。他回頭看雲端遷移，當時定義雲端的公司，主要是 Amazon，把安全做得極好。大家怕的是資料和運算跟所有人共享，別人看不看得到我的東西。他們從第一天就很強。他希望跟 AI model 有關的一切也能這樣，把主要恐懼拿下桌，讓其他人有信心去建。主持人同意，但也說今天最大的入侵和缺陷大概是雲端設定錯誤。那不是 AWS 這類供應商的直接缺陷，是基礎設施太好建、太好設定造成的。Prompt injection 會不會取代那個世界。Pomel 說有這個風險。公開的 S3 bucket 換成：這裡有一段 prompt、一段聊天，我知道我能從任何聊天介面統計式地把資料弄出來。

## Toto：第一版就站上當時的前沿

[29:43](https://www.youtube.com/watch?v=-5N53Xq5DX4&t=1783s) 為什麼做 Toto，不建在現有 LLM 上。它是另一個焦點：時間序列，而且要能預測。Foundation model（字幕聽成 under broad models）對時間序列不太好，數字上能做一點，整體不強，時間序列尤其不出色。他們還需要很小，才能在 process 裡跑非常大量的序列。第一版 Toto 純數值。餵了大量時間序列。一部分是傳統訓練資料，不是他們的，例如天氣。他說大多數是自己的 observability 資料。哪些序列有趣，他們有強訊號：哪些被拿來告警、被人看、看的頻率。這給了訊號品質。讓他們震驚的是，第一個 model 建得有點天真，是他們第一次做這種寬的深度學習 model，發布時已經是時間序列預測的 state of the art，連非 observability 的用途也是。深度學習在擴展，這幾年學到了；真正造成差別的是有很好的訓練資料。這一版沒有放到更廣的世界。他們要它當基線，做更多研究。正在做新版本，他說是比較低階的 multimodal：沒有視覺，除了數值，還看序列周圍的文字，描述、名字、tag，以及事件，例如 log 裡發生什麼，而且不是一次一條序列，是能相關的多條。全部灌進去，讓它真的會預測。異常偵測就是拿預測跟現實比。有些情況還能趕在 incident 前面：你這個 monitor 一小時後會觸發。Monitor 在資料庫的 CPU 上，他們看到排隊的 query 在上升。這不是寫成規則，是 model 學到的。第一個研究版本結果很亮眼，他們在做下一版。

[33:19](https://www.youtube.com/watch?v=-5N53Xq5DX4&t=1999s) 主持人說這符合一個趨勢：用 transformer 在特定切片做更小、更快、也更好的 model。產品上，Toto 是只出現在 Datadog 裡的引擎，還是開放權重讓別人建。Pomel 說現在什麼都在桌上。某時一定會進 Datadog，這是為什麼做它。他們很想要 open weight，但對資料很小心：合約上能做什麼、不能做什麼、什麼是對的。正在做。大客戶能不能用自己的資料做 model，他們也在實驗。今天看到較廣的 model 跨客戶更好，因為客戶的資料很雜，但共用很多元件。大家都用 MySQL 和 Postgres，是同一種資料庫；銷售指標名字裡都有 sales，語意也有點像。低摩擦很關鍵。產品第一天就要有用，人把資料接上就想立刻看到事情發生。以後變好是加分，若不能很快顯出價值，根本到不了那裡。主持人拿很有經驗的人進一個新系統作比：一部分是看過這裡的 Postgres，一部分是分析，記憶體和 CPU 長這樣就是麻煩的配方。把知識從客戶帶到客戶。上面再加一層針對單一客戶的 fine-tuning，他們也在看。

[35:51](https://www.youtube.com/watch?v=-5N53Xq5DX4&t=2151s) 基礎設施知識有用，對特定應用的熟悉也有用。Code 和應用知識傳統上不一定在 Datadog 的範圍。應用他們已經有，因為做 tracing，懂什麼造成什麼、什麼在跑。過去幾年很大的努力是把 code 放進 Datadog。客戶開始追 code 的主要驅力是 profiling。他們有一直在 production 跑的 continuous profiler，若有完整、可讀的原始碼，就能把正在執行的東西對上 code。他們也做 IDE 擴充，讓人從 code 所在的地方直接看到 production 發生什麼。

## 開發者愈少懂 code，觀察的就是業務

[37:00](https://www.youtube.com/watch?v=-5N53Xq5DX4&t=2220s) 主持人把生成式 AI 對開發的影響看成 DevOps 和持續部署的延續：加速、更獨立、軟體被更快做完、更新。他聽過 Pomel 在別的節目說類似的話。Observability 和把知識帶回 code 的迴圈會不會加速，平台的範圍會不會變。Pomel 先把水準對齊。開發生產力一直在提高，可以回溯四十年。跟四十年或五十年前的打孔卡和 assembly 比，今天至少有生產力一千倍，若不是更多。更進階的語言、螢幕、開源 library、雲端。你可以用很少的 code、很少的腦力做出非常複雜的東西。他覺得 AI 會再來一百倍或一千倍。生產力上去之後，開發者愈來愈不懂應用怎麼工作、在做什麼。工作從「讓我把 code 打出來」轉成：它動不動、動得好不好、是不是花太多錢、對業務有沒有做該做的事、其他系統或客戶變了它有沒有壞。這些問題會隨著生產力一層層疊上去，變得更有價值。

[39:13](https://www.youtube.com/watch?v=-5N53Xq5DX4&t=2353s) 若不寫 code、對 code 能見度更低，觀察還是在看 code 嗎。找到問題時，要改的不是基礎設施就是 code。不熟 code 之後，observability 的核心要不要變。他說會是端到端。最後觀察的是業務。使用者有沒有做對的事、有沒有得到價值、有沒有被好好服務。更具體：我 ship 了這個功能，有人用嗎、有沒有造成差別。再更具體：我改了這一行，影響對不對。有時你仍會做這些特定修改。未來是蓋住這條端到端，幫人回答這些問題，並接回開發者用來構想和建造應用的東西。今天大多是各種 code editor 和 IDE，寫完就 ship。主持人說自己和其他人也在建那個未來。最後狀態要看那些新的建造方式。主持人把焦點收到使用者或業務：對 code 再尊重，該觀察的是客戶體驗或結果。問題辨認該盯結果。為什麼發生，則要適應那是 Tessl 裡的 spec、是 code，還是另一條路。

[41:30](https://www.youtube.com/watch?v=-5N53Xq5DX4&t=2490s) LLM observability 這個名字，兩年後也許完全不同。他甚至不知道還會不會把 model 叫 LLM。供應商提供的形狀、名字都可能變，對語言的聚焦可能變少。把 AI 這個詞唸得愈勤，聽起來愈空。每個流行詞最後都會失去意思。但他認為應用裡非決定性的部分會變大。Model 被訓練，也許持續訓練。要量的是結果，它們實際產出什麼。不能是寫完 spec 的那一刻就知道應用在做該做的事。Ship 出去、被人用了之後，發生的事像不像你想的，有沒有新東西，安不安全，有沒有被濫用，有沒有幫到對的業務結果。人用到非決定性的那一塊時，會不會買更多、留更久。這些極難，需要新工具。建在 model 上的公司，需求會跟著 model 的世界一起變。這一段 stack 最後長什麼樣，至少還要幾年。

[44:01](https://www.youtube.com/watch?v=-5N53Xq5DX4&t=2641s) 主持人複述：人會以為 LLM observability 是抓住聊天的 trace。過渡期也許對。真正的問題是業務或結果的監測，因為產品不可預測。除錯要技術細節和 trace，但 outage 不會從 trace 看出來，要從結果量出來。Pomel 說 trace 非常低階。你很少會一步步讀聊天或 agent 裡發生了什麼。那是在驗證你對發生了什麼的假設。要緊的是有沒有回答所有請求、有沒有產生交易或其他東西。你會看到：以前 1% 的對話讓終端使用者不滿意，現在 5%。為什麼。鑽下去，那 5% 都在 embedding space 的同一區，也許某個資料源變了、那裡的資料變壞，或後面的 model，或別的東西變了。再看具體對話、agent 之間的互動，才懂哪裡錯。這是一整套新的理解和除錯。對他們的主要挑戰是空間和 use case 變很快。一年前推出那個產品時，看到的大多是 chatbot。現在 agent 比 chatbot 多。不是終端使用者問 model，是 agent 自己問 model，並且迴圈。兩年後會在哪，還要看。

[46:07](https://www.youtube.com/watch?v=-5N53Xq5DX4&t=2767s) 這條線會跟 product analytics 混在一起。他們有一個相當新的 product analytics，建在 real user monitoring 上。一開始是效能：有沒有錯誤、渲染速度、夠不夠快、有沒有變差。現在走向 click stream：人在做什麼、用什麼、不用什麼、有沒有得到你要的結果。他說這對任何跟 AI 有關的東西都關鍵。一般應用，開發完、ship 到 production 的那一刻，你對它做不做該做的事有不錯的想法。AI 應用沒有，得在 production 量。主持人說問題的核心是：要辨認問題，先得知道什麼不是問題。生成式系統定義很鬆、一開始就不可預測、任務很寬。異常偵測還可能嗎，還是只能在較窄的業務結果上找異常。Pomel 說有一批異常偵得到。可以對 model 輸出的統計分佈做各種檢查，看變化、看 drift，追一批指標。甚至有相當可靠的方法，不需要 ground truth，只看資料分佈，就能估計是不是 hallucination。這些是好的啟發式，不必等使用者先定義業務目標。

[48:41](https://www.youtube.com/watch?v=-5N53Xq5DX4&t=2921s) 另一個攻擊面是濫用或詐欺。使用者和資料、執行、功能混在一起，互動又很文字。他們會不會看這些資料，線畫在哪。Pomel 說線還很難說，因為還不知道 model 最終的功能集。商業 model，以及其後的免費 model，會不會內建保護和過濾。今天沒有，領域還年輕，可能變。他們很清楚的是：看懂應用，就要看進 model、出 model 的資料。未來沒有這個，做不出觀察。資料的輪廓變了。以前看 trace 和 log，大多不是 primary data。醫師處方、社會安全號碼通常不會進 log 或 trace。進出 model 的資料會帶上全部 primary data。能拿來做什麼、怎麼存、給誰存取，含義都不同。要新建一批功能和保護。從生意看，得先做這筆投資才打得開機會；資料在了，也能給客戶新的價值。夢一直是：觀察應用，世界在數位轉型，應用在跑業務，所以觀察應用就是觀察業務。在 AI 裡更真，因為觀察應用現在就是在看構成業務的全部 primary data。

## 介面會像人，但汽車仍該有按鈕

[51:07](https://www.youtube.com/watch?v=-5N53Xq5DX4&t=3067s) 再過五年以上，agentic 系統建起來了，安全門檻也有了，聊天被他說過是有限的路。介面會變成什麼。今天已經看得到，把系統表現得像人，對使用者有吸引力。有些也許是聊天，但不是你問問題，是機器跟你一起做，否則你很難知道該問什麼。語音也是。一群人即時處理問題時，語音會是好的方式。軟體產品，包括他們的，最後會更像你打交道的人。UI 仍會在，因為 UI 很適合消化資訊、看懂你能做什麼。啟動汽車時，有按鈕、知道發生什麼，比跟它開一場對話好。烤箱也一樣。開放式的、像人的介面是補上去的。

[52:53](https://www.youtube.com/watch?v=-5N53Xq5DX4&t=3173s) 壞的情境是 hype cycle 和賣得太滿。他不在財報電話裡把 agent 的時代賣過頭。以今天來說，技術還沒完全到。看得到地平線和潛力，但不是今天就在現場大規模發生。他擔心技術被賣過頭，跟客戶和使用者的信任破掉。Monitoring 和 observability 裡發生過很多次。公司前十年很不願意在網站上放 AI，因為他把它跟不能用的東西、跟賣過頭聯在一起。十年前有一整類叫 AIOps 的產品，裡面通常沒有 AI，那個 AI 的部分是 regex。他想 undersell、over-deliver。主持人完全有共鳴：他曾刻意把 AI 從 Snyk 那個 AI 驅動的靜態分析投影片拿掉，因為會降低客戶信任，雖然那其實是老派 AI；等它又有吸引力，還得再爭取放回去。做了三十年 AI 研究的人經歷過冬天，很熱，然後很冷，十年沒什麼發生。Pre-training 起來之後，曾怕會慢下來。結果 RL 很快補上，現在又有一條大家興奮的擴展向量。兩頭還得接上。大多數 agent 對大多數 use case 夠好，還沒到。可靠是關鍵。

[55:18](https://www.youtube.com/watch?v=-5N53Xq5DX4&t=3318s) 雇什麼樣的人來做這些 AI 產品。誰被雇，沒有大變化。他們一直最看重人能不能成長。他在 Datadog 之前和在 Datadog 都看到：雇來的人通常極聰明，又聰明又願意成長的比較少。第二天有人說你換個方式試試。他們要的人會說讓我試試，而不是我覺得我做對了。極聰明的人常常是自己最大的敵人，知道自己聰明，就不演化。新的一類是過去一年開始建的 AI research team。以前沒有，一切都是應用，做進產品，沒有正式的研究團隊。對比二十年前的研究。他的職涯從研究開始，來美國是因為在紐約上州的 IBM Research 工作。那時很酷、很有吸引力，在 Google Research 之前。當時產品來自超過十年前的研究，東西很難直接從研究跨進產品。他因此離開。今天產品裡能找到不到六個月的研究，而且很大一部分從未發表。把研究和產品開發灌在一起，價值極大。這隊放在 co-founder、CTO Alexis（字幕聽成 Alexi）底下，打破一般的產品部門。研究仍不一樣：不會每天早上 scrum、告訴研究者今天做什麼。研究要多一點獨立。

[58:00](https://www.youtube.com/watch?v=-5N53Xq5DX4&t=3480s) 過去幾年用 AI 建造，最讓他驚訝的是變化速度。他建過公司，沒看過這種創新和變化的速率。他最喜歡的笑話是：人家總問 AI 幫他省了多少時間，他的回答永遠是還沒打平。他仍花更多時間在學它。他預期這會持續。變太快，學和補齊程度都要很多時間。主持人說這回到你要的團隊能力：能應付變化速率。那本來就好，現在大概是打了類固醇。

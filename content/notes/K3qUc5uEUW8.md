# Introducing AI Native Software Development, and Announcing Tessl

片長約 39 分鐘，英文自動字幕。AI Native Dev 的第一集，由 Tessl 播出。Simon Maple 和 Guy Podjarny 主持。字幕把 Tessl 聽成 Tesla、tessel，把 Snyk 聽成 sneak、teque。這份筆記依英文原稿整理，專有名詞保持英文。

- 原片：[YouTube](https://www.youtube.com/watch?v=K3qUc5uEUW8)

## 一句話

他們要先把 AI native 定義清楚，免得它變成沒有內容的 buzzword。今天的 Copilot 這類工具是 AI assisted：在既有流程裡讓人更快，像雲早期的 lift and shift。Guy 相信那是好路，不是最好的路。最好的路是假設 LLM 本來就在，從第一原理重做開發：人講 intent，機器做 implementation。這一集也是 Tessl 網站、部落格和這個 podcast 上線的日子。

## Assisted 很有用，因為它不用你改變怎麼工作

[0:18](https://www.youtube.com/watch?v=K3qUc5uEUW8&t=18s) 兩人上次錄音超過六個月。這不是他們第一個 podcast。上一個叫 The Secure Developer，名字像是巧合。大約八年前 Guy 開始，一百多集，談怎麼把安全嵌進軟體開發，現在 Daniel 還在主持。Simon 當過共同主持，做過月報、訪問過客人。那個節目在把安全推進開發者的動作裡。

[2:08](https://www.youtube.com/watch?v=K3qUc5uEUW8&t=128s) Guy 用歷史看每一個新範式。新技術來了，第一件事是拿它改善今天的做法。雲是近例：VM 還是你要的 VM，只是跑在別人的環境，不必自己備機器、管容量，打一支 API 就在別人的資料中心拿到等價的東西。Lift and shift 很有收穫。真正的價值後來才被看出來，不在 lift and shift。那個詞現在帶一點貶。Cloud native 是真的改怎麼做軟體：microservices、基礎設施的彈性、以及其他做法，還有一起長出來的 DevOps，才能把雲擠乾。比較難。數位轉型不全是雲，但痛，因為你得改變做法。

[3:28](https://www.youtube.com/watch?v=K3qUc5uEUW8&t=208s) 他覺得 AI 正在重演。AI assisted 是用 Copilot、測試生成這類工具，加速你今天的開發。這個 podcast 會談它們。它們被採用，是因為可以待在既有系統裡。他的信念是：這是好路，不是最好的路。AI 時代真正的機會是從第一原理問：若你預期 AI 和 LLM 的能力都在，你想要的開發流程是什麼，然後把整套方法建在那上面。

[4:21](https://www.youtube.com/watch?v=K3qUc5uEUW8&t=261s) Simon 點名 GitHub Copilot，以及當時剛被稱作 AI software engineer 的 Devin。Guy 說這些工具很驚人，該探索、該在相關的地方用，也很關鍵。它們有缺點，有時是安全，有時是幻覺。長期看仍是更好的開發方式，所以這麼多人愛上它們。他要把兩者分開。Copilot 和一堆 coding assistants 在他看來是 AI assisted。門檻很低：你本來就在寫 code，工作方式沒變。自動完成你可以眼睛看過、知道對不對。摩擦低、改變少，只是讓你更快。他完全贊成擁抱。但他說這把 AI 最後能做的事賣短了。它們是助手，不是自主。你還在同一套方法、同一條路上。

[5:59](https://www.youtube.com/watch?v=K3qUc5uEUW8&t=359s) AI native 要問的是：那段 code 你本來需不需要寫。Copilot 決定塞進那一段的洞察，從來沒被講出來。若你用更高的語言說這是 intent，讓系統去生那些東西呢。一旦真的升上去，怎麼 build、怎麼做版本，都會不一樣。今天該用的仍是 Copilot、Copilot 的 tab，或 Augment，還有一批類似的。挑適合你的來試。本質上仍是輔助：人在 IDE 裡逐行寫、逐行看，做法一樣，只是希望更快，或不必再去翻文件。

[7:09](https://www.youtube.com/watch?v=K3qUc5uEUW8&t=429s) 用 AI 創造，他看到兩種模式。人在駕駛座，AI 是助手。或者像 Devin，AI 是創造者，人是編輯。多數開發者和創造者並沒有選擇當編輯。有人喜歡，很多人不是。助手自然有天花板：你還是得在場。可以去當另一邊的經理，或當編輯。機會是分開：哪些要來自人，哪些要來自機器。對軟體來說，很多就是把 intent 和 implementation 分開。

## 早上起床的理由要留著，coding 本身是另一個問題

[8:10](https://www.youtube.com/watch?v=K3qUc5uEUW8&t=490s) Simon 問，若未來只是寫一段短 prompt 給 Devin，什麼還能讓開發者有創造力。Guy 說這正是要探索的：AI native development 是什麼，AI native developer 是誰。軟體開發有趣的驅力有兩個。一是創造感：你要一件事完成，然後它完成了。這推動他。他說自己現在是生鏽的開發者，他們拿 Rust 開了玩笑；他當 overhead 之前是 polyglot。創造的興奮是「我做出了這個」，高過你在用的那套做法。編輯的問題是它感覺不是你的。創造的時候，人必須感覺自己在創造。二是遊戲機制：你一直能升級。解一個謎，再在另一層解。有點成癮。所以有經驗的人不會因為第一百次做 rollback，或又一個登入表單而興奮。那像已經 100 等，還被叫回去打第 5 關。

[10:21](https://www.youtube.com/watch?v=K3qUc5uEUW8&t=621s) Simon 說文件、測試，以及開發者因為重複或不想做而拖延的事，AI 可以拿走最無趣的部分，把時間還給別的。Guy 同意。創造是為了什麼；對多數人，軟體開發這份工作也許只有 5%、10%、20% 是 coding，其餘是周圍的事。有些仍是創造：把怪的地方熨平、測試、確認能動。很多是苦工和重複，例如把文件更新成你實際改了什麼，而不是得做兩次。這些可以自動化。

[11:30](https://www.youtube.com/watch?v=K3qUc5uEUW8&t=690s) 他絕對相信軟體開發會留下。Coding 是另一個問題，仍在探索裡。軟體開發是在數位世界把想法做成活的：重複的任務、把四周的資訊和活動聚起來、一個創造的出口，或只是好玩。沒有理由認為這些會消失，所以仍要生產軟體。他用音樂的民主化：做音樂愈來愈容易，新的創造者進來，這很棒，也造成發現的難題，挑戰了一批商業模式。產業實質變了。數位世界裡做工具的需要和能力會好好活著。有些原則會一樣：軟體不是做出來就丟掉，你要它隨時間演進；有的軟體好玩、可拋，有的是 mission critical，細節非常關鍵。會變的是怎麼做、怎麼維護、怎麼協作。生態系整體可以只往更好改，但有些角色和需要得改。他們想幫著定義那個新世界，留下好的，接上新的力量，也幫大家適應、學該學的、丟掉壞習慣。這個 podcast 就是要揭開軟體開發周圍的 AI，跟各類專家談。

## 他相當確定的假設：spec 取代 code 當重心

[14:16](https://www.youtube.com/watch?v=K3qUc5uEUW8&t=856s) Guy 的背景：很早做 AppSec，在它還沒有名字時做工具，經過幾次收購。離開後在 DevOps 創了 Blaze，讓網站更快，被 Akamai 收購，他當了幾年 CTO，字幕把 Akamai 聽成 akami。那段他學會欣賞現代開發，以及開發工具要怎麼對上做法。過程中搬到倫敦。離開後創了 Snyk，他說這是目前最為人知的。前提是開發愈來愈快，這是好事，安全跟不上，所以安全得做進開發裡。做法是做一家開發者工具公司，不是安全公司。Snyk 是他的驕傲，有高低，現在一千多人，還在長，希望是世代公司。公司變大後他被拉回創業。今年初創了 Tessl。他從這些旅程得到的是：若你去理解世界往哪走，並推動你認為對的地方，就能幫著塑造事情怎麼做。不是一個人。和思想領袖、早期採用者一起。做一個讓人發聲的平台，綜合那些意見，也加上自己的。這在 DevOps 和 developer security 都很巨大，也是這個 podcast 的核心。

[16:42](https://www.youtube.com/watch?v=K3qUc5uEUW8&t=1002s) Simon 在 IBM 做了十多年 middleware，後來進 DevRel，在 ZeroTurnaround 六年，Java 那邊很多人知道 JRebel，他在那裡把開發團隊建起來。他笑說自己不是 Java champion。他們在 Snyk 認識，他在那裡六年，也想加入新的創業，然後聽到 Tessl。

[17:27](https://www.youtube.com/watch?v=K3qUc5uEUW8&t=1047s) 什麼叫實務上的 AI native，Guy 先說他們不知道。目的地的期待和今天有差距。雲的最初幾天就想做 service mesh、彈性運算和 microservices，大概會失敗。技術的成熟和做法的成熟是一起的。有些是願景，有些今天就能用。這個對話是要當社群談原則和想法。他今天以為知道的，幾個月、幾年後會變。

[18:31](https://www.youtube.com/watch?v=K3qUc5uEUW8&t=1111s) 他相當確信的最大變化，是從 code-centric 到 spec-centric。今天：拿到需求，寫 code，在 code 裡做一百個永遠離不開 code 的決定。Code 很快變成 source of truth，我們專注於讓它演進、變大。Code 把要做什麼和怎麼做耦在一起，於是成為重心。AI native 會有辦法規定我們需要什麼，由 AI 提供實作。這很不一樣，也不容易。怎麼規定軟體、怎麼下指令、怎麼表達意圖、怎麼審查 AI 做的決定、什麼時候明確規定、什麼時候委託。都還要演進。根本是：你規定要什麼，AI 處理實作。

[19:46](https://www.youtube.com/watch?v=K3qUc5uEUW8&t=1186s) 因為實作由 AI 處理，實作會變得容易、便宜，像彈性運算：可以當場生成一份實作。於是它變成與語言無關。同一份軟體可以马上是 JavaScript、Python、Java 或 Rust。這對生態系意味什麼，哪裡有用、哪裡沒用。你造出來的 spec 是不是一種更高的程式語言，是不是你在編譯的 source code。Compiler 是什麼，一個還是很多。Spec 語言是一種還是多種。若軟體這麼好做，版本和打包該怎麼想。他比成機架上的實體機器或 VM，對上雲裡隨開隨關的彈性機器：生命週期、身份、安全態勢，管法完全不同。這些問題都會從 code 轉到 spec 這個核心變化裡長出來。

[21:15](https://www.youtube.com/watch?v=K3qUc5uEUW8&t=1275s) Simon 說新時代很大的挑戰，是熟悉寫 code、盡量活在 IDE 裡的人，要改用自然語言處理問題，看更高的概念，而不是更低的每一行。這把開發者的思路往上抬：什麼對應用重要，而不只是實作的細節。Guy 記得他們第一次談時，Simon 說這會把開發者變成 architects。他喜歡這個比喻。有人會走 architect：我要怎麼描述這個系統。有人更像 product manager。也可能有還想不出名字的職責。你能不能講清楚要什麼、你的 taste、偏好、想做的取捨，以及系統能不能把這些從你身上問出來並抓住，會決定結果好不好。Simon 補：在那個層級想的是商業價值和使用情境，而不是迷失在 code 裡，於是有機會做出更好的應用，因為焦點在使用情境，以及功能和那些非功能的面向。

## Tessl 上線，信念來自 Snyk 那次「必須發生」

[22:50](https://www.youtube.com/watch?v=K3qUc5uEUW8&t=1370s) Simon 說這個 podcast 由一家叫 Tessl 的公司主持。他開玩笑：有些公司喜歡把母音拿掉，Tesla 是一家；他搜尋之前幾乎找不到。Guy 說這是他的毛病，名字要短。Snyk 沒有母音，Tessl 至少從零到一，是進步。Tessl 是他今年稍早創的，專注 AI native software development。他說 our，因為 Simon 在公司旁邊一起做這個開發者運動。目標一邊是這個 podcast 在做的：推廣這個想法，和社群一起塑形，幫大家準備下一代開發。另一邊是做一個貫穿生命週期、為 AI native 而建的平台。未知很多，邊做邊搞清楚，這就是有趣的地方。這一集播出的日子，也是網站、部落格和 podcast 上線。

[24:13](https://www.youtube.com/watch?v=K3qUc5uEUW8&t=1453s) 任務錨在未來：世界往哪走，和系統一起演進。可以期待很多合作、對話，以及相當程度的實驗。希望今年之內就能有 beta 產品可以試、給意見、一起重塑，累積今天的技術什麼做得到、什麼做不到，把回饋送給該收到的人，再調整自己。在那之前會發內容、跟聰明人談、把舞台給他們的想法、談今天真的能用的 AI 工具。部落格和電子報是在把這個領域的對話加大。背景裡在做一個從這些對話學習的產品平台，既要兌現一些承諾，也要試這些想法看什麼有效。Simon 請人到網站訂閱，產品開放早期測試時會通知。

[26:13](https://www.youtube.com/watch?v=K3qUc5uEUW8&t=1573s) 和 Snyk 的對照：Snyk 給他的信念是，若一件事是對的運動，你真的去探索怎麼讓它發生，它就能變成現實。他開始時的反彈是：開發者不在乎安全，永遠不會擁抱安全。沒有人反對「他們必須」。於是一個矛盾：大家都同意 DevOps 和雲加速了開發，安全跟不上、已經落後、沒有別的路、必須進到開發者裡；同时又說開發者永遠不會擁抱安全，他們只在乎功能。犬儒沒有幫助。Snyk 問的是：若它必須發生，我們怎麼做；若只在乎讓開發者擁抱安全，我們會做什麼。他覺得成功了，離完美很遠，安全還沒有變成開發者清單的最上面，但他們開出了做法，讓安全成為日常流程裡自然的一部分。現在多數開發工具會放進一些安全，安全團隊也幾乎都把它放進安全計畫。盯住必須發生的目的地，可以曲折，他們沒有全部做對，但真的有機會找出那條路。門一打開，你就在塑造產業。這比生意本身更讓人振奮，像是把產業的這一片放到對的路上。

[28:21](https://www.youtube.com/watch?v=K3qUc5uEUW8&t=1701s) 這裡的野心更大。開發者安全一點也不小，但這件事更巨大。挑戰是把它收窄、拉回現實、讓它今天就能運作，才開始學習。每樣東西都是產品，V1 總是很糟，所以得開始。做法首先是找盟友：誰也在 AI native 這輛車上，聽他們的想法，拿去試。他們在做的很寬，沒辦法像當時出 Snyk 那麼快，但很想放到野外，被說笨蛋的時候聽得見。靠迭代，不會一次做對，同時守住信念。信念是 AI native 會發生。AI 太劇烈，機器能生成 code 這件事太強，正確的開發方式不可能還和今天一樣。只要這個前提還對，這裡就有價值，也有產品和方案可做。

## 不是飛天車；code 可驗證，所以會走得快

[29:53](https://www.youtube.com/watch?v=K3qUc5uEUW8&t=1793s) Simon 問這會不會只是幻想，對上今天的技術、幻覺、LLM 在編。Guy 說今天用的每一項核心技術，都曾被人當成幻想。這比飛天車不像幻想，不是科幻電影，但確實把邊界拉緊。做 LLM 的人會說它們今天仍很弱，因為他們看得到潛力。他們做 Tessl、做這個概念，是錨在未來。賭注是這些模型會好上好幾個數量級，人駕馭它們的能力也會真的變好。能生成 code 是一回事，不是每件事都得是 AI，也不是每個 AI 都得是 LLM。這些工具可以造。短期要找比較窄的路：稍簡單的軟體，或更做得到的解。公司是看著未來在建。關鍵不是 AI native 多快到來，而是怎麼把它做對、能學到什麼。團隊的背景給了多一點繩子，可以多花點時間。他們想和這裡的人一起做，把東西送出去，好被人說錯，才知道走哪條路。

[32:14](https://www.youtube.com/watch?v=K3qUc5uEUW8&t=1934s) 他的計畫 A，不一定是預測：這類 LLM，尤其是裡面的 code generation，進步會非常快。較少人想的是，code 和少數其他領域一樣，是可驗證的。領域愈難捉摸、愈難說結果對不對，愈難除掉幻覺。Code 常常能得到確定的結果，所以它大概是、或肯定是 LLM 裡進步最快的領域之一。也有只專注 code 的基礎模型。很多東西會很快來。

[33:10](https://www.youtube.com/watch?v=K3qUc5uEUW8&t=1990s) Podcast 有兩條路。Simon 每週二一集，看今天的工具：code completion、測試、文件，跟不同的人談今天能做什麼、AI 為什麼以及怎麼改善那一塊、他們在這趟旅程的下一步。Guy 從未來往回錨。有時是同一批人，或同一家公司裡想得更遠的人。很多對話會談今天，但 AI assisted 這條路上正在建的技術和做法，是搞清楚目的地的關鍵學習。這個空間裡最好的公司不只想今天做什麼、怎麼贏過競爭，也想五年後的目的地長什麼樣，常常對那個領域有獨特看法。他也想找在別的創造世界裡用 AI、做 AI 工具的人，把他們對 AI native 其他事情的學習借過來，因為很多能用回開發，也想被產業外面啟發。今天和明天合在一起，才能從已經有時像科幻的現實，畫一條線到更遠的未來。去跟一個 LLM 聊天，本身就有點科幻。Simon 說自己在寫 Python，誰想得到；那是反烏托邦還是烏托邦，不知道。

[35:32](https://www.youtube.com/watch?v=K3qUc5uEUW8&t=2132s) 他們不是來談方案，是來問問題，當社群一起學。不同人的意見，價值不能被低估。他們深在這個領域，會分享自己的學習。從 developer security 學到的是，真正的價值來自跟很多其他人談：用過 AI 開發工具的、做過的、想過它們往哪走的、正在試這些路的。有時是全新的想法，有時是你已經知道的被肯定，有時是模式：大家都在做這件事，那裡有東西要懂。資料一樣，有品質，也有數量。客人會有很亮的時刻。安全開發者這些年也給了看趨勢的角度。他打赌早幾集兩三年後再聽會有點尷尬，但能看到當時的看法。他預期理解會進化一個數量級，也許兩三個月後就會。Simon 笑說不確定學得了那麼快。

[37:22](https://www.youtube.com/watch?v=K3qUc5uEUW8&t=2242s) 下一集 Simon 要跟 Amir Shevat 談，字幕作 Amir shvat。Guy 跟他認識很多年。他們要先把 AI 工具分類，才知道深挖什麼，而不是只說深挖 AI。開發者或組織該想哪些面向、AI 能放進開發組織的哪裡，然後每一塊再深挖。第一個題目是 AI code completion。Guy 說 Amir 很會分類，在開發、DevRel 和開發者運動做過很多，包括在 Slack，以及字幕聽成 switch 的地方，現在投資很聰明的 AI 開發工具。

# From building CoPilot as GitHub CTO to building a code foundation model at Poolside w/Jason Warner

片長 62 分 17 秒，英文自動字幕。Guy Podjarny 訪問 Jason Warner。他們認識大約八年。Jason 當 GitHub CTO 時做出 GitHub Copilot 和 Actions，之前是 Heroku 的 GM，更早在 Canonical，中間在 Redpoint Ventures 待過，現在創辦並經營 Poolside。Poolside 是像 OpenAI、Anthropic 那樣的 frontier AI 公司，領域是軟體，做給軟體開發用的語言模型。他開玩笑：有馬達的東西他沒用，有鍵盤的東西他有用。節目是 AI Native Dev，由 Tessl 製作，字幕把 Tessl 聽成 Tesla。這份筆記依英文原稿整理，專有名詞保持 English。

- 原片：[YouTube](https://www.youtube.com/watch?v=-8lOXbv3DHQ)

## 一句話

模型變大、資料變多、算力變多，能解的問題就更複雜。解是加引號的：它依機率回答，數學上知道怎麼運作，卻不能每次預知答案。通用模型加進 code，推理會變好，回答程式問題是副作用。Poolside 把焦點放在軟體，因為世界不是無限的。無限的算力、能源和資料裡，通用模型是走向 AGI 的路。有約束時，專注給出更好的結果。他們一半自然語言、一半 code，並用程式執行的回饋做大量合成資料。今天仍是開發者坐在鍵盤前的世界。沒有一個模型是初級開發者。從 PRD 直接吐出能跑的系統，是以後的聖杯，不是現在。

## 加進 code，通用模型會變聰明

[2:34](https://www.youtube.com/watch?v=-8lOXbv3DHQ&t=154s) Guy 問 code generation 為什麼現在做得到。Jason 說業界欠 OpenAI 一份情。從商業化、從公司的角度，他們在這件事還不流行時做了很多年苦工，證明 scaling laws 會成立，學界和業界猜測的不少事情是真的，而且有膽子把很多錢丟進去。模型變大，丟更多資料和算力，就能解更複雜的問題。他把 solving 放在引號裡。他看這些東西的方式是：你問一個問題，它內部有一大團代表性的狀態，知道怎麼在裡面移動。業界常說我們不一定知道它們怎麼運作。他說我們知道，全是數學。不能說的是每一次答案會是什麼。它們依機率回答。我們比較懂怎麼教它們，比較不懂它們從每一筆裡蒸餾出什麼，以及怎麼把它們推到人類願意打交道的樣子。

[5:06](https://www.youtube.com/watch?v=-8lOXbv3DHQ&t=306s) 早期有人以為模型是從註解和 code 周圍的文字學會程式，後來才有專門的 code。歷史是：早期出現只在原始碼上訓練的 code-specific 模型，現在仍有人在做。OpenAI 和 Anthropic 是通用的，訓練資料裡有 code。Poolside 是領域專用，焦點在軟體，取向不太一樣。業界，尤其 OpenAI 和一批學者看到：通用的 NLP 模型一旦加進 code，會變聰明，推理和邏輯改善。有人研究為什麼。比較務實的人說這太酷了，那個為什麼他們不在乎。於是 OpenAI、Anthropic 和一批通用模型把 code 加進去，是為了讓一般推理更好。副作用是也能回答程式問題。對軟體的理解有限，但當下的 code 會很行。

[6:52](https://www.youtube.com/watch?v=-8lOXbv3DHQ&t=412s) 小型、只做 code 的模型擅長 ghost writing 和 code completion。他用自己的說法：華麗的 code completion，看你正在寫的下一行，補最後幾個 token。仍是 next token prediction，只是層級不同，然後到函式。Copilot 就是從這裡開始。Poolside 把方向反過來：把軟體當領域，推進 state of the art。機器人和藥物發現也會有人專攻一個問題。技法相同，scaling 的學習也用得上，還有 code 周圍的文字，以及從 code 走到 software。早期只看 code 的模型，常常不理 code 以外的東西。Guy 問今天是不是先有一個聚焦過的通用模型再增強，還是像過去的模型再補上。Jason 說 Claude、GPT-4 這類今天的通用模型，語言很強，把類似技法用到 code 上，所以知道怎麼回答跟 code 有關的問題。GPT-4 和 Claude 內部怎麼做，他沒那麼熟。Poolside 的網路技法稍有不同。Code 資料集和自然語言資料集要分開對待。交錯的地方得知道哪一段是哪一種：註解用一種方式，但必須相對於 code 的 context，code 也相對於註解。學習技法要稍微分開。

[9:39](https://www.youtube.com/watch?v=-8lOXbv3DHQ&t=579s) Guy 說有一整個知識世界錨在 code 上，不錨在語言上。Code 裡一個逗號放錯，功能就變了，糟得很。語言裡逗號放錯也糟，但人多半能略過，編譯器不能。儀器、telemetry、對不對，在 code 裡機會多很多。語言裡含意和你有沒有做對，往往更難推。

## 解釋比生成高一檔，初級開發者還不是

[10:24](https://www.youtube.com/watch?v=-8lOXbv3DHQ&t=624s) 什麼最讓他印象深。一件是完全不懂軟體的人，從無到有做出一個東西。以經驗看那本來要多久，循環和時間被壓下來，非常驚人。Twitter 上一直有人說用某個東西幾小時做出來，自己以前不敢想。另一件是他的玩笑：任何模型若能給出一條真的能在命令列跑的 ffmpeg，他就佩服。ffmpeg 是惡夢，旗標太多。他說在能回答 ffmpeg 之前，沒有東西算完成。真正讓他佩服的是有經驗的開發者。怪錯誤跳出來，剪貼進去，或問這是什麼，它知道，能給解法，能指到那裡。他第一次看到是做 Copilot 時的 GPT-3。他把一段 log 丟進去，它不是指 code，而是指出該從問題的哪裡想，並不明顯，他沒花很多時間看錯誤訊息，但答案是對的。最近他們自己在做的東西爆了，他把錯誤丟進去，它直接指到壞掉的那段 code。錯誤又長又複雜。他說但願自己不是 45 歲，但願是 20 或 15。接下來二十五年的職涯會完全不同。開場預告裡他還說過或是 50。

[13:14](https://www.youtube.com/watch?v=-8lOXbv3DHQ&t=794s) Guy 問這是檢索，還是推理。是省掉重複的事，還是網路裡嵌了某種深的理解。Jason 說很難答，是直覺。很多顯然是檢索，它看過。也有它不可能看過足夠資料卻答得出來的情況。他總拿冷門語言問 Poolside，Crystal、Pony。你看得到它對問題有一種智力。你要解的問題是 X，這個語法、這個語言裡的實作是 Y。前半是我們古典上叫的智力：懂問題，懂怎麼解，再套上去。那是人會做的事。話雖如此，我們所在的坡很陡。你以為我們在曲線的哪裡，其實在偏低的那端。未來五到十年會很誇張。Guy 說職涯往上走會自然變成 polyglot，懂的是概念。一開始更像檢索：這個 polyfill、這些 class、這個 SDK。坐下深想之後長出的直覺，常常超越語言，是系統怎麼運作。冷門語言幾乎證明模型的 polyglot。評估時，有經驗的人和天真的做法不同。隨便抓一個模型去打 HumanEval 和其他基準，很多是廢話，因為人們用那些資料訓練。基準一旦公開，就是那樣。另一種問法是叫它應用概念：若要在 Y 裡做 X。它得懂 X，也得懂在 Y 裡做那件事意味什麼。Rex、COBOL、Fortran，再到 Java、Perl、Python、Haskell。不是只說在 Rust 裡怎麼做 X，兩邊都得懂。

[16:37](https://www.youtube.com/watch?v=-8lOXbv3DHQ&t=997s) 今天的邊界。他的基線是：這些都是很好的 code assistant。他的詞是 Dev-led、AI assisted。開發者仍在正中央，手在鍵盤上，問問題或拿回饋。不管是 ghost writing、completion，還是並排的聊天。它 maybe 寫出行，人得接受，但仍是在協助。若十分為滿，解釋在上段，八到十。這個檔案或這個 repo 在做什麼，畫一段 code 請它解釋，或問在 Java 裡若要做這件事會怎麼做，都很行。往下一檔才是生成 code。沒有一個在生成上有解釋那麼好。客觀看，生成仍是強的功能，但若要分級，它在下面。它們都還有很長的路，才會從協助開發者，跳到自主的初級開發者。那是聖杯。大家一直說它們已經是初級開發者，不是。你仍需要一個手在鍵盤上的開發者。我們一直用包在模型外面的 agent，繞過模型的限制。GPT-2、GPT-3、GPT-4 都這樣過。最後模型本身會能到一個程度，那些 agent 也會退場，能力會在模型裡。他們還沒有強的，是他稱為 model agency 的那一側，所以才在做很多工具。它們不會自主工作。你可以把它們裝成半自主，但有限制。

[19:10](https://www.youtube.com/watch?v=-8lOXbv3DHQ&t=1150s) Guy 問這主要是可靠度嗎。助手若常常錯，也沒用。若夠常對，自主和助手之間至少有一個維度是：它做對的可能性有多高。Jason 的直覺是一條會往下掉的圖。你跟 GPT-4 或任何通用模型談軟體，愈要它具體，答案會隨時間變差，因為 context 愈拉愈寬，拉進來的東西太多。所以很多人在追 context。困難的問題要來回、要塞更多資訊，答案會愈不精確，感覺在退化。他說這是感覺，很難量。基準有用，是一把尺，但只有一個鏡頭。也有繞法：把先前要的東西塞進 context window，若模型訓練得懂這個，可以有某種信心。或在模型周圍做 embedding。他想這件事的方式是：大家問軟體開發者還會不會存在，是因為他們想像問一個問題，做一個 Twitter clone，然後 Twitter clone 就跳出來。那種聖杯他認為未來存在，今天不在。中間要的水管太多。不再只是 AI 系統，是它周圍的一切。做模型的人相信 AI 會到那裡。現在完全還沒到。

## 無限世界走通用，有限世界要專注

[21:22](https://www.youtube.com/watch?v=-8lOXbv3DHQ&t=1282s) 為什麼不先做通用模型，再把它賣向軟體。他說大家都有一個核心信念。拿 Anthropic、OpenAI、Poolside：前兩個是領先的通用模型，Poolside 是軟體的領域模型。信念是，在無限的世界裡，無限算力、無限能源、無限資料、大家同時，通用模型才是走向 AGI 的路。大家都在做同一件事：盡量用算力、丟資料、學得快、長得大、變聰明、變密。ChatGPT 已經讓我們學到，至少到相當程度，scaling laws 有用。更多資料、更多算力，結果更好。在那個無界的世界，大家會做一樣的事。我們不住在無界的世界。能源有限，此刻能網在一起的晶片有限，未來也有限，世界上的資料有限，時間要花在哪也有限。所以他和 Poolside 的信念，以及做機器人、做藥物發現的人，是專注交出更高、更好的結果。算力、資料、微調都圍著領域。Poolside 其實是一個不錯的通用模型。你問蝴蝶，或叫它寫歌、寫詩，它做得到。那不是焦點，他們不會朝那個行銷，也不會那樣微調。能量都花在這邊。分岔是焦點：資料集、人寫的回應、使用者怎麼跟系統互動。這該是第一個決定，也是務實的連帶決定。加進大量合成資料時，它在蝴蝶解剖上退步，他們不在乎。夠好就行，不必卓越。Guy 說更多資料可以變成更多分心，除此之外還有純粹的錢和算力。

[24:38](https://www.youtube.com/watch?v=-8lOXbv3DHQ&t=1478s) 他們的分布是五五分，50% 自然語言、50% code。LLM 就是資料上的分布。非軟體知道得愈多，就愈懂那一邊。軟體知道得愈多，能做的聯想愈多。微調資料也一樣。他們以 reinforcement learning via code execution feedback 出名：建一個巨大的模擬環境，產生大量合成資料來增強模型。這樣才走出世界上資料不夠的困境，是自己生出來的。這是他們秘密配方的一大塊。領域焦點要緊，是因為這件事太大。將近一半的工程、一半的整個團隊，在解這一個問題。只有把軟體當首要用途，才會去碰。Guy 說要懂 code，不只是周圍的字，也不只是靜態分析，還要看它在 production 裡。他記得 Jason 在 GitHub 時就談過未來，Heroku 的根也在。Jason 一直想把 code 和執行之間的迴圈合上。

[26:26](https://www.youtube.com/watch?v=-8lOXbv3DHQ&t=1586s) 有一條他想了十五年的工作流。開發者每按一個鍵，到 production 發生什麼，中間整條他稱為 kinetic 的鏈。最完美的系統是按一個鍵，production 就變，該有的防護都在。理論上不能把整個 SDLC 塌成那一條魔法工作流，但可以那樣想。鍵盤要緊，production 要緊，觀察軟體要緊，看 code 怎麼變也要緊，訓練時看歷史，未來才能回答某些問題。所以他們盯著領域。他著迷兩件事。一是開發者體驗，不只是聰明地回答問題。若有那條鏈，未來能讓開發者更好、更快、更簡單，把產業裡粗糙的邊磨平。Guy 把論點拆成兩半。一是有獨特資料，若你肯花時間和巧思做出來，模型會更懂開發者體驗，也做出更好的軟體。二是就算通用模型肯花這個功夫，它們要炸的魚很多，這份資料在整個網路裡的比例會比較小，結果會比較差。Jason 說第一點百分之百，他們證明過，最近一輪募資的基礎就是這個，資料都有。第二點要加 context，但答案是 yes。兩個大致相當、相當接近的東西，一直待在軟體這一側的，會做出更好的結果。不過若是 epoch 的差距，GPT-2 和 GPT-5，一個有特定取向的 GPT-2，很難補上和通用 GPT-5 的距離。那是 OpenAI 的整個論點：除了 scale，別的都不在乎。若他說唯一要緊的是專注，他就大錯。他自己也得跟上，把核心模型的推理變強，把網路變大。專注給的是另外的優勢。若一個模型大約只有 GPT-2 的規模，再怎麼專注，也不太可能接近 GPT-5 會到的地方。人得在同一個球場上，得有做出那種東西的 caliber。

[30:29](https://www.youtube.com/watch?v=-8lOXbv3DHQ&t=1829s) Guy 看 Llama 和 Code Llama，外部的理解是拿出跟 code 有關的資料子集，分開訓練，避開分心，但沒有 Poolside 那種對獨特資料的投資。Jason 說更細。把它們想成相似的家族，比較是取向。規模不會在那裡。傳言 Meta 即將放出 Llama 3，字幕把參數聽成 four and a five billion，沒有聽清。通用的 Llama 3 會有一個 Code Llama 變體，比較小，讓人用不同方式用。他猜是蒸餾得更小、更聚焦，或從較早的 checkpoint 再灌更聚焦的 code 資料。內部到底怎麼做，他老實說並不完全知道。他用運動員當比喻，因為大家把 code-specific、software-specific、general purpose 搞混。職業早期不要太早專項，先當一個通用的好運動員。想當世界最好，就得說籃球是我的，或高爾夫是我的。它們很不同，都要一定的基礎運動能力，然後專注。整個產業得接受：我們不住在無限無界的世界，得說我們自然會卓越的是這一件，其他 maybe 仍然不錯。把世界上最好的籃球運動員 LeBron James 放到 pickleball 場，基礎運動能力會贏過很多人。也會有 pickleball 專項的人贏過他，而那些人的運動能力到不了他。我們以為一個系統該解決所有事。永遠不會是那樣。

## 客戶的資料比不過公開語料，所以要偏心

[33:46](https://www.youtube.com/watch?v=-8lOXbv3DHQ&t=2026s) 在客戶的 code 上調或訓練，他說的是把客戶的 context 加進系統。客戶的資訊要讓模型拿得到，烤進模型裡，或放在模型周圍。他覺得這很要緊。程式的人可以想成：你有一個工具，周圍有一大堆文件。工具若和文件、和其他系統是抽象分開的，中間得搭一座橋。烤進去或烤在周圍，都行。不能忽略。忽略了，它只是一個抽象工具，你還得自己把它用到你的 context 上。他認為這在軟體裡比很多其他領域更重要。要知道哪些 API 存在、best practice 是什麼。在某家公司，我們用這些函式庫、這是標準、整個 SDLC、部署怎麼做、設定檔長什麼樣。大家都知道進公司第一天會問：這裡怎麼做事。最好的比喻是，就算很能幹的開發者，第一天可以寫 code，仍想看看周圍的 code。專案和專案不同，legacy 和現代的標準不同，會變成惡夢。像公牛進瓷器店，用自己的方式做，會被皺眉，也很難跟別人一起工作。

[36:17](https://www.youtube.com/watch?v=-8lOXbv3DHQ&t=2177s) Guy 問這知識對模型有多要緊。是看過 code，蒸餾出一份他說的 2100 頁、我們在這組織怎麼寫 code，放進 context。還是對系統本身的深理解，嵌在 code 裡：大家避開某個服務，擴展或卸載負載用某種 pattern。是人讀得懂、審得了的 best practice，還是得真的黏在企業裡那一大堆 code 上。Jason 先分兩種模式，最好這樣看：你是在網頁上問一個問題，還是在 IDE 裡跟這些系統互動。Poolside 把這嵌進各種 context。網頁上你問我會怎麼做。那時候有用的是解釋、給一個答案、來回。想像在企業裡問：我們這裡怎麼部署，AWS 或 GCP 怎麼部署。那是一套內部文件。或問我們一起做的 Bedrock 專案怎麼做這件事，再跟 substrate 專案比。這非常有用，專屬於客戶的 context，本身跟 code 無關，是標準和他們做過的事。但要對比，它得廣泛地看，看得到整個專案 A 和整個專案 B。它怎麼做那些聯想，就是為什麼這和只做 fine-tuning、只做 RAG 不同。烤進模型要緊，因為聯想要緊。它一般知道的，和這個特定 context，中間的聯想、分辨和推理，都要緊。

[39:09](https://www.youtube.com/watch?v=-8lOXbv3DHQ&t=2349s) Code 那一側他覺得更明顯。例如我們這裡怎麼防 buffer overflow。它愈看到這個客戶的 code，就會說這個風格沒看過，或看過但現在一直看到，這就是這個客戶的做法。這還沒到回饋迴圈。舉例：一間遊戲工作室用某種方式解決 buffer overflow 和某種安全防護。模型寫 code、跟開發者互動時，建議了一個錯的、比較通用、在通用世界裡比較常見的，而不是這個組織的選擇。你跟模型說不對，我們不是這樣，改成這樣。那個迴圈非常重要。那筆資料不是你訓練過的，也不在語料裡，它是調校資料。人和系統的互動因此很有價值。更新之後它知道：不能再給他們那種做法，得走這條，因為他們已經把它調成這樣。

[40:38](https://www.youtube.com/watch?v=-8lOXbv3DHQ&t=2438s) 巨大的企業 codebase，是十萬個小決定，還是蒸餾出一百條給新 code 的大規則。沒有一家公司比得上公開資料的規模。AI 世界資料的骯髒小秘密是：大家對資料的存取完全一樣。網頁資料、code 資料，都在做同一件事。世界上任何一家公司都完全比不過那個規模。所以不能靠客戶資料的數量。得懂怎麼偏袒客戶資料。模型長這樣，然後偏袒某些互動、某些較後的層，再進一步偏袒他說的 person preference。你說我們想這樣做，就得繼續偏袒那個偏好。你永遠不會有下一個情境那種數量。Guy 想起 Intercom 的 Dez。他們的自主客服 agent Finn，新客戶打開之後發現，Finn 把知識庫模仿得很好，但知識庫是壞的。什麼該用、什麼不該用，是支援組織裡的非正式知識，從來沒寫進知識庫。Code 是不是一樣：有些你想重複，有些不想。Jason 說在 code 裡一樣普遍，若不是更普遍。客戶最常回的一句是：若我不想讓我的資料被那樣偏袒呢，尤其是 legacy。Legacy 要在裡面，因為我們會犯錯，有時不想重複那些錯。人用錯了，或東西沒有好好變成熟。最好能給有代表性的好例子和壞例子，讓他們知道怎麼為你調。不能 YOLO。他最不喜歡的評估，是某個時間點問一個問題、拿一個回答，就說好或壞。每個系統不同。跟客戶互動時要說：給我們一些你想要的正向 context，和一些負向的。負向這個詞很難，他的意思是不要這樣做。想重複的，和不想重複的。Code 這邊他們其實有很多代表性例子，比別的多。若沒有負向，因為很多人不會把負向例子留著，正向也有用：十個現代專案，這是我們要的風格，資料都在這，但風格是這個。這全是客戶互動。不是一鍵設定。要把它們想成很大、很複雜的系統。Guy 開玩笑：我們要魔法，下一步、下一步，它就懂我整個系統。那不是 AI 的承諾。過程裡仍要說出偏好。

## 軟體先長出推理，因為它測得到

[44:43](https://www.youtube.com/watch?v=-8lOXbv3DHQ&t=2683s) 很多人覺得，基礎模型能進步的領域裡，code 排很前面，因為你能驗證對不對。寫一首詩，你不一定知道對不對。圖像也難。Code 至少看不看得過編譯，也許還能更細。Poolside 的核心信念是，真正的人類等級推理和規劃，會先在軟體這個領域出現。奢侈之一是軟體非常接近、也許是你能得到的最接近的確定性系統，而且有巨大的種子語料。回到他們的模擬器，和那個用程式執行回饋的系統。奢侈是能產生大量只有他們有的合成資料，模型會在那裡面更好地出現和演化。軟體本來更有界：可測、可執行、可驗證。有一整批產業還沒探索的東西，包括 Poolside。他們是領域公司，還沒到那裡，最後會到。想像把 Canonical、Heroku、GitHub 和他在 Poolside 的整個歷史接起來。你跟系統說做一件事，它能事先驗證生成的東西符合你的 SDLC，而且可跑、可執行、正在一個系統上為你跑。那是這裡能有的承諾和魔法。這是更難的問題，因為談的是整個軟體，不是寫一首詩或一封信、讓人腦去解釋。技術上更難，驗證上更容易。能圍著它建的魔法會很驚人。

[47:28](https://www.youtube.com/watch?v=-8lOXbv3DHQ&t=2848s) Guy 說跟藝術比，社會上的反對 maybe 少一些。法律、藥物發現，更難知道你有沒有做對。code 這件事，大家都希望我們做對。Jason 說他親身看到兩件。開發者有偏好，code review 時會說不喜歡這個風格。你不能跟「它在跑」爭。軟體裡的老話是 source code wins。理論上吵起來，寫出 code 的人通常主宰接下來的對話，因為大家都在對 code 反應。Code 最後贏。你可以一直把這個推進去。法律層級可以一直吵策略，這不是我們想怎麼處理這個問題。這裡有些奢侈。不管 Twitter 上此刻怎麼講開發者會被 AI 取代，人對推進這裡的系統更開放，因為他們習慣每五或十年一切都變。沒有人再用十年前寫設定檔的方式。沒有人再用五年前做某件事的方式。我們習慣了，所以對這種改變開放。法律或教育這些領域，則卡住很久。還有一個老套：懶的開發者往往贏，因為他們會把大部分系統自動化。這在某種意義上是懶開發者的終極工具。我們記得要獎勵那樣有創意地把工具用到極限的人，而不是百分之百的時間都當一個人肉。

## 先看過程，原始碼還在，但不是每個人都摸它

[49:24](https://www.youtube.com/watch?v=-8lOXbv3DHQ&t=2964s) Guy 的牢騷是：模型分析 code 時得拆出好幾層。它怎麼運作，位元怎麼動。它做什麼，尤其你說在結帳流程裡加一個東西，它得知道結帳流程是什麼。若要好好解釋，maybe 還得懂一點為什麼。今天的 AI 輔助開發，你用這三層裡的某一種語言提出要求，期待它懂 code、懂這些面向、對上這個請求，做完它的事，回來提案要改什麼。中間有時有計畫。有時對，有時錯。結論都只在動作上。很少有機會批評這些層。他們在 Tessl 很想 spec-centric development。Prompt 像互動、像 UX，按了按鈕。他想要的是活得更久的東西。Jason 說這是我們會走過的演化的一部分。今天你問模型，輸出是 code 或一個答案。你其實不知道它走過哪些步驟。你可以叫它解釋，但那總是事後的合理化。你想要的是思考過程。聖杯是 chain of thought 那一類。那才是有趣的部分。從輸入到輸出，中間是學校裡的 show your work。十分的題，答案對 maybe 兩分，展示過程是八分。我們得走到展示過程。等大家對那一段建立夠多信任，我們會再把展示過程藏起來，只信輸出。現在卻是在叫人相信沒有展示過程的輸出。自然會問：我能不能信。

[53:02](https://www.youtube.com/watch?v=-8lOXbv3DHQ&t=3182s) 很多人想從一份很詳細的 PRD，直接在另一頭看到東西跳出來。我們不在那裡。從 PRD 到那裡還有很長的路。中間步驟現在就得開始建。產業這個全球的我們，不要超賣。會有很多蛇油。也會不一致：有時能動，有時像魔法，有時不是。對在這上面建公司的人，更挫折的 maybe 是後者。它們可以在一部分時間、用很多膠水和鐵絲湊合著動。大多時候不會動，就是因為這些原因。那會貶低把事情做對的價值。他跟人家說：不要看 Twitter 上的 demo 或影片，就把整間公司送上那艘船去探索太空。你注定失敗。生命維持和那些複雜系統，你得懂裡面需要的世界。

[54:21](https://www.youtube.com/watch?v=-8lOXbv3DHQ&t=3261s) 明天的開發者是在寫那個 PRD 嗎，還需要懂 code 嗎。他總說世界上有兩種開發者，當然不止兩種，只是好講。一種想做一個應用，其他都不重要。我要解一個問題，原始碼、工具都讓開，它們是手段。他們不擺弄 neovim，設置很基本，在乎的是解決問題、去賺錢。另一種愛追 stack trace。光譜兩端。未來兩邊都會被加強。追 stack trace 的人會得到大量超能力，追到以前追不到的，做得更深、更好、更快。他們仍會以某種經典的方式和系統互動。只想把東西做出來的人，未來 maybe 永遠看不到原始碼。很誠實地說，很可能是一種 Midjourney 式的、正在跑的軟體輸出。東西壞了，就問系統怎麼修，試幾種修法，直到一種能動。很多軟體，尤其複雜度低的，並不需要有些人給它的那種注意。對這件事要誠實。這不是 low code、no code，但那些東西背後有這個想法。他不認為未來的人永遠都得跟原始碼互動。

[56:16](https://www.youtube.com/watch?v=-8lOXbv3DHQ&t=3376s) Guy 說他們仍需要懂系統。一邊是怎麼產出軟體，我寫了 PRD。另一邊是其他一切：怎麼版本化、怎麼包裝、怎麼散布、怎麼漸進推出，那進到營運。Tessl 想像的是整段開發圍著某種 spec，或其他指南、也許是測試和驗證，而不是圍著 code 轉。Jason 把世界切成幾個時刻。2021 年 6 月他們放出 GitHub Copilot，他不記得當時叫 beta 還是 alpha。在那之前每一行 code 都是人做的。最重要的產物是 code 本身，因為它是和這些系統互動的離散單位。進入這個 Dev-led、AI assisted 的世界之後，潘朵拉的盒子開了，這東西會留著。未來某個時刻，原始碼又變成一個產物，但不再是最重要的，因為重要的是意圖。軟體一直都是：這段 code 本來該做什麼。大家總說寫 code 有趣，但讀 code、解釋 code、理解 code，才是開發者花很多時間跟系統互動的地方。他相信未來原始碼仍是最重要的東西。我們能不能不用它。他認為不能，原始碼永遠會在。但開發者 maybe 不會用同樣的方式和它互動。就像他自己不必再用五年前跟 YAML 互動的方式。有系統讓他在更高的抽象上移動。

[58:28](https://www.youtube.com/watch?v=-8lOXbv3DHQ&t=3508s) 很多人問他 Heroku。收購前、被 Salesforce 收購之後，都有一個大計畫。收購大約十五年前。Heroku 的工作還沒做完。最高層是把開發和部署變得超簡單。`git push heroku master`，然後是魔法。收購之後他們一直想開始做逃生艙。百分之八十的時候，那條 push 很棒，你不用想。有一部分時間你得逃出去，做更複雜或更訂製的事。那一部分裡還有更小的一部分，得再逃一層。系統得長這樣。AI 系統也是。基本情況和邊緣情況。基本情況是大多數會動，spec 會動，你能從 AI 系統部署 code，不必想 code。某個時刻你得逃出去，做更冷門、更複雜、更訂製的事。若它們不支援那個，我們就有麻煩，因為你被關在一個你不懂的盒子裡。我們此刻甚至不知道該問什麼。他認為未來開發者真正在做的，是懂怎麼問問題。他不認為未來的開發者能脫離軟體開發的基本功，因為他們得懂這些系統。就像硬體工程師就算不專注那一塊，仍得懂怎麼把系統建起來的基礎。Guy 說他們常想開發者走向產品經理，或走向架構師，就算比較不必碰細節，也更懂零件怎麼互動。這和他的兩種人不會差太遠。Jason 開玩笑，他當開發者很普通。他的腦子很難看見一行一行的 code，但看得到套件和系統。把自己抽出來之後，技術上好很多。當一個很好的 CTO，比當一個很好的開發者容易。系統允許這種事。你可以看見自己走向 PM 或架構師。仍會有人想念一行一行的 code，想自己多寫。那像想拿著畫筆當藝術家的人，對上百分之九十時間用 Midjourney 的人。他們 maybe 有位置，但 maybe 不是中心。

[61:24](https://www.youtube.com/watch?v=-8lOXbv3DHQ&t=3684s) Poolside 還不能直接拿去試。追蹤方式是 Twitter 上的 poolside AI，以及網站 poolside. 註冊，他們會寄更新。字幕把網域沒念完。

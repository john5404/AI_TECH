# Does AI threaten the open web? Discussion with Netlify's CEO & Co-Founder, Matt Biillmann

Guy Podjarny 訪問 Netlify 的 CEO、共同創辦人 Matt Biilmann，談 AI 和開放的 web。Matt 的 LinkedIn 開頭有兩年音樂編輯。原片約 55 分鐘，英文自動字幕。這份筆記依英文原稿整理，專有名詞保持 English。

- 原片：[YouTube](https://www.youtube.com/watch?v=WhhGMZo-HLg)

## 一句話

AI 網站產生器現在像第一代音樂生成：快，但多半是聽過的東西的平淡版。真正會改變開發的，是開發者學會哪裡省下大量時間、哪裡只是在浪費。Netlify 把 AI 分成四格：內部怎麼用、產品怎麼變好、客戶怎麼在上面做 AI 應用，以及 AI 本身怎麼變成部署平台的使用者。往後五到十年，他預期介面會因為機器開始懂 intent 而改掉；可預測的衝突仍是封閉平台和開放 web。

## 音樂和網站，第一代都在模仿已經聽過的

[1:14](https://www.youtube.com/watch?v=WhhGMZo-HLg&t=74s) Guy 先問他對 AI 生成音樂的看法。他說這會是工具箱裡的新工具。很多人想的是低垂的果實：生成聽起來像我們聽很久的音樂。那很酷，也有好玩的用途。更有趣的是，創作者能用以前不可能組出來的複雜度做什麼。他會做現在的事，是因為他本來就喜歡技術打開的可能。樂譜改變了人以為音樂是什麼：以前音樂只存在於那一刻。留聲機又改了一次，聲音不再只在當下。早期只是錄西方古典，後來人聽的、認為是音樂的很多東西，是因為可以錄、可以傳。數位錄音帶來 sampling。一開始也有和 AI 很像的焦慮：這是在偷別人的音樂，你沒有自己打鼓就不算。電吉他、鼓，現在都被接受成音樂能做的事。他覺得 AI 在同一個階段。第一代做出來的，多半像已經聽過的音樂的平淡版。創作者會找出有趣的用法，再改變我們聽的東西。

[4:12](https://www.youtube.com/watch?v=WhhGMZo-HLg&t=252s) 網站產生器他看成同一件事。Vercel、Webflow、Shopify，以及多到數不清的新創，都在做「你描述，網站就出來」。第一批生成器做出來的網站，看起來像我們以前做的那些，而且很快，但可能也很平淡，像某首流行歌的壞版本。低端市場一直有 Wix、Weebly、Squarespace 這種網站產生器。你要開一家快閃餐廳，不會有一組 web 開發者幫你客製。第一批 AI 產生器在那裡會很有用。更有趣的是拆開的形式：不是 AI 吐出整個網站，而是開發者怎麼用 AI 加強自己的技能，做更多、更複雜、更快。

[6:10](https://www.youtube.com/watch?v=WhhGMZo-HLg&t=370s) 對 Netlify，這些 AI builder 是一種新使用者：不再是人類開發者，是 AI 開發者。他們推出 Netlify GPT，在 ChatGPT 的環境裡提及 Netlify，就能把做出來的東西發到網上。光那一條，每天就有超過一千個網站發上 Netlify。那些多半比較短暫：一個小原型，或有人幫女朋友做一個網站。Bolt.new、GPT Engineer、Devin 這類更複雜的，也用 Netlify 的 API。你叫它做一個 app，預設就建在 Netlify 上並發布。這些再加上其他工具，每天又是幾千個站。愈往上、預算和專案愈大，就愈離開「一個神奇 prompt、按一下、你幾乎不能控制」，走向開發團隊被各種 AI 工具加強。Guy 說很多工具會走 Netlify，是因為它是被寫清楚、被試過、又夠有意見的路，成功機率高。若生出來的是一套 Kubernetes 和 AWS，然後跟你說祝你好運，採用大概會停住。AI 在某種意義上是最懶的開發者：你給指示，它會聽話去寫文件、寫測試，成功程度不一，但會做。同時它會找好走、維護低的環境。教 LLM 和教開發者沒有差很多，只是開發者不一定聽話。

[9:57](https://www.youtube.com/watch?v=WhhGMZo-HLg&t=597s) Guy 說他在西班牙一家公司，主要生意是大規模幫中小企業做網站，高峰一週超過 100 個。平台從簡報、指派自由設計師、迭代、內容管理和設計工具，到上線。跟中小企業工作時，人經常不聽話。LLM 麻煩的地方是太想討好。Matt 說接入他們的工具數量在往上衝，吞吐在增加。很多仍很短暫，離「人會接手、繼續做的真專案」還遠，但已經開始看到真的轉換：人從 ChatGPT 出發，再用公司信箱註冊 Netlify，到另一側做事。他的感覺是低端市場，加上你以前根本不會花時間做的東西。他自己的例子：十八個月大的女兒看到筆電就過來，喜歡她認得的字母和數字。他做了一個全螢幕小遊戲，按一個字母就用有趣的動畫秀出那個字母。她會按、會看它轉、會興奮。他大概不會為這個去寫一個 web app，但開口請它做就夠容易。人容易以為世界上需要的這類網站數量是固定的，AI 來把那一批做完。不是。客製變容易，你就開始客製以前不會花時間做的東西。

## 四格裡的第一格：它還不是夠好的開發者

[13:15](https://www.youtube.com/watch?v=WhhGMZo-HLg&t=795s) 他用四類想 Netlify 裡的 AI。第一，內部怎麼用 AI 變得更有效、做得更快更好。第二，AI 怎麼讓產品更好。第三，使用者和客戶怎麼在 Netlify 上做 AI 應用，需要哪些新的 primitive。第四，AI 會怎麼使用 Netlify，怎麼讓它成為 AI 最好的部署平台。

[14:13](https://www.youtube.com/watch?v=WhhGMZo-HLg&t=853s) 內部他們試過這些 builder 能為他們寫多少 code。他推開發者去用 AI 加強自己，自己也坐下來用不同工具做 Netlify 的功能，看能幫多少。個人工具很多是各種用法的 Copilot，也有比較沒整合的，就是把 ChatGPT 和 Claude 當工具。公司沒有規定死，是鼓勵你找出有用的、再跟團隊分享。他們也評估過更程式化的東西：接上 GitHub issue、自動解 ticket。他仍覺得 model 還沒到那個地步，參與的成功率不夠高，不值得那些噪音。它們還不是你真的想放進 codebase 的那種夠好的開發者。一個沒那麼好的開發者開出一堆 pull request，你得徹底審，有些還有大錯，那就不是省時間，是干擾。Guy 問，coding assistant 會不會讓人送進比以前差的 code。Matt 說他們內部 code review 文化強，同儕問責強。你突然開始開一堆壞 PR，審你的人會問你在做什麼。工程文化夠強，好的開發者不會突然變差，只會變得更有生產力。Guy 說護欄愈多，你愈敢跑，因為你有信心不會在半夜出事。AI 反而把大家早就覺得好的做法照得更清楚。

[17:22](https://www.youtube.com/watch?v=WhhGMZo-HLg&t=1042s) 他也覺得，一個好開發者會不會用 AI，會變成很大的差別。這是要學的。GitHub 那種自動完成，他在自己身上看到，也聽很多資深開發者說會關掉。像跟一個低你好幾級的人 pair，對方一直說我們換這樣做，很吵。另一方面，有意圖的 prompt 可以加快本來很花時間的事。他試過叫 GPT-4 改他們 traffic server 的 plugin，那是很大的 C++ 開源程式庫。任何「幫我實作這個」都會幻覺出不存在的 API，完全沒用。但若說：我要一個函式，拿 request 物件，抽出這些值，把 accept-language 字串拆成可以處理的格式，再跟一條 redirect rule 的設定比，回傳結論。輸入、要做的事、輸出都給清楚，它大約 30 秒就寫對。做過 C++ 的人知道，那種字串比較和操作，要花很久才記得標準函式庫、才找到記憶體安全的寫法。他可以一次寫完。所以未來很強的開發者，是愈來愈會掌握這套工具：哪裡省下大量時間，哪裡會浪費時間。Guy 補了一句：它讀不了你的心。你若只說把 accept-language 跟某種西方語言比，它定義的西方語言可能不是你要的。有時你得像對團隊裡的開發者那樣，講得更具體。

## 讓 AI 寫 codemod，人仍在迴圈裡

[20:14](https://www.youtube.com/watch?v=WhhGMZo-HLg&t=1214s) 他們評估過一批工具，他願意一起工作的是 codemod.com，用來做 codebase 遷移。主應用 app.netlify.com 是傳統 React app，大約 2016 年初開始。過時得很深的是 React Router。從早期到現在改得很深，貫穿整個程式庫，又卡住後面很多 React 相依的升級。Codemod 本身是確定的：不是在文字上 find and replace，是看 abstract syntax tree，再對那棵樹做轉換。很多遷移可以寫成一組 codemod。難的是寫 AST 轉換。AI 幫他們定義、迭代、測試那些 codemod。定下來之後，系統把它套到整個程式庫，開出相當大的 pull request。他們仍要跑很多測試。這條路讓他們走完 React Router 那一連串更新，以及被那個相依卡住的 React 版本。以行數來說是很大的貢獻，經過 AI，但是人在迴圈裡、很專心的過程。

[22:48](https://www.youtube.com/watch?v=WhhGMZo-HLg&t=1368s) Guy 說這和別處的模式一樣：請 AI 在比較被約束的空間裡生成，它會做得更好。Web 裡 Wasp 有 Mage，本質是你描述的那種放大版。迴圈沒有十七萬七千種寫法，選項少，它通常做得不錯。DevOps 和 Wasp 他都看過。Matt 說 codemod 本身是開源專案，最早在 Facebook、Meta 之前。Alex 曾是那個產品的 PM，做出 codemod.com。上面有開源 codemod 的登錄，也開始跟 React 團隊、Remix 團隊合作：他們發新版本時，就有一套 codemod 可以套到你的程式庫上升級。Matt 披露自己是那家公司非常小的投資人。他覺得有趣，是因為整個生態的版本升級是個問題。你可以把大量開發者時間花在追版本；不追，就會突然被卡住，落後很多，追上變成巨大的工程，新的相依也可能加不進去，除非先把舊的抬起來。能有系統地幫忙做相依遷移的工具，很有價值。

## 產品不幫你寫內容，它幫你少等兩天

[25:09](https://www.youtube.com/watch?v=WhhGMZo-HLg&t=1509s) 他用兩分鐘解釋 Netlify：給 web 開發的平台。原來的洞察是把架構拆開，後端的商業邏輯做成一組 API，web 的使用體驗是自己站得住的應用。然後用一個統一的平台，把開發者寫的 code 盡快、高效能、高可靠地放到正式網域上的客戶面前。裡面有 release management、CI/CD、每一張 pull request 的 staging、協作，甚至讓非開發者對 PR 給回饋、在網站上做視覺編輯，再加上基礎設施本身。他們營運一張大型全球網路，有 web application firewall、DDoS mitigation、edge compute 和 serverless，給現代 framework 的 edge rendering、個人化，以及 backend for frontend，用來跟那些 API 說話。目標是 web 團隊不要把時間花在寫完 code 和內容之後的自動化和維運。Guy 補了一句：它有意見、有路徑，但可以只拿一塊、接到別的東西，內容可以有五種 CMS。Composable 是核心長處。

[27:45](https://www.youtube.com/watch?v=WhhGMZo-HLg&t=1665s) 產品哲學是：他們不進到用 AI 幫你寫 code 或寫內容。在他們的世界，那在 Netlify 的牆外。他們幫你把那些東西更快送上線。想的是，AI 怎麼減少從寫完 code 或內容、到它在 production 上的摩擦。第一個公開功能是「為什麼失敗」按鈕。很常見的摩擦是：code 推上 GitHub 的 pull request，他們跑 build，沒有上線，build 失敗。你得跳進 Netlify、看整份 log、弄清楚發生什麼、該怎麼辦。UI 上的按鈕把 build 的 context 和 log 交給 LLM，試著回答為什麼失敗，並給一個建議的解法。大約今年五月推出。之後這個按鈕做了大量除錯，他說大約省下 25,000 個開發者小時。Guy 把次數說成大約十五萬。Matt 希望有準確率，但很難量：沒有一個框叫「把這個修復做掉」，它只是給建議，你不知道對方是照做還是做了別的。開發者若常常被說錯，會來告訴他們。內部 private beta 時自己的團隊就用得很多。它一定有時會錯。也有很多時候，錯誤其實頗明顯，但 log 很大，你還得先把自己放進那個情境。按一下就指出來，感覺很好。哲學是：理想上不要從零寫；別的地方可以寫。理想上一切都接好，AI 做的事不給你的流程加複雜度，只是讓你更快。

[30:45](https://www.youtube.com/watch?v=WhhGMZo-HLg&t=1845s) 下一個功能在 Compose 大會推出，當時是 private beta，叫 AI assisted publishing。他們是開發者優先，給想用開發者做 web 體驗的團隊。願景一直是：那些開發者有一組不是開發者的利害關係人，他叫做 web team 的一部分。行銷寫要上線的文案和訊息，設計師做素材。只有開發者能幫整個團隊，他們才算為客戶成功，整條路才更快。很多 web 專案有 code、template，後面總有內容基礎設施。通常是 headless CMS，有時再加一個電商平台，有時是舊 CMS 加現代的 headless。技術從不真的拿掉舊的，只是再疊新的。開發者要有效使用內容，內容得是結構化、可當變數的格式，理想是現代 headless、內容本身也好。他的經驗是，就算在 Netlify 內部，創作者和行銷從不在結構化內容裡做創意。他們在 Google Docs。開發者要為開發者部落格寫文章，也不想在表單裡寫，想自由寫。開發者通常寫在 Notion，行銷通常寫在 Google Docs。Netlify 很早發現，開發者真正工作的地方是編輯器、本機環境和 GitHub，後面才是把它送到世界上的工具。他們接上 GitHub：每次 push 就 build，給一個 URL 看長什麼樣。現在想的是，怎麼把這件事擴到在 Google Docs 和 Notion 裡工作的人。與其先在 Google Docs 寫完，再請開發者或半技術的人去 CMS 裡鍵入，可以讓 LLM 做。到 Netlify 的視覺編輯層，說用這份文件開一個新頁面。LLM 把非結構化內容放進已經設好的結構化格式。他們就是渲染基礎設施，所以可以跑 preview、給你看實際樣子，再在上面做視覺編輯，改 LLM 弄錯的或你想改的，直接在頁面上。那個流程有時要幾天，不是密集工作，而是要找到有空的人放進 CMS、設好、把連結送回、你再找時間驗證、再迭代。他們想把它縮成一節 15 分鐘，然後就上線。Guy 把它看成進入開發平台的入口：結構是 code 需要的前提，能不能把那一步變簡單。

## 串流、非同步，以及 AI 自己的帳號

[35:13](https://www.youtube.com/watch?v=WhhGMZo-HLg&t=2113s) 客戶在 Netlify 上做 AI：AI 愈來愈是每個使用體驗的積木，開發者需要的內容或資料會來自 AI 系統。在這種前端加 backend for frontend 的架構裡，要有哪些新前提、primitive 怎麼演進，才能讓建在這些 AI 上仍然是好體驗。他們已經做的一件是：原本 Netlify functions 完全同步，請求進去、做完再回應。必須加上串流，因為建在 GPT-4 之類上面不會立刻拿到答案，而是一串 token，生得夠久，你會想流回給使用者，否則體驗很糟。再來是更複雜的模式，比較像 agent 和 assistant：不是送一個請求再流回來。先從使用者拿一些東西，觸發一個初步 prompt，也許是規劃，然後可能要開好幾個程序平行做那些步驟，全部做完才更新最終結果，過程中還要給使用者看進度。在 Compose 做 AI assisted publishing 時他們自己撞上這些。一位 principal engineer 在既有的 serverless primitive 上做了一整套 workflow engine：排程的 function、blob storage、serverless compute。再把它包成非同步工作負載的 extension，讓使用者在跟 LLM 打交道時，寫那種工作負載變簡單。他說未來已經在這裡，只是分布不均。這些能力都不是全新的，是從邊緣案例變成常見案例，所以得更內建地支援。Guy 想，網站上一次 LLM 互動也許會變得跟一次資料庫呼叫一樣普遍。Matt 也在看 local-first 的 web app 架構。那對多人體驗仍比較像邊緣。但這些 workflow 裡 agent 起來做事，幾乎每個 web 體驗都會變成多人：另一個玩家不是人，是在做事的 agent。架構上，過去的冷門需求會很快變成我必須有這個。

[39:28](https://www.youtube.com/watch?v=WhhGMZo-HLg&t=2368s) 第四格是他在錄前沒想那么深的：AI 使用者。你做的若是想被 AI 使用的工具，那和做一個 AI 工具不是同一件事。前身 BitBalloon 在 2013 年底的第一句話是 hosting for the programmable web。Netlify 本身就是一支 API，有 CLI、有 OpenAPI。app.netlify.com 只是那上面的一個客戶端，CLI 是另一個。這對想跟產品互動的 AI model 突然很有用：有一份清楚的說明，告訴 AI 該怎麼用。另一條很早推出、現在又變得相關的，是一種先部署的流程。在 Bolt.new 裡叫它做 app、再說 deploy，它就部署到 Netlify，一開始不會叫你去驗證身份。它給你一個連結：若你真的想對這個東西做點什麼，可以點進去、認領這個站，它就進你的帳號。拿掉「我有沒有 Netlify 帳號」的摩擦。做這些工具時，你要人馬上開始玩，不要先登入一大堆服務才能做事。能做的就是降低摩擦，讓 AI 以某種方式擁有自己的帳號、先在那裡工作，做完再交給使用者。他把這想成自由工作者和代理商需要的流程：AI 是一種新的隊友。若沒有清楚的 CLI 或 API 驅動的流程讓這些 AI 接得進去，它們就做不了什麼。人也有流程：註冊長什麼樣。Guy 把這收成：文件好、可程式化、有好例子，然後註冊零摩擦。對人來說，自己有信箱，註冊摩擦相對低。對 AI，它沒有代表這個使用者的信箱，註冊是大事。

[43:32](https://www.youtube.com/watch?v=WhhGMZo-HLg&t=2612s) 已經設計好的那些之外，還有仍在處理的。例如 ChatGPT：你若不認領，他們把站當成暫時的，大約一小時內刪掉。也有系統裡的人還不想認領，但想分享、不想讓它消失。一旦留著，就要處理壞事。有人跳進這些環境，叫它做出看起來像 chase.com 的東西，請人填信用卡。他們得通知那個擁有 AI 的服務：你的使用者在我們這裡做壞事。這些不全是技術限制。Composable 那側也有事。現在比較簡單的例子只是純前端。當它們還要別處的資料庫、要多個夥伴接在一起，就得想怎麼跨供應商把這些模式標準化。怎麼用開放的 web 說清楚我們允許 AI 做什麼、我們怎麼被 AI 當成工具、AI 怎麼把那些工具組起來。他覺得這是下一個前沿，大概會先發生在專有的圍牆花園裡：裡面你可以點名每一塊，把它們綁在一起。若這會變成很重要的建造和起步方式，就很重要找到以開放 web 為中心的解法。形式大概會比單一花園笨一點，但根本是開的，任何人都能發布、參與這個可以插在一起的工具經濟。

## 五年後仍是封閉和開放的拉扯

[46:12](https://www.youtube.com/watch?v=WhhGMZo-HLg&t=2772s) 他拿出往後五到十年、甚至更遠的看法，對象是 web、Jamstack、composable web。人開始談 composable、而不買一套單體工具來做 corporate.com 或電商，是為了彈性：你想用客製開發做出客製體驗，又要快上市，而且不去建造對你不獨特的部分。高端精品品牌想要非常貼身的電商 web 體驗，但不一定想自己做電商，也不想自己做內容儲存。你想拿可重用的元件拼起來，在上面很快地做，而且那些元件可以在世界變、替代方案出現時各自演進。傳統單體也許有些地方是最好的，但很多地方很差，你無能為力。他認為 AI 的大市場趨勢會加速走向 composable。AI 有很多事難預測，很容易預測的是它會加速一切：更多內容、更多 code、更多素材。進入的障礙和力氣下降，就會有更多東西被做出來。工具集會演得更快，坐在大型單體上的壓力更大。UI 和後端綁在一起的發布也更有壓力，因為更冒險。你需要吞吐很高、彈性很高的系統。

[48:57](https://www.youtube.com/watch?v=WhhGMZo-HLg&t=2937s) 他稱為 UI 2.0 的，是更大的那一件。現在 AI 帶來的加速，只是用來更快做出過去幾十年同一種使用體驗。沒有在做巨大的新東西，只是 code、素材、設計都更快。這像開場的音樂：把同一首流行歌做得更快。那本身是變化，因為會在以前做不出來的地方做出內容，也許更多客製、變更更快。但還不是新的創造，只是一隻移動更快的野獸。DevOps、雲、Java、JavaScript 都在把開發的步伐疊上去，這次內容創作也是。再往外看五到十年，會 radikal 得多。從第一個介面以來，人機介面的核心限制是電腦不懂 intent。互動必須很交易性、可預測：按按鈕，電腦做可預測的事；打指令，電腦做指令說的事。那個限制正在滲走。你可以讓它懂 intent，然後去做一堆事。到目前為止，我們真正用上這一點的，主要是聊天機器人介面，他覺得非常原始。這一部分最不可能預測它怎麼展開，但很容易預測它會展開。人會開始做出沒有 AI 就不可能做出的使用體驗。裝置和硬體也可能跟著變。他覺得這對「你該在 web 上建造什麼」的改變，會和 mobile 一樣大，可能更大。每次平台變化都一樣：iPhone 出來時，不可能預測五年後人會把哪些東西做成 app。可預測的是封閉平台和開放平台的張力。大玩家會很想讓這個再平台化變成他們擁有、控制、設閘、可以變現的專有平台。很多人得爭取一個仍能交出使用者突然開始期待的體驗的開放 web。Mobile 和社群媒體發生過的那個循環，他又要開始演。Netlify 在想的是：對開發者，怎麼讓 web 繼續是創新、做這些新體驗的對的平台。Web 的性質是沒有守門人，你可以買一個網域，在上面做任何事，放到人面前。怎麼讓這些長處仍然很有說服力，讓這份開放、共享的基礎設施繼續是最好的建造起點。

[52:52](https://www.youtube.com/watch?v=WhhGMZo-HLg&t=3172s) Guy 同意這是得處理的風險，而且每一層都看得到：最底層的 foundation model，對上 open weights，以及少數真的開源的；再往上，自主的工程師也許很有吸引力，但對開發方法意味著什麼，大多數我們不知道，因為它們還在牆後面、不公開。封閉系統有不錯的機會更快做出創新、更快做出連貫的東西，也會有優勢。我們不必接受那是終點，可以把它當成墊腳石。

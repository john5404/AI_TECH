## 一句話

背景 agent 放著跑，會交出幾千行、人讀不懂的 PR。Stack PR 的價值因此更高，不是更低。人類審查裡，驗證這件事 AI 可以接；更不該丟的是知識分享和教學。他把工程分成三階段，現在停在第一和第二之間。

## 為什麼還要切小

[0:00](https://www.youtube.com/watch?v=P4EWb6413y8&t=0s) 他挑戰「AI 寫 code 之後 stack PR 比較沒價值」。尤其是 background agents，放著跑就會得到幾千行、無法理解的 PR。人要檢查的變更必須看得懂、吞得下。他們做了 Graphite MCP。很多客戶讓 agent 開 stack PR，就是為了好審。

[0:29](https://www.youtube.com/watch?v=P4EWb6413y8&t=29s) Stack 的核心是你把東西送去審的同時還能繼續做。Agent 不想等。你要能增量審它們的工作。若審查有重大修正，它們也許會退回那個點再繼續。人做這件事會很煩。較小的片段和清楚的歷史，讓你比較容易找到是哪次變更引入問題，也比較能精準 rollback。

## 審查不只是驗證

[1:37](https://www.youtube.com/watch?v=P4EWb6413y8&t=97s) 很多人卡在「code review 的唯一價值是驗證」。那是主要好處之一，但常被漏掉的還有兩件：讓團隊知道什麼要進 production、什麼在變；以及教學，讓你從回饋裡改進自己做專案的方式。驗證和品質，AI 可以接。後兩件在很多方面更重要，因為連開 PR 的工程師都不一定完全懂這個變更。你更需要一個時刻把 codebase 裡什麼在變講清楚，告訴別人這個變更好在哪、不好在哪、要帶走什麼，再把系統性的東西餵回 reviewer，變成以後該看或不該看的規則。

[3:14](https://www.youtube.com/watch?v=P4EWb6413y8&t=194s) 所以至少人類審查的目的會從驗證，移向教學和知識分享。他甚至覺得，以我們今天做 code review 的理由來說，這兩件本來就比驗證更根本。

## 三個階段

[3:43](https://www.youtube.com/watch?v=P4EWb6413y8&t=223s) 中間是活動廣告，11 月 18、19 日紐約或遠端。網址沒有聽清。回來談的是：完全自動化的審查，最後會想把它當成 agentic development 的自然一環。它若發生在另一個系統、還得回到你這裡，就是一個打嗝。也許它們透過那個 MCP 叫 Graphite，不只開 pull request，還真的跑審查、拿結果。長期相關的兩件事：stack PR 即使不是增量審，也是時間上的分界；以及審已完成的工作，用來學習和引導 AI。到那個地步，你大概得離開「審 code」，改審對 code 的分析。未來若我們做的只是讀 code、評論、挑剔，並不愉快。

[5:23](https://www.youtube.com/watch?v=P4EWb6413y8&t=323s) 他們內部的框架是三步。第一步，他們覺得已經有點在離開：IC 工程師主要自己寫 code，或用 tab complete 生成，審查是很仔細地看每一行。第二步，現在正在進入：工程工作比較像 engineering manager，你編排一隊去建造的 agents，它們把變更交回來。你仍審 code，但很多是在審 design docs、架構和更高層的點。還能鑽進 code，但你在找的東西發生在更高的抽象。細節更多由 AI review 處理。第三步還沒到：若一切夠好，會比較像跟外部開發代理商合作。你給高層規格，拿回完成的成品來審，也許根本不用看底層 code、也不必懂它。你主要審的是那個成品。

[7:02](https://www.youtube.com/watch?v=P4EWb6413y8&t=422s) 他說我們現在在第一和第二階段之間。未來幾年有機會從二跳到三。

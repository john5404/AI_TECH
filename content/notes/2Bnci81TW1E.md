## 一句話

LLM 很會寫看起來合理的 SQL，也很會做資料衛生，但每家公司的資料都很怪，怪處活在被燒過無數次的人腦子裡。組織要協調，就得有一套大家相信為真的結構化紀錄，而且「營收」不能每次問都換一個定義。模型今天大概夠聰明，缺的是把 metadata、歷史和權限送進去的鷹架。MCP 讓「我的營收是多少」終於有答案，瓶頸就回到資料工程師：在它底下把資料建得準、建得有業務上下文。

## 從原始紀錄到能用的資料，中間有人

[1:09](https://www.youtube.com/watch?v=2Bnci81TW1E&t=69s) dbt 是資料工程師、analytics engineer 和分析師處理結構化資料的流行方式。以前是 ETL，現在是 ELT：先抽出、載入，再轉換。組織的資料量很大，付款廠商、行銷活動，什麼都在吐資料。從原始資料到有用、有趣，並不簡單。要判斷哪些有用，做轉換、做 join。還得有彈性、可信、準、而且即時。他舉一個代價：不小心把兩張表 join 在一起，查詢變成六位數的帳單，老闆進來罵。dbt 是做轉換的框架，也管編排和發現資料資產。底下是一種程式介面，上面再加工具。他的工作是讓這些東西服務做產品的人：勾出資料工程師和 analytics engineer 以後要往哪走才有生產力，動手改開源和 source available 的 repo，聽使用者要什麼，讓人把資料變成可用、可及，而且做這件事本身有趣。

[4:39](https://www.youtube.com/watch?v=2Bnci81TW1E&t=279s) 資料工程師的定義隨組織和產業差很多。他們把它想成負責建立和維護資料管線的人：搬大量資料、資料庫設對、權限和基礎設施就位。也可以靠近業務，跟利害關係人定義資料集；或靠近金屬，管編排、工作有沒有跑、測試、資料平台。這是光譜，不是硬邊界。一端是資料庫技術，一端是分析師和業務，中間都有人。資料工程師主要落在建管線、做出業務需要的資料集。

[6:26](https://www.youtube.com/watch?v=2Bnci81TW1E&t=386s) 進來的路主要兩條。軟體工程師發現自己一直在碰資料、覺得有趣，養成專長，再正式跳過去。另一條是分析或 analytics engineering，不斷 shift left，移進資料工程。也有人直接把資料工程當職涯，還有 boot camp。他說不要講太細：要麼從資料來，要麼從工程來，然後停在中間。

## 軟體工程的事都適用，但狀態從第一天就在

[7:38](https://www.youtube.com/watch?v=2Bnci81TW1E&t=458s) 資料工程有趣的地方是軟體工程的事幾乎都適用，再加一點會造成差別的調整。前幾位來賓講 AI 怎麼改變軟體工程，對資料工程師都相關，因為他們在寫 code、在做 IT。他自己最近大量用 Claude Code，很享受。差別是：用 AI 寫網頁應用，東西活在那個應用裡，周圍已有很多基礎設施。組織在處理 terabyte、petabyte 時，你想寫一支腳本去改既有查詢，就得知道它的 metadata、歷史和狀態。複雜軟體要到開發和部署後期才考慮的事，AI 輔助的資料工程從一開始就得考慮。

[9:55](https://www.youtube.com/watch?v=2Bnci81TW1E&t=595s) 最低的果子和其他地方一樣。他們推出的 Copilot 和其他 Copilot 類似，但會帶進 dbt 專案的 metadata，也懂 dbt。人最常做的是為資料寫描述和測試。那是樣板 Jinja，不一定是誰的最愛，對維護良好的專案卻很重要。今年進來時，他們把認知上費力、但不特別複雜的用例削掉，放進 AI 輔助開發的飛輪。以現在這代模型，從零做出一個 dbt model 已經相當好，但它仍得知道專案裡有哪些欄位。LLM 很可能很會寫描述。

[11:19](https://www.youtube.com/watch?v=2Bnci81TW1E&t=679s) Simon 問：測試時它怎麼知道最該測什麼、哪些欄最重要、規則是什麼。Jason 說這是領域專門和工程混在一起。第一線測試幾乎免費：主鍵不要重複、必填欄不要缺。這是衛生測試，它很會，對多數組織已經是很大的收穫。單元測試該測對的東西就不同。LLM 很聰明，知道你大概想測哪一類，但每個人的資料都怪，怪的部分活在被它燒過無數次的人腦子裡。今天的做法是你先勾出來。衛生它能給很好的第一稿，你再看過。業務特有的、很囉嗦的那部分，它不會開箱就會。你描述一個單元測試，它來搭鷹架，尤其當它有欄位、型別、預期值的 context。然後你驗證。衛生開箱就行，客製的要跟它一起做。

[13:55](https://www.youtube.com/watch?v=2Bnci81TW1E&t=835s) Simon 說 AI 不像人那麼懶，測試和文件人常拖，它會去補完。Jason 先笑說他們的使用者都很完美、總是寫文件。然後承認自己懶，總想晚點再填、晚點再測。若你先勾出十五件想做的事，做完留下一串「我該做這個」，這種苦工它接得很好。兩三年過去，人有點麻木了，他仍覺得像魔法，像自己没想過會有的東西。

[15:29](https://www.youtube.com/watch?v=2Bnci81TW1E&t=929s) 他認為最後整條堆疊都有幫助：寫資料模型、重構、管線壞了怎麼除錯、為什麼壞、要改什麼。缺的不是模型智力。模型今天大致都做得來。問題是把資料送到它們面前、做成產品的鷹架。管線一壞，第一件事往往是看 log，而現在任何人管線一壞，第一件事就是貼進這些工具。系統該建到：這一層的第一輪問題，LLM 都能先處理。他希望的最低結果是大家的資料系統更好用，資料產品更便宜、更快，製造和維護的苦工更少。那只是基線。更有趣的是這些東西接進其他 AI 應用之後，會變得多有用。

## 人看不完的 DAG，權限仍是人的角色

[17:36](https://www.youtube.com/watch?v=2Bnci81TW1E&t=1056s) 資料量大時，怎麼把 context 放對。dbt 和資料工程想事情用 DAG，有向無環圖。他們掌握很多 DAG、模型和欄位的資訊。你不能把系統裡全部資料送進去。大組織連全部表都送不進畫面，欄位和描述是成千上萬。模組化是 dbt 改變資料工作的關鍵。大約十年前、dbt 之前，人維護五千行的 SQL，一兩個人的人生就是在除錯那一支腳本。拆成模型、一段段跑，壞了看得到下游。這不只是 dbt，整個資料工程都在做人類能操作的模組。他說自己的 context window 比 20 萬 token 小得多，所以這些生成反而能塞進很多額外 context，而那是從 DAG 來的。

[19:40](https://www.youtube.com/watch?v=2Bnci81TW1E&t=1180s) 用 AI 生 SQL 時的安全，資料工程比較少碰到 SQL injection，因為寫的人通常是公司裡的人。仍要確保資料不會對內或對外露給不該看的人。他覺得自己在重複一個重要概念：為人解決難題而建的那套抽象，AI 系統也要用，然後在上面再蓋。資料庫上的 agent 應該有一個角色，範圍限到你不希望那位人類查詢者看到的資料，它也看不到。Simon 確認：LLM 只有使用者有的權限，每次請求走存取限制。Jason 說就該這樣。走他們的雲平台時，你登入，Simon 有一組資料庫權限，你跑的 SQL 早已被團隊圈好：該看的看得到，敏感的看不到。AI 的查詢用同一套。角色在對外的客服 bot 上更重要。它該看得到正在對話那個人的帳單，不該跳去 ID 剛好大一號的另一個客戶。把資料存取和角色鎖死，本來就重要，現在系統接得更多，重要性是數量級的上升。

[23:03](https://www.youtube.com/watch?v=2Bnci81TW1E&t=1383s) Simon 不願把決定權留給 LLM。他們最近寫過 GitHub 的 MCP server：人在看公開 repo，惡意使用者加一則 issue，叫它把這個人在私有 repo 裡做的事都撈出來。開發者若說把這些 issue 修掉，server 會進私有 repo，再對公開 repo 開出可能含敏感資訊的 PR。LLM 是在用那個使用者的授權自己做決定，而不是用一套規定這個人能不能碰這份資料的機制。一旦交給 LLM，錯就會發生。他說這甚至不是幻覺，你只要說服它。它們總想給一個答案。Jason 描述的是用已經知道、已經信任的機制來建，這很有力。

## 營收有五到九種定義，模型會再發明第十種

[25:00](https://www.youtube.com/watch?v=2Bnci81TW1E&t=1500s) 結構化資料重要到世界上每個組織都花大量時間做單一真相來源。要協調複雜的真實工作流程，就得有結構。企業、政府、跨很多人很多部門，最後都要有系統紀錄。他把它追溯到複式記帳，說那是幾千年前、人類最重要的創新之一。世界很複雜，機構要在上面行動，就得有系統說：我們相信世界上有這件事。結構化資料就是組織相信的那些事。他舉例：6 月 26 日下午 5:14，Jason 在電商頁訂了一杯冰咖啡；某個銀行帳戶的主人是 Simon，公司名字幕聽成 Amia Corp Bank，不另改。下個月咖啡店要訂多少咖啡，通常得回到這些先前的紀錄。若 LLM 要處理複雜到你想核對真假的事，它們就得能碰到結構化資料。除非 context window 大到字幕說的那個 billy 10 trillion，一切都在 context 裡做對。現在不是那個世界，它們就得在結構化資料上行動。

[27:36](https://www.youtube.com/watch?v=2Bnci81TW1E&t=1656s) 它們現在特別不好的，是就算答案技術上合理，也無法每次給同一個答案。這接回 Simon 的 GitHub 例子。dbt 裡講到膩的一句是：每個組織對營收的定義都不同，而且一家組織大概有五種或九種，最後總有個可憐的人把它們對成唯一的真定義。LLM 聰明、急切，但不懂你的生意。叫它算營收，它會再做出第十、第十一、第十二種。它很會寫一支看起來合理、也能跑出輸出的 SQL。若要把這接進關鍵業務系統，資料最有用的地方是讓你我看同一樣東西、形成同一個世界模型，才能一起協調。LLM 現在做不到，因為 context 不夠，也沒有那個單一真相的系統紀錄。這對把 AI 部署成組織裡真正有用的東西，很要緊。

[29:47](https://www.youtube.com/watch?v=2Bnci81TW1E&t=1787s) CEO、COO、CTO 在意的是準確數字。今天問、明天再問，因為非決定性，或問法只差一點點，答案就不同。做硬的商業決定、對董事會報告、有義務報準的東西，必須是確切的答案。他們在 dbt 專案上有一層 semantic layer，定義業務語意。你定義一個叫 revenue 的東西：就是這個欄位，按這些維度和這些時間彙總。LLM 不太會用結構化資料表那種方塊來想，用 semantic layer 裡的語意概念會好得多。給它們能對上的語意，推理方式才跟它們本來的推理合得上。他們做過基準：同樣的自然語言問題，做在語意上比做在結構化資料上準很多。他覺得生態系裡的人也看到了。Simon 說這就是給它一條走得下去的路。

## 查詢壞掉比quietly 算錯好，署名就要自己讀

[32:10](https://www.youtube.com/watch?v=2Bnci81TW1E&t=1930s) 幻覺在任何 LLM 工作流都會發生。他們看到的多數情況是幻覺出不存在的表名、欄名或資料庫函式，於是查詢壞掉。他寧願查詢壞掉，也不要一支不算幻覺、但並不正確的查詢。不完全對的查詢比直接壞掉糟得多。幻覺沒被解決，但給對的 context 時大致能壓住。足夠的 DAG 資訊現在只在某些專案、某些 skill、某些做法裡做得到。最終寫 SQL 時，你會有方言、可用函式、可用欄位和型別。然後才問它是不是恰好正確，那就要靠上面的語意對應。Simon 覺得這層抽象很好：code 若幻覺，多半在編譯、連結或不存在的 API 上壞掉，而不是安靜地給一個錯的、卻不丟例外的結果。

[34:28](https://www.youtube.com/watch?v=2Bnci81TW1E&t=2068s) 人還要驗證多少。他的信念是：若他把 AI 生成的東西寄給你，就是在簽名，必須驗證過。擁有工作流的人要知道哪些可以放手，哪些不行。現在大多數仍是：它生出 code，他讀過、確認、也許改一點、也許發現自己理解錯了。這像一層更高的程式語言，你可以在那層操作。他有一個副業，做一個 MCP server，讓人從零建構奇幻或科幻世界，幾乎全是 Claude。他看 code 說看起來行，因為那只給自己用。要簽名的東西，他就讀、審查、驗證、確認能跑。這是他今天會建議人做的。變化很快。四個月前，這些系統還不能像今天這樣倚賴。

## 「我的營收是多少」有了答案，下一個人要準備資料

[36:20](https://www.youtube.com/watch?v=2Bnci81TW1E&t=2180s) MCP 讓他覺得蓋子被掀開了。ChatGPT 上線後一週起，他有個習慣：到任選的 LLM，打「我的營收是多少」，對方說抱歉、沒有這份資訊。他就貼到 Slack：唯一要緊的是我們能不能幫人回答這句。連貼太多週。MCP 起勢之後，他們有了送出去的方法。他們做了 dbt 的 MCP server。現在他登入任何支援 MCP 的客戶端，打同一句，它看 semantic layer，看到 revenue 這個指標，算出來，告訴他營收是多少美元。這很快變成他跟資料互動的主要方式。他承認自己也許不是一般使用者。主流程度：前瞻的資料團隊在做原型和試點，再照那個基礎推出去。人人都在想、都在試。他不覺得以後人還會用別的方式跟資料互動。一頁頁翻你可能有的東西太痛。要做成企業能用的，還有很多工作。但字寫在牆上，取用資料的能力增加得太明顯。

[39:08](https://www.youtube.com/watch?v=2Bnci81TW1E&t=2348s) Simon 說組織裡一旦到處是 MCP，以前不知道找誰的人也會來要資料，需求會大增。新的瓶頸在哪。Jason 說這回到一開始：未來的資料工程師在建那組用例。資料會容易取得得多，也更必須正確，因為更多人碰得到，上面也許還跑著 agent 工作流。基本功仍難：把資料收進來、保證準、把系統磨好。那是一半。未來的資料工程師做的是 MCP 或類似東西會坐在上面的那組資料，人再來查。比較模糊的是未來的資料分析師做什麼。儀表板不會消失。他一直覺得荒唐：花這麼多力氣認識世界和 ground truth，最後卻是看一組長條圖。長條圖很好，他喜歡。現在可以把這份資料當中心，讓 LLM 的流程據此採取行動。那是一整個新的行業。Simon 想到儀表板可以跟著變：事情變差就往下鑽、把更多資料拉進來，月報或季報對著痛處，而不是固定的紅綠燈。

[42:27](https://www.youtube.com/watch?v=2Bnci81TW1E&t=2547s) 所以資料工程師更早進場，管進去的品質和結構。MCP 坐在你選的資料平台上，或坐在 iceberg 表上，它需要大量建模好、準確、治理好的資料。資料工程師編排、測試、讓它就緒。他說這個分法太簡單：有人做 MCP 之前的一切，analytics engineer 則更貼著領域專家和業務上下文。MCP 不只要技術上建得好的表，還要對業務有深的理解和上下文，抽象層和描述都對，它才採取得出有用的行動。

[44:00](https://www.youtube.com/watch?v=2Bnci81TW1E&t=2640s) AI 之前，資料工程師知道該加什麼，是因為有人來要，加上自己的業務知識。MCP 之後，每天被問的問題都看得見。Simon 問這會不會變成需求驅動，資料工程師要跟誰談才做得好，會不會愈來愈孤獨。Jason 說他們最喜歡的詞之一是 metadata：打到 MCP server 的請求都有 metadata。可以問這題答得出來嗎，還是它依賴我們現在沒有的資料。在上面做報表，他說相對簡單，還先敲木頭，因為人人會罵他講得太容易。報表會像：很多人在問這個資料源；每天的請求裡 17% 答不出來；那 17% 裡的 41%，若再接進某個來源就能處理，而且知道去哪找。這些是他勾出來的報表，不是這集裡的實測。Simon 說很多問題以前不會被問，因為那些人不會去找人問。自然語言加 MCP，反而把該補進系統的資料種出來，繞成一圈。Jason 說得把資料飛輪轉起來。他們當場給它取了名。

[47:02](https://www.youtube.com/watch?v=2Bnci81TW1E&t=2822s) 想看 dbt 去 getdbt.com。他們剛推出 dbt Fusion engine，把引擎從零重寫。解析快 30 倍，型別意識和 SQL 理解都很好，才能做出深的 DAG 意識和深的 context。人可以在 LinkedIn 找 Jason Ganz，dbt 有社群 Slack，也可以在他仍叫 Twitter 的那個網站找到他。Simon 說對自己而言那永遠叫 Twitter。這集差不多五十分鐘。

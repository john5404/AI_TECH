## 一句話

人再聰明，任務範圍變大就變成組織問題：該不該在對的時間讀對的文件、還記不記得一年前的自己。Agent 也一樣。Agent enablement 的類比更接近 sales enablement，而不是只靠個人天賦。Context 是手段：觀察、A/B、再改 context。

## 為什麼像帶組織

[0:00](https://www.youtube.com/watch?v=YhUfuq48LeM&t=0s) 雇了一群很強的人，任務範圍變大之後，問題變成會不會在對的時間去讀對的文件、還記不記得一年前的自己。這些類比現在用在 agents 上。組織哲學會進入「怎麼讓 agent 有效」。從 Tessl 的角度看，context 是平台的一大塊。他幾乎每天聽到的詞是 agent enablement。

[0:42](https://www.youtube.com/watch?v=YhUfuq48LeM&t=42s) 回答先把結果和技術元件分開。Context 是重要手段，最後要的是 enable agents。他覺得 sales enablement 比開發的 onboarding 更好懂。很強的開發者第一天也不會知道在你的組織裡怎麼把東西做好，需要材料，之後還要持續訓練。開發比較難系統化，因為很依賴個人技術和 institutional knowledge。

[1:37](https://www.youtube.com/watch?v=YhUfuq48LeM&t=97s) 業務組織變大時，你希望業務只創造到某個程度，其餘要重複 playbook。新人和每年 kickoff 的舊人都要讀同一套：流程、階段、要用的簡報、重點、訊息。然後量測、看哪種隨機行為成功、哪裡漏掉，再改做法、再訓練。他覺得這比開發的個人技藝更接近 agent enablement。

## Context 是你改得了的那個工具

[2:20](https://www.youtube.com/watch?v=YhUfuq48LeM&t=140s) 目標是讓 agent 在你的組織、你的開發、你的 codebase 裡做得好。要裝備什麼知識、怎麼用 role play 和測試評估、怎麼分發、怎麼觀察行為真的發生了沒有、再怎麼最佳化。對人做不到那麼苛，對 agent 可以。

[3:01](https://www.youtube.com/watch?v=YhUfuq48LeM&t=181s) 看 agent logs 會看到兩種指令。有些寫進 context 卻被忽略。A/B、有沒有那些指令都一樣時，代表它本來就會做。例如叫它用 Git，它本來就會用 Git，那句是浪費 context。叫它改用 `gh` 這個 CLI，就得用很特定的方式去對抗直覺，說錯了就得不到結果。觀察到問題之後，你改的工具就是 context。組織要 agent 為你工作，就得 enable 它們。管理並最佳化 context 是做這件事的手段。

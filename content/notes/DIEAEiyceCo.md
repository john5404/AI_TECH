# Why Your AI Coding Agent Will Fail in Production (And How to Fix It)

Nupur 先講，她是 Qodo 的 solution architect。後面是 Simon Maple 主持的座談，在 Tessl 的辦公室。Brian 是 Snyk 的 developer advocate，來自荷蘭 Utrecht。第四位字幕聽成 Canal，公司聽成 coast I，人在倫敦，做的是應用效能，讓人不必自己經營 Kubernetes 叢集。片長 93 分 34 秒，英文手寫字幕。這份筆記依英文原稿整理，專有名詞保持 English。座談後半有很多段字幕碎到不能當成事實，那些地方只記聽得清的主張。

## 一句話

Agent 在 production 裡失敗，常常不是模型不夠大。Nupur 看到三種：context 中間變模糊、agent 把 token 花在尋找最好的做法而不是把任務做完、一個什麼都做的 agent 被互相矛盾的結果淹沒。她要的是讓 agent 自己去取相關的東西，用 80/20 把研究和給結果分開，再用多個小 agent 加一個 judge 把噪音濾掉。座談上大家沒有同意每行都要人看。同意的是：沒有人介入，不等於可以不知道發生了什麼。能快，是因為測試、護欄和可逆。知識若沒寫下來，自動化會把團隊帶離自己的系統。

## 從黑白的 pipeline，到中間發灰

[0:44](https://www.youtube.com/watch?v=DIEAEiyceCo&t=44s) Nupur 前幾年做 DevSecOps。那裡是確定的：pipeline 過或不過，黑白分明。轉到 AI 之後，一切變成非確定的，落在灰色裡。她幫人補這個缺口，讓人知道自己在造什麼。這場不是講事情怎麼能動，而是造 agents 時什麼會讓事情不動。大家都在做 agents，也在問團隊哪裡做得比別人好、哪裡落後。她講的是跟各種組織、客戶共事時，什麼對他們有用、什麼沒有。

[2:00](https://www.youtube.com/watch?v=DIEAEiyceCo&t=120s) 過去幾年走得很快。她記得上一份工作第一次看到這些模型，覺得好聰明、能做這麼多，context 仍然有限，但大家覺得這就很好：我們給資料、給 context，它們回東西。那時 context 取決於人。人選什麼重要，就給什麼。從人的角度看，漏了一件事，邏輯會走另一條，結果會說不通。接著是 agent workflow。她把這比成後院。他們給 AI 工具去搜文件，文件再變成寫 code 的 context。找不到就再回去找文件。迴圈裡，agents 試著弄懂怎麼把一件事做完美。做了之後發現，一個 agent 要懂全部，太多了。Context window 變大，混亂也變大。再來是現在大家在試的 multi-agent。人在做專家 agents，像以前的 SME。可以有 security agent、coding agent，再把結果合在一起。往細節看，agents 愈多，混亂愈多。Security agent 說的，可能和 coding agent 完全相反。然後怎麼決定。資料、context、結果都很多，要怎麼從裡面取出意義。

## Context 的中間會糊掉

[4:11](https://www.youtube.com/watch?v=DIEAEiyceCo&t=251s) 她說現在的 agent 結構，最常跌倒的地方，第一個是 context trap。每次新 model 出來，都帶著更大的 context window。人以為愈大愈好，可以給更多資料，就會有更好的結果。她的經驗不是這樣。任何 LLM 會抓住開頭的 context、也抓住結尾，中間變模糊。它們不知道什麼對你重要，就自己決定該拿什麼來給結果。你以為我把所有東西都給了，它們會選出重要的。大多不是。Context 被稀釋，由模型決定什麼叫好。通常是第一段和最後一段，中間就糊了。

[5:35](https://www.youtube.com/watch?v=DIEAEiyceCo&t=335s) 很多人試著解。她一數跟她談建 agents 的人，幾乎三次裡有兩次會說：我們在自己做一個 context engine，要提供更多資料。Context 是不是唯一的解。Context engine 對又大又亂的 codebase 最有用，但你得有一套排序的語言，擴展會變成挑戰。若你不是在做一個很大的產品，context engine 是不是唯一選項。大多時候答案是不。不必把 context engine 當成這個問題的唯一解。還有別的辦法把 context trap 縮小。Hierarchical summarization：理解專案，做出摘要，再提供給需要它的元件。開發者要花的力氣是中等，但它有用。Knowledge graph：函式 A 依賴函式 B，把那個依賴做成圖。若有主動的 agent tools，可以做成一張圖書館卡片，這個檔做這件事、那個檔做那件事，讓 agents 決定要往哪走。短句是：要有一個機制，讓 LLM 拿到它們要的，或讓 agents 懂什麼是相關的。不要把一切倒進去，再讓 LLM 自己決定要做什麼。

[19:48](https://www.youtube.com/watch?v=DIEAEiyceCo&t=1188s) 講完有人問中間為什麼會被忘掉。她說沒有那篇論文的 context。她的經驗是，一開始處理細節和文字，模型想放進記憶、想著要做這個。它會修剪你的資料。以前有一種她稱為 four key context 的做法，人先修剪、看什麼重要。模型變聰明之後，以為自己能從更寬的 context 決定什麼重要。真的做起來，它們一直留著 backlog，於是最初的 prompt 反而變得更重要。有人記得當天讀到一個建議，字幕聽起來像 Claude Code：叫它回來看，context 裡哪些部分沒有被留下。她做 code review 是每天的事。Review 不是只看 diff、問這個問題在不在。你想知道它有沒有弄壞另一個檔。函式裡有一套認證，別的函式是不是用了同一套，那些依賴。模型很難自己認出。Context engine 是在做那張對應：這個連到另一邊。處理資料時，不要直接把資料丟給模型。Agents 先看、先對應，什麼更重要、什麼連在一起，再把那個連接送去處理。她說那比較像映射，底下是 vector database 的 semantic search。

## 80% 去研究，20% 來收斂

[7:56](https://www.youtube.com/watch?v=DIEAEiyceCo&t=476s) 第二種失敗她叫 orchestration paradox。他們內部做 agents 時也遇過。模型變聰明。你叫它去搜，它會說還可以更好、更好、更好。於是它不做該做的任務，而去找取得那個任務的方法。迴圈就出現了。API tokens 沒有花在做事，花在找最好的做法。到後端看資源花在哪，基本上是在找最好的可能選項。會花很多時間，也會花一點額度，常常不是最有效的做法。

[9:06](https://www.youtube.com/watch?v=DIEAEiyceCo&t=546s) 他們內部用的是 80/20。有些模型很聰明，可以替你做研究。有些模型能給比較確定的結果：這是我的問題，告訴我怎麼解。不要只走一邊。研究、以及你真的想看進去的事，交給那些聰明的模型，讓它們找最好的做法。最後 20%，你真的在解問題、在拿到一個結果，由那 20% 來做：給 agent 一個問題，要一個解。這 80 和 20 也可以指不同的模型。80% 的任務用高推理的模型，因為你在找最好的研究和最好的解。把那些研究處理成給使用者的解，用 20% 的模型。她用希臘度假當例子。想找最好的假期。有的模型找最好的旅館、最好的航班，但會配錯。某一季旅館便宜，航班卻在另一季。80% 去做研究，一個 agent 找航班，一個 agent 找天氣。一個結果模型或結果 agent 把結果收斂，記住最初的目標，再交出來。下一步該做什麼、該做哪件事，這種動態的、思考比較重要的，交給 80% 的模型。我已經有 X，結果該是什麼，交給 20%。重點是模型之間要平衡，不要把聰明的模型放出去、叫它去替我做點什麼。它們會一直在迴圈裡找下一步，卻進不到結果。

[12:00](https://www.youtube.com/watch?v=DIEAEiyceCo&t=720s) 限制 80% 的另一個辦法，是給那些模型一個計數或一個 timeout，讓 80% 不要一直走。它數次數，重試，把結果交給 20%。20% 的模型看結果夠不夠好。夠好就交給使用者，拿一個是或否。不夠就再跑一圈。研究模型不會一直迴圈。它們有一個停下來說這些是結果、夠不夠好的地方。她說大多時候已經夠好。你不需要很多研究、很多資料才給得出答案。你得決定什麼叫夠好，先把那個當結果給使用者，然後再去找更多細節。

## 不要一個超級 agent，要一個會過濾的 judge

[13:02](https://www.youtube.com/watch?v=DIEAEiyceCo&t=782s) 第三種愈來愈常見，她叫 generalist blind spot。例如她要 review code。可以有一個 agent 拿 context，一個拿 code diff，一個經 MCP 拿 Confluence 或 Jira 的結果。全部丟給一個 agent，它可能被淹沒，然後自己停止決定哪個 context 更重要。也許它決定 diff 更重要，或 Jira 更重要。你要的是問題各自被解開，結果再被彙總。所以不要做一個什麼都能做的 super agent。做多個 agents。每個 agent 有自己要解的任務。任務簡單，context 比較不容易被稀釋，agent 做一個簡單的目標。

[14:28](https://www.youtube.com/watch?v=DIEAEiyceCo&t=868s) 上面可以再加一個 judge。每個 agent 做完自己的任務，試著給你最好的結果。Security agent 看 code，可能把所有安全缺陷都交出來。你在零售業，也許不在乎一個醫療場景的安全缺陷，那不是你要做的範圍。金融業的安全標準，和零售差很多。這些因素都要算進去，再看什麼對你更重要，而不是拿一份泛用的結果。一組 agents 給了各種回饋之後，judge agent 幫你決定什麼更重要、更相關。Judge 可以依你在後面建的 context 工作，也可以依你寫的 rules 和 standards。現在有很多規則的機制。人在接 MCP，去拿他們的文件、架構文件或 Jira。也有入口在維護規則。任何能幫你把回饋收窄的東西，都會讓使用者更有信心。

[16:14](https://www.youtube.com/watch?v=DIEAEiyceCo&t=974s) 你做出一個 agent，很興奮，它在出結果。時間一久，你會覺得結果比較像噪音，而不是有用。她覺得幾乎每個做過 agents 的人都知道這個說法。一開始拿到結果感覺很好，這麼多東西、agents 運作得很完美。真的拿來用，對使用者太滿。過一陣子信心就掉了。她在產業裡最常看到的就是這個模式。人自己做了 agents，然後到別的組織說：可以幫我們做採用嗎。Agents 運作得很完美，採用沒有。所以不只是把任務做完美，還要把任務做小，才拿得到結果，並且要把結果濾掉。我們不需要更多資料。她覺得已經有夠多資料來說該做什麼。需要的是濾過的資料，人才對結果有信心，並且真的拿它來工作。她提早大約三分鐘講完，問題留到座談。

## 不是每行都要人看，但人得知道發生了什麼

[22:46](https://www.youtube.com/watch?v=DIEAEiyceCo&t=1366s) Simon 自我介紹：他是 Tessl 的 DevRel 負責人，公司成立不久就在，之前在 Snyk。他說自己前三、四年把 Snyk 念成 snick。Brian 從 Utrecht 來。現場有一群人，已經用 agentic coding agents 把 code 交到 production。Simon 問，agent 生成的 code 要進 production 時，最被低估、該多看的是什麼。Brian 先說安全。模型在所有資料上訓練。他說他可以當場給你看，coding agent 會產出大很多、而且在某些領域不好用的 code，例如醫療。他希望那是一條確定的流程。Nupur 說她第二個會講的是人的介入。我們把它做得更自主、更自動，但人的直覺仍然需要，而且她覺得沒有人真的在那條線上做。讓一切自動、從一步跳到下一步、中間沒有人的資訊，她不認為那就是答案。控制這一切的旅程還在展開。安全是明顯的一個。下一位把成本放進來：漏洞在變多，定價也在，有些做法可以便宜一個數量級。字幕這裡很碎，沒有把那套算法說清楚。Simon 自己的答案是 context 和 skills。Review、安全、成本，很多被這件事串起來：給 agent 它做那些決定所需要的 context 或指引。他覺得這是 coding agents 裡人做得不夠的一件。

[28:06](https://www.youtube.com/watch?v=DIEAEiyceCo&t=1686s) 他接著問，怎麼不要讓自己只變成 reviewer，一直看生成的 code，出貨量上去之後人變成最慢的那一環。Nupur 仍相信該有一個由人來 ship 的點。她說 agent 在做的也是一個過程。中間有一段字幕很碎。Brian 被問：每一個來自模型的改動，都該由人驗證嗎。短答案是不。若你有一條確定的流程，例如 code，以及其他語意上的檢查，他認為可以。你有測試套件、有讓你成為軟體工程師的那一整套，就可以信任。今天也一樣：有人提 PR，你希望有好的測試，全綠就 merge，自動進 production。不是任何東西都這樣。另一面是，現在連一起寫 code 都自動化了。問題變成開發團隊是不是還懂同一件事。若不懂，你得把人補上。他提到 junior。對他們，學習 code、試著理解發生了什麼，變得困難，他們更依賴工程師提供的東西，然後繼續往下寫。教育該在那裡，他們才說得了：自動化是下一步，全綠就往前，因為那些檢查仍得由某個人先說，這些是我們要的。

[32:45](https://www.youtube.com/watch?v=DIEAEiyceCo&t=1965s) Simon 轉述他們錄到第 101 集時回看前 100 集的一位來賓。他先說不是 ElevenLabs，也不是 HashiCorp，然後說是 Datadog 的創辦人與 CEO。那位說，凌晨三點的嚴重狀況會來：根因分析自動做完，修復推出去，on-call 的開發者甚至不會被叫醒。Simon 問，人該不該醒來、驗證、再推。答案是不。一切都要能逆轉。改動可以發生，只要能逆轉，你就可以測它沒有弄壞東西。若弄壞了，等人醒來，或下一個狀況出現，再逆轉。Simon 說他不覺得我們到了，也不覺得離得很近。中間有信任，也有要走完的路。你信任的是測試、驗證，和那份確定性。

[34:31](https://www.youtube.com/watch?v=DIEAEiyceCo&t=2071s) 有人問：很小的改動若沒人注意到，團隊會不會失去自己的 context。今天改一點，明天再改一點。不監督每一次改動，某個時點人就不知道發生了什麼。Nupur 先問，你們團隊有多少 code review 是 looks good to me。有些在 30 秒內做完。沒有人的介入，不等於你不該知道發生了什麼。這是兩件事。可以是每日摘要，也可以是每週，看系統有多重要。若是會發射火箭的關鍵系統，她絕對想知道。若沒有害，就看團隊要什麼。兩者不互相排除。

[36:17](https://www.youtube.com/watch?v=DIEAEiyceCo&t=2177s) Simon 再轉述 ThoughtWorks 的一位 distinguished engineer，字幕把名字聽成 Bicolor。她會來 AI Native DevCon。她用 Claude Code。用得愈多，她對流程、架構、底層 code 愈不熟。她沒有問這是好事、壞事，還是可以接受。Simon 覺得這接到一個真問題：我們對一個 app 的整體，到底知道多少。我們能不能問 AI 自己的應用。人對系統怎麼運作的假設，可能已經過期。也許有些東西我們不想失去控制，而實際上我們本來就沒有自己以為的那麼有控制。

[43:14](https://www.youtube.com/watch?v=DIEAEiyceCo&t=2594s) 有人寧願凌晨三點醒來，白天午餐時再睡，也不願早上起來發現 production 被改成自己沒有看過的樣子。線上有十億美元時，就算有人說我來做，你還是會醒來確認。也有人從反應時間看：問題認出後十分鐘內修好、推出去，對上要叫醒人、再叫下一個人，三小時後才動。那三小時的機會成本。Simon 說他今天同意該醒來的那一邊。若再過少數幾年這件事還沒發生，他會非常驚訝。但不要一概而論。有些情境完全成立，有些絕對不行。幾年前，自動合併的安全修復不會發生。我們對那類東西的信任，是分級的。另一位聽眾同意 Canal，不會信任 AI 去修。他也不喜歡「AI 錯了就還原」：時間還不回去。他說最近一週就有一個很小、很快、很大的錯。安全公司自己都做不對時，怎麼信任別的公司採用安全實務。Brian 後面接了一句，秘密外洩增加了很多。他問誰把秘密硬寫進檔案，誰沒做過，他不信。那次事件裡他覺得最好笑的一則是：Anthropic 現在比 OpenAI 更開放。

[49:23](https://www.youtube.com/watch?v=DIEAEiyceCo&t=2963s) 一位聽眾說，vibe coding 讓人跳過過去四、五十年的實務，走進沒有規則的地方，只跟著教學做。其實可以用 AI 降低出事、降低凌晨三點被叫醒的可能。他自己寫 code 時只盯事先寫好的測試，把它們當規格。能打中愈多測試愈好，甚至多到人寫不出來的數量。Code 愈長，就逼 AI 跟自己矛盾，於是它不能再往下。沒有人會部署一個沒通過自動化品質關卡的東西。這是在拿掉人的弱點和不一致。問題是怎麼用 AI 做這件事，那會改變你用它來做軟體開發的方式。不是把一匹瘋馬放出去，讓它去它想去的地方。Simon 轉述另一句：AI 會放大壞實務，也會放大好實務。從 agentic 工具學到的最糟一課，是改變我們建造軟體的方式。該做的是用 AI 把我們本來在做的任務加快，但那些任務還是要做。他說有個工具最早是做單元測試的，後來還能看既有 codebase、做出一份測試的待辦。怎麼讓工程師繼續當正當的工程師、走像樣的工作流，而不是用工具把 code 丟出去。Nupur 說這是文化和組織，不是 AI 才有的問題。她當開發者時就有。有人真的遵循實務，對其他人，code review 存在是因為那些基本的事。往前走，review 的內容比誰做了什麼更重要。就算有人在資深的層級做 vibe coding，只要他把腦子放進去、把 code 做得合乎邏輯，護欄在，什麼說得通、什麼說不通，那是文化。不是只把流程加快。留下來的東西要說得通、要夠安全。意外會發生。工具和供應鏈有好處，流程仍然要在。

[53:36](https://www.youtube.com/watch?v=DIEAEiyceCo&t=3216s) Simon 提出兩條可以並用的路。沒有理由不把 best practices 和政策寫成 context 和 skills，讓 agents 不要懶，它們大致會做你告訴它們的事。Code review 到這些等級，安全測到這些等級，效能的實務，先寫測試。它仍是非確定的，每次會做得不一樣，每次會漏。所以可以是：非確定的 skills，加上確定的工具。Agents 先走出它們能走的最好的第一步，再用確定的工具驗證。有人接話：若有一個 skill 說這是 linting、這些是 best practices，生成時我和 AI 都會犯一兩個錯。確定性的 linter 會把那些撿起來。另一個人說，得先定義生產力長什麼樣子。他看到有人在量上班的工人數，他覺得怪異。程式行數不會讓你成為更好的工程師。漏洞這麼多，是因為人覺得可以靠 AI 寫得很快，壞了再用 AI 解。那不是那樣。像舊的心態：你有火災保險嗎。有一則被轉開的貼文，有人說要做一個給 agents 的社群應用，把整個東西寫完，卻需要大約四百萬個信箱和 secret keys。它在社群上被傳開，沒有做安全檢查。然後比較注意細節的人去讀它。

## 規模、Waymo，以及你願意放多遠

[57:13](https://www.youtube.com/watch?v=DIEAEiyceCo&t=3433s) 有人問規模。Agents 會做出更多貢獻，要 review 的功能更多。Simon 說他在這支 podcast 上跟 Google DeepMind 的 Logan Kilpatrick 談過。Simon 記得 Logan 的估計是五年內，我們會造出比今天多一百萬倍的 code。他說這種數字很怪。Nupur 說成長不只是履歷，也是變化。每兩三週就有新東西，不只解舊問題，也帶來新問題。擴展一直是問題。Agents 能提供價值到哪裡，以及它們什麼時候開始製造噪音。我們在爬梯子，解現在的問題，同時製造新的。她看不到會在哪裡停、預設會造出多少。Context 也是：我們在做更多 context、更多感知，然後帶來另一組要解的挑戰。下一位問，更多 code 是不是目標。他說表現最好、也最安全的 code，後面字幕沒接完。他要更多效能工具。東西出錯時，得懂那段描述、懂發生了什麼。現在愈來愈多人是 looks good to me。若那種感覺變成十倍、五倍、一千倍，垃圾會更多。要更好的 agents，也要照顧這件事。Junior 開發者，他自己在變老，我們不會永遠在。新的開發者得知道該做什麼。那是我們的事。什麼是生產力，什麼時候是更多安全漏洞。那是選擇。Simon 覺得有趣的是，那些專家未來從哪來，若很多 code 是 AI 在寫、錯誤是它在第一手學。

[1:02:36](https://www.youtube.com/watch?v=DIEAEiyceCo&t=3756s) Simon 講 Waymo。他們幾個人在 Austin 坐過。他下週要去 Austin。Waymo 用 lidar。他拿它和用攝影機的 Tesla 對比。倫敦有沒有，字幕沒有說死。訓練的數字他說大約三千或四千公里，然後再帶駕駛和乘客開大約五百。他們坐上去先尖叫，因為控制不了。習慣的速度快得讓他吃驚，車也開得很好，直到一家叫 Terry Black's 的牛排燒烤店。它混亂了。另一輛車，它想繞過去，人在前進時它想倒車，像是要快點脫離。還有一次，警察對峙，有人躺在地上、槍指著，Waymo 看成沒有車流，就開過去，穿過或經過。他說 95%、99% 的時間很好。一到 edge case，事情就發生了。Brian 說這很看立法：出事時誰負責。在歐洲，多數情況下現在必須是一個人。我們會不會指到三萬英里外寫出它的那個開發者。必須有人做決定，人或公司。他用飛機：多數機場最 precarious 的是降落和起飛，飛行員負責，手在操縱上。空中那段不是問題。飛行員能做瞬間的決定。這是威脅和風險管理。若有夠多證明電腦做得比人好，時間到了大概就會走過去。Simon 說擋住那條路的會是差的護欄、差的測試。它們造成問題，降低信任，把路放慢。他認為那是必然。有了對的護欄和測試，他看不到一個未來是我們沒有把潛力放出來。99.99% 的時間它會動，不動的時候我們處理。人在其他情況也會造成很多問題。現在要有護欄和正當的 review。否則會做這件事的公司，會把不做的公司撕開。Nupur 說始終會有一個人。你會接受一次完全沒有人的開心手術嗎。零售店和開心手術之間有一段距離。飛機、手術也一樣。出事時要有人負責。若我們懂系統在哪裡運作、出錯時做什麼，團隊有那個能力，為什麼不給更多自主。若事情失控、你不知道怎麼回去，就是先前說的：自動化做的改動若能還原，為什麼不試。一旦你不知道怎麼控制、怎麼回去，甚至一個月後你不認識自己的架構，因為生成的 code 離你的理解很遠，那就是問題。你回不到當時做的事。

[1:10:17](https://www.youtube.com/watch?v=DIEAEiyceCo&t=4217s) 每個人願意放多遠。Simon 今天願意讓它對非關鍵系統做完全自主的更新。關鍵系統也可以，只要檢查和測試夠。那不是他對 AI 的信任，是他對自己測試的信任。若不信任測試套件，他會信任 junior 嗎，或週五下午喝過一杯的 senior 嗎。車要開快，需要剎車。信任的是會讓你不要失敗的那些系統。對關鍵系統的非關鍵改動，或對非關鍵系統的任何改動，他可以接受。個人生活裡，關鍵變成個人資料、PII 那一類。他預期那會被大力往前推。他願意讓更關鍵的改動發生，只有在他得到的價值，大於不允許它發生時會發生的事。凌晨三點：若他要兩到三小時，AI 五分鐘就能查出、解決、修好，他寧願它去做，然後在它做不到時叫醒他，或在它想做的改動被護欄或測試說成高度危險時叫醒他。那些驗證必須是確定性的測試。他對此自在。

[1:12:33](https://www.youtube.com/watch?v=DIEAEiyceCo&t=4353s) Brian 說大多同意，但他這個人相當多疑，在安全公司工作是有原因的，從軍也是有原因的。他不信任東西。他要知道發生了什麼，因為最後負責的是他。現在他想自己點下那個證明，有意識地做了它。要說服他對非關鍵、以及還不算設計上關鍵的系統盲目信任，會花一段時間。連 CI/CD 他都曾經想知道它是不是真的有用。他曾經是那個人。現在他信任了，但對他來說要一段時間。Nupur 在中間。關鍵系統她想實驗，做護欄，依結果和回饋決定什麼可以自動、什麼該停。非關鍵的她想玩，用試過的情境。若依結果把某些東西停下，找到那個對的點，系統夠成熟時，她可以再往前跳，比較樂觀。字幕裡她有幾句沒有聽成完整的條件。

[1:16:22](https://www.youtube.com/watch?v=DIEAEiyceCo&t=4582s) 有人問，不是工程師的人也能做應用、碰客戶、做 prospect 時，工程團隊和那些人的信任怎麼平衡，工程師會不會變成收拾殘局的人。Canal 說，事情變容易，就會有更多人做。小生意要自己的網站，他會推薦 Lovable。他不會推薦你把它部署到 Kubernetes。基礎設施、安全若有人幫你處理，你就專心把網站做漂亮。大組織裡，安全檢查和對 code 負責的人是守護者。他們有行銷同事用一個字幕聽成 lavender 的東西做簡報。他不會叫那些人把東西推上 production。看情境。為什麼要叫行銷把東西推上關鍵應用的 production。五個人的團隊是另一回事。若用的是客戶資料、網站對全世界開放，不能隨便拿 1995 年的做法。要有權限，要有把資料守住的計畫。只是簡報，他不必跳進去。Simon 不同意「現在每個人都能成為開發者」。他喜歡能寫 code 的人更多樣。寫 code，和當一個開發者，差很多。今天好的開發者，是 code 寫得最好，還是能解決問題、把事情做穩、測完整、溝通好、懂解法是不是貼著問題、能跟使用者或客戶的回饋一起工作。他喜歡 vibe code 的、用過即丟的東西。也同意那有會變危險的邊界。要開快，得有剎車。可以賦能這些團隊。他們的法務 Stephanie 做了一個 skill，用它處理合約這一類法律工作。字幕有一句沒聽清她的 skill 具體做了什麼。重點是指引，是讓 AI 在邊界裡做事。某些東西就位之後，那就是賦能。

[1:22:01](https://www.youtube.com/watch?v=DIEAEiyceCo&t=4921s) 什麼叫安全，Brian 說可以爭一整天。燒更多 tokens、燒更多電力，若你看的是法規或環境，那算不算安全。他認為正在發生的，首先是誰負責。他前面說過，這最重要。就算最好的開發者、最好的東西，事情仍會出錯，因為她沒預見到。你放了什麼來介入。可觀測性在不在，讓你能介入，以及何時介入。模型今天也許不知道，較新的模型也許知道。我們不知道。問題的一部分是人的互動擴不了。我們能產 code，但十個 agents，我有沒有夠豐富的 context 去 review 全部。他不認為有。我們得學會跟那個現實一起生活。更多 code 是不是更多生產力。什麼是生產力。談得太一般，取決於你在找什麼。沒有清楚的答案。未來才會像那樣。Canal 說，人以前寫 assembly，後來二十種語言、垃圾回收、Kubernetes，不必自己編排、不必自己管容器。就算到了一個完美狀態，仍會有人必須做的決定，直覺和願景。他要有一個人。Simon 不確定同意。世界一直在變。過去四週發生的事，是我們五年前以為會發生的。模型訓練用的東西，至少舊了四週或數月。我們得在某些地方介入，那會是瓶頸。另一位說，人常把人的敘事套到電腦上。你給很多訊號、很多 context，他看不到一個世界，那不會碰到他稱為人的做法。但 context 在多數情況下已經互相矛盾。你給得愈多，它愈取決於你怎麼看世界。一切被文化、被你怎麼被養大、被法律和法規綁住。英國和東南亞的做法不同。所以人始終會在過程裡，也許不是由人去拿那段 code。

[1:25:52](https://www.youtube.com/watch?v=DIEAEiyceCo&t=5152s) Simon 說自己大概在兩種看法中間。這些年的抽象，從機器碼到 assembly，到直譯語言，一層層升高。現在這一步是革命性的，不只是一種新格式。他不想說它為自己思考，但它做得夠好，好到我們相信它在為自己思考。它會繼續，某個時點會進入高原。差別是，今天的 agents 和 LLMs 在接手一個寫 code 的任務，它們在近似它們以為我們要它們做的事。我們的角色該從 code 的生產者，轉成創造者。AI 今天沒有把那件事從我們這裡拿走。也許未來某個時點會。今天該擁抱讓我們真正有價值的東西：最後有使用者，那些人有需求，人比 AI 更懂那些需求。我們能解決問題，能在心裡給上百個維度不同的權重，相信這個人會想要這樣。他不認為 AI 很快做得了那種事。他希望到那天自己已經退休。有人問這是默會知識，怎麼把它編碼，不只是碰到資料。Simon 說那會非常接近 AGI。依他的看法，我們離 AGI 遠到難以置信。他再提 Logan Kilpatrick：在 Google DeepMind 帶一塊產品，以前在 OpenAI。Logan 說的是，AGI 不會是一顆模型的魔法揭幕。它會是一個產品，也許是不同團隊的好幾個功能，一個感覺像 AGI 的環境，實際交出我們期待 AGI 會交出的很多東西。不是一顆突然就被標成 AGI 的革命性模型。我們會接近，然後碰到高原。對開發這類事情會夠好，但我們仍得當那個負責的創造者。在碰到他所說的 AGI 之前，不會真的看到剛才描述的那種編碼。他認為那是和現在其他實驗室在做的 AI 完全不同的做法。大多數公司不知道自己在做什麼。失敗的方式很標準。Kubernetes 出來很多年，他仍看到有人不知道自己在做什麼。安全的人在犯二十年前的同樣錯誤。

[1:30:49](https://www.youtube.com/watch?v=DIEAEiyceCo&t=5449s) 最後每人一件，交到 production 之前不一定顯而易見、但今天該被看得很重的事。Brian：確定較新的開發者也知道你在做什麼，而且你不會被責怪。你今天做得很自豪的那些，要讓未來的自己也為你自豪。新進公司、能來修你東西的開發者，也要看得到那段 code。你要能向他們解釋。他認為延續最重要。Nupur 接他的話：不是把一切自動化，而是保存知識。我們愈自動化，就離知識愈遠。我們說文件會自動更新、架構會自動做。實際上，連正在做這件事的開發者都在失去知識。你創造什麼 agent 不重要。你寫 code、修 code、分析那份知識。保存那些元素，是最重要的任務。Canal 問：什麼讓你有生產力。只是把 code 吐出來嗎。弄清楚一件事。開始，然後繼續。Simon：保存知識的最好方式，是讓它人讀得懂，也讓機器讀得懂。Context、skills。把指引、政策、工作方式、skills 放下來。你會把一個人類開發者 onboard 進團隊，對 agent 得做完全相同的事。寫進 skills，評那些 skills，給它們版本，發給團隊，讓你們像一個人一樣工作。

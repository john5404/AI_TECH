# Steve Yegge: 'You'll Never Write Code the Same Way Again'

現場對談，片長 57 分 50 秒，英文手寫字幕。主持人先介紹兩人，Steve 謝的是 Simon。Dru Knox 是 Tessl 的 head of product，做過 Chrome 和 web platform 的 PM、web standards，也曾是 Grammarly 的 research scientist，自己創過公司。他當這場的對話夥伴。Steve Yegge 在工程業超過四十年，待過 Amazon、Google，最近在 Sourcegraph，寫過原來那篇 Google Platforms rant，也做了 Gastown，以及給 agent 當外部記憶的 Beads。字幕把 Beads 聽成 Beats。這份筆記依英文原稿整理，專有名詞保持 English。

- 原片：[YouTube](https://www.youtube.com/watch?v=Rgwu9nF_Xok)

## 一句話

直接用 agent，是和它 pair programming。你開始寫 code 去讓 agent 做事，才進了 factory。Steve 把那一刻說成：工作變成一等公民，是你在操縱的物質。你花 token 生出工作，再 swarm 去修、去審，然後重來。Tessl 用兩條規矩把自己推進這個領域：沒有人寫的 code，沒有互動式的 coding agent session。認知負荷大約在四、五個 agent 就很硬。工廠是為了把便宜的模型留在軌道上，同時把人的時間留給品味和該做什麼。

## 你一開始當操偶師，瓶頸就會把人擠出去

[0:39](https://www.youtube.com/watch?v=Rgwu9nF_Xok&t=39s) 題目從定稿到現在三週，詞已經換了。他們要談 harness engineering 和 software factory 長什麼樣，自己怎麼建、客戶那邊看到什麼，以及這對軟體開發、對工程師這個角色的影響：哪裡該怕，哪裡該高興。Dru 說他不騙自己，大家是來聽 Steve 的。

[3:48](https://www.youtube.com/watch?v=Rgwu9nF_Xok&t=228s) 什麼是 software factory，Steve 說這個詞還有點不定形，大家還在定義。他的想法是：你一開始試著以任何身分當 agent 的操偶師，就進了工廠。直接用 agent，不是工廠，那是和 agent pair programming。你在寫 code、讓 agent 去做事，就進了工廠的地盤。Dru 說 Tessl 看得很像。沒有一個特定定義。大體上是：你在建一個把人擠出迴路的系統。它最明顯地冒出來，是你真的開始用 agent 做菜的時候：幾個平行 session，PR 比以前快很多。流程裡只要有人，瓶頸就冒出來，於是推你去想：端到端把產品交出去，能不能交給 agent。

[5:42](https://www.youtube.com/watch?v=Rgwu9nF_Xok&t=342s) Steve 說那就像你得到 AI psychosis 的那一刻。字幕接著聽成 software and batteries。因為它們做得到，而且可以沒人看著做。然後你說它們大概需要一點監督。然後你說我不能再叫另一個 agent 看它們的肩膀。於是你有了一個對抗的 pod，那已經是一座小工廠。工廠出現在很多表面上。他們最先注意到，是在做開發的時候。Gastown 就是這樣來的：若我想一次跑 20 個 agent 呢。你大概不會直接跟 20 個互動、引導它們。認知負荷大約在四或五個就變得很硬。但有很多任務可以平行：重構，或任何一種掃過。

## 花 token 生工作，Beads 是因為 markdown 裡迷路了

[6:42](https://www.youtube.com/watch?v=Rgwu9nF_Xok&t=402s) Gastown 是一月一日。他說時間過得細。整個去年他都在試著讓 agent 去跑 agent。他發現常常需要一種節奏。你跑一個 swarm 去生一批報告、一批 issue。跑一個 swarm 做 code review、開一批 bug。跑一個 swarm 做稽核，把所有待辦轉掉，隨便什麼。你是在花 token 生工作。然後你有了一批工作，再 swarm 去修，再 swarm 去審，然後重來。工廠是在把工作推過去。所以一談 software factory，就是你開始把工作想成一等公民，一種你在操縱的物質。工作、ticket、設計文件、待辦，不管你怎麼表示。

[7:51](https://www.youtube.com/watch?v=Rgwu9nF_Xok&t=471s) 他是倒著跌進去的。他用手跑一批平行 agent，它們在 markdown 檔裡迷路。Beads 就是從那來的：若我們用一個圖來追工作，有 git，有資料庫存取，有辦法把全部存起來、看著它走完生命週期。現在是待辦，現在是進行中，現在是做完。那像一本帳。這是三種很不同的看法。未來的工作通常很公開，誰都能認領、辯論、修改。有人認領之後，它被炸開，像車進了廠、頂起來，到處都是，也許有很多中間的小票。你通常不想讓人看見你在那個狀態裡工作。然後某個時點你把它收成一份好讀的東西，送出去、被審、被接受。完成的工作變成你的履歷，一份整理過的、你完成了什麼的視圖。那是我們要去的世界。Beads 把這個形式化。你可以用任何 issue tracker。他看到很多人預設 GitHub issues 或 Linear。那些東西被設計成非常重。但我們在做 software factory。他問大家有沒有讀他一月一日寫的 Welcome to Gastown。核心想法是鏟很多工作過去，多到在工廠裡你可以不小心把同一件工作做兩次，同時得到不同結果，然後得有人判斷挑哪一個。你也可以把工作弄丟。做了一大堆、花了 token，然後它去哪了。有人刪了，沒了。工作變得幾乎不可數。這樣工作貴得離譜。Gastown 是他在試著怎麼往前推。

[10:09](https://www.youtube.com/watch?v=Rgwu9nF_Xok&t=609s) 好笑的是，若你真的想跑 60 個 agent，Gastown 其實過度。他最近沒用 Gastown，仍在建自己的 software factory。你會養成一直在建的習慣。它們是訂製的。沒有一座工廠適合全部。有些共同點。他發現每個專案都得建一個腦。他用 Obsidian，那是很好的預設，但什麼都行。有人提了一個接在 Obsidian 上的東西，字幕聽成 G brain、Mary Tam、Gary，沒有聽清。他說沒有丟臉，會去看。腦之外還有別的零件。大體上，工廠是你在塑造工作要怎麼流過你的 agent。他正在做的、他說大家現在都該做的，是接下來六天：做一批設計工作，並把實作工作開得夠清楚，讓 Opus 做得到，誰知道能做多久。這是一種工廠的形狀。你在生產以後才會被消耗的工作。之後若你偶爾需要 Fable，也許只剩 API。所以你得用智力層級把工作標起來，才能路由，才知道什麼是穩的。你在自己機器上、團隊裡、或組織裡，把這些 agent 換進換出、對上合適的工作、以便省 token。那就是你的工廠。你有沒有把它說明白，你已經有了。

## Tessl 的兩條規矩，以及進 PR 之前先改 harness

[12:20](https://www.youtube.com/watch?v=Rgwu9nF_Xok&t=740s) Dru 把建自己的工廠、每件事都是訂製的，留到後面。在 Tessl，他們出發時覺得有點過分野心，想看限度在哪，很快就變成他們現在的建造方式。他不會做太多產品簡報，只說大部分是用 Tessl 建的，有興趣可以看。兩個核心目標。第一，沒有人寫的 code。第二，沒有互動式的 coding agent session。光這兩條就幾乎逼你進 software factory。他們安定下來的流程，會碰到 Steve 說的一些零件。一切從一張 issue 開始。若你在想建工廠，第一個問題就是你怎麼追工作、怎麼定義、怎麼管、用 Gastown 的說法怎麼把它甩來甩去。他們用 Linear。Steve 說得對，有時他們懷疑是不是需要全部那麼重。他們開票。背景有一個 orchestrator 在輪詢 Linear。票一建立，它會撿起任何你委託給他們內部叫做 dark factory agent 的東西。Agent 撿起工作，實際上建立一張 PR。他們一開始試過一些編排，自動替 agent 開 PR，常常壞。於是只給 agent GitHub CLI，做完它自己開 PR。工程團隊在 PR 這層介入、審查。人類和 agent 的 code review 會很快變成關鍵。Steve 問：你們也不做人類 code review？Dru 說那是長期目標，比前兩件要更多工作。

[15:03](https://www.youtube.com/watch?v=Rgwu9nF_Xok&t=903s) 他們有一個通則。審查 code、在你直接留言、立刻去糾正 agent 之前，退一步想：我能不能修 harness、修 agent 所在的整個系統，讓它不會犯這個錯。他們要求人，在 PR 上留任何留言之前，至少一次，你得倒帶，改 codebase 裡的 skills，或加一些 unit tests，改架構，做一件你認為能修掉它的事，再試一次。若第二次仍不是一次做完，才可以在 PR 上留言。Steve 說這是很有趣的觀察：不管你怎麼建工廠，它基本上都有持續的衛生和保養。這在 Gastown 是大事。他說 dogs 最後就是為這個，一個專門的角色，字幕沒有再解釋。不管你怎麼做，你都得花一些 token 維護工廠。若能建進流程，讓每個人離開時比找到時好一點。因為你每次用工廠，都會注意到某處有一點 bit rot。這很自然。Skills 在演變，系統在變，skills 實際上是新的文件，所以它們需要更新。Tessl 可以怎麼幫，他們會再談。這是一種心態。像工坊，機修的或工匠的。得保持乾淨，得花一定時間在工具上。很多會是完全現成的。他要說的是，你會想把維護者的角色建進工廠。

[17:03](https://www.youtube.com/watch?v=Rgwu9nF_Xok&t=1023s) Dru 覺得這是好的起點。Issue tracker 能立刻委託給 agent，它開 PR，你能留言，PR 上的 agent 會處理並送出變更。那有點像核心單位。每座工廠都會想要看起來像那樣的東西。對有些人，這聽起來像很進階的起點。他其實覺得 agent 現在已經相當好，你不會每一張上來的 PR 都在不斷改。重要的是開始用這種方式工作。你和 agent 的互動都變得非常可讀：票、所有 PR 留言、PR 本身的 commit。於是很容易開始建 maintenance agent 或 sweep。工廠裡通常下一個冒出來的就是這個。不管 code review 多好，總有東西從某處漏過。人大概也一樣。所以你想設一組，不在 diff 裡，而是一般地掃 codebase，一天一次、一週一次，任何節奏，找改進的方式。Tessl 內部通常會出現的：一個架構 agent，找重複的 code，或看起來難測的地方。一個看測試品質的：覆蓋怎麼樣，也許做 mutation testing，看 codebase 有沒有新區域可以測得更好。文件。清單會繼續長，你發現問題就繼續加。最後是 code review。你很快會發展出一整套。一般的 code review，找你還沒想到要抓的。Claude 有工具。也有 CodeRabbit。你可以自己做。Tessl 的工具可以用一個 skill 幫你設。你也想要更針對的 code review。哲學應該是：每次發現 agent 的一個錯，你再也不必糾正它。該有東西專門去找那個。

[19:33](https://www.youtube.com/watch?v=Rgwu9nF_Xok&t=1173s) 他好奇這對 Steve 有沒有共鳴。對他是很大的改變：在 software factory 的世界，lint 可以迂腐到什麼程度，因為你是在叫 agent 寫。花 50 行 code 寫一條 lint，只檢查這個檔永遠不從那個檔 import，其實不要緊，因為 agent 常常把架構反過來。他的 side project 是自己的 agent 編排工具，這時候誰沒做過。他有一個跟 Anthropic 工作的 client，和一個跑 agent 回合迴圈的 client。他說 harness 該呼叫 Anthropic，Anthropic 不該知道 harness。結果 harness 實作了自己的 Anthropic client，然後 Anthropic client 把它 import 進來、再 export 給 codebase 其餘的部分。他就寫了一條 lint：anthropic module 永遠不該從 harness module import。以前他不會把這種東西寫成 lint，現在覺得自然得多。Steve 說你得擔心的一件是，若你只是一直寫不要做這個、不要做那個，下一個模型出來時，你真的會想要 eval，告訴你還需不需要那條。不然你會永遠累積，然後變得沒用。那又是另一種 sweep。你大概會想定期設一個，去重新評估你放進去的每一條規則。又一種核心能力。

## 新工作是看顧，忘記和長大一樣必要

[21:24](https://www.youtube.com/watch?v=Rgwu9nF_Xok&t=1284s) 這可以接到職業怎麼變。模型一發布，它們解不解得出你以前解不了的問題。Steve 用過類似 pocket evals 的說法：你的硬任務，最好的模型目前做不到，下一個也許可以。反面是你為了讓這一代模型能動而做的膠水，可能不再需要。你怎麼知道那發生了。你怎麼把不再需要的 context、規則、hooks 拆掉。Steve 說那就是新工作。Software factory 最終會裝上全天候的自主 agent，執行公司現在在做的所有業務流程。我們會看顧它們。那種維護正是我們要確定被做掉的一部分。野心變大、工廠變大，那些我們用手做的事會變成 skills，被推進基礎設施。我們在看更高的關切。整件事必須不斷長大。它也必須不斷忘記。數學上愈來愈清楚，忘記是任何能運作的記憶庫內在的一部分。不然它們會失智、發狂，或乾脆變錯。所以你幾乎在建一個活的系統。

[23:13](https://www.youtube.com/watch?v=Rgwu9nF_Xok&t=1393s) 工廠會不會有一個穩定點，做完了，它就替你生產。Steve 說天花板一直在升，工廠能替你建的東西一直在升。天花板之上才進入工程、手藝和品味。在我們真的建出字面上的 Death Star 之前，永遠有更多工作。他覺得好笑。週一他看到、也跟 Dru 談過的那個 Anthropic 的人，內部覺得他們現在是被野心綁住。光是想該做什麼都變得非常難。工作變得超快。這時候會穩定嗎。他不會賭。兩年後一個軟體工程師的一天呢。希望他們工作生活平衡很好。早上帶著咖啡進來，看著 200 個 agent 的團隊，說好，開始吧，大家做得怎麼樣。有點像我們現在做的。角色在塌。理想的公司規模也許在縮小一點。大家怕工廠會縮小人力，因為工廠在做我們以前用手做的一大堆工作。但世界上其實有兩種公司，他認為多數是有野心的那種。一種只有一件事要做，在乎的只是把它做得更有效率。那些大概可以縮小。他認為多數公司私下想做的比現在多得多。一旦這些東西部署了、那些雜事剃掉了，他們終於可以把視線放高。

[25:37](https://www.youtube.com/watch?v=Rgwu9nF_Xok&t=1537s) 他現在自己就有這種感覺。他的電動玩了三十年。Covid 期間他數過 bug backlog，有一百年的工作。來自玩家的 bug、功能請求，以及他自己想做的。Backlog 堆到一百年，他放棄了。現在野心有剩。不要失去這個。你若開始想，天啊它們在做所有工作，我還帶來什麼價值，你會非常沮喪。不要那樣想。想 Death Star，或不管你的北極星是什麼。Dru 聽到角色塌掉有共鳴。比較專的人，我只把 code 寫得很好，或我只會跟使用者說話，會變得更通用一點。你會想能自己做一點設計、一點產品，大概還有很多工程紀律。Backlog 聽起來有點消失了。你在推更多平行的功能，切換任務、多工。他好奇 Steve 以前是哪種工程師。那種進洞裡三天、誰都別跟我說話、然後帶著一片漂亮乾淨、可擴展的架構走出來的感覺，好像有些消失了。現在更像同時丟五個功能，它們走的時候你去看一眼。開心、難過，還是無所謂。

[27:33](https://www.youtube.com/watch?v=Rgwu9nF_Xok&t=1653s) Steve 說到頭來是多巴胺，你要從哪裡得到。他以前從實作 Bresenham 演算法得到多巴胺。不是編的。1991 年，華盛頓大學，他看一條線在古老的 CRT 上一個像素一個像素畫出來，覺得 yeah，我是程式設計師。但他其實不想畫一條線。他想要一個電動。圖學程式設計變得劇烈。現在我們做的是我們真的想做的。他在遊戲裡寫過很多漂亮的 code。A* 搜尋，他說那對遊戲是非常好的搜尋演算法，他寫過很漂亮的實作。還有一個很可愛的 kernel、scheduler 和 property system。他把自己鎖起來好幾天。工作裡那種美妙的部分，有點消失了。但他不想寫 A*。他想要怪物來追他。你得記得你為了什麼在這裡。你為了結果、為了體驗、為了交付。沿路那種好玩，是暫時的。他仍能從寫 code 得到一些嗡嗡聲，只要叫那些 A 去重寫、寫得更好，然後看輸出，你還是能得到一點 vibe。這是新世界。他把它比成狗把頭伸出車窗。味道來得快得多。有一種味道、慢慢喜歡它，也很好。但我們正走向一個更快的世界。Dru 也注意到，很多多巴胺來自打造系統本身。很多人愛自己造的小世界：這個 agent 跟那個 agent 說話，然後這個檢查跑。每個人都想建自己的 workflow engine。至少 Tessl 愛。他離開 Google 時，那裡有 50 個工程師造的 workflow engine，他在盤點那些 Rube Goldberg 機器。你也會花很多時間想架構、技術設計。有些人也許會稱為工作裡比較高的部分，資深架構師、有願景的那一面，現在每個人都做得到。寫 code 的苦工，他叫它苦工，是為了挖出架構。他知道有人真的享受把好 code 雕出來。但它讓我們都往上移一層，大概是我們職涯裡本來就想去的地方。重點是守住那個。

## 先讓它放肆花 token，再教人停

[30:49](https://www.youtube.com/watch?v=Rgwu9nF_Xok&t=1849s) 有沒有風險，進到工廠、更多 agent 審查、更少人類審查時，該特別警覺什麼，該抓住什麼。Steve 說我們得靠做來學教訓。去燒 token。他認為大家從一月到四月學到的大教訓，可以說是 Gastown 以某種方式開的頭，是 token maxing。整個產業跟 token maxing 戀愛了一場。那是必須學的一課。首先你得教人花 token，花費會走過一些階梯。一旦他們真的知道怎麼做，他們會變成豬，然後你得教他們不要花 token。那變成新的挑戰。若你為整個組織打開 Copilot，兩個月後、或兩週後，你就有風險把今年的 AI 預算炸掉。他和 Dru 各自得到同一個結論：前面有一個訓練問題，一個賦能問題。人不知道怎麼做 coding，更別說建 software factory。他會主張，未來十二個月，每個知識工作者都得升到至少基線的 AI 識字：能用一個 agent 幫自己的工作。那很大，但沒那麼糟。依 Netflix，好的訓練只要五小時，燈就會亮。在那之前，他們都害怕 AI 會拿走工作。之後，他們興奮地談他們和 agent 可以怎麼幫。所以他們對還沒開始用 agent 的公司談 software factory 時，是在各說各話。他認為風險是我們不訓練人，然後突然有一場大出軌，公司不再好好運作。

[33:13](https://www.youtube.com/watch?v=Rgwu9nF_Xok&t=1993s) Dru 說工廠特別容易被講成前沿，給那種剛起步、996、完全被 AGI 灌滿的 greenfield 新創。其實到頭來只是找出重複的 workflow 並把它們自動化。可以非常一塊一塊。不必嚇人，走的時候不必很多進階能力。只是決心用一種特定方式工作，退一步，把東西自動化。那是你想做的很多訓練：讓人看見他們正在做的問題，讓他們至少有幾個成功點。Token maxing 現在有點變成迷因，因為大家都看到帳單到期。他確定有些成功故事，帳單尾端不必那麼多零。但有一定程度你得先讓它放肆，找到一些有用的、讓人興奮，再把它收回來。若一開始就謹慎，你每次都會打低。Steve 說讓它放肆。然後他們開放提問。

## 問答：多刷幾次，不要跟 bitter lesson 打架

[34:32](https://www.youtube.com/watch?v=Rgwu9nF_Xok&t=2072s) 沒有麥克風，喊出來。最近最喜歡的工廠技術，或試了很有衝擊的東西。Steve 先說：Fable 把一隊 Opus 像雪橇犬那樣套在一起。讓更聰明的模型去管較低層的模型，若你能調準，會是遊戲規則的改變。Dru 自己每個新專案會放一套反覆出現的 harness，很大一部分用 Steve 的說法是 sweep，做在測試品質上。他加了 mutation testing。若不熟：你去排列 code，用應該會壞的方式。改條件的邊界，或改 code 裡的魔術數字，再看有沒有測試抓到那個本該是破壞性的變更。兩種做法。可以只在 diff 上，只改你開的那張 PR 裡面。或掃整個 codebase。他現在發誓靠這個。每張 PR 都設。它找到覆蓋抓不到的東西。組合是：覆蓋設一個最低門檻。他也會在 CI、CD 裡要求開出去的 PR，在 diff 自己裡面接近 100% 覆蓋。你不想要一個已經有很多覆蓋的檔，裡面的變更偷偷混過去。但覆蓋常常是劇場，所以你想要辦法證明測試真的抓到行為。每張 PR 上的 mutation testing 不要直接擋，因為會有偽陽性。他讓一個 agent 看 PR 上的 mutation testing 報告，對沒被抓到的留留言。幾乎總是讓測試套件變好。一週一次，對整個 codebase 做同樣的事。這樣他覺得測試套件相當可靠，也讓他更接近不必審查 code。最大的例子是邊界條件。很多業務邏輯寫成這個 list 永遠不會空。測試的 agent 愛測一次或兩次。它們做五、做五十，從不查零。那是他一遍遍看到它抓到的最大區域：你烤進產品裡的小假設，得出現在 code 裡，你也想讓它們在測試套件裡。

[37:43](https://www.youtube.com/watch?v=Rgwu9nF_Xok&t=2263s) 工廠有多少是決定性的，多少只是信任模型做對。Dru 叫它工廠的 trust fall 版。Tessl 一開始非常決定性。他們試著有清楚的階段：agent 建東西，然後 harness 進來建 PR、送出去。留言來了，他們再ferry 回 agent。至少對他們，他發現你幾乎想把那拆掉。每一段試著去編排的決定性 code，都會變成工廠裡的脆點。他說這是他們的視角。你很常以為這對我們建的每一個功能都是真理，然後發現大約 15% 的功能不走這個模式。一個簡單的是疊 PR。然後你發現，糟了，我們的 orchestrator 在這一點上讓那在物理上不可能。所以他們相當積極地收回來：給 agent GitHub CLI，告訴它做什麼。他們放決定性檢查的主要地方是結尾。一批 hooks。一批像 CI、CD 的東西：跑 unit test，確認某些 skills 在你能停之前被載入。他自己的例子：agent 一試圖做 git push 或 git commit 的 tool call，就跑 unit tests 和 linter，沒過就把那次 tool call 鎖住，告訴它你得先跑這些、去修。它若想結束 session，就查工作是不是都 commit 了、PR 開了沒有。沒有就不能停。除此之外，他的偏好、Tessl 當然更進一步，是靠 agent。

[39:55](https://www.youtube.com/watch?v=Rgwu9nF_Xok&t=2395s) Steve 說決定性可以從幾條軸想。一條是 OpenClaw 對 Gastown。字幕把 OpenClaw 聽成 open claw。OpenClaw 是給 agent 一個目標，讓它們 swarm 出去做。Gastown 是把工作拆成很小的、決定性的片段，若順序要緊，就按特定順序執行，不然什麼順序都行。想法和 OpenClaw 非常不同。你給 agent 多少餘地，對上你有多想把牠們要做的事鋪好。另一個維度是品質。聽起來 Dru 聚焦的是品質：怎麼讓這些東西在一次通過裡不犯錯。若你在談 LangChain，你是在想怎麼留在軌道上、不要跳過一步，根本是在想怎麼讓它在一次通過裡更聰明。答案是你等下一個模型。他去年整年試著把這個寫成 code。GitHub 上有一個 repo，叫 Vibe Coder，也許是 VC。他有兩個，試著解這個問題，然後明白答案是你在跟 bitter lesson 打架。答案是多次通過，答案永遠是 swarm。對抗式的審查、共識。像漆這些牆。不要想我怎麼造一台機器，每次第一層都漆得完美。不，多次通過、多層漆。我們就是這樣寫 code 的。所以工廠必須非常隨機，品質變成一個旋鈕，你選擇要在上面花多少 token。Dru 也覺得工作形狀的決定性是好的，把東西拆成任務樹。他喜歡那個是為了 SOC 2。

[42:06](https://www.youtube.com/watch?v=Rgwu9nF_Xok&t=2526s) 哲學是由上而下還是由下而上。由上而下：從系統該怎麼運作的願景開始，從一個中央 orchestrator 向外建。由下而上：從一個工作單位開始，找到有用的再往上疊。Steve 說他總是在重做。Gastown 是持續重做，直到他特別喜歡的一個形狀：一邊是一小把 agent，他跟它們做很深的設計審查、很深的 context，他叫它們一個 crew。另一邊是丟掉的、短暫的、規格寫得很清楚的工作，就丟 agent 上去。那個形狀在他的工作裡一直回來，因為丟掉的那側是：我有一件很大、可平行的事，我就把艦隊拆開。所以他一直走回 Gastown 的形狀。但他最近又從第一原理開始，在建一座 software factory。有趣的是你靠加 agent 把它建起來，也許讓牠們知道彼此、共享工作。到某個點牠們哼得很順，你有大約 12 個 agent 在跑，然後你明白我的工廠形狀錯了。發現工廠長什麼樣，本身也是隨機過程。於是你得把整件事關掉，讓 agent 排空，把目錄搬來搬去，重塑工廠的腳本，讓牠們知道新地方在哪，建新的 clone 或需要的 agent，再整台開回來，看喜不喜歡。要幾次迭代。他還沒弄清哪些部分是這個專案專用的，哪些是他會帶著走的通用部分。你能多快架起、拆掉工廠，就會多快找到路。

[44:13](https://www.youtube.com/watch?v=Rgwu9nF_Xok&t=2653s) Tessl 很像。他輕推一下 Tessl agent，它試著幫你建 software factory。他們走非常由下而上、迭代的路，兩個或三個大原因。第一，一切變得太快，很難從頂端開始、一路做對。容易得多的是：這是我喜歡的一個工作單位，圍繞工作本身來塑形。這是我每週都做的任務，我只想自動化它。然後一塊一塊疊。你會有四、五個看起來形狀差不多的自動化，於是你做一個東西，讓做那種自動化變容易。像反向的 jawbreaker，你在上面建很多層。這也是真正脫困、開始工作的最好方式。任何時候你試著一次把整個軟體開發生命週期吞進腦子，說我要把一切設計完美，那是花兩個月弄出一個最後根本不能動的東西的配方。若你只說我每週做這個，若我不必做呢，若 agent 做呢。若 agent 每週幫我們 bump 版本。若 agent 跑 mutation testing，然後讓測試好一點、或少一點 flaky。他們發現那樣好不少。產品的哲學就是每週找一件事，讓它好一點。

[45:41](https://www.youtube.com/watch?v=Rgwu9nF_Xok&t=2741s) 怎麼訓練人做 AI native development，又不會在下一個模型、下一個技術、下一個工具出來時過時。Steve 剛發過文。他說不是要自吹，其實是 Netflix 替大家解了。謝謝 Netflix。他剛貼的叫 Flat Curve Society，一篇 Medium。他談 Netflix 展示的一個計畫，有一個確切的公式讓人過這個坎，要五小時，但必須是他們的經理、在工作時間、有一個訓練者祝福。他們用我們的書當課程，雖然你什麼都能拿來訓練。他們必須在做真的工作。那是沉浸。不太像訓練，更像有人帶著做真的工作，整個cohort。若不多於十人，你可以去讀。基本上他們都會翻進一天四百萬 token 那一類，也就是整個工作日、單一個 agent、同步。那才是他們變成 AI 識字、可以開始跟你做真的對話的時刻。Dru 認為最重要的是讓人到達某種時刻。對很多人，不是真的需要被訓練 AI。他們需要興奮到自己去訓練自己。很多人只是害怕，或不覺得它有用，或被全部的 hype 推開。Netflix 那種課很大一部分是：給人一天，有團隊、有經理祝福，讓他們興奮到想用 agent。然後很多東西會免費跟著來。他們會去做 side project、試東西。他們現在可以不小心刪掉你的資料庫。有人說自己在 Google 做那些訓練，文化在街上。他覺得自己在給人一把鎚子，有些人用鎚子不該被用的方式。Steve 說讓他們識字，然後多 agent 的識字，是十步旅程裡的兩步。

[48:09](https://www.youtube.com/watch?v=Rgwu9nF_Xok&t=2889s) 就算工廠是訂製的，有沒有一直出現的共同零件，像裡面的庫存單位。有人說那不就是你們的整個產品。Dru 說 Tessl 認為有一些，也試著幫忙。他們在建的：你想要一種方式把 issue tracker 接到原始碼控制。他們有給 Linear 和 GitHub 的 Tessl app。非常基本。你把工作委託給 Linear app，它轉給 GitHub app，於是你可以踢動跑 workflow 的 CI job。你需要那個。一開始他們沒有。這出奇地常見。他向 Maria 喊一聲，Maria 建了他們第一個 orchestrator。有大約兩週，每張 PR、每則留言都來自 Maria。那裡有身份問題，也有不錯的 UX 問題。你怎麼把那個接上，是你永遠會想建的一件。另一件是某種讓 agent 跑的雲端環境。你可以在 GitHub Actions 裡做。若你把很多自動化跑過 GitHub Actions，它不是最便宜的，也不是最適合長時間 agentic 任務的。你得設 sidecar、更新 GitHub token，不是最好。需要像那樣的代管服務，得有人來建。有些人把它綁到更寬的編排平台。有 factory、有 warp、有 Oz，很多人在這裡幫忙，有些可以拿來用。Tessl 的很簡單：你用一個 skill 定義 workflow，他們就在一個有 GitHub 存取的雲端 sandbox 裡跑，你要跑多久都行。那些之外最大的，大概是一套 code review 工具。你想要做 agentic code review 的方式。你留的留言，加上 agent 的留言，那些有沒有被做進 code review，讓下次 agent 會抓到。你會想要做更專的檢查的方式。Tessl 有叫 verifiers 的東西，可以想成非常聚焦、由 LM 驅動的 lint 規則。它讓你做稍寬、稍模糊、但仍針對一個特定檔、一個非常聚焦的檢查。例如每個 JSX 元素必須有 aria 屬性。後續問的是 workflow 步驟之間的 plumbing。對他們來說，那些比它們受歡迎的時間更早開始擋路。它們很快就不受歡迎。所以他們移到一個世界：多數任務就是單一個 agent 跑到完成，然後 CI 裡有一批檢查提升品質。除此之外，你就是讓它用 GitHub CLI 互動。他們跑的主要編排在任務追蹤器本身。你建一個父任務，東西擋住東西，那實際上就是你的執行 DAG。到這一步，Tessl 建過大約六個不同的 orchestrator。每個人都從很多 plumbing 開始，以沒有 plumbing 結束，因為他們總是發現麻煩大於價值。

[51:51](https://www.youtube.com/watch?v=Rgwu9nF_Xok&t=3111s) 若要用本地模型，而不是 API 上的前沿供應商來建 software factory，有沒有獨特的挑戰。Steve 說這裡有一個很大的市場機會，讓人帶著代管的本地模型、一種像 Claude Code 的代管現成方案來。他的意思是一個 Claude Code 的直接替代，用便宜推論上的本地模型，或甚至理想地用上你周圍任何 GPU。人若找得到本地模型，會想下 Claude Code 這班車，尤其若我們能修那個智力套利的問題。因為那樣你用一個 Claude Max 帳號做所有規劃，開源模型做實作。他想我們離十二月還有七個月。大家那時該有東西。他無法想像明年還會為所有 token 付錢給 Anthropic。Dru 補兩件，會再存在一陣子。大家說開源模型還沒有它們的 Sonnet 4.5 時刻，就是 agent 真的變好的那個時刻。有人覺得也許 GLM 5.2 可能是。問題是那仍得被代管。GLM 5.2 他想超過一兆參數之類。Steve 說他看過你需要的機架，你需要像 20 台之類。所以可見的未來，若你要真的本地、什麼都不租、只從插座吸電，你會被限制在小得多的模型。蒸餾曲線把知識往下帶的時候，那會很難。但回到 Steve 說的，你可以對它丟更多 token。若說有什麼不同，你可以對 token 更貪，因為那只是電。也許你需要更多編排，一個任務要跑六、七、八次審查才前進。你基本上可以用那補回很多智力，所以你可能得多接一些線。Steve 說這就是工廠這麼重要的原因。低層模型永遠重要，因為便宜、能把事情做完，但牠們是低層，需要幫忙留在軌道上。工廠正好填那個空間。對他來說，更高層的模型來了，你會用牠們讓工廠留在軌道上，但你永遠會用你能用的最低層模型。

[54:38](https://www.youtube.com/watch?v=Rgwu9nF_Xok&t=3278s) Dru 說工廠的心態把你帶進流程最佳化和監看。他承認自己對真的工廠缺乏實體知識。你可以用最鈦、最鉑的螺絲做每一件，然後說這台機器我每兩個月換一次，為什麼要在上面花所有的錢。模型也一樣。也許你用 Fable 規劃，用 Opus 拆成里程碑，然後 DeepSeek 來實作。變得擅長這個，會變成軟體工程的核心能力。你看的不是一張 PR，而是一個生產 PR 的系統。我怎麼把那個做得有效。換模型的頻率呢，尤其 code review，也更一般地。Steve 說他在往那個方向推，因為他不太想告訴太太他有五個 Claude Max 帳號。牠們審查比生成好得多，所以你通常可以整級往下，仍得到相當好的審查。Dru 說，Amy 若他說錯請揭穿。若你開始為互動 session 挑一個特定模型，那有點是輸的遊戲，因為很難預料任務何時變複雜、錯誤何時被發現。走那條路的人，最後幾乎總是一直用他們負擔得起的最大、最快、或最好的模型。他覺得比較行得通的是工廠心態。若你能找到一個反覆的任務，畫一個盒子把它拉出來：這是我常做的 workflow，或這是給 CLI 加功能、或送一個前端變更的 playbook。一旦有了，它就很固定。你知道任務會怎麼走、多久會失敗。那才是優化對的模型的好目標。而且因為你把它裝進盒子、一直在跑，這值得。Code review 是好例子，它相當穩。你可以依複雜度、diff 大小設幾道門，然後一致到你可以為每種類型設一個模型。你造的任何自動化也一樣。至少對他，那是他更成功的地方。然後任何互動 session 用 Opus 或 Fable，至少是他的預設。

# From DevOps to AI: Patrick Debois Shares Strategies for Successful AI Integration and Culture Change

Guy Podjarny 訪問 Patrick Debois。原片約 29 分鐘，英文自動字幕。節目開場把 Tessl 聽成 Tesla，也把 Patrick Debois、Des Traynor、HashiCorp、DSPy、Jupyter 聽歪。這份筆記依英文原稿整理，專有名詞保持 English。

- 原片：[YouTube](https://www.youtube.com/watch?v=U6zY644PU_4)

## 一句話

AI native 和 DevOps、cloud native 是同一類轉變：工具會換，真正要動的是整合與文化。不一樣的是速度。Patrick 進公司會先問他們的 GenAI 在做什麼；若答案全是 model training，他就知道這會很難賣，因為新遊戲是把東西送進 production，不是把資料練到完美。

## 類比成立，採用的速度不一樣

[0:00](https://www.youtube.com/watch?v=U6zY644PU_4&t=0s) 他的測試就是那一句：都在講 model training，就會很難。開場是 AI Native Dev，由 Tessl 贊助。Guy 請他比較 AI native、DevOps 和 cloud native。Patrick 是 DevOps 運動的核心推手之一，辦了 DevOpsDays，過去一兩年泡在 GenAI 對軟體開發的影響裡。

[1:11](https://www.youtube.com/watch?v=U6zY644PU_4&t=71s) 他說有些人沒料到他會把 culture 放前面。工具和文化都在。職涯裡每次都有這種技術時刻：mobile、serverless、cloud native、Kubernetes。一開始不知道會走到哪，先試、先玩，最後改變工作方式。GenAI 不一樣的是衝擊速度：今天分享，明天就有人用，然後進 production。早期 cloud native 還在摸索，現在比較容易織進日常。Guy 提到 S3 也很快。Patrick 說 hype 傳得更快，但看過 hype，LLM 這類工具被民主化了。Cloud 早期得先花基礎設施；現在律師也能用 ChatGPT、OpenAI。他把它歸到事情被做成很容易取得、很 commoditized。

[3:24](https://www.youtube.com/watch?v=U6zY644PU_4&t=204s) Guy 說他不想站在 OpenAI 的位子服務全世界：規模這件事沒變，你還是得支撐一切。公司、新創、資金像火箭在推。Cloud native 一開始也沒人知道終點，迭代很多次才settle 在 Kubernetes。他覺得現在就是快速迭代：今天這間公司紅，明天換一間，直到有個底座。每次新版本也常只是 LLM 上面一層薄薄的 veneer。有用，但人人都能開始做，所以蓋東西的速度和過去不同。

## 這次要 shift right，把人拉向 production

[4:47](https://www.youtube.com/watch?v=U6zY644PU_4&t=287s) 文化面他早期就碰過。做 AI 的團隊、做資料的工程師不習慣 production。他開玩笑說他們原本在 data lake 裡做報表，突然變成主角。一群人不跟另一群人合作，和 Dev 與 Ops 當初一樣。要進 production、把價值送到終端客戶，就有摩擦。這次他不叫 shift left，叫 shift right：把他們拉近 production。

[5:45](https://www.youtube.com/watch?v=U6zY644PU_4&t=345s) Guy 補一個大銀行資安負責人的例子。那人花多年經營和開發團隊的關係，知道找誰。突然多出一整群新人，他不知道該跟誰談，對方也不知道他是誰、在擔心什麼。資料從哪來、能不能信。營運和任何碰到 production 的人一樣。

[6:20](https://www.youtube.com/watch?v=U6zY644PU_4&t=380s) 初期專案多半在 data science，因為離資料近、做得出功能，也是公司裡的 incubation，他們懂一點術語，卻常缺進 production 的能力。很多人覺得有一本 Jupyter notebook 就夠了，那不能拿去跑 production。他看過公司刻意把工程灌進 data science 團隊，或讓傳統工程師去交付 proof of concept，不要停在永遠的實驗模式。只講 model training 的公司，是被 data science 淹沒：資料必須完美、什麼都要拿到。他相信新遊戲是整合，就像 DevOps 整合兩個世界。他不必深懂所有演算法，但放得上用場。數學曾經超出他，這套把東西送進 production 的整合，他做很久了。

## AI 工程師若只是新的孤島，缺口要由 enablement 補

[8:00](https://www.youtube.com/watch?v=U6zY644PU_4&t=480s) Guy 說有些公司成立 DevOps team，諷刺的是那些團隊常常不是在拆 silo，而是那群寫 infrastructure as code 的人：用 Puppet、Chef，後來也許用 Terraform。他們比以前的 Ops 會寫 code，卻沒處理文化轉變。今天的 AI engineer 可能會用 LLM 做應用、把 model 拧到能用，甚至再往 data scientist 走，和 production 仍有缺口。

[8:45](https://www.youtube.com/watch?v=U6zY644PU_4&t=525s) Patrick 說新技術都會有孵化團隊，mobile 也一樣。要選擇：他們是不是永遠負責這件事。有的公司說得通，例如 chatbot 團隊，只做這個。若目標是所有工程師建東西時都能用這些 AI 技術做得更快、結果更好，就要把傳統工程師訓練起來。AI／data science 團隊變成導師，像 developer experience 那種 enablement：走進各團隊，幫他們起步。重點不是把每個人變成專家。DevOps 的人也不該要求所有人做完全部 DevOps，只要夠用：知道何時該問、哪些自己做得了。

[10:09](https://www.youtube.com/watch?v=U6zY644PU_4&t=609s) 再往下是共享基礎設施。他不要每個團隊用不同方式跑 LLM，也不要每種味道的 guardrail。人少時可以用 guild 交換；基礎設施則像 cloud，只是換成 AI：過濾用的 proxy、監控、集中收回饋。做成 AI services catalog，一條 paved road。要偏離可以，成本自己付。他看到 Cisco、Adobe 用同一套：一個團隊 enable 其他團隊，再把中央的部分吸進 platform。不只是基礎設施，還有其上的 enablement，以及放在中央那塊的 governance。不想每隊各自決定能用哪些 model。不是硬壓，至少要讓人知道，寫進 guideline。

[11:48](https://www.youtube.com/watch?v=U6zY644PU_4&t=708s) Guy 把順序說清楚：一開始是數位轉型之類的專門小組，公司其他部分照舊，不需要共享基礎設施。第二、第三個小組出現，才需要 platform、治理和一致。Cloud 到後來很明顯，人人需要一台 server。是不是一切都會 LLM powered，比較可以爭。愈展開，愈需要 enablement，也進入 shared responsibility：別人在跑這些 LLM，paved road 限制你偏離。企業今天就會選定一個 foundation model 當夥伴，你被框在那個 sandbox 裡。就算用的都是 SaaS 版的 LLM，還是要勾政策、談用量折扣，像處理 CDN 成本。常被忘掉的服務是：上線之後收集終端使用者的回饋來改好，還有 tracing、observability。這些不要每隊各做一套。管的是一整套服務，包成標準方案。

## 先讓工程師在自己的工作裡嘗到，再談怎麼測

[14:02](https://www.youtube.com/watch?v=U6zY644PU_4&t=842s) 軟體工程師（先把 data scientist 放旁邊）要的文化轉變，Patrick 最常碰到的是：LLM 非確定，所以不能信、所以不能用。多半是人不懂怎麼把它測得比較可靠。不是說已經完美，而是要學會對付不確定。一旦說明有辦法把範圍限住，人就會轉成工程實務；否則就是「看起來不錯，但我不知道該怎麼做」。

[15:25](https://www.youtube.com/watch?v=U6zY644PU_4&t=925s) 第二件公司常做的事：讓工程團隊對 AI 興奮的同時，也對幫他們做新工作的工具興奮。日常工作裡看到力量，就比較想搞懂。若 Copilot 讓他們更有產能，他們也比較想把類似 Copilot 的能力放進產品。看不到價值，就會抗拒把這套工具帶進產品。

[16:06](https://www.youtube.com/watch?v=U6zY644PU_4&t=966s) Guy 說不可預測很難評價。Intercom 創辦人 Des Traynor 在早先一集說過，你得接受自己不知道產品到底能不能用。他覺得這和持續交付是同一方向的再一步：從測得很透的年度大版本，自信「我們說在做的就是在做的」，走到一天很多次發布，靠 production 裡的 observability 知道產品能不能用。測試仍要加，不是盲目 ship。要接受測試可能過了、產品仍在 production 失敗，然後靠儀表發現、回滾、學習。Canary、gradual rollout、回滾，是同一套工具，只是 LLM 又放大一階。

[17:33](https://www.youtube.com/watch?v=U6zY644PU_4&t=1053s) Patrick 說 Ops 一直在處理混亂。理論上對客戶應該很好，看 log 就不是。先有 monitoring，再有 observability：它在 production 做了什麼。Cloud 架構不再為那台不能壞的機器設計，而是假設會失敗。這裡也一樣：LLM 可能給錯答案，你用什麼控制它。他說不會拿去決定某個聽起來像核准與否的高風險 yes/no，字幕那幾個字不清楚；那大概不是最好的用途。要搞清楚哪些使用情境裡，失敗是可以接受的。

[18:35](https://www.youtube.com/watch?v=U6zY644PU_4&t=1115s) 一個例子用 UX，不是純技術。大約一年前，LLM 產生文字不一定快。他們把這點變成優勢：使用者和客戶知道是 AI 在生成，就得更用心核對。畫面上有 sparkle 圖示代表 AI，等於提醒：不完美，不代表沒幫助，重新載入、重試、重新生成都可以。有時不必技術上完美，而是圍繞不完美來設計。Guy 說這是 cloud 沒有的優勢。客戶通常不在乎你在 cloud 還是自己的 data center，uptime 和效能的期待一樣。AI 在某些情境有容錯，使用者也願意改自己的用法。這張牌有幫助，但你還是得真的做得好。

[20:00](https://www.youtube.com/watch?v=U6zY644PU_4&t=1200s) Guy 轉述和 HashiCorp 的 Armon Dadgar 的對話：若要在 Ops 做 self-healing 這類事，最好的準備是你本來就很會做營運，系統已經有儀表、累積了 observability。這樣 LLM 工具才比較能做 self-healing。會的和不會的會拉得更開。而 evaluation 會變得極端。就算很會小步推出，新能力仍要先過一條門檻才敢 ship。有些 LLM 能力上，這件事很難。

## Eval 要有三個來源，而且產品負責人得寫得出來

[21:22](https://www.youtube.com/watch?v=U6zY644PU_4&t=1282s) Patrick 說 evaluation 有進展。一開始的 eval 是給自己訓練 LLM 的人，他們有錢、有時間做完美資料集。你的使用情境通常沒有現成的標準題庫。Domain expert 出題是一條。現在 LLM 能幫忙把問題寫好、把評測生出來，這是和專家一起做的合成方式。第三個來源是 production 裡出錯的例子，餵回測試集。所以那條回收路徑重要：你得注意到差異。不完美。Prompt 裡改一個逗號，結果就不同，所以要有測試集。不必測一百萬件，至少是最常見、改了會有感的那些。換 model，測試多半會變，prompt 得再調。

[22:42](https://www.youtube.com/watch?v=U6zY644PU_4&t=1362s) 另一邊有 DSPy 這類工具，依你在用的 model 重寫、重構 prompt。像重構 code，也像 prompt 的 transpiler：這個 model 大概想要這樣講。從全手動走到有協助。然後是和 code 一樣的 feedback loop：這次 eval 不好，就換更好的 prompt。那是你的 test battery。

[23:25](https://www.youtube.com/watch?v=U6zY644PU_4&t=1405s) 測試常被當成開發者的事。他們學到的是，領域問題要挪給 product owner。他們不在 code 裡寫，也不在 prompt 裡寫，需要一個系統讓他們做得動、看得到改動的影響、做得出驗證。這比工程師再往左，往需求上游。業務測試人員那邊早就有類似問題。Guy 說過去測試是二元的：過了就好，沒過只為了把它改到過，失敗資料沒留、也沒拿來迭代。測試流程應該更像營運：把失敗留下來學習。那一塊是 Dev 要跟 Ops 學的。再往左，產品要定義什麼叫好、什麼叫產品能用，而且要能被寫成規則。Patrick 用 BDD 的測試後來拿去盯 production monitoring 作比：eval 寫好之後，另有一小組一直當 health check 跑，因為 model 可能在你不知道的時候變了。不必跑完整套，至少跑比較有策略的那些。

[25:25](https://www.youtube.com/watch?v=U6zY644PU_4&t=1525s) Guy 的收束是：什麼叫對、什麼叫錯，重要性跳了一階，因為你得評估這些不可預測的系統。他丟出一個不太愉快的想法：落後者會不會反而有一點優勢。Patrick 用歷史看，每次新技術一開始，價值好像只在「讓它動」；成熟之後才是可重複、要為失敗做準備。問一個上線五個月的團隊怎麼測，常常聽到沉默，因為還在先讓它跑起來。這不是能在規模上做的事。TDD 要不要爭，現在仍然很早。使用者給的寬容大概是暫時的。最後會變成：要我用這個工具，它就該能用；不可預測是你的問題。一開始看起來很容易，做穩是一門正在形成的手藝。不可靠的零件軟體裡早就有過，方法論仍然難找。

[27:07](https://www.youtube.com/watch?v=U6zY644PU_4&t=1627s) 他看 DevOps 這個專業怎麼成熟：一開始大約兩成是 infrastructure as code，後來轉去圍繞失敗重新設計，假設系統會壞、也不確定為什麼。夢想是 agent 把工作都做完；現實是它們不會完美，這是技術本身的性質。你可以把 agent replay 到某個點再繼續，它有時會生出多個選項讓人挑。人開始想的已經不只是最初那一步。「AI engineer」這個詞也很不穩：是會用 AI 的軟體開發者、是在做應用的人，還是那個幫你寫 code 的 agent。詞會慢慢定下來。DevOps 也從未完全定死。Guy 說就繼續分享。他推薦去看 Patrick 的 LinkedIn 和其他社群，那些動手實驗——包含用 Cursor 實際是什麼感覺——這集沒時間展開。

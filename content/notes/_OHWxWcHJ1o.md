# Unlocking the Full Potential of AI Assistants for Developers with Peter Guagenti from Tabnine

Simon Maple 訪問 Tabnine 的 Peter Guagenti。原片約 44 分鐘，英文自動字幕。節目把 Tessl 聽成 Tesla，也把 NGINX、Gartner、ChatGPT、Cohere、Eran Yahav、Jira 聽歪。這份筆記依英文原稿整理，專有名詞保持 English。

- 原片：[YouTube](https://www.youtube.com/watch?v=_OHWxWcHJ1o)

## 一句話

模型愈強，不代表答案在模型裡。Peter 說真正的工作是 app、介面、prompt，以及餵進去的 context。資深開發者覺得建議不對，常常是在跟一個讀過書、但不認識你的 chatbot 說話。Tabnine 只要 IDE 裡打開的東西，未修改就接受的比率就上升 40%。他們要的是 100%。

## 類別是 2018 年開的，買家後來換成 CIO

[0:14](https://www.youtube.com/watch?v=_OHWxWcHJ1o&t=14s) 這集接在上一週把 AI 工具分類之後。主題是 code completion：有人張開雙臂，有人只是看著，有人很懷疑。怎麼把用法拉高，怎麼讓工具真的拿到它需要的東西，才能給出最好的建議。來賓是 Tabnine 的 president 兼 CMO Peter Guagenti。字幕把主持人聽成 Sam。

[0:57](https://www.youtube.com/watch?v=_OHWxWcHJ1o&t=57s) Tabnine 是 AI code assistant 這個類別的起始者。公司 2018 年開始，當時 LLM 剛出現。語言若高度結構化、可重複、文件齊，模型就很會。還有什麼比程式語言更符合？他們放出第一個內建的 LLM，以及第一個給 Java 的 AI code assistant，很多年獨立賣給開發者。高效能的人把它藏在 IDE 裡，快一點，拿掉日常裡乏味的部分。

[1:45](https://www.youtube.com/watch?v=_OHWxWcHJ1o&t=105s) LLM 愈來愈強。大約兩年半前 ChatGPT 出來，大家突然懂什麼是可能的。在那之前 AI 已經在，他們自己做了七、八年。每個 CEO 問每個 CIO 在做什麼。FOMO 往下壓，被穩定拿來用的是 AI code assistant。Peter 做企業軟體很久。前十五年做應用，後十五年在 NGINX（字幕聽成 enginex）這類公司把生意做起來、放大，以開源的工作為傲。最近在 Cockroach Labs，做 CockroachDB。Tabnine 的買家從自己刷卡的開發者，變成 CIO 和工程主管。他加入創辦人，做 go-to-market、產品策略，以及這個空間會怎麼演變。Simon 說過去幾年像雲霄飛車；他們在變紅之前就有一門已經在跑的生意，hype 來的時候要做的是接得住更大的需求。

[3:23](https://www.youtube.com/watch?v=_OHWxWcHJ1o&t=203s) 物種正在劇烈演化，三條同時走：模型愈來愈強，大家愈來愈會用，然後發現模型本身不是答案。是周圍的工作：app、UI、prompt engineering、餵的 context、以及你怎麼跟模型互動。他們在很陡的學習曲線上，從 LLM 擠出愈來愈多、交給使用者的價值愈來愈多。客戶在拉他們，這不常發生。他做過很好的公司和產品，很多時候你盯著一個痛、拼命把產品送出去。Gartner（字幕聽成 Gardner）估計，到去年底只有大約 10% 的企業軟體開發者在用這些工具；到 2027 年底會接近 80%。他這輩子沒看過軟體採用這麼快。

[4:32](https://www.youtube.com/watch?v=_OHWxWcHJ1o&t=272s) Simon 問，照 LLM 的成長，2027 為什麼不是 100%，那五分之一是誰。Peter 說今天還沒用，就該問自己為什麼。工具鏈夠多樣，可以符合公司標準。真正的問題是：大約三分之二的 CIO 擔心 GenAI 的資料隱私，不想把最有價值的資料和洞察送到第三方、在外面處理。大約三分之一擔心版權和授權侵害，以現在 AI 的著作權法還沒定，這擔心很公平。過去五年投資爆了之後，有私有模型、有像 Tabnine 這種私下部署的 AI code assistant、有各種跟模型和訓練內容的關係，甚至可以把 assistant 訓在你自己的 code 上，不必擔心第三方。他覺得多樣性夠了，工具也夠強。

## 從打字補完，到整個 SDLC 上的工程師

[6:06](https://www.youtube.com/watch?v=_OHWxWcHJ1o&t=366s) 十八個月前、或大約兩年前的 state of the art，是打字時的簡單 code completion。預測你在寫的函式、自動補 class，已經很了不起，讓人快很多。再過六到十二個月，是一個你跟它聊天的 assistant。現在的 state of the art 碰到 SDLC 的每一段，知道你的 codebase 和標準，互動更像團隊裡剛加入的工程師。三年後在哪，很難預測。

[6:49](https://www.youtube.com/watch?v=_OHWxWcHJ1o&t=409s) 他經歷過很多次轉變。這次對軟體開發的改變， radicale 得像從沒有版本控制、什麼都在本機、waterfall，走到今天的 CI、CD、agile、雲端和可組合的基礎設施。把 1998 年寫 web 應用的工程師丟到 2018 年，他看不懂眼前在發生什麼。AI 輔助的開發即將再來一次。

[7:32](https://www.youtube.com/watch?v=_OHWxWcHJ1o&t=452s) 2027 仍有兩成不在上面，原因很多。有的公司全面禁止 AI 工具。有的開發者喜歡，有的不喜歡。擁抱的人把生產力拉高，當成 assistant。也有人覺得它會拿走工作。Peter 說能力會愈來愈強，工作會變，但「AI 會拿走你的工作」被放大了。用得最好的人是被抬上去：不必再在雜草裡擋拆、執行單點，而能像架構師、像設計師那樣想這個應用怎麼構成、怎麼互動。自動化在幾乎每個職能都這樣。九十年代入行的人會在應用裡自己寫 memory management。聽這集的人還懂怎麼做的，大概不多。早期做 web，網路那層要花很多功夫，現在不想網路了。這次變化大概比那些例子再大一個數量級，但很像。你若是系統性思考的人，幾十或幾百個 microservice 要互相說話，你還是會那樣想。機器做的是他把 Outsourcing 說成由機器完成的那部分。你仍是在創造應用和解決方案，只是不一定在寫那些 code。Simon 轉述上週共同主持人的話：寫 code 仍只是工作的一小塊，沒有我們愛想的那麼多。開發者不是每天在 IDE 坐五、六個小時。

## 聊天機器人是讀過一本書的天才

[11:03](https://www.youtube.com/watch?v=_OHWxWcHJ1o&t=663s) 比較懷疑的人，尤其資深、很清楚自己要什麼實作的人，會說風格錯了、我會換一種更有效率的寫法。試一兩三次不是他們要的，就覺得這不是效率，是挫折。Peter 說有幾分真。若你對結構、對從既有 code 怎麼重用，有非常硬的期待，工具有時會令人煩。但聽眾該抓住的是，到了那一步，差別在工具本身。很多人的經驗根本不是在用 code assistant，而是把寫程式的問題丟進 chatbot。出來的是一個無知的天才：像一個讀過軟體開發的書的人，把讀到的鸚鵡學舌吐回來，context 不對。就算最陽春的 code assistant，也會把你問的話做 prompt engineering，讓回來的東西在你的情境裡有用。Tabnine 和其他真的走得前面的，還用大量 context。差別很大。

[12:52](https://www.youtube.com/watch?v=_OHWxWcHJ1o&t=772s) 他愛車，所以用車比喻。路上碰到不認識的人問該買什麼車，他可以給一百個學術上正確的答案：Consumer Reports、汽車雜誌、Top Gear。若你是他最好的朋友，剛生了第三個孩子，在乎安全和氣候，他會推薦 Volvo 的電動 SUV，因為他認識你。Code assistant 一樣。問某種語言怎麼寫一個函式，它若不認識你，給的是 O'Reilly 書裡的東西，扎實，但不一定相關。資深的人（字幕聽成 senior JS）就是在這裡挫折。把同一個 assistant 換成對 codebase 完全有意識：他們光在 IDE 裡就看 18 件不同的事，還沒透過 git 接到全域 codebase。這時再問，回來的是你們寫這個函式的方式、你們呼叫的那個 API。

[14:02](https://www.youtube.com/watch?v=_OHWxWcHJ1o&t=842s) 他們要的是 100% 接受率：你跟 assistant 互動，回來的就是你的意思。資料點是，今年稍早加上本機 codebase awareness，只讀 IDE 裡打得開的東西，未經修改就被接受的 code，接受率上升 40%。然後加上全域 codebase，現在加非 code 的資訊來源，再加公司裡寫下來的標準和實務。未修改，是指開發者接受 Tabnine 的建議、自己不改。

[15:00](https://www.youtube.com/watch?v=_OHWxWcHJ1o&t=900s) Simon 把風格拆成兩種。一種是個人偏好，tabs 和 spaces 吵了很多年。一種是請它用這個專案其餘地方在用的 SDK 和 API，用你們內部寫 code 的方式。他覺得第二種非常重要；第一種做這樣或那樣，是化妝，對上的是架構和結構。後者是不要每次換一種方式重造，要把這個應用、這個更大的環境架構好，把每個元件用好。他甚至問，個人風格以後還重不重要。若讀 code、產生測試、做 review 的是別的 agent 和 bot，我們想的是一個一個 feature，而不是一行一行，個人風格還有什麼價值。

## 下一階是約束，而且可能不再是人讀得懂的 code

[16:40](https://www.youtube.com/watch?v=_OHWxWcHJ1o&t=1000s) Peter 說最早一代生成式工具專注在生得更多、知道得更多、做得更多。現在要加價值，得讓它們做更特定的事，也就是開始約束。它們已經能做一大堆、愈來愈聰明、自動生更多 code。接下來要問的是品質對不對、符不符合標準、公司政策有沒有套上去。他認為物種的下一階就是約束。他們叫 coaching 或 expert guidance。企業客戶的 private preview 裡，可以用很具體的標準，而且是白話英文。一份有人寫好、放在 Confluence 的文件，就能拿來約束。IDE 裡，格式就是一例：我們遵循 Google 的 Java coding standards，code 就長那樣，大家讀得懂。更重要的是：這個 API 絕不能這樣呼叫，因為那是安全漏洞，所以就不做。Code review 也能抓。Code 被推上去、在 pull request 裡，它會說這違反標準，以及要符合的話改動長什麼樣。標準可以是安全、效能、可讀性。出去之前沒有評估和驗證，就有麻煩。最好的組織今天用人工做。AI 可以做得非常快。

[18:43](https://www.youtube.com/watch?v=_OHWxWcHJ1o&t=1123s) 可讀性他反過來想。AI 會生很多 code，甚至整個函式或整個應用。若讓它跑、又把它優化到符合你的標準，結果可能不是人讀得懂的。為了跑得快，結構上的決定會讓人看了吃力。若生成是一套 AI，驗證是另一套、另一組 prompt、另一種看法，AI 讀得懂。你不必懂它。但若要走到不那麼人可讀，你必須絕對信任 agent 遵循你的標準，而且標準大概要比今天團隊裡的人更高。

[19:47](https://www.youtube.com/watch?v=_OHWxWcHJ1o&t=1187s) Simon 用既有的演進作比：assembly 到 C compiler，再到 Java，編成 object code，我們把自己從指令和 bytecode 抽開。沒有人在看那些 load 和 store。要舒服地抽開、把信任放進去，是一道心理門檻。對 AI 也是，前提是 guardrail 對。另一件一直煩他的是專案變大之後，同一件事大家拉不同的套件。五種 JSON parser（字幕聽成 Jason paes），因為不知道別人做過，或知道但找不到。像 Tabnine 這種把整個專案的 context 建起來的工具，更會認出這件事在專案裡已經用類似方式做過，沿用，而不是每次重造輪子。那會讓 supply chain 變肥、做法和格式分歧。他把這看成把 code 清乾淨的價值。

[22:11](https://www.youtube.com/watch?v=_OHWxWcHJ1o&t=1331s) Peter 說這就是 global codebase awareness。Assistant 看得到整個 repo，就可以優化重用，用反覆呼叫函式把 code 的量壓到最小。人要通讀整個 codebase、找出重複實作，非常花時間，沒有人做，因為下一個應用和故障已經滿手。這正是他們要 offshore 到 silicon 的事：推給 AI agent。重構和重組今天就很會，只會更強。Simon 說「offshoring to silicon」會變成他的口頭禪。

[23:22](https://www.youtube.com/watch?v=_OHWxWcHJ1o&t=1402s) 這是他們 CTO Eran Yahav（字幕聽成 Iran yav）的說法。他做深度學習和開發者工具的自動化二十年。他有一條 automation 的基本定理：讓一個系統按你要的方式互動，所需的力氣，必須低於你自己做完那件事的力氣。外包一直是可以把東西挪到另一個團隊。幾年前 AI 還不到能直接委託的程度。現在可以，而且委託的程度愈來愈好。

## 它已經是整個 SDLC 的助手，關係要自己養

[24:04](https://www.youtube.com/watch?v=_OHWxWcHJ1o&t=1444s) Simon 想給聽眾能帶走的：怎麼提高 code completion 成功的機會，怎麼改變跟工具的互動。Peter 從 Tabnine 說，今天的能力遠超過 completion，已經是貫穿 SDLC 的 assistant。寫應用時生函式和元件，很成功。重構、找錯誤和缺陷也很強。我們大部分時間不在寫新 code，在維護。更新和升級那些乏味的改動，它們很會，該往那裡靠。也有很離散的 agent 任務。Tabnine 有 onboarding agent：第一次打開新專案，或很久以前碰過、忘了結構，它會帶你走。這專案做什麼、怎麼組、跟什麼互動、跟哪些系統說話、有哪些相依。就是每天在這專案上的資深工程師會帶你做的事。自動生測試、自動寫文件也強。

[26:17](https://www.youtube.com/watch?v=_OHWxWcHJ1o&t=1577s) 給聽眾的建議是，這些工具碰到你做的每一段。不必去搜尋某個函式該怎麼組、別人怎麼解。在 IDE 裡問 Tabnine，它給選項，還給下一步該問什麼的 prompt，你可以做探索。這是新的工作方式。你會很快發現它哪裡好、哪裡沒那麼好、你得怎麼跟它互動。廠商想懂開發者的意圖，把工具做成你不必想、照自己的方式工作。但跟丟進 Google、或問同事，行為仍有一點不同。從小的、漸進的開始，逐項試，再推邊界，看它在你身上哪裡真的好。就像旁邊坐著一個 pair programmer，關係要自己建，要知道它對你擅長什麼、怎麼嵌進你想工作的方式。若以為丟一份需求文件就吐出完美，期待過高了。

[28:02](https://www.youtube.com/watch?v=_OHWxWcHJ1o&t=1682s) 不同任務會不會換模型？今天他們不在每個 agent 底下換模型。Tabnine 是少數整體可以切換模型的。自有模型一個完全私有，另一個完全私有、而且只在寬鬆授權的 code 上訓練，沒有著作權侵害的安全風險。也接主要廠商：Cohere、Anthropic、OpenAI，都可以試。他們發現 LLM 大多就算還沒到商品，也到了 utility，表現在收斂。Agent 的差別是：它被訓練在一件離散任務上，prompt engineering 他們做完了，再用特定的 context。Context 真的要緊。LLM 會回答不夠，還得給你的問題適當的框：你怎麼工作、codebase 裡有什麼，以及要找的東西長什麼樣。Onboarding 表面是按一顆「帶我認識這個專案」，背後是跟 LLM 來回，餵專案裡的 context，後面有 vector database 放著關鍵特徵。他把它想成做 app：邏輯、資料、怎麼回應，都要建。以後要麼模型相似到不必為每個 agent 煩惱用哪個，要麼把模型做小、做專門，換效能，那時也許每件事用稍有不同的模型。這還在辯。所以他們做成可切換，實驗哪一種表現最好。

[30:14](https://www.youtube.com/watch?v=_OHWxWcHJ1o&t=1814s) 他們有離線模式。一批客戶是 air gap。大企業把隱私和安全放最前：銀行、藥廠、製造商，要控制資料去哪。也更進政府和國防。例如能源部的一個單位，做電網工程的那部分，絕不能放到公開網路上。那些使用者就喜歡這樣。Tabnine 有自包含的實例跑在他們的私有基礎設施上，自有模型，完全 air gap。最早的 code completion 模型是在裝置上，現在仍有 on-device 模型，筆電甚至不必再連到別的東西。他們跟 Intel、AMD 和其他人的進展合作。他覺得頗大的模型能在本地跑，會來得比想像早。其他運算也這樣：以為什麼都得在巨型機器上，現在手機的算力大於他們九十年代跑的超級電腦。裝置上、私有環境裡、需要雲的算力，客戶得決定哪個適合自己的使用情境。廠商要有那種彈性。

## 三條腿：模型、意圖、以及剛好的 context

[32:25](https://www.youtube.com/watch?v=_OHWxWcHJ1o&t=1945s) Prompt 太長、太短、太含糊，他給開發者的建議是什麼。他心情複雜。做產品的人該在使用者所在的地方接住他們。他們試著在 UX 裡理解和解釋意圖，再拿那個去跟模型和其他 agent 互動。目標是使用者不必想「我問壞了，換一種問法」。常用 ChatGPT 的人可能會把問句重組很多次，因為它在解釋和 context 上做得不多。對話留著可以餵一些資料，但不像為了目的打造的 code assistant。那些工具裡，你問的是特定類型的問題、開著特定應用和檔案、IDE 裡已經有錯誤，它就該懂你為什麼問、你真正要的是什麼。有種誤解是，做一個生成式應用只要有 LLM、呼叫 API、問兩三句。那樣做出來的應用相當平庸，也許不會成功。真正的工程是他們說的三腳凳。一是模型。二是夠好的 prompt、結構和使用者體驗，懂意圖，再把意圖塑成跟模型的互動。三是 context：prompt 旁邊還餵什麼，才讓回來的答案正確。正確不是學術上正確，是你的意思、你的意圖。

[34:42](https://www.youtube.com/watch?v=_OHWxWcHJ1o&t=2082s) 若互動裡得不到你要的，就給更多 context。用 Tabnine 這種工具時，把相關檔案打開，讓它看見。第三方工具不允許，就把額外 context 貼進去，再把問句展開、給更多細節。跟人合作一樣：你給的 context 愈多，我幫得愈成功。生成式 AI 他們看到同一件事。

[35:25](https://www.youtube.com/watch?v=_OHWxWcHJ1o&t=2125s) Simon 用簡報作比。一張片子若有三個重點，一個很重要、一個次要、一個是他編的故事，觀眾記住的是故事。只給一件，觀眾或 LLM 就會盯著那一件。太多和太少之間有沒有平衡。Peter 說 context 確實可以太多，它就不懂了，或被淹沒，不知道怎麼權衡。更大的 context window、餵進更多東西，他們沒有看到這和更好的結果相關。看到的是對的 context 才帶來更好的結果。個人很難自己做到這一點。這是他們賺錢的地方。IDE 裡他們碰到大約 18 個來源，不是每個 prompt、每個 agent 都全讀，只用對那個 agent 合適的。你要修壞掉的 code，當然讀錯誤。某一刻會接上 observability，看到應用在 production 實際發生什麼。修 code 的時候，他不會去讀一份文件再餵進去。必須維持在離散、有限的範圍。人開始一項任務時，你想把什麼放在手邊、什麼才適合這件事。他們現在大量的工程就是找出最適合拿來當 context 的東西。

## 不要從整張票開始，炒作兩邊都過頭

[37:16](https://www.youtube.com/watch?v=_OHWxWcHJ1o&t=2236s) 很容易掉進幻想：一行或一句短 prompt，就生出整個應用。該要大的、中的，還是小的？他們有免費產品，每月超過一百萬個開發者在用。他說 IDE 下載總數大概七、八百萬。這些是一直在用的人，什麼有用、什麼沒用，很會講。有一次有人要一個非常結構化的請求，輸出一個處理資料、做詮釋的 Python 應用。他看到時想，這可能嗎：一組結構化需求，吐出一個完整能跑、像 microservice 的小應用。出過岔，所以他們才聽到；後來是對方那邊的連線問題。修好之後它做到了。他嚇了一跳，到了這時候其實不該嚇。工具每天變聰明，他看到這種事時一半驚訝、一半覺得理所當然。但他認為不要從那裡開始。不要把整張 Jira 票貼進去，指望它吐出整個能跑的服務。有些離散的事今天絕對做得到。他們有一個叫 Jira to code 的原型：拿一張票，這次輸出一個完整能跑、帶著 UX 的 JS 應用。那些仍比較遠。今天從離散任務開始：我要這個函式、這個特定元件。然後推邊緣，看它還會做什麼。他自己被嚇過，你也可能。

[39:37](https://www.youtube.com/watch?v=_OHWxWcHJ1o&t=2377s) Simon 說大家講很多訓練和 fine-tuning，但很多是反方向：我們得更會用這些工具，才擠得出它們的價值。Peter 說會在中間相遇。做產品的人有責任讓它就照你要的方式運作。他入行時的辯論是，還需不需要 GUI，為什麼不照電腦想被說話的方式，用命令列跟它談。他一直覺得那很荒謬。這些是我們的機器，我們要它們照我們要的方式行為。那是我們的事。但行為會改，會有新的工作方式，對此開放。做開發者十年、十五年、二十年，過去二十年已經看過這麼激烈的轉變。他從 1994 年就在做 web 應用，感覺像另一輩子。AI 會是激烈的改變，但這個社群很會演進。對改變開放、願意適應，你會更強，也更懂做產品的人該回應哪些需求。

[41:06](https://www.youtube.com/watch?v=_OHWxWcHJ1o&t=2466s) 最後對一下炒作和實際能力。看你問誰。啦啦隊在做他們一直做的事，大概比這些東西今天真的做得到的更嗨。但會很快走到那裡，最後能不能說他們錯？他自己本質上是銷售和行銷的人，做過夠多工程，但一直是銷售和行銷。同行答應做不到的事、或把能力吹大，會讓他挫折，因為那損害可信度。在科技裡做這種產品，工作就是把產品內在的真實露出來。做到了，人會用、會買。有些日子 GenAI 的炒作列車過頭了。同時他們也在很短的時間裡把期待和現實對上。能維持多久不知道，但確實在發生。另一邊是懷疑者，說這些是垃圾、根本不能用。他也不認為那是對的。工具裡有能力。他剛讀到的一件事是，LLM 現在的智力實際上是小學生的程度。那很強，也很該拿來框住期待。有值得靠上去的非凡能力，也還有很多要長的空間，該承認。

[43:00](https://www.youtube.com/watch?v=_OHWxWcHJ1o&t=2580s) Simon 問，你會讓一個小學生把 code commit 進 codebase 嗎。聰明、模式比對、相關性，和那不是同一件事，但確實有可以放進去的部分。Peter 說這句話讓他想起 Stack Overflow 幾年前的開發者調查，問你什麼時候寫了第一行程式。表現最高的開發者是在小學開始的。所以今天這個小學生程度的 code assistant，二十年後會是一個不得了的工程師。

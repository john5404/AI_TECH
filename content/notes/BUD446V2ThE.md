## 一句話

2025 讓 agent 能跑很久，也讓那件事突然變便宜。開發者要先搞懂自己站在信任階梯的哪一級：IDE 裡看著改、terminal 裡丟到背景、還是把複雜工作拆給 sub-agent。Vibe coding 適合看得到結果的軟體，不適合效能和很底層的後端。能一個人跑得比資金充裕的對手快，是因為架構先把重複的事收好，再讓模型填功能。失敗率高，多半不是模型不夠，是這個行業還不會做 agentic 系統。

## 看得到畫面，和把 agent 丟到背景，是兩種信任

[1:10](https://www.youtube.com/watch?v=BUD446V2ThE&t=70s) 正片前有一段 podcast 預告，90% 的聽眾還沒訂閱。接著主持人問：用 agent 有沒有最好的方式。一邊是 terminal，一邊是比較傳統的 IDE。近來多得讓人意外的工具偏 terminal。是比較容易給 context，還是看使用者怎麼互動。

[2:16](https://www.youtube.com/watch?v=BUD446V2ThE&t=136s) 來賓說分野是互動。IDE 加上擴充，例如 Cursor，畫面看得到，等於你同意留在 loop 裡，一直檢查發生了什麼。UI 簡化並加速上手。它不取代你，只在旁邊幫你做具體的事：寫某個檔、寫某些 unit test。你不必記指令，有按鈕，有一個打字的框。Cursor 和 Windsurf 的好處是用很多 UI，讓你在日常裡更主動地用這些工具。Terminal 依定義沒有那些按鈕。複雜的事靠按鍵組合和指令。那是給更進階的人，準備再加速、不需要視覺化、願意待在 terminal 裡的人。熟悉 Vim、nano 或 Git 的人本來就不需要 UI，直接做很難的事，省時間。代價是比較不互動，容易搞丟發生了什麼。生成的資訊量有時大到難以導航，要另學一套技巧。

[4:37](https://www.youtube.com/watch?v=BUD446V2ThE&t=277s) 主持人說 Cursor 可以在檔案之間很快跳著看改動，terminal 沒有這個。但他自己就是覺得 terminal 更快、更有生產力，而且你拿到的是 terminal 的能力。來賓說另一個很大的好處是電池裝好了：agent 可以在背景跑。Claude Code、Codex、Gemini CLI 都能用非互動模式，給一個 prompt，它就變成背景行程，自己執行複雜請求。現在 Cursor 這類助手也在往這裡走。幾個月前 Cursor 還碰不到 terminal，錯誤訊息得複製貼上到文字框。現在它看得到你在 terminal 裡的資訊。Cursor 也推出了自己的 agent，可以非互動，也可以是 CLI。他們要兩邊的人：要互動的，和只想用 CLI 的。

[6:29](https://www.youtube.com/watch?v=BUD446V2ThE&t=389s) 從哪裡開始，取決於經驗，若是公司裡的技術角色，也取決於角色。已經有不寫 code 的方案，例如 Lovable，給你一個 vibe coding 平台，立刻做前後端，零知識，你只要在場驗證、核准 AI 生成的內容。愈靠近 code、需要的規模愈大，工具就愈進階，也可能要很多手動解決。軟體工程師若目標是大量開發、大量改 code，可以先從 Copilot 開始，看它能不能讓你寫得更好、更快。滿意了，再上 Cursor 這種 IDE，把複雜助手當同伴。自主的範圍在變大，你可以委派的不再只是一個函式，而是整個檔案。那也沒問題了，就到階梯頂端，在 terminal 裡直接用 Claude Code、Cursor 或 Gemini CLI。這時你知道它們的強項、知道能委派什麼、也熟悉核心能力，才能把更大的範圍放進完全自主的 pipeline。推理是：從完全不需要懂 code 的東西開始；已經懂了，就往更進階走。

[9:27](https://www.youtube.com/watch?v=BUD446V2ThE&t=567s) 主持人把這收成信任。學開車不會一上來就開 Ferrari。小步走，信任自己也信任工具，再上一級。自主性的成長就是信任的成長。熟悉 IDE，就從 IDE 裡的 GitHub Copilot 開始，想留在 IDE 就去 Cursor。愛 terminal，再從那裡探出去。

## Sub-agent 是再叫一個實例：拆工作，或平行搜

[10:21](https://www.youtube.com/watch?v=BUD446V2ThE&t=621s) Sub-agent 基本上是主 agent 拉起來、並由它控制的另一個實例。通常用在任務複雜到一個 agent 不夠，或有不同路徑要探索。兩種情況：問題要拆成小塊，或要搜尋、把空間探過再選一個。他把它比成主從架構。你在 terminal 裡對主 agent 說，做一個有前端和後端的服務。一個 sub-agent 做後端，一個做前端，各自獨立，再回到主 agent 報告。主 agent 判斷合不合總目標。不合就把回饋轉回去，它們繼續改。探索時，sub-agent 也可以是同一個 agent 的平行複本，從不同角度看問題。例如同一個問題，一個用某種查詢搜尋，一個搜 Wikipedia 的文章，一個搜本地資料庫。技術上他認為未來也許不需要 sub-agent，因為主 agent 會聰明到自己解決難題，不會弄丟 context，自己在複雜結構裡導航。另一個動機只是速度。Agent 非常慢。平行化是一種做法，sub-agent 就是其中一種。你得到十份實作，也許一兩份是好的、做了你要的事。換來的是延遲和吞吐量，對上閒置時間。

[13:52](https://www.youtube.com/watch?v=BUD446V2ThE&t=832s) 壞處是成本大致線性成長，agent 愈多花愈多。有時拉起來的那些根本收斂不到任何東西。啟動方式也不只一種。主 agent 可以自己拉。Claude Code 現在做得到。你可以在 prompt 裡明確說，用平行 agent 分析這份複雜文件，它就會自己開多個版本。但你也許想要專門的 sub-agent，不是通用搜尋，而是對準問題的一個切面。那就得額外設計指示，這本身是一門手藝，要花力氣。不做的話，主 agent 會自己做，品質可能不一樣，因为它可能漏掉結構裡重要的片段。

[15:52](https://www.youtube.com/watch?v=BUD446V2ThE&t=952s) 主持人問，人是不是不能繞過主 agent 去跟 sub-agent 說話。來賓說看系統怎麼設計。在 Claude Code 裡很難控。Sub-agent 通常在背景，你不能直接看它們在做什麼，只能看 log。打開那個 JSONL，字幕聽成 code JSONL，才看得到背景裡的指令。Terminal 裡不一定看得到每個 sub-agent 的思考和規劃。這可能是缺點，也可能是優點：你得更相信它會交出有意義的東西。進入 sub-agent 的世界，信任要再多一層。

## Base44 看得見的地方能做，底層仍然要看 code

[17:08](https://www.youtube.com/watch?v=BUD446V2ThE&t=1028s) 話鋒轉到不做 code 的人。無論是 Base44 這種平台，還是本地的 Claude Code、Cursor，你和 code 的關係都很緊。出問題時，監督發生在 code 上。Base44 看得到 code，但它被藏起來，設計上不會把 code 推到你臉上。人看不懂 code，系統失敗時怎麼跨過那一關。是不是只是多給指引、然後希望它做對。

[18:05](https://www.youtube.com/watch?v=BUD446V2ThE&t=1085s) 他說不只如此。在 Base44 裡做 app，和用 Claude Code 或 Cursor 做，是不同的互動，很多時候是不同的使用者，目前也常常是不同的軟體。Base44 使用者的迭代和實驗，大量靠視覺。App 在面前，錯了會在互動裡看到，或先看到丟出來的 bug，然後才看 code。平台能做的軟體集合仍然有限，會隨時間擴大，那是他們在做的事。但要誠實：有一類軟體，用 Cursor 做會比用 Base44 好。Base44 自己，前端是用 Base44 做的，後端不是，後端是用 Cursor 和 Claude Code。因為你得看 code、懂 code。他認為這會在接下來幾個月裡很兇地變，幾年內更是。愈來愈多現在要寫的軟體，可以只靠視覺或只靠 prompt、不看 code 來做。他們給使用者的工具也不一樣，大量是一直看得到應用，以及把正在發生的事解釋得更好。一個小功能很多人很愛：你在 Base44 裡下 prompt、它開始寫 code，多數使用者不想看 code，那讓他們害怕。於是另一個小 LLM 看著 coding agent，即時用白話解釋它在做什麼，例如現在把 UI 從淺色主題改成深色。他們在做一套讓人不必看 code 也能做軟體的工具。

[20:58](https://www.youtube.com/watch?v=BUD446V2ThE&t=1258s) 主持人回述：今天 Base44 最有幫助的，也許是驗證和決定比較產品導向、尤其視覺導向的情況，而不是你怎麼實作。另一種是創新也在視覺上，技術不是要做全世界最花的 progressive web app，內容和導覽很常見，LLM 本來就會，你可以很有效率地做，創新在內容和樣子。他說會隨時間擴大，但更取決於你在做哪種軟體。效能非常重要的東西，沒辦法 vibe 過去。例如 VPN。或非常倚賴後端的東西。主持人補了一句，前一家公司大概也不能 vibe code 出 Snyk，至少現在還不行。字幕把 Snyk 聽成 snake。另一類應用，只要資料庫、一組整合和 API 就做得到它該做的事，用 Base44 可以做得很好，而且可能比用 Cursor 寫更容易。差別在東西有多底層、後端有多複雜。他們在這方面也在變好。

## 一個人能快，是因為先把會重複的部分做成架構

[23:16](https://www.youtube.com/watch?v=BUD446V2ThE&t=1396s) 主持人要看幕後。一個人做出一個不小的平台，還把它做大。沒有 AI 幫忙開發，做不做得成 Base44。短答案是絕對不行，至少不是他做出來的那種結構。開始之前，他還不知道要做什麼，就知道進入了另一個時代。前一家公司他就在用 AI，產品裡有，寫 code 也有。他強烈覺得，做軟體的人數不再是重點。你有獨特的看法、獨特的產品，而且軟體設計得好。他說的不是 UI 設計。那就不再是把愈多人丟上去、那些人就寫愈多 code、寫得愈快。所以他從第一天決定一個人做。他會把 repository 架好，並且持續花 20% 的時間在怎麼再提高速度。很多是實驗 LLM 怎樣把 code 寫得更好，產品上做，自己的 repository 也做。他講過的技巧包括當時 JavaScript 比 TypeScript 更能讓前端寫得像光速，只因為那個設定。現在也許隨著某個模型在變，字幕聽成 cloud for。

[25:39](https://www.youtube.com/watch?v=BUD446V2ThE&t=1539s) 後端這邊，他做了一層很高的基礎設施，處理資料庫和使用者管理。就算想法整個轉向，80% 的 code 還在。那部分比較是他寫的，不是 AI，他要它完美、成形。有了那層，加一個新功能，例如新的資料表、和平台其他部分的互動，就變得非常容易。他的度量是：讓 LLM 端到端做一個新功能時，他自己要寫的 code 愈少愈好。所以 repository 裡放了很多這類東西，還有 rules。他一個人跑，速度仍要跟對手一樣，甚至更快。這個類別的對手資金非常充裕。很多方面 Base44 執行得極快，若不比很多同業更快的話。他把大部分功勞給 AI，說想謝謝它。主持人笑說像 NASCAR 的致謝。

[27:27](https://www.youtube.com/watch?v=BUD446V2ThE&t=1647s) 主持人聽到的是好架構的價值：預先想好未來會變什麼，寫出可以分隔的 code。這很像雇junior，或外包。架構對了，就可以給比較不能完全信任的人清楚指示，讓他們在裡面寫一塊，你再判斷做得好不好、再引導。他說正是如此。還有一件很多開發者沒注意到。做一個簡單的全端 web app，叫它做 to-do。它做出一些路由，接上前端。你在 Cursor 開一個新聊天，要做另一個功能，例如管理後台。它會看你的 code，把任務做完，這點它很強。它不強的是停下來說：這裡有共同概念，可以收成以後其他功能能用的基礎設施或套件；我在重複寫同一段，先停一下，重構，這樣就不必寫那麼多。它會照你說的把任務做完，但還缺「先停一下，我找到共同層，要重構」。那些是他仍然手動做的：看 AI 建了什麼，再自己去改。

[29:39](https://www.youtube.com/watch?v=BUD446V2ThE&t=1779s) 主持人說，AI 很多時候是最初的創造，而且有一種 reward seeking。它可能把房子燒掉，把其他功能弄壞，只為了讓你剛要的這個功能能動。另一面是可維護性、重複的 code，這些對品質軟體是壞習慣。問的是：Base44 做出來的應用，怎麼有壽命。兩條。第一，現在在 Base44 裡做 app，LLM 寫 code 之前就有大量基礎設施和設定。那會限制它，但不是限制它該做的事，而是 guardrail。守住就大致沒問題。他們自動做出整套 CRUD SDK，做得很好，上面有 rate limit，這些是 LLM 不太會在乎的。API 和整合維持很嚴的 schema。很多東西做進應用裡，免得 LLM 為了完成任務，把你的 app 暴露出去。第二，有些時候他們會自動回饋給 LLM，使用者知不知道都一樣，告訴它需要重構。整個 vibe coding 這個類別裡，最讓 LLM 混亂、也讓人感覺「我叫它做一件事，它做了相反的、或刪了一個功能」的情況，是 code 檔變得太長。一開始叫它做一個頁面、一個簡單的 to-do，像別的 React 一樣很簡單。然後一層層加：用 AI 寫任務描述、使用者管理、指派不同團隊和看板。不小心就會變成一個很大的檔。他們在背後跑重構測試，也許告訴 LLM：你過了門檻，先重構這個檔，再做使用者要的事。還有很多可以做。像是一個 code quality agent，在某些點推 LLM 一下：這裡一段、那裡一段，去做點重構。

## 長時間的遞迴突然變成月費，失敗則是還不會做

[33:21](https://www.youtube.com/watch?v=BUD446V2ThE&t=2001s) 下一段換了來賓。什麼東西讓我們敢在生成 code 時把 agent 打開。是 context、是人對流程的信任，還是 LLM 的能力。他不認為是信任。做這些系統的人天生不信任輸出，得花不少時間驗證它給的是真的、有效、能動，而不只是你要的東西的 mock 或模擬。系統傾向走最短的路把結果給你。工程師做的很多事，是用穩的結構和架構，去驗證做出來的東西在功能上是真的、是對的。

[34:07](https://www.youtube.com/watch?v=BUD446V2ThE&t=2047s) 什麼使 2025 成為 agentics 的一年，如果那甚至算一件事。去年的大突破之一是遞迴。他們一群人做出能在很長時間範圍上運作的系統。Agent 可以跑幾小時或幾天，最後完成被給的問題。缺點是貴。他做過一次 36 小時的測試，多半只是證明自己能讓 agent 跑 36 小時。成本貴到做不起。要有效跑，就算最小規模，一天大約 4,000 美元。拉到幾十個 agent 同時跑，一個 10 個 agent 的 swarm 同時跑，是每小時 7,500 美元。那個價錢請一個人做還比較便宜。就算產出很大，多數應用也不需要那種規模。今年四月，Anthropic 的 Claude Code 開始提供一種無限、吃到飽的 token 和能力。他們做的第一件事，是重新想像先前那些迭代，他們叫 spark protocol，它允許那種遞迴。突然可以拉出跑好幾小時的 swarm，而費用是固定的，常常從 20 美元起，一整個月。從每小時數千美元，變成一個月 20 美元。能力上來，可以做得戲劇性地更快、更多，成本指數下降。這種事通常不會一次同時發生。那基本上是五月。

[36:22](https://www.youtube.com/watch?v=BUD446V2ThE&t=2182s) 主持人說，變得付得起，加上平行化，也打開了回應的品質。接著問 Agentics Foundation。它不算很新。需要是什麼，要解什麼問題。他說這是工作的有機演變，然後講了一段他覺得會讓自己聽起來很瘋的前史。他很早就進了 ChatGPT，夠幸運當早期 beta，OpenAI 在 2022 叫它 VIP program。他大概比大家早三到四週拿到。上線前的 ChatGPT 第一版，他問的第一件事是：我要怎樣成為 AI 裡最有影響力的人。他自己說這聽起來很自我。它給了一套步驟。先問你擅長什麼、喜歡什麼、幾年後想在哪。值得做的事要多年準備。依問答給了一份大綱。它說你得建立社群媒體追蹤，焦點要窄。他問那是什麼意思。它問他喜歡做什麼。他喜歡做自主的東西，做了快 25 年的雲端基礎設施。它讓他先去開一個 subreddit。他當時對 Reddit 一無所知，但照做了。三年半後，那個 subreddit 有超過 10 萬訂閱。他還不確定要拿它做什麼，但它很紅。關鍵是一致。它叫他不斷公開貼自己在做的有趣的事，放上 GitHub，每週做直播跟人們互動。他照做。接著成千上萬的人來看直播、追蹤他，本質上是在買他的時間，他說像一種給 geek 的 OnlyFans，按小時買。最瘋的是它真的有效。他現在可以說有超過 100 個客戶、20 個 Fortune 500。他就是一個人、一家公司。妻子幫忙一些非技術的部分。一般來說是他和他的 bot。整份商業計畫和流程，就是 ChatGPT 第一版訂下來的。

[39:48](https://www.youtube.com/watch?v=BUD446V2ThE&t=2388s) 主持人問，是 LLM 叫他創基金會，還是他自己。他說基金會是那些早期對話的演變，它沒有明確說要創。社群圍繞 agentics 的概念，以及他們實作 agent 系統的實際做法聚起來之後，很清楚他們正處在一個新職業裡。看歷史上的職業，他先承認 AI 常常給人自大的錯覺。但這次是一群人發現，大家在用類似的方式做 AI 的工程。光譜一端是 vibe coder。他不是說 vibe coding 不重要。它是很好的發想、學習、發現，但很自由、很流動，沒有什麼計畫。他們做的不一樣：做出可重複的架構、流程和方法，結果是定義好的。那是工程活動。Agentics 和 agentic engineering 這兩個詞開始被大公司挪用，本質上是在 AI washing。他們說那是 agent，其實是 chatbot，或是一套 vibe coding。他們看到機會說：這是我們的做法。Agentic engineer 作為專業，技術上該包含什麼，以及幾乎像一個公會。他們是這個新領域的石匠。團體圍著這個形成。它是開放的，跟某些企業的「開放」團體相反。OpenAI 在光譜另一端，由企業利益主導。他們要讓這件事屬於人，在專業上賦權。也許更有抱負的是，圍繞 AI 的社會成形時，它長什麼樣，怎麼保護最終最受影響的人的利益。他們想當成對兆級美元公司的一種對沖，如果做得到。今年三月成立。接著大概 60 個城市，每週都有有機長出來的聚會。

[42:36](https://www.youtube.com/watch?v=BUD446V2ThE&t=2556s) 怎麼參加。溝通和社群大多在 Discord，網址他說是 discord.agentics.org，或 WhatsApp。WhatsApp 已經滿了，他不給網址，因為過了某個門檻就不能再加人。大多已經轉到 Discord。網站字幕聽成 Gentix.org。它是會員組織，他說是一種 meritocracy。想參加、想在另一個城市開分會、辦聚會，就是志願，他們讓它發生。

[43:13](https://www.youtube.com/watch?v=BUD446V2ThE&t=2593s) 今天 agentic 的天花板是什麼，什麼最讓 agentic 開發失敗，或給想用的開發者造成問題。他說限制因素，以及幾週前一份 MIT 報告。標題大致是 95% 的 agentic 專案失敗。標題相當聳動。挖進去有兩種看法。95% 的專案失敗，大概是真的。但失敗的原因，很可能是 99% 的工程師、程式設計師、開發者、專案經理，其實不知道怎麼做 agentic 系統。那是新空間的副產品。真正的限制是很難看穿他說的 AI washing、agentic washing，去判斷產品和做這些產品的人，能力到底是什麼。高失敗率說明我們在一個正在冒出來的空間。若你夠老、待過網路初期，會在 90 年代末企業做的很多網路專案上看到同一件事。當時有一種想法，網路對大多數商業應用還不夠。他們錯了。錯在產業還不懂怎麼做對使用者友善的網路應用。後來有了可跟隨的模型，Amazon、eBay 出現，大家才知道怎麼做一個容易互動的網路服務，而不是把舊軟體重做一遍。25 年、30 年後，AI 是同一個問題。人傾向用一直以來的方式做應用：以人為中心的模型、審查週期、拉得很長的 sprint，那些是為了慢慢、逐步建造而優化的。現在可以在一瞬間複製任何地方的任何東西。Code 的品質雖然重要，卻不如你在速度和上市時間上得到的動能。擁抱這件事的公司，不是只取代開發者，那也許是副產品，而是用開發者以前做不到的方式增強他們。給他們一種超能力，做得更有效、更快。那本身會製造一整串次級問題。最終這是讓開發者用更少做更多。

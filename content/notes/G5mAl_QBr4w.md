## 一句話

反覆出現的主題幾乎跟開發者無關，而是產品、設計，以及本來不該開 pull request、現在卻在開的人。非技術的人開的 PR，有人量到 74% 會被合併，其中 84% 沒有開發者碰過。產品經理若要變成像工程師那樣的 orchestrator，系統得先學會這個產品，也得知道自己知道的邊界在哪。

## 有票和設計，仍缺周圍的 context

[0:00](https://www.youtube.com/watch?v=G5mAl_QBr4w&t=0s) 六月倫敦一個反覆的主題幾乎跟開發者無關。是產品的人、設計師，以及本來不該開 pull request、現在卻在開的所有人。

[0:13](https://www.youtube.com/watch?v=G5mAl_QBr4w&t=13s) Tessl 的 Marc Sloan 用一個匯出按鈕說明：agent 有票、有設計，卻沒有周圍的 context 時，什麼會消失。他在一個給開發者的會上談非開發者：product managers、designers、executives，傳統上不碰 code 的人。情境是一個有網頁產品的公司。客戶請產品經理在儀表板上放一個匯出按鈕。匯出功能本來藏在設定選單後面，還有幾層，很難找。這個故事的後段摘錄沒留住。

## 非技術的 PR，多數會進去

[3:26](https://www.youtube.com/watch?v=G5mAl_QBr4w&t=206s) Autonomy AI 的創辦人兼 CEO Tammuz Dubnov，有跨幾百個組織的數字。旁白說：非技術的人開的 pull request，74% 會被合併，其中 84% 沒有開發者碰過就進去了。

[4:00](https://www.youtube.com/watch?v=G5mAl_QBr4w&t=240s) 他說第一件要追的，坦白講就是 pull request 的數量。中間有一句百分比聽壞了，不採用。後面他再說一次：對他們來說那是 84%。非技術的人生成、然後被合併的 PR，84% 就這樣合併。這是一種確保你沒有增加開發團隊負擔的方式，不只是 PR 疲勞，也包括任務本身。

[6:24](https://www.youtube.com/watch?v=G5mAl_QBr4w&t=384s) IDC 預測到 2028 年會多出超過五億個新應用。他說自己是那個問題的一部分，比過去四十年加起來還多。想一分鐘：四十年被壓進三年，就像這個房間。

## 產品經理也要變成編排的人

[7:50](https://www.youtube.com/watch?v=G5mAl_QBr4w&t=470s) 她認為產品經理需要變成 orchestrators，就像工程師已經變成的那樣。那需要一個學過你的產品、也知道自己所知邊界的系統。多數 PM 現在的位置，是試著做基本的 workflow，幫日常工作，例如把事情拆成票。她說 Rezonant 這些也做得很好，但順便一提。她覺得該去的地方，是軟體工程師已經變成的樣子：agent orchestrators。

[8:20](https://www.youtube.com/watch?v=G5mAl_QBr4w&t=500s) 所以要找出產品管理裡哪些切片可以真的端到端自主做完。為此你需要一個會學習、懂你的產品的系統。這裡多數人在用 ChatGPT 之類。然後他們開始編排一組 skills 來跑那些 workflow。她覺得再往下，是 agents 有品味、有連貫性，也懂自己的限制。

[8:54](https://www.youtube.com/watch?v=G5mAl_QBr4w&t=534s) 從產品角度看，軟體工程已經走過這段。Cursor 一開始很像逐行協助，後來不只那樣。然後他們在 Claude Code 上走得很深，現在還有 OpenCode。若你從權限的角度夠勇敢，可以讓那些 agents 端到端跑。但真正的自動化過程更難。你要最佳化的工作和訓練資料沒那麼一致。所以你得自動化從客戶、Slack 對話、郵件收集資訊的過程。你得想出人和 agent 的 control plane。你要怎麼保證 agents 和 PM 之間有對的制衡，讓他們能有效工作。

[9:48](https://www.youtube.com/watch?v=G5mAl_QBr4w&t=588s) 片尾約十一月紐約的 AI DevCon，網站是 ainativedev.io。

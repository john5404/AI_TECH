Guy Podjarny 訪問 Base44 創辦人 Maor Shlomo。原片約 55 分鐘，英文自動字幕。字幕把 Base44、vibe coding、Claude Code、Cursor、Tessl、Snyk、Supabase、ChatGPT 聽歪。這份筆記依英文原稿整理，專有名詞保持 English。

## 一句話

用 LLM 做複雜軟體，要把複雜度從 LLM 身上拿掉，像用母語發表演說。Base44 把使用者管理、資料庫、寄信、LLM、分析與 log 先做進產品，讓非技術的人用英文做出天天會用的應用。Maor 自己一個人能追上資金很多的對手，是因為架構讓 LLM 寫最少的 code。護城河不是 model，是速度、品牌，以及還做不到的 agentic 應用。

## 電池內建，stack 要順著模型已經會的寫法

[1:04](https://www.youtube.com/watch?v=TKrXyZr6UgM&t=64s) 這集談新創、用 AI 建造，以及 vibe coding。Maor 說 Base44 是 AI app builder，像現在很多的 text to app，但走很有意見的路：幫人做真正能跑的 full stack 應用。Vibe coding 一開始很擅長網站、介面和一些 MVP，主要是前端。Base44 是最早、或最早之一，提出 batteries included：在裡面做 web app，功能需要的東西已經在了。使用者管理、資料庫、寄信、呼叫 LLM、analytics、log。做出來的軟體，是他們自己、他們的使用者或客戶天天會用的。

[2:54](https://www.youtube.com/watch?v=TKrXyZr6UgM&t=174s) Guy 問這是選了一套有意見的 stack，還是因為部署和營運也一併處理。Maor 說兩者都有。Stack 的選擇會隨時間變得沒那麼重要。開發者社群愈信任 Base44 在做什麼，用哪套技術、怎麼部署就愈不重要。Vibe coding 在變好，還不完美，production 應用仍然難做。在 Base44 上稍容易，路還很長。有意見的做法是在修正你希望 vibe coding 長成的體驗。你不想開始把服務縫在一起：要接 LLM 就去 OpenAI 拿 API key 塞進平台，要接資料庫就看表、跑 migration。至少在他想像的未來，這些完全在幕後處理，你用英文寫出想做的東西，不必懂 API key 是什麼。要做到那樣，技術棧上得做很多有意見的決定。

[4:57](https://www.youtube.com/watch?v=TKrXyZr6UgM&t=297s) Guy 問，是挑 LLM 本來就寫得好的 stack，還是把事情整個移出 LLM 的決定範圍。Tessl 做軟體時，有一段時間模型不肯守你指定的相依，叫它用 A 和 B，它用 B 和 Z，還會發明。後來規定不准再選相依，import A、import B 先放好，其餘它填。模型變好之後，那條限制拿掉了。Maor 說晚進場的好處是很多東西是繞著 LLM 設計的。Base44 用 backend as a service，開發者會想到 Firebase 或 Supabase。那些產品是 LLM 時代之前的，有自己的 endpoint 和語法。他做最初幾個 app 時，看 LLM 想做什麼。有些地方你再限制：叫它別用那些套件，它還是用。Prompt 裡寫重要、加驚嘆號，也不見得有用。對他們真正有效的是順著它。看它困惑時想做什麼，幾乎用它正在用的語法把東西做出來。它一直用某個套件、你想用另一個、兩者又沒有實質差別，stack 也許就該用它選的那個。有些地方順著模型訓練過的東西，結果會更好。SDK、後端服務、套件、技術，多半繞著 LLM 真正寫得好的 code 來設計。

[7:53](https://www.youtube.com/watch?v=TKrXyZr6UgM&t=473s) 用 LLM 做複雜軟體，而這領域的人都知道模型在這裡會掙扎，就要盡量把複雜度從它身上拿走。很長、很複雜的演說，用母語講比較容易。他試著找出 LLM 做出能跑的軟體的最容易方式，再把技術、SDK、endpoint 設計成那樣。Guy 聽下來是兩層：一層 backend as a service 在 LLM 的決定之外；上面的 stack 則順著它已經會的、流行的知識。他們後端選 Python，因為那是模型最熟的語言。前端有爭議：模型寫 JavaScript 比寫 TypeScript 容易，TypeScript 會讓它混亂。所以很多前端仍只用 JavaScript。技術圈裡意見很硬。事情也會變。在你真的限制模型、規定只能用這些積木的地方，他們在 Tessl 看到模型變好、會適應。Base44 裡人們用來做 app 的技術也一樣：模型進步，他們就拿掉一些 guardrail，給它更多彈性。

## 給餐廳經理，也給覺得開 repo 太重的工程師

[10:28](https://www.youtube.com/watch?v=TKrXyZr6UgM&t=628s) 對象肯定是非技術的人。最早幾個使用者是餐廳經理、做行銷的人、他一些最好的朋友，離 code 很遠。讓他意外的是，時間拉長，有一大群開發者在用。他們也在為懂一些技術的半開發者做功能。他看到的未來是這件事不再要緊。做一個 landing page，在 LLM 之前，就算你是開發者，用 Wix 也比自己寫 HTML、PHP、自己 host、自己部署容易。沒有人想做那些。LLM 和 vibe coding 變大之前，他自己女朋友的網站就是用 Wix 做的。很大一部分軟體會變成這樣。就算你非常技術，vibe coding 仍是優勢，而且會明顯比開一個新的 GitHub repository、開始寫 code、部署、跑測試更容易。

[12:28](https://www.youtube.com/watch?v=TKrXyZr6UgM&t=748s) 開發者用 Claude Code 或 Cursor，和 code 的關係很緊。Agent 改 code，出問題時監督發生在 code 上。Base44 看得到 code，但它被藏著，不是設計來把 code 推到你臉上。互動不同，使用者常常不同，目前做的軟體也常常不同。在 Base44 裡迭代，很多是視覺的：應用就在面前，互動裡就知道錯了，或看到 bug 被丟出來，還不必看 code。這類平台能做的軟體仍有限，集合會愈來愈大，那是他們在做的事。但要誠實：有一組軟體，用 Cursor 做會更好。Base44 自己的前端是用 Base44 做的，後端不是，是用 Cursor 和 code。因為你得看 code、懂 code。他認為這會在接下來幾個月裡劇烈改變，幾年內更是。愈來愈多你現在在做的軟體，可以只靠視覺或 prompt、不看 code 就做出來。給使用者的工具不一樣。必須一直看得到應用，也必須把正在發生的事解釋得更好。有個小功能大家很愛：你在 Base44 下 prompt、它開始寫 code，多數使用者不想看 code，那讓他們害怕，也不懂。於是有另一個小 LLM 看著 coding agent，即時用話解釋它在做什麼，例如把 UI 從淺色主題改成深色。他們在做一套不必看 code 就能做軟體的工具。Guy 說進度提示和讓人留在過程裡，非常重要。

[16:29](https://www.youtube.com/watch?v=TKrXyZr6UgM&t=989s) Guy 複述：今天 Base44 最有幫助的，一是驗證和決定比較偏產品、偏視覺，而不是實作細節；二是創新常常就在視覺和內容上，技術是常見的導覽，模型本來就會，你可以做得很有效率。Maor 說還要加上你在做哪一種軟體。效能超級重要的東西，沒辦法 vibe coding 硬做過去。他舉 VPN。Guy 說自己前一家公司，至少目前還不能用 vibe coding 做出 Snyk（字幕聽成 sneak）。若一個應用用資料庫、一組整合和 API 就做得到它該做的事，Base44 可以做得很好，而且可能比用 Cursor 寫更輕鬆。這跟底層程度、後端複雜度有關。他們在變好。

## 一個人、兩成時間拿去加速，八成基礎設施Pivot 也留得下

[18:41](https://www.youtube.com/watch?v=TKrXyZr6UgM&t=1121s) Guy 想看幕後。一個人做出夠大的平台，還把它放大。沒有 AI 的開發協助，做得出 Base44 嗎？短答是絕對不行，至少不是他實際走的那種結構。開始之前他還不知道要做什麼，但知道時代不同。前一家公司裡，產品裡有 AI，寫 code 也用 AI。他強烈覺得，做軟體的人數不再是重點。更上位的是：你有獨特的看法、獨特的產品，而且軟體設計得好。他說的不是 UI。不再是丟愈多人、寫愈多 code、就愈快到達。他從第一天決定一個人做。把 repository 建好，然後把 20% 的時間持續花在怎麼再提高速度。很多是實驗 LLM 怎樣把 code 寫得更好，產品上如此，自己的 repository 也如此。JavaScript 對上 TypeScript 就是這種技巧。也許現在隨著 Claude 4（字幕聽成 cloud 4）在變，但當時因為那樣的設置，他做前端快得像光速。

[21:05](https://www.youtube.com/watch?v=TKrXyZr6UgM&t=1265s) 後端他做了很高層的基礎設施，處理資料庫和使用者管理。就算後來 pivot 到完全不同的點子，80% 的 code 也會留下。那幾塊稍微比較是他在寫、在確認它完美，而不是 AI。有了那些，加一個新功能、新的資料表、和平台其他部分的互動，就變得非常容易。他的度量是：讓 LLM 端到端做出一個新功能，他自己要寫的 code 愈少愈好。規則之類放進 repository，一個人跑，速度仍追得上競爭者，甚至更快。這個類別的對手資金非常多。很多方面 Base44 執行得極快，若不說更快的話。他把很多功勞、大部分功勞給 AI。Guy 開玩笑說他要謝謝第二座奧斯卡。

[22:52](https://www.youtube.com/watch?v=TKrXyZr6UgM&t=1372s) Guy 聽到的是好架構的價值：預見未來的變更，寫出可以分隔的 code。像雇用 junior，或外包給比較不能完全信任的人：指示要清楚，才能判斷他們做沒做好、才能引導。Maor 同意。他注意到用 AI 寫 code 時，開發者常常沒看見的一件事。做一個簡單的 full stack web app，例如 to-do。AI 做出一些 route、接上前端。你開一個新 chat，要再做管理後台。它會看你的 code、把任務做完，這件事它很會。它不會停下來說：這裡有共同概念，可以收成以後其他功能用得上的基礎設施或套件；我在反覆寫同樣的 code，先重構，再做你給的任務。開發者還沒注意到：它會照你說的把任務做出來，但還缺少「停一下，這裡有共同層，要重構」。那些他仍手動做：看 AI 做出來的東西，再去改。

## 檔案太長就先重構；測試先是進瀏覽器的 prompt

[25:06](https://www.youtube.com/watch?v=TKrXyZr6UgM&t=1506s) Guy 說 AI 在最初的創造上會追獎勵，可能為了做成你剛要的功能，把房子燒掉、弄壞其他功能。另一面是可維護性和重複的 code。Maor 在自己的 codebase 上自己處理了。那 Base44 做出來的應用要怎麼活得久？兩條。一，現在在 Base44 裡做 app，LLM 寫 code 之前就有很多基礎設施和設置。那會限制它，但不是限制它需要做的事，是它該守住的 guardrail。他們自動做出整套 CRUD SDK，上面有 rate limit，那些是 LLM 不太會在乎的。API 和整合維持很嚴的 schema。很多東西做進應用裡，免得 LLM 變成「我什麼都做，但把你的 app 暴露出去也沒關係」那種追獎勵。二，有些時候他們會自動回饋給 LLM，使用者知不知道都一樣：你該重構。整個 vibe coding 類別裡最讓模型和人困惑、也讓人覺得「我叫它做一件事，它做了相反的、或刪了一個功能」的，是 code 檔變得太長。一開始叫它做 to-do 頁，它做出很簡單的 React。然後一層層加：用 AI 寫任務描述、使用者管理、指派不同團隊和看板。不小心就會有一個非常大的檔。他們在幕後跑重構測試，告訴 LLM：你過了門檻，先重構這個檔，再做使用者要的事。還有很多可以做。這有點像一個 code quality agent，發現過了第一道門檻，這裡一段 code、那裡一段，就推它去重構。

[28:48](https://www.youtube.com/watch?v=TKrXyZr6UgM&t=1728s) Guy 說 Tessl 一直在講 spec，也有愈來愈多人覺得要把 code 外面的知識或它的摘要抓住，拿測試當 guardrail。有人甚至從測試開始。Maor 說軟體在變，多年來的一些典範不再相關，有些變得更相關。Test-driven development 看起來會很不一樣。Base44 的頭幾個月沒有 unit test。測試很不一樣：一個 agent 進瀏覽器，打開 Base44 的本機版本，試不同功能。他寫測試的方式是 prompt。例如使用者第一次登入、而且是第一個使用者，確定這個 popup 在。進首頁、寫一個 prompt、跑它，不到 3 分鐘應該看到這些。早期為了速度高、軟體仍有品質，很多是端到端測試，甚至不是用 code 寫的，是高層次地叫 agent 進瀏覽器測。原因有現實的一面：他一天裡把 code 改那麼多，維持一組 unit test 更常是頭痛，因為得不斷重構。一天結束時你要確定的是 code 能跑，不能跑時能很快走到哪裡不行。Unit test 的部分理由是：這個 unit 失敗，你就知道 code 裡哪裡有問題。否則就寫很多端到端流程，那些過了，軟體就在做它該做的。頭幾個月重構那麼兇，他找到的端到端方式，擴展起來幾乎像有一隊手動 QA。若要放大、要在團隊裡工作，unit test 重要，它們解釋軟體該發生什麼，尤其後端變得又大又複雜的時候。這套端到端是 AI 驅動的、在瀏覽器裡：找到按鈕、按下去，而不是告訴它 DOM id。UI 改很多時，重點更在邏輯。現在跑瀏覽器的 AI agent 對邏輯還不錯。他記得以前的 UI 測試像 jQuery 選擇器去找按鈕，改一點東西整份測試就壞，20%、30%、40% 的時間拿去在改完 UI 之後重構測試。他還在消化：AI 寫愈來愈多 code 時，事情該怎麼改，他們未必做得很好。另一部分是，你告訴 AI bug 是什麼，它會搜、會試著懂，你很快走到發生的地方。所以他沒有在 unit test 上投很多時間。他不確定這是對的。其他事情他意見更強。測試在這個新世界長什麼樣，他覺得還沒被改對。

[34:22](https://www.youtube.com/watch?v=TKrXyZr6UgM&t=2062s) 文件和 spec 是個有趣的角度。他看到很多 Base44 使用者先去跟 ChatGPT 聊，做出某種 PRD 或 spec，再上傳到 Base44。因為 Base44 更傾向行動。就算你說先聊聊想做的 app，它也可能直接做。他想也許在建立 app 之前加一個階段：先聊、先做 spec，然後隨著你改應用，LLM 一直看著、驗證 spec 仍在現實裡發生。最多人要、他還沒想清楚怎麼做的功能，就是一份「這個 app 該做什麼」的 spec。你叫它變漂亮、改按鈕、加功能時，它要不斷回到 spec，確認沒有覆蓋或改掉別的。這是現在 vibe coding 最大的痛：你叫它做一件事，它也許沒完全懂，做了，但弄壞另一件；或沒有正好做成你要的。測試和 spec，他覺得兩邊都還在地平線上：Base44 自己這個 app，以及在它上面做出來的 app。

## 小團隊、寬 context，六個月內也許能用 Base44 做出 Base44

[36:35](https://www.youtube.com/watch?v=TKrXyZr6UgM&t=2195s) 一個人可以轉彎，因為不必說服別人對齊。被收購之後呢。他預期團隊會多大，三個人還是三十個？這套方法在必須協作的團隊裡還站不站得住？他的論點是，現在做很棒的軟體，需要小得多的團隊。不只是人少比較容易。人少時 context 更多。他寧願有人認識整個 repository，一次改很多地方。他現在把團隊維持很瘦：大約每一兩百萬美元 ARR 一名成員，他還說到三這個數字，字幕這裡不穩。這些人的 context 要盡量寬。他不要「我做了後端這塊，交給另一個人做介面，再交回去做別的，出現資訊問題，於是需要第三個人」。任務盡量隔離，每個人幾乎像獨立工作者。產品切成大塊交給一個人，這個人大部分時間自己做。他想看到很少為了對齊而開的會。現在雇一個 10 倍工程師，其實有千倍工程師，因為他們可以丟出任意多的 AI coding agent。不再是任務很大所以要放四五個人。不再是每個人寫多少 code。Guy 說至少還需要配對：有人休假或離開，只有一個人會讓他不舒服。Maor 同意，也很難找到後端很強、又懂一些設計和前端的人。能多小就多小，做法是分而治之。Guy 說這其實不新，像 Amazon 的兩個披薩團隊。他們在 Tessl 的做法是軟體邊界、資料模型邊界，最後甚至希望時程獨立，你什麼時候能 ship 就 ship。那些線永遠不會完美，但是值得投資的方向。

[41:10](https://www.youtube.com/watch?v=TKrXyZr6UgM&t=2470s) 一年、三年、五年後，開發者還是什麼、什麼會消失。他用今天能用 Base44 和同類工具做出來的軟體比例來量。Cursor 和 Claude Code 顯然瞄準開發者和半開發者。Base44 這類瞄準日常的建築師、律師、醫師。Guy 說這是在擴大開發者的定義，把 coding as literacy 推到別的地方。Maor 更正：不是 coding as literacy，是 software creation as literacy，讓每個人都做得到。能被做出來的軟體比例會大幅上升。他押很多注意力的兩個地方，企業是其中一個。時間線上，寫 code 先是做出很棒的網站，landing page、一些互動，前端很強。然後 Base44 瞄準能用的應用：專案管理、CRM、發票。現在愈來愈多組織用它做內部工具、後台、以前要花很多錢買的客製軟體。這個類別有兩條必須變好的向量。一是企業級應用，真的改變組織被建造的方式。每個大組織都有大量軟體需求。他認為面向客戶的只是一小部分。內部的很多。想像 Pepsi 這種組織，內部要多少軟體才跑得起這門生意。工具和自動化愈多，生意愈有效率。

[43:50](https://www.youtube.com/watch?v=TKrXyZr6UgM&t=2630s) Guy 同意機會很大：多少苦工和無效率，若能輕易做出軟體就會消失。但有一個論點說，你不會去做應用，你會把那些任務交給 agent，不會留下我們今天理解的、活著的應用，而是外包給 AI。Maor 說他最近告訴團隊：vibe coding 很棒，顯然讓他致富，但它目前擅長的是做出 2023 年、ChatGPT 出現之前軟體看起來的樣子。Agentic 應用仍然很難做。軟體裡很多價值、最新那些突破性的軟體，Base44 就是好例子，會變成 AI 的軟體。他覺得不會只是聊天加上接工具，那裡有東西要修正。Coding agent 的介面上看得到：有互動，但是另一種軟體。Base44 接下來會大量投入、近期會看到很多更新的第二件事，是幫每個人做 agentic 軟體。那可以是像 Base44 這樣的軟體。也可以是你剛 vibe coding 出來的 CRM 裡嵌一個 agent，能研究 leads、會前送更新、補資料。也可以是你為自己的 SaaS 公司做的內部客服工單，有一個會自動回覆、用人的回應訓練的 agent，而這整個應用你用 vibe coding 做出來。企業級的要求兩邊都要，不管是好看的 web app，還是真正的 agentic web app。把 vibe coding 帶到能做出很好的 agentic 應用的地方。

[46:23](https://www.youtube.com/watch?v=TKrXyZr6UgM&t=2783s) 這些都做了之後，多久能用 Base44 做出 Base44？這也取決於 agentic 應用這件事能破解多少。他猜一個完整能跑的 Base44，有付款、有點數、裡面還有會寫網站的 coding agent，大約六個月，也許更短。他看六個月前 vibe coding 和 Base44 的狀態，當時很糟。所以六個月，也許更少，他會說絕對不超過一年。Guy 說這很大膽，但他跟得上。不是任何人都能做出一個 Base44，需要某些技能，但也許可以用這些工具帶著那些技能去做。

[47:50](https://www.youtube.com/watch?v=TKrXyZr6UgM&t=2870s) 若預測成真，Base44 這種平台的長期差異是什麼。一兩天前他發文，覺得荒唐：改一行 code、改一個字串，就把大約 40 萬美元的工作量從一個 LLM 廠商挪到另一個。護城河在哪。那些公司長得很好，但若一切變成商品、model 某一天也變成商品，會走向哪。他覺得 model 這一層比較麻煩，但他不會真的叫它麻煩，只是太容易換，沒有真正的 moat。頂尖的幾家卻在印鈔票。現在很難進那個群體，也難在群體裡移動。這會是很有趣的市場，不像雲端廠商。進雲端也很難，但把整套從 Microsoft Azure 換到 AWS 也很難。Model 之間不會這樣。新 model 稍好一點，他花五分鐘改一下，每個月幾十萬美元、以後大概更多，就從一個廠商換到另一個。

[49:38](https://www.youtube.com/watch?v=TKrXyZr6UgM&t=2978s) 護城河有很多處。一是領先。這些日子領先競爭者四個月就非常重要。他知道有些對手會做出內建後端、batteries included，因為看到那對 Base44 使用者的效果。到那時 Base44 會更前面。速度是他認為的第一護城河。還有品牌、通路、社群。Base44 幸運，有他見過最強的社群，使用者非常好，會互相幫忙。難複製的獨特產品判斷仍然重要得離譜。對他來說，非技術的人做功能型應用有個問題，他能想像體驗該長怎樣：打一些字，不必懂資料庫是什麼，一切都建好。再把那個翻譯成技術上怎麼實作，而且要能擴。現在人們一天做出成千上萬個 app。你怎麼擴、怎麼撐住這整件事和後端。那裡仍有一些技術上的護城河。速度就是做好決定、然後很快執行。架構上的好決定，速度就會跟著來。Guy 說場地並不平等，尤其現在，字幕把那句聽成 within weeks。但也許比以往更平等，Maor 自己就示範了。

[52:05](https://www.youtube.com/watch?v=TKrXyZr6UgM&t=3125s) 給正在面對這場變化的開發者，最上面的建議是什麼。他認為未來屬於能在領域之間跳的人。至少懂一點別的領域，才能用 AI agent 把事情端到端做出來。這會比現在在某一件事上非常深的人更成功。很懂 React 裡裡外外的優秀前端，不會像能端到端執行的人那麼有價值。那些人跟 AI agent 一起，懂一些前端、後端懂得好、懂一些設計和 UI，能拿一個功能或自己做一個產品，從頭帶到尾。他給一些朋友的建議是退一步，去端到端做一件東西。那會教你還沒碰過的地方：產品、設計、使用者、社群，視你是哪一種開發者。未來屬於對多個領域有一些理解的人，因為 AI agent 會專門化。對語法更深的理解不再是優勢。LLM 會比我們更懂最新、最好的套件、怎麼用、語法是什麼。Guy 說這就是把自己往上抬：要麼走更懂產品的產品經理那條，要麼走更懂系統架構的架構師那條。兩條都得把視野放寬。他恭喜這段旅程，他理解這只是開始。

## 一句話

工具帶來生產力，也拿走很多人當初愛上這行的那一塊：自己把問題解決、戴耳機寫到像在彈鋼琴。Annie 把這比成她很不情願轉去做主管。那次是選擇，這次可能不是。她的建議不是抵抗，而是承認身份會擺，去練溝通、規格、驗證，以及非決定性系統怎麼管。面試還在考反轉 linked list，進公司之後九成時間是在接別人的 library。AI 把那層做掉之後，還沒被練過的是需求、架構，和怎麼測試一個自己決定下一步的 agent。信任的方向跟人相反：人是慢慢建立，AI 是一開始很高，然後因為太有把握地說錯話而垮掉。

## 流暢感被 boilerplate 換走了

[0:47](https://www.youtube.com/watch?v=GI2ywMl2gQk&t=47s) 她愛當 coder、愛解問題很久了。新技術感覺像魔法，不能不問軟體工程師的日常會變成什麼。這也是碩士題目。她在挖自己為什麼問：是想幫人設計更好的 AI 工具，還是深怕失去當初吸引她和很多人進來的東西。她在寫怎麼學這些工具。寫 code 時 Windsurf 是她現在的首選，另外還有 ChatGPT。她覺得 Windsurf 強得離譜。生產力有，角色在變，核心是我們也在失去什麼。很多工程師把身份綁在工作上，以自己寫的 code 和解法為傲。看你在職涯哪一段。成形的那些年，學怎麼寫、怎麼結構、怎麼找 bug、怎麼修，是靠練習磨的。交給 AI，那些就練不到，也可能不再做你最享受的事。

[5:00](https://www.youtube.com/watch?v=GI2ywMl2gQk&t=300s) 她回想當 IC 的年，還有業餘時間寫 code。進 zone，有人叫 flow state。你知道要做什麼，腦子裡已經有一條路。她總是大耳機、好聽的音樂，把世界隔掉。寫 code 的那個模式像在彈鋼琴。世界消失，只剩她和電腦，魔法來自己的技術，還有她很小就自學的打字速度。這些幾乎不再要緊。沒有人禁止你繼續這樣做。工作上若 AI 能快得多地生出至少所有 boilerplate，你為什麼不？雇主為什麼要說慢慢打就好。

潘朵拉的盒子開了，精靈出了瓶子。工具會留，很神奇，也換掉很多人相當享受的那一塊。

[6:16](https://www.youtube.com/watch?v=GI2ywMl2gQk&t=376s) 她問這到底是什麼意思。放下跟自己綁在一起的東西，但有些人職涯裡已經歷過類似的改變。她中途很不情願地去做主管，因為她真的喜歡寫 code，不想離開。能不能比成 Charity Majors 講的 engineer-manager pendulum。也許可以在兩邊擺，不必選一個。對很多人，平衡才對。文章因此很長，也被轉很多。

## 去做主管是選擇，用 AI 可能不是

[8:47](https://www.youtube.com/watch?v=GI2ywMl2gQk&t=527s) 用 prompt 開發還有沒有創造。她說還有，但在觀看者眼裡，看你個人從做解法裡享受什麼。她是解謎的人。正面是結果快很多。家裡的專案，以及碩士在收的資料，時間要緊，愈早上線愈好，洞察來得愈早。轉管理不一樣。她把職涯想成四十年，五、六年並不長，已經有人說你軟技能很好，考慮做主管。她說不是，我當工程師不是為了這個。她要自己跟電腦一對一，自己解，看到東西做出來，再發現有更好的做法，那種完成感。太早不想放。各種主管施壓，她擋到大約第十年。那時她發現自己對怎麼把 code 寫得更好，沒有再學到多少。寫 code 不再那麼難。她開始自學更深的，例如怎麼 debug memory leak。最後屈服去試管理，因為那裡一定有可學的技能。轉換很硬。很多公司沒意識到，把一個還不錯的工程師放去管人，不會總是平滑。

她面試別的主管、若是第一次做管理，一定問為什麼，並要對方懂：優先順序不同，時間花在不同的事。職缺寫還能花 50% 時間寫 code，不太可能發生。管人或管專案是 wetware，另一套球局。溝通、同理、人與人的關係、優點缺點、怎麼配對讓人學、讓人做出最好的工作。每天練的是另一套。

[12:11](https://www.youtube.com/watch?v=GI2ywMl2gQk&t=731s) 文章裡她說身份在建造，不在管理。工程師轉主管，常常至少有幾分是自己的決定，人會想完成那個決定。AI 工具則會被強加。她看到公司說我們絕對要你用，不用就要說明為什麼不用這些生產力工具。從轉管理能學到什麼，好度過這次身份危機。她當天早些也在想：管理理論上是選擇，這裡也許沒有選擇。要緊的是別抵抗。遲早工作會期待你用這些工具，而且用得很好，因為它們是新工具箱。擁抱是因為你在建一套新技能。她待在同一個角色太久，新技能不多，橫向去做管理時覺得自己回到新手：one-on-one、招聘和面試流程、performance review。這些大學沒教，程式是教過的。做那些工作、很在意，學到的技能就算回到 IC 也有用。能用主管的鏡頭看：主管為什麼要我做這件我覺得沒道理的事。待過那個位子就比較懂。所以把它看成機會。跟這些工具變好，溝通是根本技能之一。新工作會冒出來。AI engineer 這個詞已經在飄。還要有人做 prompt library、規格、怎麼把 spec 寫好、怎麼驗證 AI 輸出的 code 對、決定對。我們在跟非決定性工作，很多人會不舒服。coding assistant 要管，若在建 agentic 系統也要管。新的專精區域。門沒有關，只是在移。

[16:12](https://www.youtube.com/watch?v=GI2ywMl2gQk&t=972s) Simon 說剛進這行的人會把這些技能當成本來的路，學得很快。在行裡很多年的人會有點劣勢。但他們有巨大優勢：從底層懂軟體怎麼被做出來。錄音前她提過 production 出問題，要懂為什麼，從爛 code、爛設計、爛架構學教訓。那是機械同情，知道蓋子底下怎麼動，再加上學新的 AI。以後幾年這組合會相當少見。她拿歷史比。工業革命她沒經歷，歷史會重複。Compiler 出現時，職涯走到一半的那一代得信任一個東西輸出他們以前用手寫、而且 íntimately 懂的 code。一定有人批評 compiler 不可能寫出跟我一樣好的 assembler，我沒寫怎麼 debug。可以回頭看他們怎麼過那個位移，誰佔便宜、誰吃虧，以及怎麼幫覺得更難的人。

[18:26](https://www.youtube.com/watch?v=GI2ywMl2gQk&t=1106s) 她看到世界經濟論壇一份看向 2030 年技能和就業市場的報告，290 頁，她沒讀完。吸引她的是技能會變得更重要或更不重要的象限。最突出的是現在已經重要、還會更重要的：resilience、flexibility、agility。學校教這個嗎，大學能修嗎。有趣的是，看來變得關鍵的技能，是你成熟之後才長出來的。她的難題是怎麼教，怎麼把那種靠經驗、刻意練習的學習短路，直接到你已經在批判思考、在更高的層、有整體觀點。那是 Dreyfus model（字幕聽成 Drafus）右手邊，專家，靠直覺運作。沒活過，直覺怎麼建。

## 審查沒有樂趣，DORA 已經看到不穩

[19:47](https://www.youtube.com/watch?v=GI2ywMl2gQk&t=1187s) 文章寫角色從 builder 到 manager、從 creator 到 orchestrator，從寫 code 到管理 AI 系統。她引用 Patrick Debois（字幕聽成 Dwis）的四種 AI native development 模式，社群還能貢獻：從 implementation 到 intent，從 producer 到 manager，從 delivery 到 discovery，從 content 到 knowledge。他們會把兩篇文章放在 show notes。跟這集最貼的是 producer 到 manager。AI 產 code，你審查。Simon 覺得這是問題，我們本來就不擅長審別人的 code。Patrick 還寫認知負荷下降：AI 給情境註解，解釋改了什麼，不只是紅綠色 diff。還有接受疲勞。Simon 承認自己用 Cursor 時，前幾次有效就一直接受，比願意承認的更常。可靠之後這算好事嗎。還有情境意識：我們沒寫那段 code，失敗時很難指出哪裡錯。文章也寫把責任拿回來，做更多設計和 systems thinking，今天那仍是很專的人在做。

[22:18](https://www.youtube.com/watch?v=GI2ywMl2gQk&t=1338s) Simon 問：AI 產 code、我們審查，樂趣在哪。她說我們不是好的 reviewer。當工程師或管工程師，都在求人請審 code。PR 想合併，有點長，抱歉重構過了頭。自己寫完全部、沒有不連續的時候都已經很難。誰把審查變有趣，大概會很有錢。她喜歡 Patrick 寫的、比紅綠 diff 更好的想法。回想以前連好的 diff 工具都沒有。她給剛開始玩的人的訣竅是：source control 是朋友，常常 commit、常常開 PR，不然它會跑掉。Simon 也遇過，不知不覺改了 18 個檔，方式不是你預期的，連自己都不知道 PR 要挑哪些。那不是好狀態。你會交上自己誠實說沒真正看過的東西，下一個人也可能沒看，vigilance fatigue 是真的。會變成更大的問題。2024 年的 DORA report 已經指向這件事。生產力有增益，code 品質甚至上升，交付穩定性卻略降，可能是因為 PR 變大，人接受了問題更多的 code，code churn 變多。她文章裡提的較新的 GitClear 報告（字幕聽成 get clear）有很驚人的數字：code 重複變多，churn 變多，放出去很快又改、又放，多半是因為有問題。

以後幾年 DORA 值得看。我們快很多，若更常 rollback、重做同一塊、產出更多 code，那算更有生產力嗎。這裡賺到，那裡失去，只是把焦點移了。

[25:01](https://www.youtube.com/watch?v=GI2ywMl2gQk&t=1501s) Simon 說若我們離 code 這麼遠，我們還是判斷什麼是好 code 的人嗎，還是更要靠測試和自主：不管 code 好不好看，它做對或做錯。可以再把它變快、重構成比較好維護、比較好看，但我們知道對錯。審查也許該更集中在正確性，而不是風格；很多 review 在風格上轉太久。用更好的測試把這件事自動化。我們歷史上並不擅長測試，但那大概比坐著看 code review 有趣。她仍讀 code。一是有趣，二是那最接近真相。有人說問題解決了，若對方忙，與其請他描述，她可以直接看 code。這些年她很會認出 code 的形狀。結構還算好的話，一頁就能很快看出流程。要練的技能也許是：為了正確性，哪一段該花更多時間審。測試是自動化的驗證。她當天看到一篇文章，product manager 開始把建 eval 當成像 unit test 的東西，只是對象是比較決定性的系統。PM 想做很酷的 agentic 系統，能替你訂機票。請找舊金山附近一個很棒的週末出遊，它就出發，一半的時候你訂到荒郊野外，不是你要的。怎麼阻止。這跟大家開始講的 spec-driven development 一樣。Eval 是在評估輸出符不符合預期。她不知道他們想像的工具是什麼。安全網、guardrail 愈能自動化愈好，不然大家都變成 AI 保母，盯著輸出，防止它漏到我們不想要的地方。那種工作和當創造者比，她不確定有同樣的喜悅。

## 反轉 linked list 會被放下，架構不會從大學畢業就會

[28:28](https://www.youtube.com/watch?v=GI2ywMl2gQk&t=1708s) 什麼技能最難放手，什麼要長出來才算 AI assisted 或 AI native 的開發者。她想到面試。她大約入行三年面試 Google，那是夢想。還沒有視訊，拿著電話解謎題。差不多在 LeetCode（字幕聽成 elite code）之前。她沒過。後來給了 offer，但是 software engineer in test，她對那個有意見，那是另一篇文章。這些年我們仍考排序、搜尋、遞迴、反轉 linked list。業界到現在仍相信，也許正在變，那些技能對當一個很強的工程師絕對關鍵。她說九成時候你進公司後根本不做那些。你在把別人寫好精巧排序演算法的 library 接起來。除非你在 Google，而且你大概也不會從零寫下一個精巧的排序。有人喜歡刷那些題，網站有排行榜，解最難的、解最快。她覺得那不會再很重要。很多工程師把這當成很強的核心。面試上和個人上都得學著放手。AI 能生出夠好的，為什麼還要當那個層級的專家。空出來的洞很大。那些題是挑戰、是解題、是有趣的問題。有替代品嗎，還是得學著愛別的挑戰。

她覺得是抽象上了一層。系統怎麼工作、怎麼互動、介面在哪、怎麼從韌性保護系統的一部分，這些仍重要。字幕裡安全那句沒聽清。它們給的多巴胺，跟你終於讓遞迴照你要的方式跑起來，她不相信一樣。不知道用什麼換。好玩的話也許還會做那種工作，但會變少。有人仍喜歡寫一點 assembly，因為幾年前喜歡，但面試和日常大概不需要了。

這就是文章對她那麼重要的原因：有些缺口她對不齊，看不出這種角色怎麼給出同一種享受。可預見的未來仍有很多工作是懂系統、知道怎麼手寫或手改，因為軟體在每樣東西裡。舊系統、舊語言還在。COBOL 開發者（字幕聽成 Cobalt）仍有薪水。三十年前大概有人覺得那是有期限的。2025 年她還有幾個好朋友在做。有些變很快，有人跟著快，有人慢，也許真的找到利基。今天講的，一週後可能就不成立。Simon 說那些人薪水也很好。

[34:02](https://www.youtube.com/watch?v=GI2ywMl2gQk&t=2042s) 抽象抬高就是架構、系統、應用之間怎麼接。這些技能要長，因為它們常常更決定應用怎麼跑、怎麼互相工作、好不好維護、最後成不成功、甚至解不解得了客戶的問題。她另一篇文章也相關。大學電腦科學教完整個 SDLC：訪問客戶引出需求，搞懂他們要解的問題，把他們從「我覺得解法該是這樣」拉開，當時 use case，UML 還流行，建模、每個 use case 的情境、各種測試和邊界、做出來、把測試想完、維護和升級。她幸運在好幾份工作裡真的做過整條。很多工作在小公司：新創十個人甚至更少，到大約四百人的 scaleup。什麼需要做、你有技能或有興趣或沒有別人，你就戴很多帽子。練出整體圖。這些年她感到對軟體工程的需求巨大，因為軟體在運轉世界。想像口袋裡沒有手機、沒有一直連著的網路、沒有你依賴的 app、遊戲、滑太久的媒體。很難想像。幕後是工程師在建我們當成理所當然的系統。大學再努力，畢業生仍不夠。業界於是專精化。受過相當教育的人專心寫 code，因為別人做不了那一塊。設計交給 architect。搞懂問題交給 product owner 或 product manager。測試別人做，別浪費你的時間。維運部署、運行、on call，你別擔心。不是到處都這樣。很多人仍做整條。同樣多的人最後只被期待寫 code。其他技能沒機會練，那是別人的工作，那些人也變得很強。現在 AI 把我們專精得相當好的那塊做得比多數人打字更快。得把視線放寬。引出需求大概是很值得找機會練的技能。跟反轉 linked list 一樣享受嗎，不是每個人。架構系統也是。技術職涯階梯把 architect 放在食物鏈頂端。得走過那些辛苦。大學一畢業就當 software architect 說不通，你還沒痛過，還沒活過那個架構為什麼不合理。沒有那段背景，那些技能怎麼教。又回到開頭。至少現在是軟體工程師的人，去找機會想更大的圖、這個 use case 最合適的架構和系統設計。Agentic 系統是全新區域，專家還不多。LLM 自己當 orchestrator，決定下一個用哪個 tool 或 skill。這怎麼測。它是非決定性的，我們不擅長想非決定性，不可預測讓人不穩。

## 信任是先高後垮，縫要露出來

[39:49](https://www.youtube.com/watch?v=GI2ywMl2gQk&t=2389s) Simon 說愈自主，信任的動態是兩件事：看懂 code 有沒有做對，以及只有真正信任生成它的 AI，才能從那段 code 走開。主流才兩年左右，大家談信任和安全反而少了。以前是不能放進 production，得先問 CISO。現在從董事會、CEO 往下趕著要生產力。Annie 說信任的研究還在冒出來。生產力增益的研究多得多，所以公司搶著上車。她自己用工具的感覺是期待很高，因為讀過，第一次體驗也不錯。然後不可預測開始侵蝕信任，很難重建。人是從較少的信任開始，靠互動堆上去。她想當最好的工程主管時讀了很多：怎麼取得足夠的信任，才能給建設性回饋。沒有人真的喜歡聽。大家說想要所有回饋因為幫助成長，這是真的，但聽到自己沒做好會痛。跟沒有關係的人給回饋，不要期待對方照單全收，你對他們是陌生人。她記得大約三次正面互動之後，再談回饋比較可能是正面的。人的信任這樣堆，久了會接對方的句子。破了要花很多力氣重建。AI 感覺不同。一開始信任很多，然後撞牆：它繞圈，做出完全不是你要的，你說不是，它同意，因為它常常不發出懷疑的訊號。信任垮掉的主因是它非常有把握地告訴你錯的事。你只是問一句，它就完全改口。你沒有要它把剛才的東西撤掉，請停。

[43:41](https://www.youtube.com/watch?v=GI2ywMl2gQk&t=2621s) 她讀到 Google 研究者叫 seamful AI 的論文。她以前沒聽過 seamful。我們多半在做 seamless，把縫藏起來，讓你不知道有縫。論文說也許錯了。為了提高創造力和使用 AI coding assistant 時的信心，也許該把縫標出來，拿來用。例如 AI 沒有把握時不該假裝有。它可以說這是能解問題的 code，但我的信心是 20%。這是給迴圈裡的人的信號：這裡我要多接手，不能只信它。Boilerplate 的信心應該高很多，解法沒有太多種，就讓它做。用這些有意的、細的暗示校準信任。Code review 就可以集中在它最不信任的地方，而不是平均花時間。最高風險、AI 信任最低的地方，人跟 AI 一起把它做結實。同一群作者另一篇，訪問軟體工程師後發現，軟體工程裡的創造力不一定是全新的東西。是把既有元件、library、framework 用新的方式縫起來，找到新的重用方式，把更大的系統組出來。複雜邏輯上若 AI 有多種解法，有些鼓勵重用，它可以給你不只一個選項，並解釋為什麼：這個比較能重用，那個你可能把這些面向放前面。標出這裡有很多選擇。AI 不替你決定。你決定，創造力是從那個互動表達的。也許信任也多一點。Simon 說若 LLM 給多個選項、他選對的、看得到它的過程，他會更信任，也更有擁有感。

## 想像力，以及會收拾非決定性機器的人

[46:55](https://www.youtube.com/watch?v=GI2ywMl2gQk&t=2815s) 身份的擺，Charity Majors 的說法。軟體工程師這個頭銜還在嗎，會有幾種味道。她覺得我們得非常習慣用 AI。有人會把它當成跟另一個人說話，因為 prompt、跟 AI 聊天確實很像。她的研究裡，問人怎麼把 prompt engineering 變好，很多答案是把溝通變好。有人覺得是比較正式的溝通，有人覺得就是跟同事講你希望事情怎麼做。寫作變好、教學和帶領變好。若角色多了很多這個，你還是軟體工程師嗎。她覺得這個角色還會在一段時間，幸好，因為還有這麼多系統需要我們今天的技能。也要學用各種 AI，model 之間有細微差別。Windsurf 和 Cursor 跟 GitHub Copilot 相當不同，雖然 Copilot 在追上。還有能生圖的多模態 AI。用好各種來把自己放大，不只工程師，任何人都該變好。再往下，認真想這種新工作方式會製造的新問題。我們會寫得更快，因為剛才說的 vigilance 下降，產得更多。已經看得到 code 的形狀變了，也許比較不穩。可以把力氣放在問題發生前就指出來的工具。想像從外面看一個解法，說你即將放到 production 的這個版本，改動比你以為的多。你知道這段業務邏輯變了嗎。也許還沒有人做這個工具，可以變成一整個領域。測試自動化今天有一種想像，若把 eval 算進去是延伸，周圍會有工具，你可以變那個領域的專家。會有新的專精。關鍵是想像力。把它叫技能有點怪，除非你想寫童書。能想像，事情才開始。今天用這些工具，你想得出來，大概就能做出一個版本。好奇和想像的種子從哪來。Simon 說陷太深在細節裡，反而把我們從那裡拉開。他喜歡她前面的 architect 比喻：今天的人把從工程師到 architect 當進展，他個人看到的一個未來是人仍是工程師，但那個工程師的角色是 architect 的角色。

[51:16](https://www.youtube.com/watch?v=GI2ywMl2gQk&t=3076s) 她再補工業革命裡寫下來的事：本來用手做的人，有些轉去真正懂那些現在能做他們舊工作的工具和機器，才能駕馭、拼起來、改進、壞了就修。LLM 核心大概是一種特別的工作，不是每個軟體工程師都會變成 data scientist 或 AI 專家。但她覺得那是會驅動很多其他系統的心臟。可能是 agentic 系統的 orchestrator，或 IDE 裡好幾個 agent 底下的那層。懂這些系統怎麼拼、telemetry、observability，怎麼駕馭一個本質非決定性、核心是自己做決定的計算腦子的系統。變得擅長運行跟今天完全不同的系統。相似的是大概仍用資料庫、仍跑在某台伺服器上。編排會很不一樣。學會駕馭、壞了會修、能指出問題在哪，會是很有趣的工作。也許那就是未來的 architect。歷史一再顯示這種破壞式改變會造出這些工作。Simon 說那是該努力去的目的地，並請人讀她的文章；若想徹底擁抱 AI，也可以叫 AI 摘要。

# RAG beats Fine-Tuning in learning your code base - but it doesn't make AI a better dev

片長 56 分 32 秒，英文自動字幕。AI Native Dev。主持是 Guy Podjarny 和 Dion Almaer。來賓是 Augment 共同創辦人 Guy Gur-Ari，字幕把姓聽成 gurari、guer。兩位 Guy 多年前在同一組，組裡有四個叫 Guy 的人，帳號在 Solaris 上。Dion 之前在 Augment 帶很多產品。另一位共同創辦人他叫 Igor。這份筆記依英文原稿整理，專有名詞保持英文。

- 原片：[YouTube](https://www.youtube.com/watch?v=McsKNfWPsUM)

## 一句話

Augment 要讓模型好像懂你整個 codebase，但 context window 裝不下真的大庫，所以他們用 RAG，而且實測比 fine-tune 客戶的 code 更好。Fine-tune 學得會 docstring 的格式，學不會怎麼呼叫你的 API，也跟不上每個開發者一分鐘前改過的分支。這讓你在這家公司裡更快上手，不是把你變成一個更會寫程式的人。世界的知識已經在模型裡。

## 裝不下整個庫，還得跟得上你正在打的字

[2:28](https://www.youtube.com/watch?v=McsKNfWPsUM&t=148s) Augment 是 AI coding assistant。每次互動都想讓模型看起來真的懂完整個 codebase，於是你可以改 code、寫新的，不必把整個庫記在腦子裡。他舉的例子是走進從沒碰過的一塊：有了它，通常幾小時到一天就能有把握地改，否則有時要一週或更久才搞懂那一塊、或一個新 repository。對他們來說就是 context。把 codebase 的 context 給模型，結果好很多。Dion 說他第一次用就覺得跟其他 coding assistant 不一樣，像很多搜尋引擎之後 Google 出現的那種差別。錄這集時是 1 月 17 日星期五，已經可以自己下載，他建議在真的 repo 上做真的任務。

[3:48](https://www.youtube.com/watch?v=McsKNfWPsUM&t=228s) Guy Gur-Ari 六年前進 Google，當時很興奮，覺得 machine learning 是一生一次的科學革命。他看到的討論比較多是 vision、convolutional neural networks。GPT-3 對他是轉折：不必為了做一件事去 fine-tune，可以 prompt，可以 few-shot，字幕把 few-shot 聽成 F shot。他和團隊把工作轉去語言模型，開始評、也參與訓練 Google 的大型模型。他相信生成式、很通用、能生出大量文字的模型，是這場革命的核心。

程式沒有一開始就明顯。推理很重的工作看起來更遠、更難。多年來有人做特徵工程、找架構、做符號工作、對 code 和數學做語意分析，那些很多仍有用。讓他和其他人驚訝的是：把算力和資料放大，用跟寫詩、改法律文件同一套很通用的技術，就能解很難的推理。Code 是例子，數學和科學也是。最早的跡象之一是 Codex，Google 自己的 code model 也有一些成功。進度快得讓他意外。社群曾以為 code 和數學要特別處理，neurosymbolic 或純符號都是大路。意外是大型語言模型用跟其他文字一樣的架構和訓練，放大之後結果就很好。

[8:01](https://www.youtube.com/watch?v=McsKNfWPsUM&t=481s) 他們還做過數學和科學題。那是 Eureka。做法仍是把資料放大：下載找得到的 arXiv 論文，在網路上掃跟數學有關的論文。在 Google，基礎設施讓這件事直接。然後拿當時拿得到的最大模型，他說是 Google 的 PaLM，字幕聽成 Paul，用那些資料訓練，看它數學能做到什麼。品質讓他們震驚。這些模型通過了大學入學考。他當時想：推理做得到，code 和很多別的領域大概也做得到。推理不是一種特別的東西。

## 它對齊的是這家公司，不是「更好的開發者」

[10:34](https://www.youtube.com/watch?v=McsKNfWPsUM&t=634s) Context 的第一面是不管你在做什麼，都要能深懂 codebase。呼叫一個函式時，游標上的 completion 要從庫裡各處把欄位填對。走進新 repository，要能問這庫在做什麼、高層結構、元件怎麼說話，不想讀常常缺漏或過期的文件，只想知道 code 現在的樣子。或六個月前寫的元件找不到，問聊天就該找出來。這些都要分析整個庫。他說今天的 context window，以及看得到的未來，裝不下真正大型、複雜的 codebase。得用別的辦法讓模型知道那些 context。一邊是為這一次查詢、這一次 completion 拉對的片段。另一邊是互動。不快的話，品質再好也很快煩人。還有即時：我在一個檔案寫完函式，切到單元測試要為它寫測試，不該再告訴模型我剛寫了這個。它該跟著我編輯。做過 RAG 的人知道要索引，索引又慢又難。全部要在幾百毫秒內合在一起，而且任何開發者可能做的任務都得這樣。

[13:51](https://www.youtube.com/watch?v=McsKNfWPsUM&t=831s) Guy Podjarny 問：context 是讓你變成更好的開發者，還是只讓你在這個環境裡更好。一個很會寫的人進新公司，五年後更懂怎麼在這家寫 code，不等於變成更好的開發者。世界的 context 已經編碼進 LLM。Gur-Ari 說對。他們現在從 codebase awareness 開始。組織還有很多別的資訊來源。這是把模型對齊到組織的知識。關於世界的東西，通常已經烤在模型裡。他看到它讓自己變成更好的開發者，是因為學習變快。模型會注意到 codebase 裡有用的模式、技巧、別人做得好的事，透過建議浮上來。這本來就會發生：跟同事談、讀別人的 code。Context awareness 把那個過程加速。你也會把一些東西帶到下一份工作。它比較不是在教你這個領域最新的方法。Dion 補了一個開發者的故事：聽說 JavaScript 有了 Set，一直想用，卻從沒在做事的時候用上。寫 code 時建議突然把 Set 用出來。同事也很聰明，它也會把那些撿過來。Dion 覺得像跟所有同事的智力同時 pair。

[17:01](https://www.youtube.com/watch?v=McsKNfWPsUM&t=1021s) 二十年的企業庫裡有很多不該被新 code 複製的東西。他說這屬於輕量的 steering，像自駕：完全自主還要幾年，他相信最後會到，但要時間。自動分辨哪些部分跟現在這件事有關、哪些有關但該避開，還要時間。那些知識常常不在 codebase，在 Slack、Google Docs、設計文件。能給模型的 context 愈多愈好。也可以給永遠生效的一般指南：在這個目錄、這個 module、這個元件做事時，少看那一塊，因為那是舊的。不是萬無一失，AI 仍會錯，但至少把方向舵過去。目前是盡量多給 context，加上人的 steering。

Dion 說有些工程組織被覺得手藝更好，以前 Netflix 常被放在上面。他胡思亂想：Netflix 能不能賣自己 code 的 context，讓別人的自動完成寫到那個水準。就算資料不會外流，組織內部也有想優先看的人。他點一位 Webflow 的 principal engineer，字幕聽成 Merrick，很懂前端。對那個人的頓悟是：他等於在跟公司裡所有新開發者虛擬 pair。用 React 時我們要 hooks、要這種做法。把轉向的能力交給人，影響很大。Lint 和事後檢查標準，很費力，所以做得不多。寫完再被要求改 50 個美學差異也很煩。可以把那些事後才檢查的東西，反過來注入助理在寫的時候。

## Fine-tune 學格式，RAG 才教得會怎麼呼叫

[22:03](https://www.youtube.com/watch?v=McsKNfWPsUM&t=1323s) 主持問：RAG 是把 code 切得很聰明、在對的時間給對的 code。另一條路是直接在客戶的 code 上訓練，讓模型和世界、和你自己都在一起。就算客戶願意讓你訓練，技術上為什麼仍要即時去拿。他們早期真的比過兩種做法。RAG 全面給出更好的結果。

人對 fine-tuning 的想像有時像人讀書：讀一次就學到很多。模型掃一遍、甚至多遍 code，學得沒有人讀一次那麼深。它很容易撿到常見模式。若你們的 docstring 大多長那樣，fine-tune 之後它會很會生出那種格式。但在你的 API 上 fine-tune，不表示模型現在會正確呼叫那個 API。Fine-tuning 是讓它一次預測下一個 token，不是教它「我被訓練過這個函式，所以我知道怎麼呼叫」。RAG 可以走到那一步：給它看一個函式時，呼叫那個函式要做好。品質更好。

操作上也不一樣。大組織裡每個開發者有自己的分支，每人的 codebase 都不一樣，而且跟他一分鐘前改的東西也不一樣。要給最好的體驗，模型得適應每個分支的當下狀態。用 fine-tune 很難做到，比一般 fine-tune 還多，某種邊訓練邊打的做法也不太行。也許用 LoRA 這種 parameter-efficient fine-tuning，字幕聽成 Laura，每個開發者一份小的適配。但能改的權重少，品質會犧牲。若 fine-tune 有很大的品質差距，故事會不一樣。他們沒看到那種差距，而按人客製在操作上又難很多，所以覺得 RAG 適合得多。主持提到上一集 Notion 的共同創辦人 Simon 對 fine-tuning 失望。他的解讀是：你加進去的資訊只是海裡的一滴，優先級不高。RAG 給的優先級高。Simon 講的另一個問題是難除錯：一個魔法盒子，給很多好例子，希望它吐對。不對的時候你不知道為什麼。Agent 的流程比較像開發者熟悉的步驟，看得到哪一步失敗。RAG 呢。Gur-Ari 說這是他們要解的。客戶說這次 completion 或聊天錯了，他們會挖。第一個問題通常是 retrieval 失敗還是 generation 失敗。沒拉到對的東西，錯在那裡。拉到了，錯在下一步，模型不知道拿那些資訊怎麼辦。這是最基本的分診。他們有工具。一般不請使用者自己做。還沒聽過這種要求。他們要給的是魔法。

[28:16](https://www.youtube.com/watch?v=McsKNfWPsUM&t=1696s) 往前看，他把 RAG 當入口，不是永久的差異。以他們的測試和客戶的話，現在有優勢。當週有一個客戶的 eval 在比，他聽到的是 Augment 因為 context 帶來的生產力在另一個等級。他猜這是暫時的。這一行進步太快。一兩年後若 RAG 仍是差異所在，他會很驚訝。他們準備很快推出的是 RAG 的另一面。前面講的是給模型更好的輸入。同樣重要的是模型能不能在 codebase 裡採取行動。不再是游標在這裡、給我幾行。使用者已經期待：請在整個庫裡幫我改。那是另一個預測任務。不只是拉什麼進來才做得好，而是在這個又大又複雜的庫裡要去哪裡改。這不是現成的 retriever，就他所知也不是現在最好的 retriever 做得到的。他相信還會有很多額外的模型，合成一個系統。還沒想完那些東西是什麼。

## 不從頭訓練，也還不能給模型送補丁

[31:45](https://www.youtube.com/watch?v=McsKNfWPsUM&t=1905s) 他們其實也訓練模型，看功能、看哪個模型在驅動。多數功能最後既要訓練、也要 retrieval，兩者一起才動。他們不做的是從頭訓練，不做 pre-training。這個賭注下得很早。開始時最好的開源 code model 跟現在比相當差。他賭它們會追上、會變得很好。在 Google 他看過 pre-training 裡有什麼：拿資料、清、去重、一批 GPU、盯著 GPU 故障。有一份 playbook，照做會得到好模型，然後比賽變成再擠一點、再把資料品質做好一點。開源做得到這件事，而且比他預期更快、程度更大。AI 世界一再比他們想的快。他們很快就有極好的 code 基底模型。這些不能原樣放進產品去驅動 completion。例如游標附近的 completion，模型要看游標前面和後面，而且要在對的地方停。他看過的現成模型目前都做不好。這些要另外訓練，超出 RAG。RAG 是一大塊，但基底愈好，上面再加的訓練，最後的模型愈好。他們跟上最好的開源模型。通用模型之後，下一個出來的常常是 code 專用模型，對他們很好。大量訓練做在開源模型上，自己不做 pre-training，然後做 RAG。

[35:03](https://www.youtube.com/watch?v=McsKNfWPsUM&t=2103s) 主持把 open source 和 open weights 分開。開源軟體可以回饋，Kubernetes、Linux 會因為大家共用而變好。Open weights 通常看不到資料集，不能改資料再加回去。什麼會讓它們長期贏。現在感覺比較像某些組織的商業策略，願意發布、願意代管。Gur-Ari 把這想成模型的生態，不是單一贏家。不同功能用不同模型，大小、延遲、這個功能有多專、多通用，都要配。有時用閉源，有時用 open weights。待在前沿或靠近前沿，需要愈來愈多算力，也就是愈來愈多資本。也一直有最佳化：小模型做到以前十倍大的模型的水準。Llama 發生過，最近 Qwen 也發生，字幕聽成 Lama、quen。算力不夠的任務，小模型又把它拉回很多人夠得到的範圍。小模型這一側，若延遲要求嚴，他相信會繼續用小模型，訓練也比較不費。小模型就算丟一百倍的資料，也學不完那些資料。

回饋的選項很有限。他們受惠很多，很想回饋。拿到權重之後，可以繼續 fine-tune，讓它在你在意的特定任務上更好。但不能像開源程式那樣修一個反覆出現的錯、送一個 pull request。模型仍是黑盒。可解釋性的研究想找出哪些神經元對哪些輸入和輸出，出問題時改那些神經元。那個研究比訓練黑盒更早。他看得到的回饋路徑是那套研究做出來之後，可以送權重的補丁：套上這個補丁，模型在這些問題上好一點。現在沒有，因為研究還限制他們。Dion 很高興大家不把非開源的模型叫成開源，就算有公司想混進去。Open weights 仍有很多價值，人也更願意在周圍做工具。有些開源專案你送 PR 也永遠不會被收。他覺得這一行的競爭比什麼都重要，這樣就不會被鎖住。主持說，就算訓練腳本、訓練日誌、訓練資料全部公開，你發現一個問題，還是只能回到資料去改，再花時間重訓，看有沒有修好。跟 fine-tuning 的問題一樣，很間接。給模型送一個 bug fix 是巨大的工程。被卡住的是修補模型的能力。

## 工具變好之後，你做的事變多，不是變少

[44:02](https://www.youtube.com/watch?v=McsKNfWPsUM&t=2642s) 今天 Augment 做自動完成，也做聊天式的生成。五年後還需不需要 IDE 裡的 completion。他說這一行的五年像永恆，完全是推測。簡單的任務，五年後進到工作區的 issue 會有某個百分比被模型自動修好。他覺得這基本上是保證。是 20% 還是 50%，看專案。仍會有開發者得自己挖的 issue。他喜歡自駕的類比：動作空間簡單得多，方向盤和踏板，完整自駕還沒解完，但一路上自動化已經有很多價值。寫程式的動作空間更富。他猜 completion 仍會有用。工具變好之後，他不是把以前的工作做得更快、於是更少用 completion。他完成的事變多了。聊天和其他功能會用一些時間，completion 仍用得很多，因為還是得親手改，有時是很多 code。在又大又複雜的庫裡尤其如此，那些會最慢被自動化，因為最難。自然語言寫愈來愈多 code 是很清楚的趨勢。他預期這些工具會一起活著。

給現在的初階到中階開發者，他覺得可見的未來有兩件仍必要。第一，模型會繼續犯很多錯。軟體系統已經極複雜，AI 自動化愈多，系統更複雜，也更常搞砸。搞砸時沒有東西能取代你對系統怎麼運作的深理解。他用 Augment 可以吐出幾百、幾千行，有時一陣子都好，然後出事。出事時他仍要知道系統怎麼建的、建在什麼上面，常常是 full stack，才能在 Augment 修不了的時候自己修。第二，在光譜另一端，要懂這些模型、懂怎麼 prompt，才拿得到最多價值。它還不會讀心。他們和所有人都在讓這件事沒那麼難、愈無縫愈好。愈懂模型，這套技能目前只會更有價值。

主持覺得兩件今天都同意，但壽命呢。Prompt 該變容易，模型該更懂前後文。現在去學 prompt engineering，很多會過時。圖像那邊，從 diffusion、一堆關鍵字，到後來用英文就好。系統理解也該在五年內聰明很多。極端的問題是：現在會不會建議小孩去讀 CS。Gur-Ari 說這個答案幾乎每個月在變。他不確定。一方面他同意會變容易，那正是他每天在做的事，更多人更容易做出更多東西，對社會是好事，對職業有影響。他澄清：不是叫人去當 prompt engineer。他要說的是，人試一次，有時好有時不好，就以為這就是模型能給的價值。還有更多。去各個方向推，才知道極限在哪。CS 學位若是為了深入認識世界，他仍覺得有價值。當職業選擇，他偏樂觀。這些討論裡常暗含一個假設：想做的東西數量有限，AI 自動化之後就沒東西可做。看程式語言的歷史，每一種新語言都是要把上一種的雜務自動化、讓寫軟體更容易。同時我們寫的軟體數量和複雜度是暴增，不是五分鐘做完就去海灘。他猜會看到更先進、更複雜、更有用的系統，人仍要掌舵，也仍需要深的理解。會讓他重想的一個數據是：若自駕被端到端解掉、那個任務完全消失，也許其他真實世界的任務也會這樣。主持說他不會建議現在去當計程車司機，但開發者的光譜跟司機不一樣。他信任去改 Chromium 或 Linux kernel 的人，是很小的一群，跟他信任去做一個 web app 的人不一樣。小孩想活在哪一層抽象。Dion 希望小孩若想做，就去做，把這件事民主化，專注在解真問題，活在更高的抽象、做更大的東西。CS 學位不像最差的選擇。Gur-Ari 站在樂觀那邊：十年、二十年、五十年仍需要做軟體的人，或用軟體做解決方案的人。他對 CS 學位能不能跟上變化，信心少得多。主持說自己是那個學位的空頭，就算今天去讀也可疑。要做 machine learning 的博士，電腦科學和數學大概仍是好地方。就算是去貢獻 Linux kernel，或未來同等的、由 AI 驅動的開發，他不確定一兩個十年後 CS 學位給得了那些工具。Gur-Ari 說若仍有人要做軟體、又需要對系統的深理解，他希望學位會演化去配合。然後就等著看。

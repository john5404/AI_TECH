# Daniel Jones & Tomasz Maj - More software, faster - Odevo's AI Native transformation - AI DevCon '26

片長 36 分 51 秒，英文手寫字幕。Daniel Jones 在北歐的小型顧問公司 re:cinq，做 AI native transformation，以前做 cloud native。Tomasz Maj 在 Odevo，2024 年加入；兩人說其中一個是前 McKinsey。Daniel 就是他們口中那個留鬍子的人。這份筆記依英文原稿整理，專有名詞保持 English。字幕把 spec-driven 聽成 spectrum，把 TRIZ 聽成 trees，把 BMAD 聽成 be mad；下文用校正後的詞。沒有留問答，後面是午餐。

- 原片：[YouTube](https://www.youtube.com/watch?v=mB74LGAmmV0)

## 一句話

Odevo 幾乎每週併購一家物業管理公司，七年從 5 萬戶、1000 人，長到 250 萬戶、1.4 萬人。技術棧、文化和流程都不一樣，發 Claude 授權解決不了。他們的前提是：AI 會讓壞的更壞、好的更好。所以先做 discovery，看 CI/CD、平台、測試和程式標準在不在，再用同一套訓練把每個開發者帶過失敗模式，而不是快樂路徑。訓練在二月做完之後，採用率大約 94%。他們用來衡量轉型的，不是儀表板本身，而是人敢不敢做更大的實驗：一套做了八年、20 個人的平台，三週重寫到功能對等，現在 4 個人接著做。

## 併進來的公司，沒有一種做法可以進化

[0:47](https://www.youtube.com/watch?v=mB74LGAmmV0&t=47s) 主題是更快做出更多軟體，結尾會繞回來。Daniel 說朋友叫他 DJ 是因為縮寫，不是因為他去跳舞。Tomasz 的名字有波蘭文的幾種叫法，那是內部的事。re:cinq 看到的模式和當年雲、Kubernetes 的轉型一樣：把 agentic coding 用好，不是發一些 Claude Code 授權就結束，旁邊要一起改。

[2:12](https://www.youtube.com/watch?v=mB74LGAmmV0&t=132s) Odevo 做住宅物業管理，自己有物業管理公司，也提供服務，其中一項是技術。最近的排名裡，他們是瑞典第三大的私人科技公司。第一是 Lovable，中間還有一家他們不談，然後是他們。物業管理在這裡是：租房子，每個月付一筆錢，讓人管垃圾桶、公共照明、HVAC、電梯、帳單，東西壞了要修。英國現在還有消防，美國有電梯安全。終端使用者有些是志工，常常裝備不足，還得管財務。軟體做好，生活可以好很多。

[4:10](https://www.youtube.com/watch?v=mB74LGAmmV0&t=250s) 他們成長很快，幾乎每週併購一家。併進來的常常是爸爸、媽媽、小孩和一隻狗組成的物業管理公司，從美國到歐洲，北半球都有。據點在美國、墨西哥、英國，起源是瑞典，再擴到英國、美國和其他地方。時區不能再增加了，所以守住現有的，往北或往南長，或把東西收在一起。七年：管理戶數從 5 萬到 250 萬，員工從 1000 到 1.4 萬。

[5:22](https://www.youtube.com/watch?v=mB74LGAmmV0&t=322s) 併購帶來非常雜的技術。你想得到的技術棧，他們大概都有。有的軟體沒有 UI，打電話給一台伺服器，上傳資料有時要 30 分鐘。這仍是紙筆產業。英國的物業管理人會把要向屋主協會收多少錢寫成海報去貼，海報有時會不見。數位化的空間很大。文化、流程、方法也不只一種。不是有一條舊路要進化，而是有很多條路。

[6:49](https://www.youtube.com/watch?v=mB74LGAmmV0&t=409s) Tomasz 2024 年加入時，開發者已在用 GitHub Copilot。他們自己做了一套聊天，建在 OpenAI API 上，字幕把名字聽成 dogfight。原因是敏感的客戶資料，不想讓員工把不該傳的東西丟進各種聊天。另外有 Claude 的小島：一兩個人自己去買授權，興奮地用，不成氣候。採用率大約 30%，大部分是 Copilot。PR 很大，大約一週一次，有時更少，合併很慢。他花時間把 flow、速度和透明度做出來。多數團隊不知道自己表現不好，氣氛是大家一起走就好。那一年半、把現代做法帶進各種技術棧和文化，讓後面的 AI 訓練容易得多。2025 年夏天之前他們就知道 AI 會是大事，Claude 的小島愈來愈多，決定找夥伴。

[9:24](https://www.youtube.com/watch?v=mB74LGAmmV0&t=564s) 他們做了一個很大的宣告：組織裡每一個開發者，用同一種方式訓練 AI。RFP 發出去，Tomasz 還在 LinkedIn 寫自己在找 AI 訓練公司。回來大約 80 則，有 15 歲的人說自己有 25 年 AI 訓練經驗，也有人說 agent 這個詞出現之前他們就在做 agentic。收到十家看起來不錯的，談過幾輪，最後三家很接近，選了那個鬍子。那是去年夏天，Opus 4.5 之前，spec-driven 還不流行。Spec Kit 大概九月才出來。他們要的一句話是：有了 AI，壞的會更壞，好的可以更好。

## 先看基本功，再把人找進同一間房間

[11:06](https://www.youtube.com/watch?v=mB74LGAmmV0&t=666s) Daniel 說這不是銷售。第一件事是 discovery。2025 年的 DORA 報告，大約八月，看了幾千家公司：你現在軟體開發做得不好，再把 agentic coding 丟進去，會更糟。你是在讓一個互相連接的系統裡的一塊跑得很快，瓶頸會在別處露出來。若交付本來就做得好，會快很多，像一根曲棍球棒。沒有人知道那個平衡點在哪，產業還沒算清你要多糟才會變慢。他們在 Odevo 各團隊要看的是：有沒有 CI/CD，有沒有平台。沒有平台，code 無法可靠、快速地送出去，生出來的 code 沒有地方去。有沒有測試。Agent 不能跑測試來發現自己弄壞了軟體，就不要意外它會弄壞。人若沒有共同的 coding standards、沒有同意什麼叫好，agent 也很難生出團隊願意收的 code。他樂觀的地方是，這也許又是一次把基本功補上的機會。RFP 裡寫明他們期待、也願意付錢做 discovery。以前有廠商帶著錯誤假設進來。夥伴得認識公司和要受訓的人。

[14:39](https://www.youtube.com/watch?v=mB74LGAmmV0&t=879s) 工作坊在 Spotify 的舊辦公室，面對面。Liberating Structures 是一套會議形式，用來壓過像他這種嗓門大的人。他們問人對即將到來的 AI 訓練有什麼感覺：害不害怕、工作滿足會不會掉、以後還有沒有動力。另一輪用 TRIZ，他說是創意解題理論的縮寫，俄文房間裡的人會懂。題目是：想像 Odevo 要雇 200 個初級開發者，來自一個永遠說好、從不說不、從不推回、從不睡覺的文化，點滴打著 Red Bull，日夜寫 code。怎樣才能讓這件事成為一場盡量大的災難？大家貢獻想法。下一題是：我們這裡有哪些事有點像那些壞事。人互相看：我可以說測試不夠好嗎？跨技術棧、跨文化，答案出奇地一致，像蜘蛛人互相指。這是在降低抗拒、猶豫和恐懼，讓人開始想解法。他說若只帶走一件事，就是讓人面對面、互相有同理、先知道恐懼是什麼。

[17:20](https://www.youtube.com/watch?v=mB74LGAmmV0&t=1040s) 正式大場之前先做試點，11 月 11 日，波蘭獨立日。小群體裡把會出錯的地方看過，後來 80 人的那場成功得多。Daniel 也學到：不要在講課或演講前一晚，跟一個很高的波蘭人出去喝，前一晚的 Jägermeister 有點多餘。

[18:07](https://www.youtube.com/watch?v=mB74LGAmmV0&t=1087s) 訓練技巧是練習做完問：我們剛剛做了什麼。裝了 Claude，它從哪來。打了 prompt，prompt 去了哪。它呼叫了工具，工具在哪裡執行，模型怎麼決定用哪個工具。一塊一塊畫出來。社交上，不答完不會往下；視覺上也比較記得住，比只做練習更深。而且必須本人到場，在斯德哥爾摩。瑞典很重視吃飯，他們供餐，還有 after party。上午前半不要筆電，把事情說出來。否則人會一心多用，不聽那個留鬍子的人。進辦公室互相認出對方，也是很大的改變。

[20:02](https://www.youtube.com/watch?v=mB74LGAmmV0&t=1202s) 課綱第一塊是 context、context 管理，以及有效 context window 的上限。塞得愈多，LLM 愈容易出軌。於是有人把每種情境的每條指示都放進 AGENTS.md。他說已有幾份學術研究顯示這有負面效果，沒有指示可能比一大堆更好。他們也用容易幻覺的舊模型，做 prompt biasing，讓人看見失敗。快樂路徑不必教。能動的時候像魔法，重要的是失敗模式。第一個模組就是這個。從 VS Code 加 GitHub Copilot 跳到 Claude Code，對很多人是心理上的一跳：在 VS Code 裡你決定開哪些檔，終端機裡的 Claude Code 由 agent 決定給你看什麼。後面才是 MCP、spec-driven development、多 agent 流程，以及 Gastown，現在叫 Gas City。這些是積木，最後要能想到團隊流程，不只是個人。

[21:47](https://www.youtube.com/watch?v=mB74LGAmmV0&t=1307s) 訓練沒有一次上完。人需要一段旅程。每週半天，上完就回去。剛學完 MCP，回座位裝上，問它下一張票該做哪張、驗收條件怎麼看，讓它推回來，看這套在真實工作裡成不成立，而不只在練習裡。要先告訴 IT，大家會在筆電上裝軟體。他們因為人裝不起 Docker，一場訓練掉了 15 到 30 分鐘。練習是導覽，讓人看 code、看 skills 怎麼運作。真正感到力量，是回到自己的 production codebase 上自己玩。

## 採用率之後，他們量的是敢不敢

[22:52](https://www.youtube.com/watch?v=mB74LGAmmV0&t=1372s) 核心開發者的訓練大約二月中做完，Tomasz 後來又帶了一些其他人。AI 採用率大約 94%。問法的字幕聽成「過去十年」，後面卻是十次裡十次，所以比較像最近十次有沒有用 AI。94% 至少用了三次或更多，50% 到 60% 是十次全用，只有 6% 沒用。他們正在訪問那 6%：是什麼擋住你。上市時間明顯變快，東西做得更小、品質更好，合併和發布更容易，PR throughput 持續上升。他們做了儀表板，每個開發者看得到別人在哪個 repo 工作，跨團隊透明，還可以跟資料聊天。他覺得只發工具也會有類似趨勢，但不會這麼有用。訓練讓人更有意圖、更聰明，不是因為想實驗就把一切都丟給 Opus 4.7。

[25:13](https://www.youtube.com/watch?v=mB74LGAmmV0&t=1513s) 他認為最大的影響是膽識。若有人問 AI 轉型怎麼算成功：你多做了多少大膽的事，試了多少實驗，有沒有真的做端到端的 agentic workflow。他們有一個做了八年、不算成功的平台，在外部專家支援下整套重寫，三週做到功能一比一。以前 20 個開發者做八年，現在 4 個開發者用 AI 接著做。他們也試過三天做一個手機 app，沒成功，但試了。各國軟體之所以碎，也因為法規。現在他們要試一個平台，用同一份來源應付所有市場，再用 AI 依需求客製。他說沒有這種膽識，去年不會發生。

[27:22](https://www.youtube.com/watch?v=mB74LGAmmV0&t=1642s) 有一個團隊退回去重想交付。人在個別 story 上工作，在 coding agent 這麼快的時候行不通。他們改成 AI first。兩週用嘴談產品需求，全部自動轉錄，再讓 agent 做成 PRD，打得很深，把 entity relationship 和業務邏輯畫出來，領域先定義好，然後交給 agent 拆成任務計畫。像 spec-driven，但是更高一層的抽象。開發者一天拿起好幾個 epic。有人要用 BMAD 可以，有人要用 Spec Kit 可以，有人仍在 vibe coding，各有做法。拿起 epic 之後，那個團隊不再做人類的 code review。他們自己看 code，但已經不寫 code。送 PR 之前自己過 7 到 8 輪審查，然後自己合併。別人讀 code 會變成瓶頸。他說讓人做 code 的靜態分析，本來就是個笨主意。整個步驟都變成 AI native 之後，再用既有的 scrum 或 Kanban，瓶頸會很快出現，該重新看 SDLC。這個團隊被當成燈塔，別人可以去看、去問。他們有 podcast，最新一集就是這個團隊的開發者在講這套做法。

[29:43](https://www.youtube.com/watch?v=mB74LGAmmV0&t=1783s) 人的變化有三個例子。Dominic 來的時候是 AI 懷疑者。以前讓 ChatGPT 在隔離的情況寫過不緊急的 code，覺得是垃圾，永遠不會有用。他也有正當的倫理顧慮：模型怎麼訓練、能耗。十一月有機會玩 Opus 4.5、可以自己探索之後，那些信念不成立了。好好跑起來，這些工具可以寫出他願意署名的 code。組織裡會有人一年前試過 VS Code 的 GitHub Copilot，一次很爛，就認定永遠不會好。他們需要看到現在的水準。他在 podcast 上說，工作上已經四或五個月沒寫 code，回家卻當興趣在寫，像買 IKEA 家具，業餘再做木工。另一個 Daniel 在 developer experience 團隊，也不寫 code，做的是追蹤、telemetry、觀測工具。他是高表現的人，說自己的表現提升了，字幕把數字聽成 2000 30s，沒有聽成一個能確定的倍數。Nicholas 從一開始就是 train the trainer。他們要內部有能力持續演進這套訓練。他本來就是重度使用者，也在教 Ralph Wiggum loops。現在他去還沒參加第一輪的公司教，講自己在 Odevo 的經驗。鬍子和運動服可以，但產業裡的自己人講自己的事，更真實。有些人不喜歡被外人教。

## 下一個瓶頸是產品，以及人關不掉

[32:39](https://www.youtube.com/watch?v=mB74LGAmmV0&t=1959s) 他們發現投資工程師的時候，忘了另一塊：設計師、字幕聽成 Vas 的角色、product manager。工程師那套訓練被調整之後轉向產品同事。產品的人會變成下一個瓶頸，很多地方都看到，Dominic 在 podcast 裡也提過。再下一步，是教其餘員工用 Claude Code 這類工具做基本的事。大約 1.3 萬人。已經有財務經理或會計在用 Claude Code 給自己做小工具。他們想用訓練把這件事收好。

[33:52](https://www.youtube.com/watch?v=mB74LGAmmV0&t=2032s) 也有工程師說關不掉。下午六點、七點，有時凌晨一點，多巴胺是真的。他們開始說：放下，出去過生活。瑞典的天氣那句字幕聽成 a lot of cell。Daniel 想講 Skinner box 和背後的心理，但強迫是真的。這件事還沒發生在 Odevo。Multitudes 的 CEO Lauren Peat 的研究說，很多組織在採用 agentic coding 之後，功能壓力變大，人覺得應該做出更多，於是加班。那是感受到的壓力。

[34:44](https://www.youtube.com/watch?v=mB74LGAmmV0&t=2084s) 目標是讓每個人都成為 builder。他們想從替人做軟體，轉成在支援之下一起做；字幕那句聽成 up coast to coast。他們要 1.4 萬人為自己做東西。1970 年代，新的業務流程是拿紙、做一張表、告訴大家。後來為了用上計算，這件事全部交給工程師，你自己改不了。雲的時代更糟，因為分散、複雜。現在可以把解決問題的能力還給業務使用者。有的 product manager 已經在用 Claude Code，也在 Lovable 和其他工具裡 vibe coding，做出每天在用的東西。他們看到的不是軟體開發消失，也不是開發者因為這些更大、更膽的改變而變得多餘。而是更多軟體，更貼身、更好用，解決個別人的業務問題，而不是要花好幾年的那種又大又慢的軟體。以前放在某人硬碟上的複雜 Excel 模型，正在變成真正有人用的 vibe coded 方案。刺激，也有點可怕。時間到了，後面有人很堅定地搖頭，所以沒有問答。LinkedIn 的 QR code 在投影片上，鬍子比較好認，會後可以找他。

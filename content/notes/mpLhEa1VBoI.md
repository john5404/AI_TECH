## 一句話

語法正確的 code 從大約 17% 走到他上次看到的 98%，安全基準卻是平的，甚至略往下。人在指數級地多寫 code，安全姿態沒有一起變好，產品表面變成瑞士起司。Casco 做的是對 AI 應用和 agent 的自主安全測試：像加了類固醇的 pen tester，同時試幾千種攻擊，只告訴你真正可被利用的漏洞。小團隊已經能做出過去只有大組織才做得動的關鍵軟體。一年測一次，趕不上每週都在 ship 的世界。

## 規格可以一次做完，live coding 用來試

[2:57](https://www.youtube.com/watch?v=mpLhEa1VBoI&t=177s) Casco 對 AI app 和 agent 做自主安全測試。找出軟體有哪些漏洞，讓你只修真正可被利用的那些。他從幾段經歷裡帶走的是客戶體驗：很容易陷在單一指標裡，長期有回報的是一直對準整體體驗。第一份軟體工作在做資料庫 ORM 的 Prisma，在那裡學 developer experience，開發者的每一次按鍵都該讓工作更快。Skype 做可嵌到各處的網頁 SDK、一個小聊天元件。2015、2016 年 chatbot 很紅，但遠不如今天有用。在 Microsoft 做過接語音辨識的 web SDK，當時可以跟 Cortana 這類助理說話。在 AWS 發明 Kiro，是他最有趣的專案之一：用 specification 做一種幾乎全新的開發者介面，在現在做得到的事和未來之間找平衡。

[5:46](https://www.youtube.com/watch?v=mpLhEa1VBoI&t=346s) 2016 年他贏了歐洲最大的 hackathon，做的是 voice-to-code agent，遠在 ChatGPT 大約 2022、2023 年成為大家嘴上的事之前。當時的 AI 不是今天這種隨意、自由的生成。想做部落格或電商，得先有幾條預設路線：意圖辨認你想做東西，實體抽取是網站、手機、部落格還是電商，再對到很確定的程式。Demo 很酷，但路線是半固定的，沒有今天 coding agent 的用途。今天可以去看機器上某個檔、再把資訊合進來，當時做不到。他們得把 IBM Watson、Google Cloud 和 Microsoft 的 Language Understanding 接在一起，後來那個服務在 Azure。很難做。他覺得自己推開一扇門，瞥見技術變好之後的機會，也因此愛上開發者體驗：你可以說出任何東西，讓它存在。這是軟體開發獨有的。

[10:47](https://www.youtube.com/watch?v=mpLhEa1VBoI&t=647s) Spec-driven development 這個詞現在很滿。他看到的、包含 Casco 自己團隊的，是今天就能把個別功能做到很高的品質。Live coding 像電玩，來回小步前進，很難看見整張地圖、最後要落在哪。規格是把思考做在前面：use case、要打開的客戶體驗、系統裡的限制、怎麼對著那些限制工作。規格本身要迭代不少，然後一次生出很多 code。適合給功能劃邊界，把終端客戶體驗內化到夠深的保真度，再生成。他們在做一個會去駭其他軟體的 AI agent。每找到一個漏洞，就做一個 gym 讓 agent 對著練。先寫一份 base gym 的規格：限制是什麼、怎麼部署、這一個要不要放在 Kubernetes、那一個能不能只是 serverless。這份模板把系統限制先給出來，又不會把程式怎麼寫死。再為每個漏洞寫具體需求。於是一天可以做出數百個 gym。像真的去健身房，持續去就會變好。

今天的規格適合把單一功能做深。正在移過去的，是讓功能自己變好的迴圈。

[13:23](https://www.youtube.com/watch?v=mpLhEa1VBoI&t=803s) 他說 gym 現在可以看成 Casco 的一個功能，用規格做出很獨特的功能，是今天的世界。正在移過去的世界是：人少、人才密度高的團隊可以贏過很多大組織。突圍的新創一直如此，現在更明顯。贏過大團隊的辦法，是把心態從做個別功能，轉成做會讓功能隨時間變好的 reinforcement loop。例子是 agent 在做滲透、試著利用一個系統時，覺得那裡有東西，但沒有對的工具。它會踢起另一個 coding agent，發現工具有缺口，趕快做一個新工具，放進下一次部署。下一個客戶來、再測的時候，agent 的能力變多了。要用自己的 agent，讓產品每天自己變好。人睡覺時產品在變好。小團隊因此能贏過整個工程組織。這是接下來幾年會看到的範式。現在這些他們自己扛，也許還缺一個圍繞它的開發框架。Simon 說，人比較常想應用怎麼變好，比較少想工作流程、東西怎麼被做出來。

[16:12](https://www.youtube.com/watch?v=mpLhEa1VBoI&t=972s) 他不認為規格會取代 live coding。手寫 code 也會留下。以後不會回頭說只該做規格、或只該 live coding。新範式是讓開發者留在 flow 裡：鎖定時，用一種有生產力、也平靜的方式走向結果。現在還手改，常常是因為腦子在拆一個演算法問題，要手動改出那種前所未有的優化。Live coding 他覺得會變成最快試新點子的方式。先給客戶看，再灌水泥把功能鎖死。多數 Y Combinator 新創，在想法定下來之前，已經做出值得一間公司的 code，因為實驗快得多。他看過有人在給客戶 demo 時現場 live code 新功能：這是不是你要的，可以排進以後的路線，當下造出新機會。客戶幾乎也可以說我想要什麼，甚至自己 live code 一個「那這個呢」。Simon 說設計團隊覺得自己成了瓶頸，工程給他們 Cursor 之類的工具，他們就能把設計做成工程和其他人看得懂的原型。René 說這把地板抬高了：軟體有一個已經很好的最低線。他們自己的安全工程師一輩子用 Python 寫 exploit 腳本，產品幾乎全是 TypeScript。他們看見產品缺口，可以先做原型給工程團隊，再由工程把它做成能上線的東西。跨職能的人開始說同一種語言。地板是 vibe coding 讓不是工程師的人進得了 POC。天花板是用自然語言把想要的東西寫得更緊，讓結果更可預測，再加上驗證，才信任得了輸出。那是工程師在 vibe coding 裡缺的。

規格和 live coding 會並存。手寫留下的，是腦子已經拆開的演算法問題。

## 一行壞規格，會變成一百萬行壞 code

[21:38](https://www.youtube.com/watch?v=mpLhEa1VBoI&t=1298s) 什麼叫好的 spec，他先講試過、但沒成的使用者體驗。他們試過把規格對齊到 end-to-end 測試：每一條 spec 對一個測試，測試寫好了，就讓 vibe coding agent 對著那些測試跑到通過。若規格裡說的都為真，就該有一個測試讓它為真。實務問題是，沒弄清怎麼讓規格和 code 一直同步。一對一很難，因為語言沒有邊界，code 的路徑很具體。規格會重疊、會衝突。一條說使用者邀請只給 admin，另一條說只給 member。雙向同步尤其難。那個想法在紙上和 demo 上看起來好，實作上不行。LLM 跑得更久，體驗不再愉快，而開發者想留在 flow 裡。

[24:09](https://www.youtube.com/watch?v=mpLhEa1VBoI&t=1449s) 他很喜歡一場字幕聽成 Dex Horfee 的演講，談 coding agent 的 advanced context engineering：agent 怎麼管自己的 context window，最後才寫出高品質的 code。先研究、弄清終端使用者要的結果，再寫幾乎像設計文件的東西：系統該怎麼實作、哪些因素重要。拿那份設計去做出實作計畫，然後寫 code。那個人說的、他覺得很相關的是：研究階段的 user story 或規格裡有一行是壞的，會引出一千行壞的設計；一千行壞設計會引出一百萬行壞的 code。時間花在哪、context 怎麼管，非常重要。網路上有個迷因：主管說去幫我做這個網站，不要有 bug，然後就走了。那不是現實。大部分時間是在想。好的工程不會直接跳進 code。他共事過最好的工程師，總是先問終端使用者的結果、要推動的業務結果、系統裡的限制。他會花時間把 user story、限制、以及現在的夠好和未來的夠好攤開。可以用 Claude 或 ChatGPT 來回做。他常常發現，問 Claude「這份規格裡我漏了什麼」很有用。會冒出一些走到實作才會碰到、自己忘了問的問題。終端結果和限制想完，再請 Kiro 或字幕裡的 Code Layer 做設計或實作計畫，計畫會更細、更精煉，因為 context 管得更好，做出來的 code 也更好。他說可以一次做出一萬行、而且能用、人願意收的 PR。

自檢很簡單：vibe coding 時，模型總說你完全正確。做規格時，它會問硬問題。

[28:56](https://www.youtube.com/watch?v=mpLhEa1VBoI&t=1736s) 自檢的方式是：vibe coding 時，LLM 總是說你完全正確。做規格時，它會問你必須弄清的硬問題。你想被放在有未知、被問硬問題的位置，而不是「你說得對，我就照做」。現實裡只會同意你的人，對你要推動的結果通常不是最有生產力的。Simon 覺得 LLM 問人自然不會問的問題，有時比人還好，因為人的焦點停在規格的某一段。

## 去吃午餐，網站自己用舊憑證上了線

[30:46](https://www.youtube.com/watch?v=mpLhEa1VBoI&t=1846s) 安全要放進規格的哪裡，他從 Kiro 很早的原型說起。那時還沒有工程團隊，他自己用膠帶把東西黏起來，不是後來出貨的產品。他寫了網站該怎麼走、長什麼樣、放在哪。他在 AWS，所以該放在 AWS。然後讓它跑，自己去吃午餐，電腦留在公司。回來時終端機爆了。他發現它從來沒有他的 AWS 憑證，部署本該走不通。可是有一個連結，網站在線上。它找到一條路：電腦上有一份很久以前、完全無關的開發環境留下的憑證。它搜過檔案系統，把那些憑證接進新專案，部署了一個網站。他的反應是這很酷，也很危險，這是 AGI 的樣子嗎。幸好當時只是開發用憑證。它沒有把憑證提交進 git。它是複製之後，加在 CDK 的部署指令前面。更糟的是，那些憑證進了 bash history。他幾乎生不了氣，因為它真的找到一條路。LLM 到達答案的方式很多。Simon 把它比成 WAF 那種：解法若是無限的，規則會跟著很多因素變，很難事先寫死什麼可以、什麼不行。

[32:58](https://www.youtube.com/watch?v=mpLhEa1VBoI&t=1978s) 這讓他想，團隊開始每天 ship 幾萬甚至百萬行的 PR 時，安全意味著什麼。他查到 LLM 生成的 code，語法正確從大約 17% 走到上次他們看時的 98%，幾乎是 100%。安全基準卻是平的，還略往下。於是我們活在一個寫出指數級更多 code、安全姿態卻沒變好的世界。產品表面滿是洞。誰去找、誰去修。Code 太多了。所以他去做 Casco：在幾百萬行不斷 ship 的時候，哪些漏洞對你真的要緊、哪些真的可被利用、該專注哪些。

[36:16](https://www.youtube.com/watch?v=mpLhEa1VBoI&t=2176s) 軟體開發的角色在經歷技能的壓縮。兩年前叫工程師在沒有設計師的 Figma 或線框時做 UI，會覺得難看、不好意思給客戶。那變了。人通常更會審查，而不是從無到有創造。看一件東西好不好，比照著別人畫的精確做出來容易。設計如此，產品也如此：有產品判斷力的好工程師，因為有時間，能做更多。安全也會這樣，但慢一點。靜態分析該是基線，很多 GitHub 整合開箱就有，開關很容易。安全不是單純的軟體工程問題，也不是單純的安全工程問題。不能孤立看，要放在業務脈絡裡。隨機掃你公開的 URL，會標一個公開的照片網址是錯的。若這是 Google Photos，而你有意把照片公開，那是業務決定。今天的安全技術缺語意，於是一堆誤報、吵鬧的警報，人被呼叫，工具卻不知道這件事按設計就是這樣。安全壓進軟體工程會發生，但更慢，因為還得把業務脈絡、安全範式和軟體工程範式綁在一起。他建議做規格的人，在 stack 裡放一份很簡單的存取控制說明，字幕聽成 access control.env：終端使用者該做什麼、有哪些角色、這些角色該做什麼。實作完，對著這些規則檢查有沒有被影響，標回來，或帶著這些再實作一次。這一點語意，就能讓 LLM 幫你做出更安全的軟體。

安全不能孤立看。公開的照片網址，在 Google Photos 裡可以是有意的業務決定。

## 七家裡的十六家，三十分鐘

[40:17](https://www.youtube.com/watch?v=mpLhEa1VBoI&t=2417s) 他在 Y Combinator 春季班裡，三十分鐘駭進 16 家已公開上線的公司中的 7 家。那一批超過 95% 的公司說他們用 AI 幫忙寫 code。他說若你不用 AI，大概走不遠，很多速度從這裡來。Demo day 上，一起開始的人多數 ARR 是 0，很短時間裡到了幾十萬美元，以前聽都沒聽過。大組織還會有複利。但安全上，過去小團隊做不出那種要很注意安全、又那麼關鍵的軟體。現在不是了。他們那批裡有公司在結束前已經和美國政府有生意，或在跟金融機構打交道。人少、密度高的團隊會做出極度關鍵的軟體，安全就重要了。這 16 家都在用 AI，但生命週期不同。有的軟體已經做了一年，然後用 vibe coding 加一個新功能，就造成新的漏洞。也有人幾乎是對 LLM 說請幫我做這個功能，希望它成。安全不是 80% 的 code 以前手寫、審查過，未來一年就安全。多一個功能、範式稍有不同、存取控制和設定不同，就是一個全新的、可能被利用的漏洞。軟體量指數增加之後，最好的安全測試是從攻擊面看：盡量去駭，找出真正要緊、真正可被利用的。再饋回開發週期，邊走邊補。他覺得這只是開始。大公司若更大規模採用 AI、卻沒怎麼想安全，會看到很嚴重的大型入侵。那時整個產業會重新看，在每天幾萬行 PR 的時代怎麼做安全。

[44:48](https://www.youtube.com/watch?v=mpLhEa1VBoI&t=2688s) 該擔心的是新漏洞，還是舊漏洞變多。兩者都是。賭 code 會變少，是在賭過去。Code 會指數變多，今天已知的漏洞也會變多。第二，軟體會從確定變成隨機，因為整個系統都在用 LLM：解鎖使用者功能、做前面說的強化迴圈、做業務流程。和 LLM 工作會有安全問題。可以誘它去叫一個範圍沒設好的 tool，資料就有機會被帶出去。他點了 Sam Wilson 常講的 lethal trifecta，字幕是這個名字。更重要的是這兩件事現在疊在一起：code 指數變多，行為又比以前更不確定。

[46:54](https://www.youtube.com/watch?v=mpLhEa1VBoI&t=2814s) 開發者該改的，第一是有安全意識、懂好的安全設計。想得對，code 會跟著對。一行好的，引出一百行好的實作；一行壞的，引出一百行壞的。把存取控制矩陣寫下來。寫下你期待的 rate limit。就算不知道，也可以問 Claude：這類 API 在產業裡可接受的 rate limit 是什麼。很基本的東西放進 markdown，放進給 LLM 的 context，就已經幫很多。另一件是像 Casco 這樣的工具會變多。目標是讓軟體不費力地安全。Code 進了 preview branch，立刻被安全測試，立刻知道為什麼有漏洞，立刻餵給 LLM 去補。三十分鐘他覺得還不夠短。他每天想的是把迭代壓到能自然嵌進開發週期，成本也要低到它就是系統的一部分。不然就做不到讓所有軟體不費力地安全。軟體變得這麼容易做，更放大了對這種自主的需要。

[49:08](https://www.youtube.com/watch?v=mpLhEa1VBoI&t=2948s) 賣 B2B 軟體的人，合規常常要求做滲透測試。多數框架說一年一次就夠，然後你就通過了。這必須改，因為軟體做得快得多。測的那天安全，隔天開發者可能加了你不知道的功能，或在實驗。開發用憑證突然出現在不該在的地方，字幕聽成 in fraud。變化快到一年一次管不住。買方的 CISO 該開始要求更頻繁的滲透測試。你買下軟體時，它可能已經變了。第二，攻擊面的測試要週期更短、成本更低。CISO 喜歡買滲透測試，是因為它被當成你能得到的最高品質評估。認真的一次、不是隨便一個自動掃描器，大約一萬美元，對世界上多數公司是付不起的。每次軟體一改就付一萬，行不通。單次成本要大幅降下，讓它變成每天的開發週期。也許一個月付一筆小的訂閱，它告訴你找到新漏洞、已經修了、這是 PR。Simon 說他在 Snyk 時，很多人說有做 pen test，頻率是每六個月、每年、或大版本。但他們每週都在 ship。新 code 誰測，沒有好答案。

[53:00](https://www.youtube.com/watch?v=mpLhEa1VBoI&t=3180s) LLM 應該更安全地生成 code。今天有 context 問題。把存取控制放進 codebase 很重要。也有模型訓練截止之後才發現的新漏洞，LLM 還不知道。那是一塊會繼續存在的問題。他不認為只有這個就夠。問任何安全工程師，他們看你的軟體、問一串安全問題時，第一件事是畫一堆盒子和箭頭，然後看這些箭頭在做什麼。始終是東西怎麼連、後面的業務語意是什麼。那些多半不在你的 codebase 裡，甚至不在你的 CI/CD 裡。你可能在叫一個會在你不知道的情況下、在底下自己改變的外部服務。所以在建和發布的當下，你其實不知道軟體真正的安全姿態。因此他認為攻擊面的安全會變成往後評估姿態的主要機制。自動做滲透、帶進業務語意和 context、持續跑、把成本降下、跑得更快，這些忽然因為生成式 AI 做得到。過去被認為最好的評估方式，會變得大多數公司和大多數軟體團隊用得起。他相信可以活在所有軟體都不費力地安全的世界。

[55:35](https://www.youtube.com/watch?v=mpLhEa1VBoI&t=3335s) 安全工程師的角色，會像軟體工程經歷過的那一波。GitHub Copilot 出來、然後是 ChatGPT 的包裝、然後是第一批 agentic IDE，當時很多情緒是不再需要那麼多軟體工程師，管理者就能做。現在知道不是那個世界。判斷力高、非常好的工程師生產力高了很多。在問的是中階管理還需不需要。腳本和兩三年前那些東西剛出來時的情緒相反。安全現在感覺一樣：問題冒出來，有人說也許不需要個別的安全工程師。那不會是我們要活的世界。會發生的是安全工程師去做他們真正喜歡的事。今天他們花在追誤報的時間，多過花在修真正的安全問題。整天把你相當有把握不是真問題的警告，每個花四小時做 triage，不是有成就感的工作。讓他們興奮的是做安全研究、把線索拆開、發現可以怎麼利用、找到另一個漏洞、趕快去修。當偵探比較有趣。或者做更策略的事：怎麼把安全帶進 platform engineering，讓整個組織一致。警報無關緊要、某個 header 沒設但其實完全不能被利用，那些苦工會消失。人去做喜歡的事，安全才會被烤進組織，對其他人變得不費力。

[58:33](https://www.youtube.com/watch?v=mpLhEa1VBoI&t=3513s) 產業通常要一次大駭或大型入侵，才認真投時間和錢。他認為今天最大的安全風險其實是流程風險。團隊被賦予權力，也該如此，在很短時間裡交付前所未有的功能和 code。但沒有給他們對的工具，讓安全是烤進去的、不費力的。組織裡常把安全和軟體工程看成會帶來官僚、叫你做一堆工、一半問題是誤報的那些人。那是流程失敗。每個人該重新評估：安全和工程是不是在同一條水道裡一起游，兩邊都能更快，而不踩到對方。意思是把更多業務脈絡帶進安全，給不會丟出一堆無關誤報的工具，也讓安全工程師能更直接把變更貢獻進正在 ship 的軟體。想看自主安全測試，他說去 casco.com。

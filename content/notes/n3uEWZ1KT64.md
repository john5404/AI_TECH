# Stop Maintaining Your Code. Start Replacing It

Guy 在 AI Native Dev 訪問 Chad Fowler。Chad 現在是 Blue Yard Capital 的 VC，帶過 Ruby 最紅時的 Ruby Central，做過 Wunderlist 的 CTO，賣給 Microsoft 之後在微軟幾個部門當過 CTO。片長約 62 分鐘，英文自動字幕。這份筆記依英文原稿整理，專有名詞保持 English。字幕把 Wunderlist 聽成 Wunderkind，把 Tessl 聽成 Tesla、Tessell。Blog 在 aicoding.leaflet.pub，Guy 說網址不好找。

- 原片：[YouTube](https://www.youtube.com/watch?v=n3uEWZ1KT64)

## 一句話

Code 是負債，系統才是資產。Phoenix architecture 把規格當成要保存的東西，code 當成 build artifact，不斷換掉每一塊，不換掉系統的形狀。目標是 production 上跑 AI 生成、人沒審過的 code，因為人一定會走容易的路，所以要把系統做成走那條路也沒關係。採用會在新專案上很快，在沒人懂的舊系統上慢得驚人。

## 先學會反覆殺掉，才敢改

[3:41](https://www.youtube.com/watch?v=n3uEWZ1KT64&t=221s) 二○○○年代初期，他的顧問和全職工作常常是把一套還在做事、但跟不上技術或業務要求的系統安樂死。他累了。自己花那麼多時間、力氣和情緒做的系統，為什麼五年就死。人照顧自己並不好，人還在。軟體花很多錢，仍會腐壞，被自己的重量壓垮。他想的是系統能不能活得比人久。

[5:17](https://www.youtube.com/watch?v=n3uEWZ1KT64&t=317s) 一個洞見他多年沒怎麼做。九○年代大家為一台伺服器的 uptime 高興。他記得一台 Sun 伺服器兩年沒重開，當時覺得驕傲，現在想起來可怕。若你想能改，就得一直改。不練習改變，系統就無法前進。所以反覆殺掉，讓自己習慣殺。他從基礎設施開始。現在 immutable infrastructure 是老話：永不修改一台伺服器，永遠換掉。實體硬體做不到，容器和當時的 EC2 做得到。目的不只是敏捷，是你真的知道伺服器掛了能恢復，因為你故意一直在做。Guy 說改不了，就是你其實不懂這個系統。一直改，你就不得不懂需求。軟體也該如此。大約十五年前，一直丟掉 code 太貴。

[6:48](https://www.youtube.com/watch?v=n3uEWZ1KT64&t=408s) 他想的是 disposable software、immutable code。一個工作單位一旦寫下，不再修改，直接丟掉。單位要小、有邊界，它該做什麼可以平凡地懂，因此可以安全換掉。對上 LLM 生成的 code，這個想法才扣上。Guy 說伺服器本來就不總是照你要的方式走，世界不是確定的。DevOps 的 cattle 對 pets：你認得那台機器的名字和 IP，自己裝過，會依戀。Immutable 之後你不能依戀任何一個正在跑的實例。Code 也一樣。開發者幾乎崇拜 code，忘了 code 不是要做的東西，只是實作。

## 一頁以內，三個月換掉七成

[9:29](https://www.youtube.com/watch?v=n3uEWZ1KT64&t=569s) 在 Wunderlist，第一條規則是：用任何語言都可以，只要不要比這個大。大約編輯器一頁。眼睛好、字小，可以多一點。他們做很激進的 microservices。呼叫慣例一致，離線的 mutation 有一套做法，REST 和 CRUD 有一套做法。Code 都很小，所以換得掉。他用 Haskell 寫過一個服務，全團隊只有兩個人願意看。他喜歡。問題是改得太少，底下的 build 系統過期。被收購之後無法再編譯。它還在跑，很好。Toolchain 壞了，因為沒有一直改的紀律。後來有人一個下午用 Go 重寫、部署，沒問題。

[11:11](https://www.youtube.com/watch?v=n3uEWZ1KT64&t=671s) 另一件是 Wunderlist 一次重大發布，技術上的王冠。當時數百台伺服器跑很重的 Ruby on Rails，因為那是他們會的、一致的選擇。之後大約三個月，換掉 codebase 大約 70%，改成 Clojure、Go、Rust 等。他記得跑起來的成本大約是上線時的 25%，因為那些跑 Ruby 的小系統換掉了。呼叫慣例一致，好插。那是第一次試 disposable code。Guy 說模組化可以回溯到 Java 的 design patterns，但我們仍常把模組裡的 code 本身當成珍貴的。

## 規格是源頭，code 是編譯出來的

[12:31](https://www.youtube.com/watch?v=n3uEWZ1KT64&t=751s) 一致的介面、CRUD 怎麼想，不限於 REST。這些約束讓你懂元件怎麼互動，元件就可以用任何語言或框架實作，系統怎麼運作仍在。他常跟 Wunderlist 說：我們有的 code 是負債，我們在建的系統才是資產。Phoenix architecture 把這寫死。他還有一個尚未釋出、以後會開源的專案就叫 Phoenix，是這套想法的實作。系統裡任何軟體都該想成 build artifact。Makefile 或 Ant 從一個頂層資產往下編，依賴變了就讓對應的目的碼失效，只換該換的路徑。頂層通常是 Java、C 或 Rust。Phoenix 說頂層該是系統的 specification，code 只是實作細節或建置產物。名字來自鳳凰：毀掉、重建、從灰裡起來。架構是不斷換掉每一塊，不換掉整體。你需要一致的形狀和呼叫慣例，生成式地跟系統互動。想安全、快速地改，而且把改當成跟系統相處的方式，系統就得對改變很友善。

[15:16](https://www.youtube.com/watch?v=n3uEWZ1KT64&t=916s) 他從 extreme programming、Kent Beck、早期 Agile 拿教訓：難的事就一直做。測試難就一直測。Code review 難或貴，就用 pair programming 一直做。改變若難，就做進系統，讓你沒有選擇，只能一直改。你也可以永遠不看 code。目標是把某種 AI 生成、人從未 review 的 code 部署到 production。六個月前這聽起來更瘋。現在很多人在做。大型企業系統或很複雜的舊系統，當然還做不到。為什麼這是目標：因為這會發生。不是因為技術趨勢，是因為人的行為。現在太容易了，人總是做容易的事。那就做一套系統，讓容易的事做了也沒關係。Guy 補：這也是機會。保持競爭力就是接上這件事，把人從方程式拿掉。他一兩年前說 code 會變成可丟棄的，不久前還被當成異端。大約兩年前。今天沒那麼遙遠。

## 夠用就鎖住，agent 做的決定比較好刪

[17:04](https://www.youtube.com/watch?v=n3uEWZ1KT64&t=1024s) Guy 問 spec 要多細，細到什麼時候就變成另一種你寫的 code，上面只是模板。答案每週在變。Guy 談這件事至少兩年，表示大約四年前就在生成 code 的挫折迴圈裡：一下子魔法，一下子又不是。Chad 上次有那種感覺是九月或十月的工具。現在沒有了。今天用很少細節就能 one-shot 很多。他的做法是迭代到看見東西改變。他在重啟一個 IRC 網路，沒有 one-shot，裡面有很多技術，叫做 Freak。Spec 沒有很高的具體程度，但迭代到夠。他知道夠，是因為軟體裡看得到證據。他比成二○○○年代初期 Java 的 Naked Objects：生成物件，UI 即時出來，跟客戶坐在一起看資料模型，而不是長專案。

[19:11](https://www.youtube.com/watch?v=n3uEWZ1KT64&t=1151s) 問題是，要在時間裡活過改變，不能一直把整套重新生成。使用者會用的介面每天因 spec 改了、UI 重想了而變，即使明天更好，也不行。技術地基也不該一直變，因為它們可能是錯的。IRC 最底層他想很快做對、釘死，除非有錯或要升級協定。最好有一套可以迭代的規格，用建置圖連回生成的 code。依賴樹前面不變，它就不必變。開頭協定可以亂改，然後鎖住，因為連當初夠模糊、卻生出夠好東西的 spec 也不再改。聽起來可怕。然後你只在該大量改變的那一層工作。他記得一個詞叫 pace layers，不記得誰造的：架構不同層，改變的速度不同。

[21:14](https://www.youtube.com/watch?v=n3uEWZ1KT64&t=1274s) Guy 說他們在 Tessl 曾有一套系統框架，後來擱下，專心做 context。Spec 可以在任何解析度。你用過、看過、覺得夠好，就祝福它。然後要的是穩定的再生。按鈕顏色你可以委派，但不希望每個版本換色。主題色全改了，按鈕才該跟著改。他們用 lock：把某個測試鎖住。誰做的決定也重要。付錢、脖子上的是人，那比 agent 當時做的決定更神聖，agent 的決定應該更容易覆蓋。Chad 說任何新語言都是在解 LLM 目前用白話還解不了的問題，然後語言會過時。他起初以為該用 Haskell、OWL、本體、靜態型別。其實都不重要。需要的是語言以外的 paradigm 和 pattern。

[24:28](https://www.youtube.com/watch?v=n3uEWZ1KT64&t=1468s) 他的 Phoenix 實作是從粗糙的人寫規格，煉成他叫 clauses 的東西，把 intent 正規化，再用密碼學雜湊一路追蹤。這給你建置系統，也給你出處：誰、何時、為什麼。對知道該再生什麼、以及怎麼從系統拿掉東西，都很要緊。生成太快會堆出一大堆垃圾。Agent 做的、不是人做的，大概可以刪，還有很多因素要查。Freak 上他不小心有兩個平行的 web app。一個是他迭代出來的好的，一個是 agent 自己決定要做、還被連到一些地方，他得移除。至少他知道哪個決定是自己的。要把人跟 LLM 的互動，在 code 被建的時候抓住，從 intent 對到可替換的實作單位，再生才是真的。

[26:24](https://www.youtube.com/watch?v=n3uEWZ1KT64&t=1584s) Guy 說人的祝福有三層。人明確下的指示。人明確 review，按了 yes，但你真的讀了嗎。以及完全沒有人，agent 自己決定。他們叫後面那些 shadow specs：你沒做、但已經替你做了的決定。Chad 喜歡這個詞。他承認自己現在大多是 shadow spec，指令又高又隨便，然後 YOLO。所謂明確 review 是掃過，覺得聽起來對，就換掉。還有兩層他不知怎麼命名：理論上你 review 過的，和從未呈現給你、你也沒祝福的。

## 編譯到系統的形狀

[27:36](https://www.youtube.com/watch?v=n3uEWZ1KT64&t=1656s) 他這週跟一位語言創新者談，沒問過能不能說名字。一致的呼叫、非同步的 mutation、是不是有 message bus，這些在他腦子裡是 Phoenix 要能動的條件。一生成就撞上：web app 要用哪個 MVC、哪種語言、哪個 runtime。他的結論是整個系統、任何生成的 code，都該先決定。今天最適合生成 web app 的框架，一個答案是 LLM 知道的，大概兩年前的 Next.js 或 React。他不喜歡說這個。那是目前權重裡的寵兒，歷史上的流行會留着。以後會鎖死，因為我們會一直再生它，它自己餵自己。他當年福音 Ruby on Rails，今天不會把自己綁死。Code 要正確、跑起來盡量便宜、盡量快。不必對人友善，不必時髦，甚至不必有 unit test，不必 peer review。用 Phoenix 時，你不該決定它生成哪種框架或語言。那也該能改。我們要編譯到的是系統架構：可插、可換的元件，因為形狀、呼叫慣例、一致性，也許還有某種型別。性質是它怎麼跑、元件怎麼互動，不是程式語言。

[30:45](https://www.youtube.com/watch?v=n3uEWZ1KT64&t=1845s) Guy 說自己在 Tessl 追 spec-centric 追很久。想法變了，也許是退步：從想用一種資料格式好好抓住 intent，變成想讓 agent 做良好決定。最好的開發者、以及未來的自己，不是要把歷史決定原樣復述，而是把智能和資訊合在一起，用對的 context 把重心放對。你在乎預算還是延遲，在乎函數式還是 Ruby，在乎安全到什麼程度，業務環境是什麼。約束有時包括必須用這種語言。在微軟裡若有人規定，這必須跑在 Windows 上。他仍希望這些有一種表示，但懷疑我們還不夠往前想。我們喜歡能代表穩健、有一點確定性的資料模型，真正要的卻是做好決定。Chad 說與其想 spec，不如想知識圖：這個人的價值、變異、intent。LLM 很容易從你身上挖。他在 Phoenix 的測試裡就是這樣，它會說你好像漏了這個。不變量、成功的指標，是系統的一部分。部署目標仍在：有時仍是 Windows app，有時仍是 Mac app。他會有一套自己的 pattern，套到原生 macOS、iOS、web、主控台的 TUI、伺服器、分散式系統。編譯進去的架構可以包含平台。他多半對平台和語言不可知，再把不同約束加進系統。他說這很揮手，因為我們還沒到。也許只有資料底層，app 即時長出來，可以是畫面，也可以是跟 LLM 的對話。

## 可改的軟體，和不必每次從 kernel 做起

[35:03](https://www.youtube.com/watch?v=n3uEWZ1KT64&t=2103s) Guy 喜歡個人化的軟體。他用的工具他喜歡，不想 vibe code 一個替代品，付一點錢沒關係。挫折是不能改。缺一個功能就煩到想自己寫。他想像作者交出軟體時，定義哪些可以動、哪些是本質、必須嵌在裡面。Chad 若要不同的 UI 或配置，可以改。這套東西能不能就是你發給使用者的那份軟體。Chad 從資料模型往上想，來自 local-first。Ink & Switch 寫過 malleable software。資料在你的裝置上，應用跟資料互動，用 CRDT 同步。若有一套共通事物的共享資料模型，會議、任務、郵件，任何人都可以寫跟它互動的軟體。不在雲上、不必部署到私人伺服器，在本地跑，新介面就是假設。一家公司寫了你開始用的軟體，例如 Linear，它本身是 local-first。別人可以很容易寫第二個介面，Linear 擋不住，也不會想擋。他承認自己可能還在追重用和 semantic web。若產業或至少一些聯盟把 local-first 當預設，共享 schema、JSON Schema、schema.org，新的 vibe coded app 就假設這些在。他不認為該限制你能改哪一塊。IT 的角度他懂：有人打來說我改了所以壞了，那很糟。Guy 說重點不一定是准不准改。Wunderlist 裡深想過的功能、視覺、怎麼把待辦做對，他不想丟掉，只想加一個功能，加的時候降低風險，保住 Chad 的判斷。大軟體一直這樣，CRM 讓組織自訂。再生軟體立刻會被反駁：不能整份重生成，使用者不會用。若 UI 裡也能有 pace layers，某些面板永遠可擴，就說得通。這是八○、九○年代企業軟體的教訓，通常不是為了保住體驗，體驗通常不好，而是每個人都要自訂。

[40:54](https://www.youtube.com/watch?v=n3uEWZ1KT64&t=2454s) Guy 喜歡重用。就算 LLM 和 agent 能很可靠地從零做出一切，那也極度沒效率。做一個待辦不該去建 kernel。系統之間的熟悉、企業裡的一致、一個 bug 不必每個人各刮一次。幾週前他跟 Radical 的一位創辦人談。Radical 是開放、分散式的 GitHub 替代。那位現在做 Radiant Computer，從地面做作業系統，想很多 LLM。他寫過：縮小你跟作業系統互動的表面，對 LLM 的效率有好處。預設私人，可以跑本地模型。本地有電力限制，模型不如前沿。從開放的場地做出一種受約束的語言，表達系統該做什麼，LLM 就很容易互動。每個系統都可以隨時間從開放凝成這樣。也許這就是未來的程式語言。Guy Steele 1998 年左右在 OOPSLA 的 Growing a Language：他從零定義這場演講能用的英語子集，教訓是先長詞彙和地基，才能表達。每一代他都再介紹一次。在這種快速造軟體的環境，應該能造出大量可重用詞彙，並且分得清對我、對組織、對全世界可重用。理想是有市場或分享的方式。Tessl 早期也想過：做一個 HTML 轉 markdown，聽起來規格很簡單。哪一種 HTML、哪一種 markdown、哪個瀏覽器。這些會隨時間腐爛。

## 測的是程式員，不是只測系統

[45:08](https://www.youtube.com/watch?v=n3uEWZ1KT64&t=2708s) Guy 問耐久性。一切都在再生，學到的、偏好、分布在累積。Chad 寫過 evaluations 才是真正的 codebase。他說這個詞可能超載，聽起來像 LLM 或 ML 裡的 evals。他也是那個意思，但更是不變量、指標、約束。電商裡一筆訂單的 CRUD：正確性、下單時期望的副作用且能量到、速度、記憶體、IO。這堆東西是知識圖，不是 spec，可能很難讀，我們大概也需要工具。它抓住業務 intent 和技術 intent。他舊的、現在仍會用的天真做法，是跟團隊談 mean time to resolution，而不是 mean time between failure。不要那麼擔心事先測完一切，要把各層儀器裝好，包含業務和技術，並且容易回滾。他改軟體的方式是在 production 裡 YOLO，然後立刻看即時指標和系統的真實狀態。快速變化的系統，這至少現在還有一部分成立。測試可以在之前也可以在之後，現在用 AI 可以很快做。Guy 講過鎖住的測試。不然 spec、code、測試不一致時，誰對。Chad 現在想的是至少有一層測試全部鎖住，不分成鎖和不鎖。他當然不再寫測試，也不寫 code。他明確跟 agent 講測試的目的，目的來自對系統的當下理解。在 IRC 上，他會叫它找某一類 bug 可能沒想到的 edge case，多個模型、多次。他 review，叫它做出能發現 bug 的測試，做到測試一直過，這一層一直鎖着。再往前是 spec、正規化的需求、不變量這條鏈，才能更自動地推理。現在他認為指標加測試就夠。

[49:36](https://www.youtube.com/watch?v=n3uEWZ1KT64&t=2976s) Guy 很相信 evaluations。Tessl 第一年他想的是測試會留下、會被鎖住，那是功能的行為。現在他更想做好決定。他要的測試比較是 agent 的行為，不是建出來的系統。他覺得槓桿更高：你在做你要的開發者，不是只做你要的系統。那個開發者更能以高保真做出系統。你仍得蒐集、累積、策展那些 evaluation，我們還不知道怎麼處理量。但 evaluation 講的是較高的話：這件事發生時，開發者這樣行為。規格本身是可塑的，因為它們跟着模型變。你對 Haiku 的指示，和對 Opus 的不一樣。Opus 很有創意，有點聰明過頭，不聽指示。Codex 較不創意，較服從。Gemini 有自己的長處。從程式語言走到 programmer language：你用來指示 agent 的語言，對上你用來定義系統的語言。他一週前為了額度從 Opus 換模型，挫折了一天，隔天早上才發現。感覺像回到 2025。他怪模型，大概該怪自己跟模型互動的方式。

[52:23](https://www.youtube.com/watch?v=n3uEWZ1KT64&t=3143s) Chad 說這跟他想的相反。他假設程式員現在是白痴，以後是天才，而且依模型以不同速度進步。他傾向做一套生成系統，也許那就是程式員，但不是一個智能。最笨的 LLM 和天才都能插進去，結果仍是他覺得信得過的，而且跟底下的模型脫鉤。模型會一直變好。他們談的這些最後也會過時，因為未來某點，幾個 AI 模型的對話會比這集更有智能。Guy 說這份工作兩者都要。團隊裡需要那個智能程式員的輸出定義，抓住系統是什麼，讓程式員可以比較不智能，也讓大家對齊系統做什麼，而且愈來愈對 LLM 友善。另外還要開發者的指示。他說 context engineering 就是這個。Agent 會處理 SDLC。開發者該坐在 context development lifecycle 裡。Context 是操作手冊：agent 該怎麼行為，你的 intent 是什麼。他的朋友 Jess Martin 在做 context library，把這些決定自動累成 context，目標是你睡覺時 agent 整晚跑，因為系統裡的 context 夠，它們做的決定大概是你會說的。Guy 的不同看法是：觀察我、懂我今天做什麼，但今天的我不是一年前、更不是十年前。Context 是你開發的東西，不是一個時點。曾經流行「學會我的 codebase」，然後大家發現 codebase 裡很多東西不想被複製，大部分是累積的垃圾。Garbage in, garbage out。有用，但你要開發的是實踐。

## 新公司今天就能做，大企業會很慢

[55:38](https://www.youtube.com/watch?v=n3uEWZ1KT64&t=3338s) 從今天的軟體走到這種不可變、可再生的 Phoenix，採用路徑會又極快又極慢。慢的是我們得意識到，有些系統開發了幾十年，沒有人懂。前沿的人大多還沒在想它們，有些人開始了。他若現在創公司，今天就會這樣做。Greenfield 現在就是答案。他知道有人在不同程度地做。他也知道相當前傾的公司裡，開發幾乎沒碰 AI，在抵抗。很大一部分開發者害怕，或根本沒在看。Java 來的時候他們不想做 Java，也不想做 Ruby 和 Python。多數人想工作有趣、做少一點。人就是人。組織是向後的、慢的。多數人不知道怎麼處理，會去看大型顧問公司。最大型企業裡，AI 生成的軟體從上到下大規模採用，會是很長的時間。未來一兩年仍該有很多有趣的工作。以 VC 的角度，他談的公司都在抓 intent：spec 對上 intent，intent 從哪來。可以從幾十年的公司郵件挖，從版本控制和專案管理挖。先弄清舊系統的 legacy intent，再用 strangler fig 把應用一塊塊拆開自動化。一邊快到離譜，一邊慢到意外。

[58:38](https://www.youtube.com/watch?v=n3uEWZ1KT64&t=3518s) Guy 說 Tessl 選擇訓練開發者、而不是只定義系統，有一部分是因為那在模擬人的行為。那些脆弱的老系統裡仍有人在做決定，公司還活着、還在成長、還在改。概念上訓練程式員是更高、更遠的一層。某些方面它更近：更好的程式員可以幫你把系統做得更好，即使沒修好脆弱，也沒讓系統從灰裡起來。Chad 同意。他說他們談的一切某時點都會過時。會有一波，用今天談的方式解決，完全有效，有用很久。產業快到我們會覺得現在談的很傻，但它仍有用，只是不再是未來。今天快到可以處理這些不同階段。公司的路線圖可以說等它變成問題再處理，然後下週整個新版本。當軟體開發者是奇蹟，也可怕。繫好安全帶。想找他談投資，他說 Blue Sky 最好，帳號是 Chad Fowler.com。

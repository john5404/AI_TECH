## 一句話

Eval 不必拖慢進度。憑感覺看幾次輸出很快，但對不齊、也不代表 production。追求完美的 eval 則永遠做不完。Tessl 走到的地方是：輸入只要有代表性，指標只要方向對，用來爬山。再往上是 product-led eval：先跟團隊講好這版要服務誰、要會哪些操作、發射的門檻是什麼。Eval set 變成 AI 功能的 Figma mock。模型還不夠好時，就照錯誤來設計產品，而不是等魔法。

## 憑感覺，然後又衝到另一頭

[0:12](https://www.youtube.com/watch?v=oXTr1yVtH5E&t=12s) 他要說的是 Tessl 的 eval 過程怎麼演變，以及做 AI 功能時很常見的幾個階段。特別是 code-centric eval 有自己的細處。他想說服人：eval 不是「還得補測試」那種擋路的東西，而可以是很快的迭代，像 flow，把整個團隊拉進來。

[1:10](https://www.youtube.com/watch?v=oXTr1yVtH5E&t=70s) 幾乎都從 vibe-based eval 開始。開發者、產品經理，習慣做了就看它動不動。寫一個 prompt，也許從 Hugging Face 拉一個 model，跑三、四次，野心大就十次，看感覺對不對。快。但不穩定：同一個人、同一份輸出，不同時間、趕不趕，heuristic 不會每次一樣。更難的是跨團隊、跨時間對齊。改一版功能時，你真的有仔細跟上次比嗎，隊友也一樣嗎。五到十個例子抓得到很淺的問題，例如格式很糟，但代表不了 production。也難行動。你要 Fibonacci，它給遞迴。是只對 Fibonacci 這樣，還是它一般偏好遞迴、而你不要。沒有更廣、更有代表性的集合，就不知道修哪。像在做平台，不是做單一功能。

[3:34](https://www.youtube.com/watch?v=oXTr1yVtH5E&t=214s) 例子加到二十個、指標想標準化，手看就慢了。讀 code 本來就慢。每次改功能都要從頭讀十到二十份新實作。第一次 debug 也許還好。第十輪、三天後、下週回來，會覺得若早自動化就快得多。這回到軟體開發的老循環：會重複發生的事就自動化。

[4:32](https://www.youtube.com/watch?v=oXTr1yVtH5E&t=272s) 下一階通常整個翻過去。讀很多文章和論文，變成對品質著迷。要幾百、幾千個真正有代表性的例子，每個輸入都剛好對，還要手調一個萬能指標告訴你對或錯。結果比以前更慢。手看的問題是例子多。把 eval 做到完美的問題是你永遠做不完，所以永遠不發射。五十個 code 例子再標上正確輸出，牽涉深的話要好幾天到一週。超過五十就失控。標「什麼叫對」時會發現沒有客觀的品質線。可讀性、註解風格都會有人不同意，就像團隊裡的 PR。等到把行長、註解方式一層層疊上，複雜到自動化只能靠 LLM judge。對 code-centric 的評測，那把很多做得到的價值留在桌上。

## 只要訊號，然後用產品把訊號排好

[6:42](https://www.youtube.com/watch?v=oXTr1yVtH5E&t=402s) 走幾輪之後，eval 是數字的遊戲。放掉「完全可控」和「完全不看、只憑感覺」。輸入不必完美，只要有代表性。讀起來真正好的也許只占 80% 到 90%，甚至 70%，裡面可以有雜質。指標可以會被鑽，只要方向對，能告訴你生成物哪裡對、哪裡錯。最後你只需要知道下一步做什麼、最低的果子在哪。這像是讓步，但若它只要把你往上推，就可以進一種只要有訊號就繼續走對方向的狀態。於是合成資料變得可行。LLM 可能在某些地方作弊，程式風格可能怪，大致對就夠。幾小時能拿到資料，不必幾週人工標註。診斷指標變成很小、很緊：有東西變了，或這個相對其他是 outlier。也不再問「這是不是最好」，而問「這是不是壞」。迴文偵測生出 400 行、15 個 helper，大概不好。最好的迴文偵測很難認，這種過長很好認。

[9:07](https://www.youtube.com/watch?v=oXTr1yVtH5E&t=547s) 指標切得太碎、輸入又有錯，儀表板會變成巨獸。訊號太多，怎麼前進。若回頭抽幾個例子看，就又掉回 vibe。Tessl 目前停在他們叫的 product-led eval。也許還有第五階，還沒到。先定義什麼叫好、什麼叫夠好、現在最該修什麼。它是疊在前一階上面：那些細指標、統計上夠好的合成資料，怎麼用來快走，並把整個團隊帶進來。

[10:33](https://www.youtube.com/watch?v=oXTr1yVtH5E&t=633s) 第一件是看對資料。先定義 input distribution。跟產品經理、CEO、lead，或團隊裡任何人，講清楚要支援哪些使用者、功能該好好處理哪些內容。要非常具體。做自動完成或 test runner，先問語言、是 unit test 還是 integration test，再往下：這版只測 library，並給出 15 個我們想能寫測試的 function 例子。然後是 operation taxonomy。這組 function 該能生成哪些測試：能不能 mock，能不能為檔案做 fixture。誘惑是說 Gen AI 幾乎什麼都能做。他要人切開、分類我們認為會生成的測試或操作。再把特定輸入配上預期的操作。之後才能問：哪些操作我們最差，某個輸入是不是特別差。那是 P0 還是 P1。也許 Python 比 JavaScript 重要，Python 的測試差就得跳進去，JavaScript 沒那麼差就可以先不管。

[13:29](https://www.youtube.com/watch?v=oXTr1yVtH5E&t=809s) 有了分布和分類，要生一些輸出，而且團隊每個人都做。這是產品探索。你會碰到描述使用者和「我們做這種 unit test」時沒想到的邊角：要 mock 一個帶 API key 的東西時怎樣；要生成的檔案格式對 AI 來說很麻煩指定，它常常在那裡錯。他建議每個人當一下這個產品的 LLM，生一點東西，弄清什麼難、什麼容易。

[14:19](https://www.youtube.com/watch?v=oXTr1yVtH5E&t=859s) 品質線要講得很具體，不是「應該很好」「不該犯錯」「體驗要愉快」。先同意這次的嚴謹程度。快速實驗、給三四個使用者看、或只是 demo，eval 集合 n 等於 10 也許就夠，只要大致合理。要上 production、業務關鍵、是核心差異，也許要一千、兩千，或一百。事先對齊。Tessl 很痛的經驗是沒對齊：團隊覺得可以上了，然後有人說不信任這份 eval，看到一兩則不好，問為什麼不修。五到一千都可以，只要同意大小、蓋到對的概念和輸入。接著看輸出。用分布和分類做合成，自己標一些，再多看。看到壞的，就想怎麼偵測。不必一對一。這則特別長，也許加一個生成長度。變數都是三個字母以內。不能編譯，那個明顯。久了會有門檻：function 一百行或更長，大概是壞的生成。

[17:03](https://www.youtube.com/watch?v=oXTr1yVtH5E&t=1023s) 還要同意 P0。用使用者和內容、以及操作分類來定義。哪些不能錯。不是全球意義上的不能錯，系統是機率的。意思是：不能有已知的這種例子。看到這種輸入配這種操作得到壞輸出，就要放進 eval set 並修掉，不能帶著已知的例子發射。然後坐下來講發射條件：我們生成的 package 大致有這個比例要低於這個檔案數，所有 P0 必須解決。Eval set 和指標合在一起，要讓大家有信心發射。達不到，eval set 就還沒做完，得加例子、提高嚴謹、加指標，直到每個人都同意。

## 模型到頂時，照錯誤來設計

[18:28](https://www.youtube.com/watch?v=oXTr1yVtH5E&t=1108s) CEO 說要 90% 或 95% 的品質，做下去發現大概只能到 60%。Tessl 叫這 first mover disadvantage：你比別人更早撞上模型的極限，這還不是大家都知道、模型廠商開始優化的問題，你的團隊也還沒累積到能 fine-tune、超過基礎能力的資料。他當場生成一張圖，不好，再試好一點，還是不對。他判斷那個圖像生成器做不出來。要不要寫邊緣偵測去找文字、改字母、去掉模糊。開始變貴。等他所說的 DALL-E 7 或 Midjourney 12 出來，這些就不需要了，系統裡留下一層殼，是技術債。

[19:50](https://www.youtube.com/watch?v=oXTr1yVtH5E&t=1190s) 明顯的事做完之後會碰到品質極限：prompt 調過了，團隊若會 fine-tune 也試過了。再往下就不是一輪快迭代。他們的決定是反過來，照 eval 結果設計。不要設計成一切都是魔法時的最佳體驗，那會把你困在一個模型永遠準備不好、所以不能發射的東西裡。先看錯誤：這些特定錯誤怎麼容易被發現、容易恢復，也許還能拿到一部分價值。給使用者選項：多個實作，這個過了這些測試，那個過了那些，讓人自己判斷。多次迭代拿到高品質，比一次做對容易。避免串接：某一步已知很差，就不要自動跑下去。停下來，讓使用者改正，再用已知是好的輸出進下一步。最後為資料飛輪設計。現在也許不好，但若能發射一個會收回 feedback 和資料的東西，就能更快把更好的 UX 送給使用者。常有人說這是壞 UX，把我們的問題推給使用者。對產品和設計，這直覺過去很對。在 AI 裡，工作是設計一個好體驗，同時拿到好資料。這是 AI 開發裡耐久地難的事之一。向人要資料很難，不再是不做的藉口。

[22:40](https://www.youtube.com/watch?v=oXTr1yVtH5E&t=1360s) 上線之後的 bug、production 資料、功能請求，全都進 eval set。Bug 要有很順的流程直接加進 eval set，團隊繼續對它爬山。Production 資料要能自動跑合成管線，更新、擴大 eval set。新功能請求要更新 input distribution 和 operation taxonomy，並確認 eval set 裡有代表性例子、有沒有缺指標。Eval set 本質上變成這個 AI 功能的 Figma mock。在裡面的，我們知道怎麼對著它做、怎麼在下一版把品質往上推。

## 合成資料可以很奢侈，指標要很笨

[23:53](https://www.youtube.com/watch?v=oXTr1yVtH5E&t=1433s) 只要訊號、不必完美，打開的是合成資料。他的第一建議是讀論文。不必懂全部訓練技巧或評測標準。多數論文有一節講資料集怎麼做，現在那些章節很金，有很多把問題扭一下來做合成資料的方法。WizardLM 和 Math-Shepherd 是兩個例子。Tessl 不用論文裡做出來的那個東西，但一直用它們的資料集生成技巧，做 eval set 和訓練集。第二，filter 就是一切。資料可以有很多種生法。若有可靠濾掉噪音的 filter，就能得到好資料集。值得把工具箱都用上。即使是又長又難的專案，也不要怕把 static analysis 加進去：能不能編譯、這個 API 和 import 對不對。Filter 品質的一點增量通常會複利。第三，生成可以超頻。用你能用的最大模型，不必是 production 會跑的那個。跑一千條分支再挑最好的。Eval 只需要一百、一千，也許兩千則。即便規模上不划算也沒關係，重點是快點拿到資料。

[26:22](https://www.youtube.com/watch?v=oXTr1yVtH5E&t=1582s) 指標小而笨。行數、總長度、有幾個 function、測試過不過，都很具體。看的不是絕對數字，是相對移動。平常大約 100 行，prompt 一改平均變成 300，就是壞了。再用這些指標排序：最長的檔、最長的 function。然後看見它誤解了什麼，或加了一堆不需要的註解。它們幫你排對地方跳進去，也幫你發現底層實作變了。

對 code-centric，測試是金標準。內建的 oracle 就是測試過不過。很多 code 沒有測試。這是新風景裡耐久地難的一塊：要培養為 code 寫測試的能力。野外來的 code、生成的 code，都該有輔助管線寫出好測試，之後才能評品質。Outlier 不是問好或壞，而是問它跟其餘生成差很多嗎。分布集中在這裡、有一個遠在那邊，就該挖。它也許沒問題，但能幫你排手動時間花在哪。最後問好不好，不會有專案一開始就定死、永遠對的單一指標。它會是很多東西的混合。例如好的生成少於 200 行，平均行長約 30 個字元，function 數量大致相當，API 裡 private 對 public 大約 3 比 1。立刻就能想到反例。這是統計：設下這道門，被標出來的多半是好的，另一桶多半是壞的，夠給你繼續走的訊號。

## 用手做過，才知道什麼叫蠢

[30:07](https://www.youtube.com/watch?v=oXTr1yVtH5E&t=1807s) Michael Wolf 喜歡他建議大家用手做一些例子。Dru 說 AI 團隊的人必須看資料，招募時要找得到這種人。面試流程裡他們明確看一種韌性：坐下看一堆輸出，覺得怪，花 30 分鐘搞懂並調整。Eval set 要一天、兩天，有時更久。那是真正的工作。好處像好的測試套件，覆蓋好就開發、推 code 更快。更大的是產品上的學習。很多邊角抽象描述很容易，若不懂任務、不懂它會在哪裡錯，prompt 難寫，UI 也難設計。這像一種新的使用者訪談，他叫 data interview。

[32:04](https://www.youtube.com/watch?v=oXTr1yVtH5E&t=1924s) 完全新的東西，什麼叫好的 eval。Simon 提到 Intercom 共同創辦人 Des Traynor 早期在 podcast 上講的 torture test，最難的是什麼叫好。Tessl 有兩種想法。第一，為什麼不盡快進 production。尤其空間很新、很難知道夠不夠好。產品可以設計成：品質還不好也能發。可以是選項，也可以只是標成 alpha。能做更多就做。這回到要設計好體驗、同時給好資料；也要設計不必等完美、不必等 AGI 也能用的介面。第二，人的判斷和 LLM as judge 一直有位置。抓最大的低垂果實。上線 AI 功能時，人知道會犯錯，那通常不是大問題。大問題是愚蠢的錯，讓人覺得怎麼會覺得這可以發。你也許分不出真的好，但分得出蠢、分得出會不會讓人難堪。先抓這種 blunder，那是發射的最低門檻，然後找方法發出去。有了訓練資料和 eval 資料，比在實驗室裡只用概念解決容易得多。

[34:46](https://www.youtube.com/watch?v=oXTr1yVtH5E&t=2086s) 人要幾個才剛好，他說會因問題和團隊而變。簡單的答案是團隊每個人都該花過時間在迴圈裡：看例子、生輸出，對功能有感覺。再往下，一個通常不夠。合成資料大約只有 70% 準；兩個人走同一流程，同意度也大約 70%。合成資料大約和一個人一樣準。人若只有 70%，兩到三個人互相比，會好很多。這是 inter-annotator agreement。若不是核心團隊、不能指望某人在一個例子上花 30 分鐘弄對，至少兩個，最好三個，才能比、才能打破平手。還要整理這組人：某人一直和其他標註者差很多，就換人。可行動的數字他給三。若不是大到又貴、必須做得很講究的標註工作，三十也還可以；那種就去讀文章。若只要一百到兩百則，送到 Mechanical Turk 或 Scale AI，三是好的起點。

收尾時他說，他們在 AI 開發加上的技術，沒有拆掉下面那層。資料集仍有 lineage，有些地方仍用 XGBoost。通常是再往上一層，不取代下面。產品也一樣：仍要跟使用者談，仍要用自己的直覺，現在還能看資料來拿例子。

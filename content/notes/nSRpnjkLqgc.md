# AWS's Marc Brooker: Specs, Not Code, Are the Hard Part

AI Native Dev。片長約 57 分鐘，英文手寫字幕。主持人 Simon Maple，在倫敦；來賓 Marc Brooker 在西雅圖，他說雨只是在威脅要下，兩週好天氣之後又回到西雅圖的天氣。Marc 是 Amazon Web Services 的 VP 和 Distinguished Engineer，在 AWS 十八年。主持人還有 Guy Podjarny，製作人 Tom Dowler。這份筆記依英文原稿整理，專有名詞保持 English。

- 原片：[YouTube](https://www.youtube.com/watch?v=nSRpnjkLqgc)

## 一句話

Marc 讀過三千到四千份 postmortem。他學到的謙遜是：樂觀可以留著，但下次要更聰明地做。日常的 on-call，刮 log、看 metrics，自動化已經接得走。留下的是系統為什麼會這樣。他相信軟體最難的部分正在變成規格：把你要的東西寫到夠完整。一旦寫成，可靠、有效率的實作會愈來愈被自動化。測試因此變成最重要的工程。人要做的是 oracle、什麼叫好，以及不要把讓新人上來的梯子抽掉。

## 自己做一個 agent，才知道商業產品底下在做什麼

[2:17](https://www.youtube.com/watch?v=nSRpnjkLqgc&t=137s) 最近幾年他專注在 agentic AI、agentic 開發工具，以及那套基礎設施。他深度參與 AWS AgentCore，一套在雲端建 agents 的工具。最近在組團隊，看 agent 建造和 agentic development 的未來。他們擁有 Strands，AWS 的開源 agent framework。Strands 這個空間還有技術要來，他們也在做新的開發工具，從相當基礎的研究到大量寫 code、做產品。

[4:36](https://www.youtube.com/watch?v=nSRpnjkLqgc&t=276s) Strands 是開源 SDK，用來建 agents。任何 model、任何雲、本地的 agents 都可以。目標是盡量容易地做出能上生產的好 agent。最小的 Strands agent 只有幾行。往上可以加 tool、內建的 MCP client、內建的 OpenAPI client、context management。團隊對什麼是好的 agent pattern 很有意見。你可以擴充、怎麼用都行，但有一條鋪好的路，把他們現在認為對的做法做進去。

Simon 說，沒做過 agent 的人會以為背後很複雜，其實可以只是包在 model 外面的薄薄一層，他鼓勵聽眾自己做。Marc 也鼓勵人做自己的 development agent。不會有主要的商業產品那麼好。但幾個小時內，你會對那些 agent 底下在發生什麼有好很多的直覺。懂封面底下，會讓你把那些商業產品用得更好。

## 十五年的凌晨三點，留下的不是刮 log

[6:44](https://www.youtube.com/watch?v=nSRpnjkLqgc&t=404s) Simon 要談他大約十五年的 on-call，很多凌晨三點。Marc 說他享受。那是學習真實世界怎麼運作的機會：系統實際怎麼跑、顧客真正在乎什麼。他從研究所出來時，以為自己有很多實務知識，其實很多是理論。On-call 是職涯裡的催化劑：系統怎麼運作、怎麼失敗、怎麼阻止失敗、那怎麼影響顧客、怎麼幫顧客。Simon 說，很多人以為做了五年以上就是 senior。他覺得比較像是這種角色，你才接觸到做一個真的可靠的應用要什麼。

Marc 認為這是軟體的大主題：大量自動化，把重複的事自動化掉。這不新。雲端和計算的歷史就是這個。以前單機故障要人處理。十五年前 AWS 的 autoscaling 開始替我們處理，load balancer 的 health check 也是。AI 正在做同一件事。On-call 裡基本的調查、刮 log、鑽 metrics，像 AWS DevOps agent 就很會把比較日常的部分自動化。留下的是有意思的推理：系統為什麼這樣。大規模的失敗我們看到什麼。大規模把效能變好，我們看到什麼。自動化會幫很多，但今天還沒有那些問題的答案。

Simon 希望自己凌晨三點被叫醒時，agent 已經走過 log 和資訊，把可能的根因整理好，醒來時決策需要的東西都在。

[10:28](https://www.youtube.com/watch?v=nSRpnjkLqgc&t=628s) 他寫過自己讀了三千到四千份 postmortem。不當班學不到的是什麼。其中之一是很深的謙遜。我們傾向樂觀，這很好：我們能做、我們能解。然後你看到事情怎麼失敗、什麼時候不行，得到一劑謙遜，也把迴圈關上：我仍樂觀，仍相信做得到，但這次要用更好、更聰明的方式。

一個很具體的例子是過去十年愈來愈熟悉的 metastable failures。大型系統裡，過載或某個元件故障，系統下去了。直接原因修好了，系統卻不恢復，因為它卡在一種穩定的壞狀態。深深懂這件事，對避開一整類又長又痛的中斷很重要。他個人的理解，很多來自看真實事件，自己的和產業裡的，再分析那些時候系統的動態。可以完全用分析、從外面看。但他覺得看真實系統怎麼失敗，學到的多得多。是什麼把它踢進那個狀態，是什麼讓它下不去，是什麼導致恢復。怎麼讓系統更扛得住，恢復更快。以及怎麼做出自動化，人在那種狀態時，恢復可以自動發生。

Simon 說，AI 成為主流之前，這種學習就是把人推到 senior 的東西。你帶著另一種心態寫 code：我知道這會壞，只是不知道怎麼壞、什麼時候。

## Agent 可以從事故學，但「感覺變慢」它還不懂

[13:42](https://www.youtube.com/watch?v=nSRpnjkLqgc&t=822s) 人可以從自己的錯、經驗、別人的 postmortem 學習。Agent 呢。例如 loop：自動理解 agent 哪裡可以更好，更新 context 和 skills，下次類似的應用就能繞開或擋住。對會被寫進 postmortem 的那類 bug，這是不是空想。Marc 說非常實際，而且就是今天這些 agents 前沿在發生的事，有一組技術。

可以把所有 postmortem 放進 model 的訓練集，用別的方式改進 model。也可以給 agent 一個工具，在那些 postmortem 上做語意搜尋：給我看像這次的事件，我就能懂當時怎麼恢復。然後 agent 寫自己的記憶：我試了 X，不行；我試了 Y，行了。下次它會從 postmortem 和自己的記憶裡取出來，在那個階段跳到前面。Agents 也愈來愈會看：我做了這步、這步、這步，可以把那些編成一段 code，幫自己做一個 tool，放進記憶，一種程序性的記憶，需要時從架子上拿下來。所以有為 agents 建 context 的函式庫，有讓 agents 建立並管理自己的記憶，有 model 的客製，有手動和自動幫 agents 做工具，還有其他技術。每一種都能讓 agents 從經驗學習，解某類問題更可靠，也更快、更便宜。

這種學習最有價值的是事件當下，還是能沉進以後的架構和開發決策。他希望是後者。那是他們在賭的，他覺得還沒看到那麼多。拉回人的層級：Amazon 一直讓做產品的人，為那些產品 on-call。主要就是為了驅動那個學習迴圈。你得到生產經驗和顧客的軼事，直接帶回開發。拆成不同團隊有好處，但學習迴圈難推得多，也抽象得多。進到 agent 的世界，他要的是寫軟體的 agents 從生產經驗學習，和維運自動化的 agents 一樣。路徑是記憶、共享 context、共享那些記憶和工具，甚至把 development agent 當審查軟體設計的專家顧問。但就產業而言，這段旅程比把個別零件優化好，還更早。

Simon 記得 prompt engineering 曾經是：喔對了，另一個 agent 會審這個，所以做好。他喜歡另一個想法：喔對了，你要為自己寫的 code on-call，凌晨三點可能被叫醒。Claude 或 Gemini 或 whoever。

[18:18](https://www.youtube.com/watch?v=nSRpnjkLqgc&t=1098s) Agent 從 postmortem 學不會、或會直接掠過的，是沒有清楚、確定結果的事。它解得了的是：我有一張 Amazon.com 訂單的圖，或 EC2 開機次數的圖，它應該長這樣，它長成這樣，找出那個缺口，把它關上。目標很清楚。比較難的是：我在 Twitter 上聽到顧客看到比平常多一點的錯誤，人或許對產品比較不開心，或我打開時整體覺得慢。愈模糊愈難。Agents 可以幫你挖，找出 maybe 驅動那些感受或軼事的 metrics。但一般來說，它們沒那麼會懂工作的端到端脈絡。顧客怎麼用這個系統。怎樣叫感覺快。怎樣叫感覺可靠。而我們知道，把那些編成 metrics 常常非常難。

## 人當不好監督者，盒子要先寫清楚

[20:10](https://www.youtube.com/watch?v=nSRpnjkLqgc&t=1210s) Simon 說他在儲存、計算、資料庫做了二十年之後，轉到 agentic AI 的安全和政策。錄音當下很應景：Dario 談到 Anthropic 該放慢 model 的開發，也在談別人是否一樣。Sam Altman 同意了，Elon Musk 也是。Marc 說他沒有要分享對 model 開發速度的意見，那組取捨很有意思。他聚焦的是從顧客和開發者那裡聽到的。

非常常見的主題是：我們用 Strands 做了一個很棒的 agent，放上 AgentCore，demo 看起來很好，董事會超興奮。現在真的擔心怎麼進生產、怎麼讓它可靠、怎麼讓顧客信任這個 agent 替他們做事。解這個問題的一大塊是 agentic policy。Agent 做對的事是什麼意思。怎麼非常清楚地定義它能做什麼、不能做什麼。哪些屬於環境、harness、把 agent 關起來的方式，哪些屬於 prompt 和 tool 的描述。顧客要的是一種很清楚、很確定的方式，在 agents 外面做一個盒子：我信任它做這件、這件、這件，它不會有任何途徑去做那些。

很多人把它當成經典的授權問題，像對人那樣：這個人有權做這一步。但人有判斷、有回饋，agents 沒有。經典的授權語言也缺顧客想用來描述 agents 需要的那種力量。他們最近推出的是 Dogwood，一種新的政策語言。他願意講深。它是專門的語言，用數學上的確定性描述 agent 被允許做什麼、按什麼順序、能不能在做了 B 之後做 A。這全部來自顧客的需要。產業裡的人說 agents 超令人興奮，想自動化更多、把顧客服務得更好、把人的時間用在更重要的事。關鍵是有好的安全故事、政策故事、隔離故事、身份故事。這樣才能建出我們信任它自主跑、在公司裡做關鍵事情的 agents。

[24:52](https://www.youtube.com/watch?v=nSRpnjkLqgc&t=1492s) Simon 說過去一個月左右，更顯出信任有多重要。往自主、factories、長時間跑的流程走，人怎麼用這種工具。Marc 說，幾十年對心理學和維運的研究知道，人是很糟的監督者。看事情過去、出事時按紅按鈕，人真的很糟。背後有好幾種動態。其中一個是八零年代的經典論文，The Ironies of Automation。系統愈來愈好，失敗模式變得更怪、更少見，人更難在它們發生時懂、認出、並正確反應。他認為唯一的解是自主。把人拉出迴圈。不要讓他們看迴圈轉、壞事發生才按按鈕。更不要讓他們對每一次 code 生成說 yes、yes、yes，誰會做那個。把人彈出去：先描述什麼叫好，先描述你希望系統做的那一組事。有了那個描述，就把它用在 agent 上，不必人繞一圈去做那些事。

怎麼做。有些是把常識編成政策。你在開發一段 code，知道它該跟系統有哪種互動。它會 git pull 和 git push，但只在它正在做的那個 repository。它若去對另一個專案 git push，那大概是壞事。把那一小塊常識寫進政策。一部分是那類常識政策的函式庫。一部分是自然語言到政策：它可以讀我硬碟上的任何東西，除了 secret documents 那個資料夾，並且自動、可靠地變成一條政策。一部分是走遍公司，發現既有的政策和做法，把它們編成政策。

直接寫政策的是少數。有些人會寫 Dogwood、Cedar 或 OPA，或他們在用的政策語言。絕大多數不會進到那一層，也不想，因為那些語言相當專門、相當難學。他們會停在自然語言：什麼叫好。可以是開發者個人說，對我這個人什麼叫好。也可以是 CISO 辦公室說，對我們這個組織什麼叫好，我們處理顧客內容的標準、處理我們 code 的標準，然後把它們編成政策。這些常常會合在一起。CISO 辦公室一些，法務一些，我自己作為開發者一些。全部包成 agent 外面的那層殼，再用這些較低階的語言，強而確定地確保 agent 遵守。

他覺得比較接近五五開，不是多數從安全或法務往下壓。有些事安全團隊非常在乎，例如顧客內容怎麼被處理、允許出現在系統的哪裡。他要公司裡每個開發者的 agents 都被要求維持那個標準。有些事安全團隊不在乎。我的 development agent 能不能刪掉我文件資料夾裡的文件。沒有顧客影響，沒有組織影響。但作為終端使用者，他非常在乎，不要那些東西被刪。所以是混合。而且落到個別開發者，產業裡、甚至團隊和組織裡，開發做法差很多。正常長什麼樣，範圍很寬。用的工具也寬。大多數大型軟體組織不會往下壓「你就用這幾個工具、在這個時間」。他們也不會成功地把一套完整、端到端的 agent policy 壓下去，因為它必須配合你在做的那種開發，甚至每天都不一樣。有時他在寫 Rust，想要某種標準：Clippy 不滿意，不准 commit。有時他在做一個很快、很髒的 web demo 原型，給人看十五分鐘就丟掉，那些標準他一個都不想坐。政策要來自不同地方，要動態，要看情境。

## 難的是把「要什麼」寫完整

中間有一段請人訂閱。[32:14](https://www.youtube.com/watch?v=nSRpnjkLqgc&t=1934s) Simon 要他講他寫過的軟體開發假說，弱的、強的、最強的形式。Marc 說得提醒自己那篇到底怎麼寫。核心是：做軟體最難的部分，他要說是做規格。意思是描述你要什麼，而且描述到夠細，它是一份完整的描述。一旦那份規格、那份「你要什麼」寫下來，他相信我們會看到：做出並維護可靠、有效率的實作，隨著時間變成完全自動化。先看到的是封閉的規格。我想要一個東西實作某種檔案格式，而且描述得很清楚。這已經看到了。然後會長到更大的系統，更多 UI、更複雜的互動。他認為隨時間，那種從規格往下的軟體開發會被自動化，由一個自動化迴圈驅動。比較強的宣稱是：絕大多數軟體都可以被規格寫到夠清楚，好讓那種自動化發生。

同一篇裡他寫過，很少有任務有完整的規格，也談過 oracle 可以是確定的、也可以不是。Simon 問，難的部分是不是被搬到：找出一個確定的 oracle，或寫出那份完整規格，那仍是人的問題。Marc 說當然。大量人的工作就在做出那些 oracle、那些規格。某種意義上，測試現在是軟體開發最重要的部分。有人會說它一直都是，但它對大多數開發者從來不是那個閃亮的東西。現在，怎麼做出一個測試，說這段軟體好還是不好，就在前沿。有些會是規格：我能不能用夠形式的方式，確定地描述它。他舉了一個他說可以完整規格化的例子，字幕聽成 Jesus，從上下文是一種寫得死的東西。若是替顧客做一個 UI，也許就不能。那就得用別種正確性的 oracle、別種評價，更開放，maybe 顧客在迴圈裡，把回饋送回去。

若看自動化推理那種規格層級，用 Lean 這類語言規格化軟體，有非常大的進展，能處理的軟體塊愈來愈大。但那些元件擴大成整個系統、系統有複雜互動，就更難。所以他也想做這種 oracle：看一個系統，說它運作得好不好。那 maybe 是看生產的 metrics，maybe 是顧客回饋，maybe 是對一個資料庫引擎的兩種實作做 fuzz test，還有很多其他技術。

Simon 記得 Kiro 剛出來時，Amazon 的人來談過，specs 是往前走的 source of truth。他一直難分什麼算規格、什麼算測試。規格裡寫的常常就是在描述一個測試。寫測試時，你又是在說某件事該怎麼運作，那又像規格。功能規格和測試幾乎合成一件。Marc 說，測試是一種非正式的規格技術，而且一直都是。他喜歡那個團隊在 spec-driven development 上做的事，有很強的進展。回頭看，他對當下這一刻有點不滿足的是：宣告式的需求，和比較屬於實作細節的東西，仍然混在一起。我想用這個語言做，或要這種 UI。作為系統的建造者，他不想在乎那些。他想要好的決定被做出來，而且更自動地被做出來。規格和測試應該聚焦在軟體的產出什麼叫好，不是它裡面怎麼運作。

## 部落格是一份社會契約，code 愈來愈不是

[39:56](https://www.youtube.com/watch?v=nSRpnjkLqgc&t=2396s) 他以前說過，不會讓 AI 寫他部落格的任何一個字，但很放心讓它寫 code。現在仍是這樣。差別在意圖。大約五年前，他會很有把握地說，大多數 code 的目的是跟人溝通。執行重要，但不是主要目的。所以他非常在乎註解、非常在乎命名、非常在乎把 code 寫成能溝通意圖，尤其是 code 的意圖。他覺得這正在變，而且在產業裡變得很快。人離開 code 那一層，進到規格那一層，很多編碼變成完全自動，code 愈來愈只是實作的載具，不是溝通的載具。

他的部落格相反。這是給人讀、給人參與的。他心裡有一份社會契約：我花了很多時間深深想過這些字，我把這些字分享給你，我希望你作為讀者花時間深深試著懂我的字。若他讓 Claude 五分鐘寫一篇，然後比方一萬人讀，每人花十分鐘，他投入的努力和讀者投入的努力會極度不對稱。他覺得那不公平。拿到工作上也一樣。Amazon 是非常靠文件驅動的文化。他為工作寫很多文件，關於計畫、技術、他們在做的事。他和讀者之間有契約：他期待他們深深讀、懂、參與，他們期待他深深考慮過那些字，並對它們有完整的所有權。若那些是 Claude 的字，他就沒有做到。第三部分：你有一個想法，想跟我分享，也想分享 Claude 對它的想法，他覺得那很好。但讓它變成互動的。把 prompt 寄給我，我們跟它聊。這些 agents 酷的地方是可以繞迴圈、問後續問題。若我們要選那種溝通，就選那種。不要落在彆扭的中間：人的用心被拿掉了，卻沒有加上互動和追問。

什麼情況下他會讓 AI 寫部落格。個人部落格在某個層次是哲學問題：這些是我的想法，照我寫下的，連我的錯誤一起。工作文件若 Claude 能寫得精簡，描述 context、把業務 context 拉進來，他會相當自在。區別 maybe 是：把 Claude 當擴寫器，一個 prompt 變成六頁文件，那是浪費讀者的時間。把 Claude 當 context 的提供者，加一段這週的業務 metrics，他覺得可以，因為你在帶進人還沒有的新資訊，而且形式幾乎就是他會手動做的那樣。部落格他仍想說，那是一件手藝。Simon 說，手藝能不能被放大。有時手藝最好就留著手藝。創造和閱讀的快樂，在於知道沒有 slop 的可能，它直接從手上來。

## 回饋要先能擋下 commit，再談跨團隊的記憶

[46:37](https://www.youtube.com/watch?v=nSRpnjkLqgc&t=2797s) 團隊今天能做的、讓 agents 得到最清楚訊號、以便下次跑得更好的事，取決於你在 agent 開發成熟度的哪一層。產業裡很多團隊才剛開始。有很多人現在會翻白眼、但其實很有效的事：一份給 agents 的檔，寫下什麼叫好。不是前沿技術，但已被證明有效。他覺得很多團隊太早跳到終點，說我要做 parametric memory 之類的。你還不能在 Clippy 不滿意、測試沒全過的時候就把 code 送出去。那件事非常有效，額外負擔很小。

再往上，有意思的是讓 agents 有辦法記住團隊的 context 和過去的對話。一部分就是很多 agents 內建的 agentic memory，跨 session 記得事情。你說不要再這樣做，它有時記得太好、太多，會煩。問題是 agentic memory 不好散佈到團隊，甚至不好散佈到別的人。你需要一種方式把那些記憶抓住、寫下來，讓整個組織或整個團隊用。他看到很多人用現在相當流行的 agent wiki：團隊的 agents 維護一小本 wiki，關於什麼叫好，agents 之間共享。還有像 AWS Context 這樣的工具，讓 agents 為環境裡的 context 建一張正式的圖，接回記憶，可以接文件，而且跨組織。一部分是動態的發現和學習，一部分是從組織裡把已經寫下來的對的資訊拉進來。有人對 RAG 翻白眼，說那是 2004 或 2024 的東西。底線是，讓 agents 對組織裡的資訊做語意搜尋，仍然非常強。他就是要把它接上，讓 agent 碰得到。商業 agents，尤其看 Kiro，或 Amazon 的 Q，愈來愈容易把組織的 context 拉進來、放進團隊的 context，並透過 AWS Context 這類東西共享記憶，把從經驗學習的模式烤進整個組織。

[51:08](https://www.youtube.com/watch?v=nSRpnjkLqgc&t=3068s) 給個人、尤其給 junior 的建議，他繞回那些 postmortem。擁有一個專案，跟一個顧客說話，擁有一個截止日，並從團隊和個人過去的錯誤學習。這些歷史上常常是 senior 做的、而且常常守著的事。能不能期待 senior 現在把這些交給 junior，還是他們會抓著不放。這是 junior 和 senior 之間那道缺口的老問題。他說，我們必須交。軟體產業未來十年在重要性和經濟影響上會長大非常多。若我們把梯子抽起來，軟體工程師這個社群只會愈來愈灰，就不會有那種成長。不會靠一群鬍子裡有灰白屑的人，把這個新產業建起來。經驗、年資、待得夠久，仍然非常要緊。深度的專業仍然非常要緊。但我們絕對需要把這個產業建在教學、成長、把新人帶進來、訓練和學習的文化上。技術上每天具體長什麼樣，很難知道。他不懷疑那會是產業成功、以及個別組織成功的關鍵部分：找出那條路，把人從大學帶進來。他們常常有很好、很新鮮的理論知識，再把每天的實務補上。我們得想出來。往前走，這會是組織的大差異：能不能帶進新人、帶進新想法。好處是他看到從大學出來的人，花了很多時間跟 AI、跟 agents 學，沒有我們很多人帶去的那些先入之見，帶著很多新鮮的想法和角度。那對組織或開發團隊是很好的添加。

Simon 說這是組織和 senior 工程師的共同責任，讓 junior 進到很多決策裡，並把他們帶上來。Junior 是真正的 AI native。我們有幾十年敲鍵盤、code 就出來的方式，正在學新的。他們是這樣長大、這樣學的。我們絕對可以從那個新鮮的角度看。

他的部落格字幕說在 Brooker，主要來源是部落格和它的 RSS，很老派。他也會在 LinkedIn 和另外一兩個平台分享。

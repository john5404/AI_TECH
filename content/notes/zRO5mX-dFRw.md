# The Man Behind World’s Largest Dev Con | Stephan & Devoxx

Stephan Janssen 在 2001 年創了 JavaPolis，也就是現在的 Devoxx，他自己跑比利時那場，也跟 Mark 一起共創 Voxxed Days，字幕把 Mark 聽成 Hazel。Simon Maple 主持。這集約 64 分鐘，英文自動字幕。字幕把 Stephan 聽成 Stefan Yansen，把 Devoxx 聽成 Devox、DevOps，把 vibe coding 聽成 VIP coding，把 Claude Code 聽成 cloth codes、close code，把 CLAUDE.md 聽成 cloth MD、cloud MD。這份筆記依英文原稿整理，專有名詞保持英文。

- 原片：[YouTube](https://www.youtube.com/watch?v=zRO5mX-dFRw)

## 一句話

他把現在叫做開發的文藝復興：vibe coding 把要花好幾天的環境架設壓成很快的事，五週做出來的東西，他確信沒有它要三個人做六個月。但純靠一句句 prompt，兩週就做出一個上不了線的 Frankenstein。他把 React 原型反編成 spec，再用 Angular 從 spec 寫回去，加上 lint、測試，和一份會長大的議題文件。資深的人仍要看 code 和腳本。Devoxx Belgium 的主題是 agent，會場本身也在用這些做法。

## 票在幾秒內消失，會後他才有時間做研究

[1:10](https://www.youtube.com/watch?v=zRO5mX-dFRw&t=70s) 正片前的預告點了 Datadog 的 Olivier Pomel、ElevenLabs 的共同創辦人（字幕聽成 Matty Stanisowski）、Synthesia 的 CEO（字幕聽成 Victor Ripelli），以及 Tessl 的 Patrick，字幕聽成 Dubois。90% 的聽眾還沒訂閱。Stephan 的頭銜不是「Devoxx 的頭」。他創了 JavaPolis，跑 Devoxx Belgium，並盡量知道其他 Devoxx 和 Voxxed Days 在發生什麼。Simon 說這大致是全世界首要的 Java 會議，也是最大的一組。Stephan 同意。每年大約 20 場活動迎接 20,000 名開發者，其中八場 Devoxx，其餘是 Voxxed Days，字幕把後面的數字聽成 12 又 10。加在一起，每年接觸到的人不少。旗艦是比利時，每年十月大約三千五百人到安特衛普，字幕聽成 Antworp。Tessl 今年贊助，也有幾場 session。票像搖滾演唱會，幾秒就沒了。因為這樣他們做兩批。上一批是上週一，下一批是 9 月 1 日。有人真的打電話來哭，老闆叫他買十張，一張都沒搶到。第二批小一點，用來解註冊上的一些問題。開放前有 4,600 個不重複 IP 在重新整理。搶到票的人後來還是會釋出一些。現在還有 deep dive 和 combi 的票，會議票沒了。疫情之後很多會議沒有在掙扎，但確實看到下滑。很多人在家工作，把這五天當成社交：聽好的演講，晚上喝一兩杯啤酒談技術。

[5:18](https://www.youtube.com/watch?v=zRO5mX-dFRw&t=318s) 名字後面，他是很活躍的開發者，玩 AI 開發工具不是剛開始。Simon 在 Twitter 上跟很久，記得早期的影像辨識，還有籃球那種東西。辦 Devoxx Belgium 不是全職。節奏慢慢加快，最後幾個月很亂。會一結束，他有四五個月可以做純粹的研究和開發，玩在會上看到、讓他想試的工具和框架。兩年前 JetBrains 宣布 AI assistant，還在 Devoxx Belgium 開幕主題裡示範。他問 Anton：能不能用本地模型、是不是開源、能不能選別的雲端模型。答案一直是否定。等了四個月，他決定自己做一個以前沒做過的 Java plugin，完全開源的程式輔助，叫 Devoxx Genie。上個週末已經 30,000 次下載。目標是支援本地模型：Llama、LM Studio、字幕聽成 YAN 的那個、llama.cpp，也支援雲端模型。瘋狂的是可以切換。可以先用本地模型，再換雲端模型，讓雲端模型審查本地模型的回應。他過去八個月左右花了不少時間在這上面。後來 CLI 出來了，Claude Code 這類。Devoxx Genie 能用，人們在用、也開心，他開始更注意 CLI。對他來說前沿的三個是 Claude Code、Gemini、Codex。七月還不太忙，他決定做一個 vibe coding 實驗。

## 兩週的 React，做到九成，最後一成是義大利麵

[8:04](https://www.youtube.com/watch?v=zRO5mX-dFRw&t=484s) 這集主要談這個實驗：一個給十月 Devoxx 用的小助手，他用的方法和工具，以及痛點。他們已經有一個開源專案大約兩年，字幕聽成 Foxring，作者聽成 Fri Caml，用 Firebase 當後端，很漂亮，但對那個人比較像晚上的嗜好。Stephan 開始想念功能：搜講者、用臉部辨識放講者照片、登入之後收藏可以同步到手機。基本上是 Devoxx 的同伴應用。他說那就用 vibe coding 重做。他加給自己的限制是不碰任何 code。可以看，只能 prompt。Simon 說這就是 vibe coding：用很短的訊息建議變更，測試多半是點一點前端，不是先寫一堆測試。他還加了另一個限制：用 React，而他不懂 React，所以更不敢看 code，因為他從沒做過 React 應用。選 React 不是技術選擇，是因為他不懂，而且他看過別人的 vibe coding，知道 LLM 把 React 索引得很好。更冷門的語言，例如 Go 或 Rust，前沿 LLM 的支援可能沒那麼多。React 在最上面。他腦子裡有既有應用的功能想模仿，也想超出去。

[11:29](https://www.youtube.com/watch?v=zRO5mX-dFRw&t=689s) 頭幾天是巨大的加速。做出來的 UI，他這個比較偏後端的人永遠做不出那麼好看的設計。CSS 也漂亮，而且是響應式的。他花了兩週純 vibe coding，功能走到 90%。最後 10% 真的在掙扎。他開始看得更近，做比較像反思的 prompt。他注意到幾件事。需要深色和淺色，於是用變數重構 CSS。需要國際化，於是引入 resource bundle。已經在用 Firebase，然後又要 Firestore、storage，也許還要即時資料庫。你是在做原型，再讓 LLM 依你一連串還沒在開始前刻死的需求去重構。那也可能造成一些奇怪行為。兩週之後 90% 能動，10% 真的壞了。調查之後，它造了太多重新導向、太多抽象層，基本上是義大利麵。快不到能部署到生產，cache 也壞了。他說老实说，兩週做出了一隻 Frankenstein。Simon 說那是因為迭代：你把整塊東西栓上去，它盡力改已經在那裡的東西，而不是從第一原理把整個應用重生一遍。

[14:25](https://www.youtube.com/watch?v=zRO5mX-dFRw&t=865s) 這段實驗主要用 Claude Code，CLI。他買了 100 美元的訂閱，其實綽綽有餘。那段時間他每天做三塊、每塊五小時。不是工作 15 小時。大約三小時就沒 token，要等兩小時才能開下一段，所以常常一天十小時左右。日子長，但很好玩。主力是 Claude。第一階段有時卡住，或 prompt 找不到解法，他就把 Gemini CLI 也接上。Gemini 是 Google，Firebase 也是 Google，它可能更懂 Firebase 的文件。他覺得有兩次，Gemini 修好了 Claude 給不出的解法。那個用 API key，按 token 付。他也常去 DeepSeek 做腦力激盪，把對話給它，它做深度思考，帶回別的建議。DeepSeek 他从没付過錢，也用 ChatGPT 的免費版。只付了 Claude Code 和 Gemini。

## 從 code 抽出 spec，再從 spec 寫回 code

[16:00](https://www.youtube.com/watch?v=zRO5mX-dFRw&t=960s) 兩週後完全卡住，他做了一次 control-alt-delete，重開實驗。這次用他比較懂的 Angular。會更積極地看它產生的 code，把自己當技術專案負責人，當生成物的 guardrail。更重要、他認為確實幫助成功的，是拿 React 的 code 當基礎來寫規格。第一階段沒有任何 spec，只是 prompt，雖然 prompt 很大。他把 React 應用餵給 Claude Code，按功能請 Claude、Gemini，有時還有 ChatGPT，為某個功能寫出規格。三個模型互相審查，會得到一份非常清楚的功能規格。每個功能存成 docs 目錄裡的一份 markdown。規格非常細，不只描述功能，還會討論要用的模型，甚至放進某些實作片段。給一個資深開發者，他或她會精確知道要實作什麼。那只有三個、有時四個前沿模型在審查才做得到。他一定建議至少兩個，三個或四個更好。這四個一起做出漂亮的 spec，然後再拿進 vibe coding。

[18:52](https://www.youtube.com/watch?v=zRO5mX-dFRw&t=1132s) Simon 說他們想規格的一種方式，是把 what 和 how 分開。今天的 code 常常兩者都寫。Stephan 因為是從 code 生成規格，等於把 what 抽出來，又撒了一點 how，於是會偏向某個實作。若這個 app 就是為他的需求寫的，那樣也可以。他說正是如此。第一個原型在 React，拿它做 code to spec，最終實作走 spec to code，像繞一圈，幫助很大。他也有 CLAUDE.md，寫必須做國際化、要支援哪些語言、要有 theming、Angular 要用新的迭代式 for 和 if。他還做了 code style 的規格，引入 linter。到這裡故事裡缺的、他認為真正關鍵的，是測試：unit test，還有 integration test。他沒做測試驅動。先讓 LLM 寫 code，他用眼睛看功能動不動，再讓它做 unit test 和 integration test。新功能每次都加上去。這很關鍵，因為你會發現新功能可能在不知道的情況下弄壞舊功能。沒有 unit test 蓋住，你不會知道。好的 integration test 和 unit test 也是 guardrail，讓 vibe coding 不要出軌。Simon 說規格裡描述能力時，幾乎可以讓測試領頭。能力可以用自然語言寫它該怎麼行為，也可以用測試寫細：這種輸入、這些非預期輸出、要這樣反應。變更不該有連帶效應。

[22:58](https://www.youtube.com/watch?v=zRO5mX-dFRw&t=1378s) 純 vibe、搬到規格之前，那 10% 就是這種問題。他卡在 Claude Code，因為是 Firestore 的問題，轉去 Gemini。回應不可思議。它說為反覆的失敗真誠道歉，它改規則的方法有缺陷，目前找不出語法錯誤。他說你可以找到。它又說這已經難堪到不行，深深抱歉，它顯然不是這份工作的正確工具。他說 Gemini 在經歷身份危機。然後它說要還原變更，真的找不到。他得自己進去看。問題只是一個字元：Firestore collection 路徑裡，interactions 後面是底線，應該是斜線。Claude 和 Gemini 都找不到。Simon 問他什麼時候覺得自己像 LLM 的輔導員，在說 Gemini 你夠好、你可以。他在網上看到他們開始修 Gemini 這種道歉行為。Google 也在學，CLI 版本幾乎每天在出，一定會愈來愈好。他會去截圖，就表示當時多驚訝。使用者會失去信心。它幾乎在懇求自己不是對的工具。你開始相信它，覺得也許真的做不到，也許該換方法。

## 沒有護欄就是太自由；規格要活著，人才不會偷懶

[25:12](https://www.youtube.com/watch?v=zRO5mX-dFRw&t=1512s) 純 vibe、只是一些 prompt，太自由，沒有 guardrail，不夠。他的護欄從一個好的 linter 開始，每次部署都走完整份 code。然後是 unit test、integration test，以及規格怎麼管。他認為那裡有巨大機會，知道 Simon 他們顯然在看。他用一個開源專案，還邀請了開發者，他相信對方來自奧地利，來 Devoxx Belgium。那個專案字幕聽成 backlo.md。對方也是 vibe 出來的。你在本地安裝，瀏覽器裡有一個看板。你建一個 issue，它產生 markdown。你在 Claude Code 裡說現在做 issue 一號，它會到檔案系統找那份 markdown，做完之後把做了什麼寫回既有的 issue。再回去看那個功能，它已經知道原本的抱怨或功能、做過什麼、還要做什麼。他想起以前好用的 Jira，這是輕量、本地的版本，CLI 可以很快讀和更新。狀態有建立、進行中、完成。你有原本的規格，這讓你在規格上面或旁邊繼續對話，文件是活的。他認為這絕對是方向。大約一個月後 Amazon 出了 Kiro，字幕聽成 Cairo，也是 spec to code。他快速看過，還沒完全被說服，但這個空洞顯然需要被填上。那種組合更有趣，因為活的文件、功能、bug、issue，LLM 都能碰到。

[28:49](https://www.youtube.com/watch?v=zRO5mX-dFRw&t=1729s) 從使用者、從開發者的感覺：很快做出能動的東西、交得出八九成功能，非常好玩，也很肯定你能創造。然後你撞上 90% 的天花板。規格驅動要先用自然語言寫、要想測試、要想其他事，若你要的是快速應用開發，那會慢下來。享受，以及對過程的信心，哪一邊比較多。他把這叫做開發的文藝復興。你明顯得到更多樂趣。若沒做 vibe coding，你得自己架 Maven，光把建置環境弄到能動就可能要好幾天。有了它，那件事很快就為你生出來，立刻滿足，回饋迴圈短很多。一般來說，快速原型顯然該走這條。若真的要部署給成千上萬的人，vibe 的部署和除錯是不是該走的路。他有個軼事。他有開發、staging、生產。他做了一個 task 檔，用來建立部署之類的任務。它顯然漏了從生產到 staging 的設定。他在部署到 staging 時，實際上部署到了生產。這種事讓你說哇。你仍然需要有知識的人看它產出的東西，不只看 code，也看腳本。若你不是技術的人、不是開發者，你會碰到問題，因為你不知道它能產出的規模，也不知道你叫它做的事有哪些效果和副作用。身為比較資深的開發者，這絕對讓他更有生產力。那個 UI 他永遠做不出來，這肯定取代了一個網頁設計師。他現在這個專案大概做了五週。沒有 vibe coding，他完全確信要三個人做六個月。這是 game changer，更有生產力，但你仍然需要資深的人引導。不然會出問題。例如 Angular 的路由前面可以放 guard。你若不知道那個概念，junior 或非技術的人會在不知道的情況下把某些頁面開放出去，或把 API key 曝出去，那是真正的安全問題。所以他做過一些練習，對 Claude Code 說：你是白帽駭客，試著黑我的系統。它會走你的 code、走你的網站。那些練習很有價值。它會點出：我沒登入就看到了管理頁。好，修好，再看深一點。另一個練習：Devoxx Belgium 有 3,000 個不重複使用者，系統怎麼擴、效能如何、瓶頸在哪。它會說 Firebase functions 該有更好的記憶體或更多記憶體、要允許更多 instance。這些比較不是開發、而是 DevOps 的討論，也是流程裡必須走的一步。

[34:20](https://www.youtube.com/watch?v=zRO5mX-dFRw&t=2060s) 多少審查是他自己做的，多少是讓不同的 LLM 跳進來。他能不能讓 DeepSeek 說這可以，然後信任它。他不是百分之百自在。就在這天早上，已經部署、已經有幾百人為 Devoxx Belgium 在用的應用裡，他又找到一個 bug。他用 prompt 做了重構，講者可以編輯從 Flickr 用臉部辨識找出來的照片，決定個人頁上要顯示哪張。那個動了，但公開頁面上的照片不再顯示。他問發生了什麼。他只能靠端到端測試事先抓到或預期到，他選的是 Cypress，但那個特定情境沒有測試。於是生產環境壞了一件事。他說老实说，正常團隊不做 vibe coding 也會發生，這是現實。他的目標是 unit test 蓋到 80%，也想要更多端到端。就算只是 prompt，那仍然要很多力氣，但會提高他部署之後往前走的信心。沒有那些，你就是在暗房裡走，一定會撞到頭。測試驅動，或至少 unit test 和 integration test，愈來愈重要，用來強制你定義過的規格。那個搭配會成功。

[37:16](https://www.youtube.com/watch?v=zRO5mX-dFRw&t=2236s) 新功能是開一份新 spec，還是改既有的。規格的生命週期是跟著變更，還是跟著應用。他說目前不是。規格不跟著他做的變更走。這也許是流程的缺陷。他大概該讓它活著、保持最新。README 或 CLAUDE.md 他會審查、會更新，因為那很容易。若有工具就算在背景也幫他保持同步，從工具的角度會是很棒的功能。他在給 Simon 暗示。現在他必須明確說。壞掉的照片那個功能，該被某個 integration test 蓋住，驗證它沒壞，也該反映進規格。因為他懶，或沒想到，規格就過時。有工具保持同步會很棒。這些 CLI 都有會回去遵守的規則，例如 CLAUDE.md 或 Gemini 的 markdown。還有改進空間，產品公司有巨大機會填這個洞。Simon 確認：他用規格驅動開發，但之後的變更比較像直接進 code，不是先改 spec。規格就不同步，幾乎把你推回 vibe coding，而不是第一次覺得有價值的那種以規格為中心。Stephan 說那是他需要改的紀律。要確保規格保持同步，而且開始新功能或加強既有功能時，永遠引用它。

[39:56](https://www.youtube.com/watch?v=zRO5mX-dFRw&t=2396s) 他做過幾場關於 RAG 的演講。現在這些 CLI 他叫做檔案系統上的 RAG。它們對檔案做某種模式辨認，結果注入 context window。若某些關鍵字不在某些規格裡，它可能找不到、也不會放進 context，於是它不知道。要嘛開發者有紀律，說永遠把這份規格包含進來，像他現在對 Claude 明確說載入 CLAUDE.md，讓它成為 context 的一部分。就在昨天，Claude 出了一個新的斜線指令叫 context，可以看到 window 有多少被哪種文件用掉，非常有趣。開發者很懶，會忘。他認為工具該在那裡扮演角色。就算 code 不是每次都直接從規格生成，把整套規格交給 Claude，也會加強它怎麼改：它更懂應用、更懂你的意圖，做某個變更時知道可能會弄壞什麼。Simon 說我們談起來好像它真的在想，跟我們一樣。Stephan 說它非常有知識，語法它真的懂。另一件浮上來的是，他在 GitHub 上做 feature branch，開一條新分支再開始。他當然已經用 GitHub Actions 把 Claude Code 接進 GitHub。更有意義的是先在 GitHub 開一個 issue，再用那個 issue 當 feature branch，而且讓 Claude 或其他 LLM 先做一些預先調查，把你的功能在 GitHub 上補齊，拿那個當開始做功能時的 context。他相信目前做不到，只能事後。那本身可以是一個專案。你讓 LLM 調查、看實作這個功能需要什麼 context，然後你才開始做，它已經有 context。

## 擴展是資深的人先選的，junior 則有了一個什麼都敢問的家教

[43:07](https://www.youtube.com/watch?v=zRO5mX-dFRw&t=2587s) 非功能需求：安全、效能、可用性。這是生產應用，會前、會期、會後一段時間都要活著。三千五百人可能同時打，一場結束人們會跳去看議程、看每場的評論。沒有規格、或沒有你說它必須夠快、必須在特定時間承受大量使用者，LLM 有多好。怎麼讓它在做實作決定時滿足這些。他說在這點上他有罪，因為他有做可擴展系統的經驗。疫情期間他和 Celestino 做了 Rockets，一個辦線上活動的平台，有時幾千人同時在線，同一件事。資深開發者知道架構選擇，從一開始就扮演大角色。他立刻說要用 Firebase，也就是 Google Cloud，要用 lambda 或 functions，因為非常能擴，尤其再跑在 Cloud Run 上。那個架構選擇，Firestore、functions 或 lambda、Cloud Run，你已經知道若跑在 GCP 上可以很能擴，因為 Google 基本上幫你做。若他沒有那個知識，它也許會用 Python 做出比較快的 API，他可能真的會有問題。現在只是設定：從一開始允許多少 instance、timeout 是多少、functions 拿到多少記憶體。基本上是無狀態的 function、serverless 的後端，在可擴的雲上。若他完全沒經驗，他可以跟 LLM 開會，問最好的可擴方案，它也許會給出那種建議。對他來說那不是，那是他從一開始就要的架構決定，他知道那會擴，也相當有信心。

[46:26](https://www.youtube.com/watch?v=zRO5mX-dFRw&t=2786s) Simon 問，未來怎麼長出知道這些非顯而易見選擇的資深工程師。他有點質疑那個缺口還會不會在。我們都從錯誤和建議裡學。現在比以往更能問 LLM 或人，什麼是好的開發。我們也能更快撞上錯誤，因為 vibe、部署都更快。Junior 不是會更快犯錯、更快學到這不能擴、要用更能擴的做法，而不是六個月後才在自己的 code 變更裡發現問題嗎。Stephan 說有兩個角度。生意主人要的是盡快、盡便宜、但有品質的解。從生意看，有一個資深開發者，就算現在是他自己，會比有一些 junior 快得多地達成。從技術看，junior 現在有一個普遍的家教，一個好到不像話的 coding assistant。你可以問所有想問的，連最蠢的、以前絕不會問同事的問題，都會得到很有知識的答案。若你是有動機、投入的 junior，你可以很快爬上去變成資深，因為有這些 LLM 引導。這是幾年前沒有的。你得有動機。唯一的問題是生意願不願意雇這些 junior、投資他們變成資深，若他可以用一個資深開發者就完成專案，那個人也許會當這些 junior 的專案負責人。往前走，那是需要發生的平衡。

[49:20](https://www.youtube.com/watch?v=zRO5mX-dFRw&t=2960s) 任何開發者，資深或 junior，都可以對 LLM 說你是效能專家，有一二十年做高效能系統的經驗，也許是 fintech，也許是特定日子會有巨大訪客的網站，為這類系統加上好的寫法。他有沒有用這種角色。大約四週前 Claude 放出 sub-agent。你可以為一個 agent 寫 prompt，給它名字，基本上是一份某種角色、某種剖面的 markdown，你啟動那個 sub-agent 時它會用。你可以說你是測試者，解釋測試者該做什麼。你下 prompt 時，它會看它的 sub-agent，啟動那種化身、那種剖面，先把那個角色的場景設好，再為那個特定請求以那個角色行為。所以 Devoxx Belgium 的主題基本上是 Java agents。他認為 Devoxx Belgium 現在是最大的 AI 會議，因為幾乎 75% 都關於 AI、大型語言模型，也有用 Java 在 GPU 上做 inference。網站上寫的是 agents。興奮和新機會在於，你不只能在 CLI 裡做有特定角色的 agent，還能有非同步的 agent，在你睡覺或遛狗時在背景做那個角色裡的動作。那非常令人興奮。即使 Java 的框架，LangChain4j、Spring AI，都在走向下一層抽象，也就是 agent。他認為接下來 12 個月會看到很多新的創新。

## 十月的會場應用，以及會議本身要反映興奮在哪

[51:52](https://www.youtube.com/watch?v=zRO5mX-dFRw&t=3112s) 錄音是 8 月 22 日。Devoxx Belgium 從 10 月 6 日到 10 日。大約一個半月。Simon 笑說不知道他為什麼還在浪費時間上 podcast。一個半月後三千五百人、也許更多，會同時碰同一份資料。最大的擔心是什麼，對它完美運作有多有信心。他加了一些新的互動。人們終於可以私下用自由文字給講者回饋。他們常常收到比較不專業的人，輸入不符合行為準則的文字。他用 Gemini Flash 2.5 的輕量版審查所有評論，看是否符合行為準則。就算只用表情符號，不恰當的它也會找出來說這不符合。它能動，但若一萬人給回饋，會不會夠快。那種事比較難模擬，若要同時模擬兩千則評論也很貴。那是他最大的擔心。應用會跑，他知道。它是 Angular，放在 Google Cloud，回傳的就是 JavaScript，那會動。Firestore 會動。他看不出那裡有問題。另一個功能是人們可以說房間有多滿，例如佔用率 90%。那個資訊現在顯示在數位看板。你立刻知道不必進那間，因為滿了。有這個功能的好處是，他喜歡知道某個主題和講者的房間有多少人。若這能動，他就不必再自己去。他可以坐在報到處，看儀表板，依社群驅動的回饋看房間有多滿。Simon 說像 Google 路線會說這班火車比平常擠。是社群驅動的。若它壞了，他會當場 vibe coding 把它修好。

[55:02](https://www.youtube.com/watch?v=zRO5mX-dFRw&t=3302s) 另一個他本來只想在主題演講公布、但想給 Simon 首播的功能，也是 vibe 出來的：即時逐字稿。他已經在做畫面上看得到的即時逐字稿。現在他從這場談話即時抓逐字稿，每兩分鐘做出重點、關鍵字雲，以及談話進行中的摘要。你可以在行動 app 裡，開場五分鐘就看到重點、對方在用的關鍵字，以及摘要。他一直在測，但有幾個會動的部分。那是他會緊張的地方：這會不會動。Simon 說若他是與會者，講到一半覺得這場不對，可以滑去看別人在講什麼、摘要是什麼，然後跳過去。那給人更即時的感覺。Stephan 說再下一層也想像得到。談話結束，把逐字稿給 LLM，說寫一份兩個人互相說話的腳本，再拿去 OpenAI 做出兩個聲音對談，像 NotebookLM。從技術上完全做得到。有些講者不喜歡從他們的演講做出真正的 podcast，擔心準確度。所以他先放進冰箱。從技術看，那就像科幻。兩年前根本不可能，現在可以。

[57:16](https://www.youtube.com/watch?v=zRO5mX-dFRw&t=3436s) 會議的角色。從 JavaPolis 到 Devoxx，曾經很以語言為取向。開發者要學的技能若愈來愈少繞著怎麼用一門語言、或設計和架構的能力，因為愈來愈靠 AI，會議要不要演化。是不是 AI 的最佳用法，加上對應用該怎麼被建造的那種機械同情，兩者的組合。他的願景。他說自己幾乎花九個月製作和籌備這場，但不是全職的九個月，然後就這樣過去。他總說這是我們的派對。五天的活動是他們辦的派對，講者和題目是挑選過的。他要會議內容反映興奮在哪、他自己在哪裡興奮。他的興奮顯然在 AI 和大型語言模型，他要確定會議反映那個。到目前為止，他的興奮和其他開發者的興奮對得上，他們好奇、想學這些新東西。他認為今年已經轉了一點。他明確打了那張牌：AI agent、LLM、coding assistant 是buzz 和興奮所在，Devoxx Belgium 就全力去做。老实说週一他很緊張。人們可能把它看成工作保障、看成危險，反應可能跟他要的相反。看起來人們對此感到興奮，他們想學。也有一點聲譽。人們知道 Devoxx 會給什麼。他們做了 25 年。但你說得對。看今年的內容，我們需要擁抱這個新可能。興奮在，生產力也在。危險一定有，但會議該把那點出來，從講者和內容反映它。他甚至有 Rod Johnson，Spring 的創辦人，人在澳洲，會過來做一場動手的實驗課、一場主題，以及一場會議演講，談他新的 AI agent Java 框架，字幕聽成 Embab。興奮在那裡。人們想知道什麼是可能的。會議若反映那個，他認為還有幾屆可以活。他已經看到美國另一些會議用同樣策略，說我們需要擁抱 AI。有趣的是，就算從低階看，仍然有很多可談。Paul，字幕聽成 Sundos，在 Babylon 上工作，做 Java 和 GPU 上的 inference。還有曼徹斯特大學的 TornadoVM。仍然有很多低階的東西要討論、探索、做知識轉移。會是這兩者的混合。也許完全不是開發者的人，去 Devoxx 也能得到一些好處。但仍然有人想知道那一層下面是什麼、框架下面是什麼，像小時候打開車子想知道裡面有什麼。會議要照顧那種人。他需要保持興奮、辦得有趣。若那停止，Devoxx Belgium 對他來說也會停，因為他不是非做不可。他真正討厭的是，你辦了這個很棒的派對，自己卻不能好好享受，因為他像無頭蒼蠅從一場火跑到另一場，確保一切順利。最大的失望是不能像普通與會者那樣享受。幸好他們全都錄了，他可以線上看。Simon 說若他知道自己在享受，那就會很強，那就是你會預期的。若那停止，就停。放幾年假只做研發也完全可以。他不認為已經到那個點。Simon 說抱歉通知他，這會從這裡再長大，工作很安全，抱歉又往他的盤子加東西。網站是 devoxx.be。Simon 說自己去過很多年，十月會再見面。Stephan 期待 Tessl 的產品在不久的將來釋出。

他說若興奮停了，放幾年假只做研發也完全可以，只是現在還沒到。

# The Agent Trick That Stopped Hallucinations Cold

AI Native Dev 播客，片長 66 分 4 秒，英文手寫字幕。來賓是 Cyera 的 tech lead Ori Shoshan。對談的人在正文沒有自報姓名；片尾說主持人是 Guy Podjarny 和 Simon Maple。開頭預告十一月三日、四日紐約的 AI DevCon，Super Blind Bird 票 100 美元。這份筆記依英文原稿整理，專有名詞保持 English。

- 原片：[YouTube](https://www.youtube.com/watch?v=zFbaipV2FHw)

## 一句話

Ori 在客廳裡想要一個私人助理，卻不願把生活交給什麼都能做的 OpenClaw。他的做法是白名單工具、不給 bash、留一個逃生口，並且逼每一句話帶出處。第二個模型在乾淨的 context 裡核對主張和原始資料。這套東西進了 Cyera，變成大約 30 個 agent、數百個使用者的內部平台。機密資料上，調查的 agent 什麼都看得到，但只能說一份事先驗證過、不會外洩的詞彙。

## 什麼都能做，就遲早會做一件可怕的事

[2:04](https://www.youtube.com/watch?v=zFbaipV2FHw&t=124s) Cyera 是資料安全平台。掃描你的資料，找出敏感資料、是哪一種，然後讓你做真正要緊的事：決定姿勢該是什麼、看什麼被暴露、怎麼暴露、修掉它。AI 安全這邊，是讓 AI 能碰到那些資料，但是以受控、安全的方式。若你怕資料外洩，你會癱瘓。所以是控制。主持人說這很像被賦權的勞動力長出來的問題：每個人都能在雲上造資料，然後一團亂，DSPM 來收拾。進到 Agent Land，agent 是更不被信任的賦權個體，得勒得更緊。先前為賦權時代做的解，正好用得上。

[5:50](https://www.youtube.com/watch?v=zFbaipV2FHw&t=350s) Ori 是 tech lead，工作跨很多地方，很多在 DSPM，也帶 AI 採用。大約一年前因為一次收購加入 Cyera。字幕把那家公司的名字聽得不清楚。他和團隊、以及共同創辦人 Tomer Greenwald 一起進來，一起帶 Cyera 的 AI 採用。主持人是在 intent-based access control 那段認識他的。公司工程師的量級是數百人。

[6:50](https://www.youtube.com/watch?v=zFbaipV2FHw&t=410s) 故事從 2026 年一月的客廳開始。他坐在那裡用手機做事，問自己為什麼還在用手。現在是 2026，不是 2025。2025 年十一月下旬，模型跨了一大步，至少從他的角度看。字幕聽成 40 year models。他當時能做出一個原始的 harness，基本上是帶測試的 coding agent，讓 agent 跑得比前一代前沿模型久得多。幾週後他在客廳想，為什麼還在自己做。他在蓋房子，要追所有承諾，以及他正在和承包商吵的那一場。他想要一個像 OpenClaw 的東西，但當時不喜歡它。它還在用前一個名字，字幕聽成 Cloud Bot，像個青少年在長大。OpenClaw 真的什麼都能做，感覺不受控，一場等著發生的災難。他的看法是：LLM 在 agent harness 裡，若有一張空白支票可以做一切，它們遲早會做一件可怕的事。就像演化，那條路存在，它們就會去探。把 OpenClaw 接到他所有的東西、讓它管他的生活，他覺得生活本來就夠 precarious。

## 不給 bash，每句話都要能指出來源

[8:08](https://www.youtube.com/watch?v=zFbaipV2FHw&t=488s) 他自己的助理走另一條路。不讓它做任何事，只讓它用一組特定工具。他把它接到 WhatsApp，傳訊息給它，它要能說資料從哪來。他想知道它沒有在編。他手上有那份資料、有那個連結，所以為什麼不讓 harness 告訴他來源到底是什麼。後來他想工作上也要。為什麼還在收 Slack、跟 Salesforce、消化任務。他想一直知道一切，但只知道最重要的，而且每一項都有連結。他不想猜這是模型編的，還是有資料撐著。

[11:09](https://www.youtube.com/watch?v=zFbaipV2FHw&t=669s) 主持人問這樣限死會不會太殘。從把智力讓路的那條路看，不要擋在智力前面。Ori 給它相當多工具。他不給的那一個是 bash，也就是為所欲為。其他工具例如讀他所有的 WhatsApp、瀏覽 email。每一個的攻擊面是已知的。他總是留一個逃生口。你不想要的是 LLM 拿一組工具，其實在試著做別的事。若它有 bash，它會去做任何事，然後因為沒有選項而做一件說不通的事。那是壞的失敗模式，除非你去看 thinking tokens，你可能不會發現。逃生口可以是另一件有人在迴路裡的事，或是把回饋記下來。模型要能告訴你：我想做這個，但我沒有選項。然後你去加。你很快會到一組 50 個工具。它幾乎什麼都能做，但你知道它只能做那些。結構上 harness 逼它不能做災難性的事，例如把所有私人筆記用 email 寄給承包商。

[12:55](https://www.youtube.com/watch?v=zFbaipV2FHw&t=775s) 引用的靈感來自 ChatGPT，它們有一陣子開始在主張旁邊加連結。他想很容易知道模型有沒有在騙他。LLM 給你一面牆的文字，你得想哪些基於事實、哪些推理是對的、哪些推理是錯的。一直評估，認知上很累。和 coding agent 在互動 session 裡、你在狀態中，是一回事。私人助理你不想付那麼多注意力，那正是這個用例。主持人說，你可以接受更多回合，換最後是對的，因為你沒坐在那裡監督。錯的答案可以造成實質損害，或至少浪費很多時間。Ori 假設模型會弄錯一些，他要讓那件事對他明顯。做法是不讓模型只產散文，而產結構化輸出。輸出是一組區塊，每一塊是一個主張和一個來源參照。來源參照就是 citation。渲染給他時，每一段主張帶一個來源，連結自動畫出來。

[15:35](https://www.youtube.com/watch?v=zFbaipV2FHw&t=935s) 有了這個，他發現可以拿來做 context engineering，也做主張驗證。LLM 在 context 裡有一大堆東西時，更容易幻覺或得到錯的結論。它們的注意力被歷史動作佔走，像在乾草堆裡找針，可能看錯那根針。注意力是稀缺資源。Attention is all you need。於是他可以把每一個主張，配上 Supposedly 在它後面的原始資料，至少 LM 是這麼說的，再拿這兩塊去問另一個 context 乾淨的模型：這個主張有沒有被這份資料支持。那種模式下它們幻覺少很多，因為沒有噪音。每個主張各自更準，整體幻覺少得多。若仍是幻覺，你看得到來源，也容易看出引用說不通、引了一個完全無關的東西。這很少發生，因為模型已經相當好。主持人說，任何一個 agent 都可能幻覺，再疊一個來審查，機會會大幅下降。Ori 又多走一步，要求原來的那個用稍結構化的格式。逃生口是：若沒有來源參照，它們仍可以產出主張，但必須標成 opinion。所有推理都去那裡。那些他會保留懷疑。其餘的才是他用來評估的。主持人說，惱人的常常不是 LM 犯錯，而是它用那麼有信心地說錯。標成我有證明、或這是我的意見，大概就有用，甚至可能幫到 LM，因為那在輸出的 context 裡。

## 名叫 Borg 之後，它就變成你的

[18:54](https://www.youtube.com/watch?v=zFbaipV2FHw&t=1134s) 在家他跑在一台 NUC 上。他原本不知道它有風扇，結果有。進公司後他先在本地跑，但想 24 小時跑，而且能碰到一些東西、不能碰到筆電碰得到的另一些。他必須知道可能的失敗模式，並且能接受。在資料安全公司，這是好傾向。工作上第一個是私人助理，工作模式是 chief of staff。要讓更多人用，明顯的選擇是 Slack bot，可以私訊、可以在討論串裡標。把 bot 帶到人已經在工作的地方。最好做的第一個用例是 on-call 分診。分析彈出來，有人在討論，你可以問 agent：你能查這個嗎，影響是什麼，影響哪些 tenant。非常營運。這和以前不同。以前是一個使用者對一個 agent。現在很多人用同一個。早期其實仍是每個人各自問。但冒出一些性質：agent 能讀討論串，看得到先前的討論，看得到人在談怎麼用這個 agent、在抱怨幻覺。你標它時，它看到 prompt，也看到 context，所以可能還回應別的事。它自然就是多人的，這是免費得到的。

[22:23](https://www.youtube.com/watch?v=zFbaipV2FHw&t=1343s) CTO Tomer 提議 Slack 上那些頻道，產品和研發會被問問題。有些問題可以靠內部知識庫、公開知識庫、有時靠 code 來答。很多時候你並不知道該搜什麼，像 Google：關鍵字對了就找得到，有時你得先弄清它是什麼。Agent 相當會這個。這裡人和它互動的方式不同：他們不加 bot，只是在頻道裡問。Bot 用 ephemeral message 問你，就是 Slack 上只有你看得到的那種，像標了一個不在頻道裡的人、Slack 問要不要加他。Bot 問：要不要我試著答。你點是，它才在討論串裡公開答，給所有人看。這是後來改的。一開始它直接答，惹惱一些人。他就讓它先問。像人一樣：你先問能不能，別人就不會生氣。這叫 ambient mode。它看每一則訊息。一個便宜模型當分類器：這是問題、公告，還是別的。只有問題才真的去答。

[24:40](https://www.youtube.com/watch?v=zFbaipV2FHw&t=1480s) 一開始只有他自己的 Slack bot。他叫它 Borg，星際爭霸艦，cyborg 的 hive mind。平台上所有 agent 會共享同一份知識和所有回饋。它們都會被同化。這個笑話太好了。Cyera 網站有一個飛行太空艙的圖示，他加了一張可愛的臉，那就是 Borg。別人要做 bot，就建一個新的 Slack app，給它名字，也許還有個性。功能上的理由是讓他們能改 system prompt、工具、context。平台對準工程師，他們可能會改 agent 收到 prompt 時怎麼被設起來的那段 code，做 context engineering。很好的副作用是他們會幫 agent 取名，覺得那是自己的東西。採用因此好很多。不再是往 Ori 的 agent 加一點 code，而是我的 agent。他的目標是 Cyera 每個人都能用這個平台來建 agent，拿到資料基礎設施、引用、知識圖譜，還有 guard rails，滿足他對控制的需要。主持人說，你一取名就會照顧它。它們回答時會講蠢笑話，因為你可以加個性。人也更敢改，因為這是我的，我沒有擋到別人。

[28:00](https://www.youtube.com/watch?v=zFbaipV2FHw&t=1680s) Cyera 是複雜系統。資料安全天生要處理很多資料，有些光是規模就要掃很久。有些操作會跑很久，那就難除錯。若十秒就結束，你一看，它做完了。這些 on-call、操作、除錯的 agent 觸發不同。有的互動，有的像環境式回答問題。它們會回應警報，或客戶開的票，做初步分診。有的依票裡的內容分給對的團隊。還有一整類仍是 Slack bot。成本 agent 分析 Cyera 的雲端成本，做報告，對變化做根因。它看到成本上升，試著歸到工作負載變大，或 code 改了，幫你隨時間把它壓住。像春季大掃除的管家。也有給產品經理的：看客戶的功能請求，或 Slack 裡客戶提到的功能，幫 PM 在本來會被發現之前看到趨勢正在形成。以前要有人說我們需要這個功能，然後大家才意識到其實是同一件事。LLM 擅長找相似，說這裡、這裡、這裡，注意。大約 30 個 agent，大約同樣數量的開發者做出來。使用者他沒有精確數字，他想是幾百，因為不只公司裡的開發者，每個人都用，有些甚至是間接的。

## 大約 60 個工具，以及每週做一次夢

[31:24](https://www.youtube.com/watch?v=zFbaipV2FHw&t=1884s) 工具這邊，所有 agent 有一份共享的基線，你可以排除一些，或加自訂工具。像 skills，只是它們有會被驗證的 schema，可以跑 code、做決定性檢查。另一個例子不在 Slack 上，而在 Sentry。Sentry 是錯誤管理平台，錯誤出現在那裡。和 Slack agent 同一件事：分診、若是 bug 就找根因並修，若是環境問題就處理。這些是 agent 設定的一部分，也就是 harness 的設定。主持人問，多久會因為缺工具而失敗。他說前幾個 agent 轉起來之後，其實已經相當少。他們在大約 60 個工具左右停住，多數 agent 都有。因為工具在 agent 之間共享。有人加一個，其他 agent 自動得到，然後那件事就變得可能。發現需要新工具，最明顯是有人來告訴他，那相當糟，因為很多時候人不會告訴你，甚至不知道該告訴你什麼。引用會出現在文字裡，不管介面是 Slack 還是別的。也有回饋：讚、倒讚，倒讚幾次可以寫為什麼。你寫的回饋會連到撐起這個主張的原始資料，不是連到那一則特定回答。所以 agent 已經在學：若它再查同一份資料，context 裡會看到那個。若有人在 agent 回完之後說，我真希望它每 15 分鐘給我一次更新，那也被記下來，它就在 Slack 上。平台還有排程。Agent 可以按時觸發。他當例子加的第一個是夢境：agent 每週起來，回顧所有互動、回饋，以及回答。人在答案周圍說的話也在。然後夢境會開一張 pull request 來改進 agent。他開玩笑說，這一部分是來取代他的。在那個 context 裡，agent 可能回來說我需要一個新工具，或改一小處。還有一個叫 Submit Feedback 的工具，給 agent 自己提交回饋。它看著工具清單，想做一件事，卻不知道那些東西在哪，那就存下來。夢境看到，可能就提議那個變更。

[36:12](https://www.youtube.com/watch?v=zFbaipV2FHw&t=2172s) 工具在 agent 之間共享。主持人以為將來會把它們隔離、再收緊，但還沒發生，因為已經夠被包住。它們之間有一點分歧，大多是功能，因為現在不都是 Slack bot，還有 Sentry 那種介面。發 Slack 訊息是一個工具。關於控制和約束：agent 不能自己選訊息送到哪。它在一個特定 context 裡被觸發，可以呼叫 send message，但只能送到為它解鎖的同一個討論串。它不能選目的地，所以不能犯那種錯，前提是 harness 只允許它在對的 context 裡被觸發。那是決定性的部分，大多數時候我們知道怎麼處理。主持人把今天的 agent stack 說成：模型像我們在上面建的作業系統，上面是 tools、context 和 harness。Context 夾在 tools 和 harness 中間。Harness 造約束，帶來一些決定性和安全。Tools 再帶來另一組約束和決定性。Ori 不是出發就要省錢，但實際上省了不少。用量相對他預期相當便宜，因為非常結構化，約束把它留在軌道上。

## 圖譜是讓它走，不是把搜尋結果倒進去

[38:24](https://www.youtube.com/watch?v=zFbaipV2FHw&t=2304s) 知識圖譜的建置相當貴，但是一次性的。這也連到引用的基礎設施。很早他有了引用的想法、想讓所有資料都有來源參照時，他用 ChatGPT 輔助讀了一批白皮書。來源、主張驗證這些概念，這些年、尤其去年，被探得相當完整。把它們這樣拼在一起很合理。不是一開始就來的，是逐漸來的。知識圖譜是那個的延伸。

[39:53](https://www.youtube.com/watch?v=zFbaipV2FHw&t=2393s) 明顯的做法是給 coding agent 或互動式 agent 資料，也許一個 LLM wiki、一些 markdown，讓它們去探。身為使用者他知道，它們有時不會探所有該探的。於是就落到：它們會不會找到一個提示，把牠們推向對的方向。Andrej Karpathy 寫過，wiki 裡的那些連結幫它們找到要的資料。但用 RAG 把 context 建好、一開始就倒進 agent，已經不再必要，因為 agent 現在更會探索。Agentic search 對上 RAG。他看得到這點。但回到他要完全控制：他不喜歡結果有時不一致。他的解法是把所有資料放進知識圖譜，其實是一個有實體互連的資料庫，幾乎像 RAG，然後不要真的當 RAG 用。讓 agent 像走磁碟上的 LLM wiki 那樣走那些連結。因為現在有索引，搜尋快、找關係快，你可以有多得多的資料塊。

[41:29](https://www.youtube.com/watch?v=zFbaipV2FHw&t=2489s) 裡面可以是 code、Slack 訊息、某一則跳出來的例外，基本上什麼都行。建置成本不小，因為抽實體要過 LLM。最重要的一塊是資料品質，到現在仍很手動。若他把銷售資料、至少相關的那些，不是全部，直接塞進知識圖譜，他想大多會是噪音。Slack 上反覆送警報的 bot，大概會蓋過人類訊息，而人類訊息才是訊號。所以要弄清想讓 agent 碰到哪些資料來源、在圖裡怎麼建模。一個帳戶、一個例外、一個服務，那些實體要在圖裡。資料進來時看噪音在哪，真的去清。花了他幾週，瓶頸是他自己看資料的能力。他看最吵的那些，依來源和出處分組，再清。現在圖裡大約一百萬筆左右，否則會是好多好多個百萬。Agent 會找到令人意外的東西，他覺得這是訊號夠多的好跡象。

[43:54](https://www.youtube.com/watch?v=zFbaipV2FHw&t=2634s) 圖譜有 episodes，也就是發生過、被吃進去的事，然後有實體，以及實體之間的關係。它若在看某一則例外，或一則 Slack 訊息，那則訊息裡有參與的實體。所有 agent 共享一段 system prompt，解釋怎麼走圖、agent 該像什麼樣子。另一段是每個 agent 自己的。共享的那段說：若說得通，先用精確查找；不然用語意搜尋。找到相關實體之後，用 Find related 走圖。那就像列出目錄、看相連的實體。在 LLM wiki 裡，那些會是檔案裡的連結。然後每個資料來源有一批專門工具。它可能找到一則 Slack 訊息的 episode，然後有工具去讀那個討論串，或查那個人的更多訊息。工具的大頭就是這些，每個資料來源大概五或六個。通用工具和這些都是唯讀。少數寫入工具才真的在解決問題：做 code review、在某處留留言、開 pull request。目標是 context engineering，讓對的資料在 context 裡。回到第一個用例：找到一塊資料，以及和它相關的東西。若有人在談一個例外，他想看到引入它的 pull request、那個例外、log、它的影響。以他的經驗，agent 要可靠地做到，必須有辦法找到那些關係。若他當人去看一行 log 找得到，他要做的就是造一個工具，讓它呼叫 Find related 時那些東西就彈出來。

[47:47](https://www.youtube.com/watch?v=zFbaipV2FHw&t=2867s) 主持人把它說成結構化和非結構化。Agent 很強，你給它們 bash 和檔案，它們能做很多。但到了規模、要審查大量資料、反覆做動作、又想提高可靠，有幾條路。一條是把 agent 教得更好，最後自己摸出來，那是在做更聰明的個體，不是在把它們編成一組。另一條是把資料變得更有結構，讓它們更容易在對的地方查到對的資訊。再往前，有了結構化資料，就可以把一些認知工作卸到工具上。那很像我們和人一起工作的方式。Ori 說他真的把 LLM 想成人。把它們想成電腦很誘人，但世界上我們知道的、只要訓練對、資訊對、一般就做得不錯的另一種東西，是人。人不是不會錯，LLM 也不是。所以你在幫它們。這些約束和工具，就是他當工程師對自己的做法：把開發環境設成他做錯時編譯器會對他吼，讓自己的錯在造成影響之前被抓到。他也這樣對 agent。

## 胡蘿蔔，以及隔著牆的兩個 agent

[51:54](https://www.youtube.com/watch?v=zFbaipV2FHw&t=3114s) Tomer 和他做了一個小組，叫 AI captains。他們挑了幾個已經對建 agent 有興趣的人。稍早，大約十二月，他建了第一個 agent，因為他想做一件事：從引入 bug 的 pull request，到修好它的 pull request，分類修一個 bug 要多久。他用 coding agent 試，有一些成功，但非常不一致。在他們的規模上，要從不那麼一致的東西得到有意義的統計，對他非常難。於是他想建一個 agent，給它提示，讓它留在對的路上。你和 coding agent 工作時，有時系統提示會漏進 context。Agent 突然對一個系統提示起反應，說 something like got it，指令是這樣回，所以不要告訴使用者，然後它不小心告訴了你。他看到把 agent 收住、只給它這份工作需要的工具，差別有多大。當然要幾次迭代，不是一次就成。一致性和品質確實變好。他覺得讓別人去建 agent 的最好方式，是也給他們那個頓悟。他們會說，天啊，我得多寫 agent。他就是那樣覺得。小組一開始只有 10 或 12 人。他們辦了一個很簡單的 agent 工作坊。有了這個平台，做出 Borg 的複本其實是複製貼上，一份設定檔。一旦你做了，你就看到它的力量。門檻從「建 agent 是未知的事」，降到「有一個 Python class 我可以改」。先讓他們看見，再讓進場變容易。把營運問題變容易，那些其實不太有趣：agent 跑在哪、guard rails 是什麼。那些問題難答，但從應用的角度看不有趣。這很有效。它變得能自己維持。那些人真的採用了，有些在組織裡變成很大的擁護者。他加強這一點：你不需要我的 code review，你可以問那些人。Guard rails 確實需要他的 code review，但他也把其中一些人加成那裡的 code owner。Guard rail 是他們用來不讓 Claude 或其他 coding agent 真的失控、把安全拿掉的方式。他的做法全是胡蘿蔔，沒有棍子。讓它非常容易，讓它安全。讓它安全，是讓它容易的另一種做法。避開爆炸半徑的擔心。有人有效、接過韁繩，他就說好，繼續，把人指過去，慶祝成功。

[56:18](https://www.youtube.com/watch?v=zFbaipV2FHw&t=3378s) 機密資料。On-call 分診的 agent 看得到所有資料，你也看得到同一份，容易確認它是對的。另一些環境，因為法規或對客戶的承諾，你不被允許看資料，甚至不能存取。但 bug 還在。有 agent 之前，唯一的辦法是一小群事先核准、看得到資料的人去除錯。公司長得很快。一年半前他們小非常多。你可能需要比那一小群更多的人。他們的想法是：一個 agent 在受控環境裡，看得到資料，你可以讓它調查、除錯，它什麼都碰得到。但有一個大約束：它不能輸出，除非是結構化、被驗證過的輸出。它只能對一份固定詞彙輸出，而那份詞彙你可以驗證不會洩資料。它做完調查，用固定詞彙輸出，那就可以離開那個範圍，給沒被核准的人，因為你知道沒有敏感的東西被送出去。另一個 agent 讀那份資料，看得到 code 和更寬的可用資料，再為人拼一份說明，撐在前一個 agent 的結論上。這兩個叫 Mulder 和 Scully，因為他們辦 X 檔案。基本上是兩個 agent 隔著一堵牆說話。專長不同。一個沒有資料存取權的團隊上的人，可以用那個團隊的知識、怎麼除錯、例子，去寫這個 agent。Agent 在受控環境裡做。回饋是固定的、安全的。逃生口仍在：受控的 agent 若必須說詞彙說不了的事，可以把自由文字輸出給那一小群人，然後由核准過的人做人類審查，再把詞彙擴大。主持人說這不只是機密資料，on-prem 支援和其他你不能讓資料出去、卻仍得運作的路徑，都很有說服力。

[1:02:09](https://www.youtube.com/watch?v=zFbaipV2FHw&t=3729s) 接下來最讓他興奮的，是他們的 coding harness，用上這整套基礎設施。誠實說，若兩週後再問，可能是別的，因為有很多想法是以前不可能有的，像這個機密資訊的 agent。他不認為幾個月前、在他把思考內化成 agent 之前，想得到那個。他興奮的是新點子，是一種 meta，不是某一件特別想做的東西，而是能那麼快把它們做出來。有了這套設置，建一個 agent 真的容易。讓它碰到對的資料，那個機密 agent 聽起來像很多活動零件的重活。兩天。主持人說那很瘋狂。不只是 LLM，是這套都設好了，而且他們是資料安全公司，知道你有什麼資料、在哪，可以讓 agent 碰到，並知道它們不會失控。

[1:03:35](https://www.youtube.com/watch?v=zFbaipV2FHw&t=3815s) 他給聽眾的一個建議：AI 採用其實是採用，是讓人採用這種新的思考方式、去建 agent。他建議用 platform engineering 的做法。所以他全走胡蘿蔔。你是在讓人為自己採用一種新的能動。你不能叫他們做。他們得內化。所以你得把門檻放低，讓它看起來誘人。他很想說這些他事先都想過，但其實是事後。主持人說，DevOps 轉型教過鋪好的路的價值。路鋪好了，人走起來容易，但仍允許人在旁邊開路，也許找到捷徑。多數人走鋪好的路，少數走到旁邊，有些會後悔回來，有些會找到新路，那就是學習的機會。若你只是集中、用棍子約束，結果是只有平台團隊那些聰明人能創新，其餘的人只是套用。鋪路、但允許人走到旁邊，是一條有力的路。Ori 說，當平台團隊更容易有這種想法，因為 agent 對每個人都是新的。他不必做什麼心理體操，就假設有他沒想到的事。

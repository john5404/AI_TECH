## 一句話

模型一年比一年聰明，但放進組織之後，智力不會自己複利。缺的是情境。Anthropic 這一年把情境工程從一份 `CLAUDE.md`，走到代理自己寫的記憶，再走到一個叫 Dreaming 的帶外整理程序：趁代理沒在做任務的時候，回頭看一批工作紀錄，提議怎麼改記憶。人決定接受或拒絕。

## 這場演講要回答的四件事

講者在 [1:44](https://www.youtube.com/watch?v=tTcxVv8HHNw&t=104s) 先列了行程。

1. 過去一年，情境工程裡哪些原語真的有用，哪些已經不夠。
2. 今天記憶系統的現況。
3. 理論上好看的設計，放進生產環境還要補什麼。
4. 持續學習的下一步：Dreaming。

## 為什麼智力不會自己複利

從 [1:20](https://www.youtube.com/watch?v=tTcxVv8HHNw&t=80s) 起。新模型不會一開箱就知道「在你的組織裡，成功長什麼樣子」。那批知識跟模型智力是正交的：程式庫的慣例、使用者偏好、任務怎麼算做完。

沒有這層情境，會出現兩種熟悉的失敗。

- 代理不認識程式庫，也不夠認識使用者。
- 同一件事做第二次並不會更好。它沒有從錯誤裡留下可再用的東西，所以沒有持續學習。

情境工程的投資會跟著模型變聰明而放大。模型越強，同一份整理好的情境越值錢。

## 這一年的四個原語

Anthropic 的原則是做簡單有效的事。時間軸從 Claude Code 推出 `CLAUDE.md` 開始。

### 1. CLAUDE.md：會話一開頭就注入的 Markdown

[3:57](https://www.youtube.com/watch?v=tTcxVv8HHNw&t=237s)。一份人跟代理都能讀寫的 Markdown，放程式庫說明、組織慣例、使用者偏好，在會話開始時注入情境視窗的最前面。效果好得不太合理：它把代理導向重要的事，並依偏好調整行為。

不夠的地方也很快出現。檔案一長，一開頭就全部塞進情境，視窗被占滿。重要偏好越多，越需要另一種管理方式。檔案本身仍然值得留著，因為人類可讀，代理可寫，人也可以寫。

### 2. 記憶工具：讓代理自己決定何時讀寫

[5:02](https://www.youtube.com/watch?v=tTcxVv8HHNw&t=302s)。下一步是把記憶的讀、寫、更新交給代理自己決定。這一切發生在帶內（in-band）：就在這一輪會話的情境裡。字幕把 in-band 譯成「樂團」，指的是這件事。代理一邊做任務，一邊判斷這段值不值得從記憶讀出來，或值不值得寫進去。自主性在這裡很有效。後來他們把工具的形狀放鬆，不再規定死一套專用記憶 API。

### 3. Skills：漸進式揭露

[5:50](https://www.youtube.com/watch?v=tTcxVv8HHNw&t=350s)。要解決的是環境一直變大。Skills 把你已經有意見的程序性流程寫下來。代理先只看檔案開頭那幾句，需要時才把正文載進情境。細節可以很深，卻不會每次都占滿視窗。

講者的比喻是書房。每次有人說話，先掃過書背，標題相關才把那本書抽出來。有人突然用法語說話，就抽出法文字典，不必把七年法語課全部預載進情境。

瓶頸是：技能仍然是人跟代理一起決定「什麼值得做成技能」。人還是很有意見。

### 4. 把記憶建成檔案系統

[7:32](https://www.youtube.com/watch?v=tTcxVv8HHNw&t=452s)。講者認為這是當時記憶儲存的現況，也是他們採用的做法。前面幾步學到的東西收成三條。

- 記憶用 Markdown 放進檔案系統。代理本來就會用 `bash`、`grep` 這類普通工具，不必再發明一套專用的讀寫記憶工具。
- 搜尋本身就是漸進式揭露。索引做好，代理可以先找到相關的檔，再決定讀多深。
- 寫入時把自主權留給代理。

個人任務上，這樣就會有一直在學的感覺：同一個代理下次做同一類事會更好。

## 一進生產環境，這套乾淨想法會撞牆

[8:56](https://www.youtube.com/watch?v=tTcxVv8HHNw&t=536s)。多個代理同時協作、跑很久、程式庫變複雜之後，同樣的問題反覆出現。

1. **同時寫入。** 好幾個代理要改同一個記憶檔，怎麼收斂。
2. **一個代理改了所有人正在讀的東西。** 它遇到問題，就把結論寫進組織層級的情境。那裡如果寫錯，錯誤會放大到整支代理艦隊。
3. **人跟代理一起改記憶。** 要能追是誰、在哪一次會話、根據哪一份紀錄做的更新。
4. **記憶會過期，也會被寫壞。** 昨天相關的今天不一定相關。寫錯，或有人用提示注入讓代理把壞內容寫進記憶，都要擋。

所以自主記憶要在生產環境運作，必須有護欄。

## 生產環境的四條原則

### 版本

[10:42](https://www.youtube.com/watch?v=tTcxVv8HHNw&t=642s)。每次更新都留版本，才能在新版本不好時回滾。還要記下這次更新根據的是哪一個代理會話、哪一份逐字紀錄，以及是哪個代理或哪個人做的。

### 並行：寫入前後比對雜湊

[11:17](https://www.youtube.com/watch?v=tTcxVv8HHNw&t=677s)。上千個代理共用同一套記憶時，他們用的是樂觀並行。

1. 代理決定要改某一則記憶時，先取一次雜湊。
2. 起草修改。
3. 真正寫入前再取一次雜湊。
4. 兩次不一致，表示中間已經有別人寫過，這次不能寫。
5. 代理重新讀取記憶（講者說 ripple the memory），依新內容再起草，然後重試提交。

### 權限：組織知識唯讀，草稿區可寫

[12:11](https://www.youtube.com/watch?v=tTcxVv8HHNw&t=731s)。記憶庫從上到下不是同一種東西。

- 上層是組織範圍的知識：組織要達成什麼、程式庫的關鍵原則。這層是仔細策展過的，通常應該唯讀。不能讓單一代理自己決定改寫。
- 下層是這個代理自己的草稿區（scratchpad），記工作記憶，高度個人，應該有寫入權。
- 中間可以是某個組織或某個切面共享的內容。

### 可攜性

[13:08](https://www.youtube.com/watch?v=tTcxVv8HHNw&t=788s)。這份策展會越來越值錢，所以不該鎖在單一產品裡。要用乾淨的 API，讓多個產品表面、多個系統都能讀到同一套記憶。

## 護欄就位之後，他們看到的效果

[14:10](https://www.youtube.com/watch?v=tTcxVv8HHNw&t=850s)。

- **準確度。** 同一件事做第二次，因為記住了上次問題在哪，結果更好。
- **速度與成本。** 代理更常一次做對，token 花得更少，延遲跟著下降。
- **人的注意力。** 代理自己在背景做這圈自學之後，做產品的人可以把情境預算拿去換產品上的勝負。前提是基礎設施先建好。講者說這段關係是共生的。

## 帶內記憶的天花板

[15:23](https://www.youtube.com/watch?v=tTcxVv8HHNw&t=923s)。帶內是指讀寫記憶都發生在這一次會話裡。以 Claude Code 為例，新會話的注意力在當下任務；從記憶讀、往記憶寫，都還是這一個視窗裡的事。對一整支艦隊的持續學習來說，這有結構上的限制。

**資源互相搶。** 你要它把眼前的任務做完，又要它投資記憶，好讓以後的自己更強。該分多少能力給未來、多少給現在，是一個很難的最佳化，而且會拉高這一次的延遲。

**看得見的範圍只有這一次會話。** 跨會話的重複錯誤，它感受不到，因為每一扇視窗都是新的情境。艦隊裡其他代理在別的環境撞上的失敗，這一個代理也看不到。

**記憶會陳舊。** [18:00](https://www.youtube.com/watch?v=tTcxVv8HHNw&t=1080s) 講者補上第三點：需要有人回頭檢查寫進去的東西現在還對不對。

## Dreaming：帶外的第二層程序

[18:12](https://www.youtube.com/watch?v=tTcxVv8HHNw&t=1092s)。Dreaming 不是把記憶再做一次，而是記憶之上的第二階程序。它批次、非同步、有自己的資源預算，專門讓記憶保持有效，並幫助代理跨時間學習。

三層疊在一起。

1. **任務情境。** 代理當下真正參考的內容。
2. **帶內記憶。** 代理在會話中自己讀寫的那層。
3. **Dreaming。** 帶外整理前面留下的結果。

### 為什麼要有老師

[17:17](https://www.youtube.com/watch?v=tTcxVv8HHNw&t=1037s) 的學校比喻：很多學生交很多作業，科任老師各自看自己的科目，班主任看得到全體。專門幫人學習的人有效；看得到整隊學習者、能發現模式、再回頭改課程的人也有效。他們做系統時沿用這個結構。

### 程序實際怎麼跑

[18:52](https://www.youtube.com/watch?v=tTcxVv8HHNw&t=1132s)。

輸入有兩包。

- 現有的記憶庫，也就是一組記憶。
- 一段時間內的會話逐字紀錄。紀錄不只是代理、系統、使用者之間的對話，也包括工具呼叫、用過的 Skills，以及其他對表現關鍵的元資料。

然後分五步。

1. 協調器派出一隊子代理（講者稱為 subjects）去分析這些紀錄。
2. 你可以引導它們：在你的組織裡，什麼算重要、什麼不算。記憶跟 Dreaming 都可以依組織來策展，不是一套通用口味。
3. 協調器看子代理的回報，判斷哪些模式夠普遍，值得改記憶。
4. 它對記憶庫提出一條一條的變更。每條附上模式出現在哪些紀錄、有多普遍、為什麼值得改。
5. 人決定接受或拒絕。

### 三個具體例子

**地理課缺了一整章。** 班主任看完紀錄，發現每個地理學生都把同一題寫得很糟。對照記憶庫（這裡比喻成課程），那個主題根本沒放進去。於是提議補進課程。隔天代理再跑，就有了先前缺少的資訊。

**數學考卷全用弧度。** 題目要的是度數，全班都輸出弧度。對應到代理，就是工具設定一直錯：工具呼叫裡同一種失敗反覆出現。修法像是補一條「計算機要這樣設定」。重點是審查不能只看對話正文，工具呼叫跟元資料都要看。

**全組織的風格。** 例如每個人都用了太多破折號，而你不喜歡。這可以變成一則組織範圍的公告或情境變更：不要這樣做。

### 生產環境裡怎麼組

[21:45](https://www.youtube.com/watch?v=tTcxVv8HHNw&t=1305s)。記憶庫可以就是一個目錄裡的 Markdown 檔。逐字紀錄是對話往返，加上工具元資料與用過的 Skills。協調器派子代理分析，再自己決定哪些模式夠格變成記憶變更。輸出交給人審。

## 兩條程序並行，不是二選一

[23:52](https://www.youtube.com/watch?v=tTcxVv8HHNw&t=1432s)。

| | 帶內記憶 | Dreaming（帶外） |
| --- | --- | --- |
| 何時發生 | 做任務的這一次會話裡 | 批次、非同步 |
| 資源從哪來 | 跟任務搶同一份情境與 token | 另有專用預算 |
| 看得到什麼 | 只有這一次會話 | 跨會話、跨代理的模式 |
| 效果多快 | 下一次會話就會變好 | 較慢，但是在補帶內看不到的洞 |
| 人的角色 | 代理自主寫 | 人接受或拒絕提議 |

Dreaming 聽起來很貴。講者的算法是：有效的記憶庫會讓代理更常一次做對，任務本身的 token、重試、延遲下降。額外的整理成本是用這個換來的。

## 講者要人帶走的三件事

[25:14](https://www.youtube.com/watch?v=tTcxVv8HHNw&t=1514s)。

1. **至少先做簡單有效的事。** `CLAUDE.md`、Skills、讓代理自己管理記憶，對表現的影響已經很大。
2. **規模變大再加護欄。** 代理變多、單次跑很久、長期在同一個工作區或很複雜的領域裡開發時，記憶的管理要安全、可驗證、可稽核。版本、並行雜湊、權限、可攜性就是這層。
3. **真的要把迴圈關上，就加一條帶外程序。** Dreaming 用來合併記憶、刪掉不再相關的、補上代理一直缺的、把記憶庫整理乾淨。

這不是程式任務專用。講者自己做簡報時也用記憶：她怎麼寫、簡報長什麼樣子，會隨時間累積。

收尾時她說，這整條情境工程的路，很多是過去一年才發生的，仍是開放的研究與工程問題。她鼓勵聽眾繼續想、繼續學、繼續 dreaming。

## 問答裡三個實務問題

### 企業上該用什麼記憶儲存，而不是筆電裡的檔案？

[27:38](https://www.youtube.com/watch?v=tTcxVv8HHNw&t=1658s)。提問者要的是比「檔案放在筆電上」更企業的做法。講者說他們本來不該在台上做產品呼籲，但既然被問到：她講的版本、雜湊這類生產機制，做在 Claude 託管代理（Claude Managed Agents）的 memory 與 dreaming API 裡。若要現成方案，她指向那裡。

### 幾百個使用者、權限各不相同，Dreaming 怎麼沿用同一套護欄？

[28:56](https://www.youtube.com/watch?v=tTcxVv8HHNw&t=1736s)。提問者提到 Claude Code 外洩資料裡，記憶與 Dreaming 是最有趣的部分，並問：Dreaming 發生在帶外，情境跟使用者當下使用代理時不一樣，怎麼保證它遵守同一套權限。

回答是：觸發一次 Dreaming 工作時，你可以精確決定要附上哪些會話紀錄。它不是「把某一段時間裡的全部紀錄都吞進去」。可以那樣設定，但也可以只搜尋跟這份記憶庫擁有相同權限集合的紀錄，讓兩邊對上。Dreaming 的權限應該鏡射代理本身的權限，而不是另開一個更寬的視角。

### 這是不是在從第一原理重造資料庫？

[30:16](https://www.youtube.com/watch?v=tTcxVv8HHNw&t=1816s)。講者認為這是在找一條界線：哪些事讓代理自主做，哪些事應該是寫死在 harness（代理執行框架）裡的確定性程序。

一開始他們讓代理把想寫的都寫進 Markdown，想提交就提交。等看夠哪些原語真的有效，就把那些原語編進 harness。雜湊與版本控制是舊的軟體工程做法。現在要做的是讓自主代理能有效地跟這些做法互動，而不是重新發明輪子。訊號已經夠了：這些事應該確定性地做。
